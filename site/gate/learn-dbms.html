// what this page is

The reasoning behind functional dependencies, finding candidate keys, why each normal form exists, and how SQL/relational-algebra actually evaluate — with worked examples. The single most-tested skill here is attribute closure; master it and normalization + keys fall out automatically. Pair with the cheatsheet.

A database stores facts in tables and protects them from contradicting each other. Almost every GATE DBMS question is one of three moves: compute an attribute closure (keys, normal forms), evaluate a query (relational algebra / SQL), or name a normal-form violation. Get closure fluent and most of the subject collapses into mechanics.

01 The relational model & keys

key ideaA relation is a table; a tuple is a row; an attribute is a column. A superkey is any set of columns that uniquely identifies a row; a candidate key is a minimal superkey (remove any attribute and it stops being unique); the primary key is the chosen candidate key.
  • Entity integrity: primary key can't be NULL.
  • Referential integrity: a foreign key must match some existing primary key (or be NULL).

02 Functional dependencies — the grammar of the data

think of it likeA functional dependency X → Y means "X determines Y" — knowing X pins down Y exactly. Like roll-number → student-name: once you know the roll number, the name is fixed. FDs are the rules the data must obey.

Armstrong's axioms generate all implied FDs: reflexivity (Y⊆X ⇒ X→Y), augmentation (X→Y ⇒ XZ→YZ), transitivity (X→Y, Y→Z ⇒ X→Z).

03 Attribute closure — the master skill

key ideaThe closure X⁺ is every attribute you can reach starting from X by repeatedly applying FDs. If X⁺ = all attributes, X is a superkey. This one procedure answers keys, candidate keys, and normal-form checks.

How to compute X⁺

  1. Start with X⁺ = X.
  2. Find any FD A→B where A ⊆ X⁺; add B to X⁺.
  3. Repeat until nothing new is added.
  4. X⁺ = all attributes → X is a superkey. Minimal such X → candidate key.
worked — find the candidate keyR(A,B,C,D), FDs: A→B, B→C, C→D. Compute A⁺: {A}→add B→{A,B}→add C→{A,B,C}→add D→{A,B,C,D} = all. So A is the candidate key (and it's minimal — A alone). B⁺={B,C,D} misses A, so B is not a key.

How to find ALL candidate keys (fast)

  1. Attributes that appear on no right-hand side must be in every key — start there.
  2. Take that core and compute its closure; if it's everything, it's the unique key.
  3. Otherwise add other attributes one at a time and test closure for minimality.

04 Normalization — why each form exists

think of it likeNormalization removes redundancy that causes update anomalies. If a fact is stored in many rows, changing it in one place and not others corrupts the data. Each normal form bans a specific kind of bad dependency.

Fig — the normalization ladder, each rung removing one class of anomaly.

  • 1NF — atomic (indivisible) values; no repeating groups or lists in a cell.
  • 2NF — 1NF + no partial dependency (no non-prime attribute depends on only part of a composite key). Only an issue when the key is composite.
  • 3NF — 2NF + no transitive dependency (non-prime attribute → another non-prime). For each FD X→Y, either X is a superkey or Y is a prime attribute.
  • BCNF — for every non-trivial FD X→Y, X must be a superkey. Stricter than 3NF (drops the "Y is prime" escape).

How to find the highest normal form a table satisfies

  1. Find all candidate keys (via closure). Mark prime attributes (in any candidate key).
  2. For each FD X→Y, check the BCNF rule: is X a superkey? If all pass → BCNF.
  3. If some fail, check 3NF: is Y prime for those? If yes → 3NF.
  4. Else check 2NF (partial-dependency test). The lowest failing level minus one is the answer.
the catch2NF only matters with a composite key — a single-attribute key can't have partial dependencies. And 3NF allows X→Y when Y is a prime attribute; BCNF does not. That tiny difference is the most-tested normalization distinction.

05 Relational algebra & SQL evaluation

  • σ (select) — pick rows matching a condition (SQL WHERE).
  • π (project) — pick columns (SQL SELECT); set semantics removes duplicates.
  • ⋈ (join) — combine rows from two tables on matching attributes.
  • ∪, ∩, − — set operations on union-compatible relations.
key idea — SQL logical orderSQL is written SELECT…FROM…WHERE…GROUP BY…HAVING…ORDER BY, but it executes FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. That's why you can't use a SELECT alias in WHERE, and why WHERE filters rows but HAVING filters groups.
the catch — NULL logicNULL means "unknown," so comparisons with NULL yield UNKNOWN, not true. WHERE x = NULL never matches — use IS NULL. COUNT(*) counts all rows; COUNT(col) skips NULLs. Aggregates ignore NULLs.
workedTo filter groups: "departments with avg salary > 50k" → GROUP BY dept, then HAVING AVG(salary) > 50000 — not WHERE, because the average exists only after grouping.

06 Indexing & file organization

  • Index = a sorted lookup structure (usually a B+ tree) that turns O(n) scans into O(log n) searches — at the cost of slower writes and extra space.
  • Clustered (primary) index — table rows physically sorted by the key; only one per table.
  • Non-clustered (secondary) index — separate structure pointing to rows; many allowed.
  • B+ tree — all data in leaves, leaves linked for range scans; balanced height O(log n).

07 Data warehousing & OLAP

  • OLTP (transactions) = many small reads/writes, normalized. OLAP (analytics) = big aggregating reads, denormalized for speed.
  • Star schema — one fact table referencing denormalized dimension tables (fast, some redundancy).
  • Snowflake schema — dimensions further normalized into sub-tables (less redundancy, more joins).
  • OLAP ops: roll-up (aggregate up), drill-down (detail), slice/dice (filter), pivot (rotate axes).

08 The master decision tree

Read the question → branch

  1. "Candidate keys / is X a key" → attribute closure (§03).
  2. "Highest normal form / which NF violated" → keys → prime attrs → test BCNF/3NF/2NF (§04).
  3. "What does this query return / equivalent RA" → apply σ/π/⋈, mind SQL order & NULLs (§05).
  4. "Star vs snowflake / OLAP op" → §07.

09 The high-frequency exam traps

memorize these

  • Candidate key = minimal superkey; compute via closure.
  • 2NF needs a composite key to even be at risk.
  • 3NF allows prime Y; BCNF doesn't — the key distinction.
  • NULL comparisons = UNKNOWN — use IS NULL; aggregates skip NULLs; COUNT(*) doesn't.
  • WHERE filters rows, HAVING filters groups; SELECT alias unusable in WHERE.
  • Star = denormalized (fast), snowflake = normalized (more joins).
  • Index speeds reads, slows writes; only one clustered index per table.

10 FAQ

Quickest way to find candidate keys?

Attributes never on any FD's right side must be in every key — start with them, compute closure. If it covers everything, that's the unique key; else extend minimally and re-test.

3NF vs BCNF in one line?

For every FD X→Y: 3NF requires X is a superkey or Y is prime; BCNF drops the "or Y is prime," requiring X to be a superkey always. So BCNF ⊆ 3NF.

Why doesn't WHERE x = NULL work?

NULL is "unknown," so x = NULL evaluates to UNKNOWN (never TRUE), and WHERE keeps only TRUE rows. Use IS NULL / IS NOT NULL.

  • Attribute closure is the master skill — keys and normal forms both reduce to it.
  • Know the 3NF vs BCNF distinction and the 2NF-needs-composite-key rule cold.
  • SQL executes FROM→WHERE→GROUP BY→HAVING→SELECT; NULLs evaluate to UNKNOWN.
  • Star = fast/denormalized, snowflake = normalized/more joins; index trades write speed for read speed.
