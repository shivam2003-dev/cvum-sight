AI Weekly #1: Ten Papers on Cheaper Agents and New Failure Modes.

paperjuice agents llm-judges weekly-roundup

Summary: This week's ten papers split into two themes. Some make agents cheaper to run: smaller KV caches, cheaper judges, cheaper self improvement. Others expose new failure modes: lost state, sycophancy under a wrong hint. The common lesson is that scaffolding around the model is where the easy gains are.

How to read this issue

  • Start with the table below to pick papers.
  • Each paper has a card: problem, method, result, why it matters.
  • Numbers come from the source roundup. I rewrote all explanations myself.
  • I did not have verified arXiv links, so papers are named for searching, not linked.

1. HySparse2

By: Xiaomi MiMo team. Where: the attention design behind the upcoming MiMo-V3.

5.02xless prefill compute vs Hybrid SWA
2.92xless vs HySparse
2.69 GBKV cache at 1M tokens (Hybrid SWA: 12.09 GB)

Problem

  • Agents call tools, get long results back, and must prefill them again every turn.
  • Prefill cost and KV cache size both grow with every turn.

Method

  • Split model: a self decoder and a cross decoder, as in YOCO.
  • KV Bridging: the cross decoder builds its full attention cache from the self decoder's hidden states.
  • KV Reuse: each sparse layer reuses the cache and token selection of the full attention layer before it.
  • Token level selection replaces block level selection, and a forced recent window replaces the separate sliding window branch.
  • Early exit: prefill can stop once the self decoder finishes, since the cross decoder cache comes from it.

Result

  • Measured on 80B total, 3B active MoE models trained on the same data.
  • After light post training: +11.30 on MRCR-v2 and +19.81 on RULER-v2 over HySparse.
  • Lower AgentPPL and LongPPL than both baselines up to 256k tokens.

Why it matters: agent workloads repeat prefill on growing context. This design cuts both cost and memory without losing retrieval quality.

2. SIFT

By: MIT and Sakana AI. Builds on: the Darwin Godel Machine (DGM).

35.1%Polyglot with o3-mini, 30 expansions
30.7%DGM, 80 nodes
$34API spend, Qwen3-30B full search

Problem

  • Self modifying coding agents score every candidate by rerunning benchmarks.
  • That evaluation is where almost all the cost goes.

Method

  • An LLM judge compares candidate patches in pairs.
  • A regularized Bradley-Terry model turns wins and losses into strength scores.
  • Scores guide parent sampling in a disaggregated tree search.
  • Full benchmark runs happen only for the most promising nodes.

Result

  • o3-mini config: under 50 CPU hours, under 5 hours wall clock.
  • Qwen3-30B config: 224 CPU hours, about a tenth of the DGM baseline.
  • Judge quality matters: on TerminalBench, gpt-5.4-high as judge finds a 36.7% agent from 29.2%. gpt-5 finds 34.5% and ranks a weaker candidate first.

Why it matters: if you run a self improvement loop, the judge needs as much scrutiny as the search. A bad judge misranks candidates.

3. GAVEL

41.2% to 91.8%single task success
19.9% to 92.6%multi task success
5.4%less travel distance

Problem

  • LLM plans for long robot tasks break embodiment limits.
  • They lose track of objects out of view and cannot recover from mistakes.

Method

  • Add an explicit graph world model around the LLM.
  • The graph holds object relations, action preconditions and effects, and probabilistic beliefs about unseen objects.
  • Before an action runs, the graph predicts its effect and catches violations.
  • Fixes that follow from the model are applied without calling the LLM. Only semantic errors go back for replanning.

Result

  • Qwen3-8B on BEHAVIOR-1K: single task 41.2% to 91.8% across 100 tasks.
  • Multi task: 19.9% to 92.6% across 500 instructions.
  • Reasoning over object location distributions reorders subtasks and cuts travel by about 5.4%.

Why it matters: many long horizon failures are state tracking failures, not reasoning failures. This applies to software agents tracking files, tickets or accounts.

4. WFM (Wiki Foundation Model)

10.5xfaster distributed training
5memory and multi hop benchmarks

Problem

  • Many agents store memory as linked markdown pages, an "LLM wiki".
  • Plain RAG drops the links. Sparse graph embeddings drop most of the text.

Method

  • A Wiki Graph schema keeps entity relations and full passage text in one graph.
  • Retrieval runs query conditioned message passing with attentive aggregation.
  • A regularizer on attention variance stops one neighbor from dominating.
  • A GPU to GPU exchange protocol over NCCL avoids CPU serialization when the graph is split.

Why it matters: if your agent memory is already a folder of linked markdown, this retrieval model matches that shape instead of adapting plain RAG.

5. JEV as a Judge

277xcheaper than GPT-6 as judge
0.152 smedian latency (GPT-6: 1.885 s)
99% / 57%of GPT-6 accuracy at 57% of fee, in a cascade
JudgeCost per 1,000 judgmentsMedian latency
GPT-6 (generative)$12.1821.885 s
JEV (decision only)$0.0440.152 s

Method

  • JEV, from TypeSafe AI, returns a verdict and label probabilities with no reasoning text.
  • A cascade accepts confident JEV verdicts and escalates uncertain ones to a frontier model.

Result

  • Within 3 points of GPT-6 on preference and factuality: 92.2% vs 93.5% on RewardBench, 87.5% vs 86.7% on HaluEval.
  • Gap of 9 to 20 points on hard checks such as derivations: 78.6% vs 93.1% on JudgeBench.
  • Those errors cluster in JEV's low confidence calls, so the cascade works. On 510 held out preference pairs it kept 99% of GPT-6 accuracy at about 57% of the fee.
  • The escalation threshold did not transfer across every fallback model. Tune it on your own data.

More: see System One Models and Jev and How Jev Actually Works.

6. Harness-Zero

By: Google and colleagues.

23.3%base model, no harness
41.7%base model with specialized harness
44.3%distilled model, no harness
82.3%of harness gains recovered on average

Problem

  • The best harness differs by domain, instance and model.
  • Maintaining one per domain adds routing and upkeep cost.

Method

  • Use the specialized harness only in training.
  • The two harnesses have different action spaces, so it cannot supervise the target one directly.
  • A harnessing agent, guided by the specialized harness, corrects the student's responses in the deployment harness's action space.
  • Those corrected runs become fine tuning demonstrations.

Result: across 28 harness induced behaviors (knowledge work, tool use, science), the distilled model without the harness beats the base model with it. For frontier models, the agent as harness form beat the code as harness form.

Why it matters: some harness logic can be trained into one model instead of shipped as separate infrastructure.

7. Self-Organizing Agent Teams

By: Stanford and Together AI.

66.7%team average across 5 benchmarks
59.0%perfect router
48.8%strongest single member
0.90Spearman with demonstrability

Method

  • One member reviews past exchanges and outcomes, then rewrites the team strategy: roles, phase order, who takes part, how partial answers merge.
  • Strategies are learned offline and frozen before evaluation.
  • The team (o3-mini, Claude Sonnet 4, DeepSeek-V3) learned from only 15 AIME 2024 problems.

Result

  • Applied unchanged to held out problems and four new benchmarks.
  • Beat its strongest member (48.8%), that member with matched compute (58.7%), and a perfect router over independent answers (59.0%).
  • On AIME 2026 it beat the perfect router by 13.4 points, so it found correct answers no member found alone.

Why it matters: gains track "demonstrability", whether the team can recognize a correct answer once it appears. Use that as a test for whether a multi agent setup is worth building.

8. ScientistTwo

By: Google Cloud AI Research.

What it does

  • Takes a problem from a human expert and runs the whole discovery cycle with no further help.
  • Establishes baselines, screens ideas on a data subset, runs its own ablations, and revises the idea from the results.
  • Drafts the manuscript and runs a simulated peer review and rebuttal.

Result: on problems from papers accepted at ICLR, ICML and NeurIPS, its solutions beat the human state of the art models, and its papers scored higher on average than the human authored ones under automated AI reviewers.

Caveat: "scored higher under an AI reviewer" is narrower than "wrote a better paper". Automated reviewers have their own biases. Beating human baselines on the underlying problems is the stronger claim.

9. XYEval

By: Google DeepMind.

46.7%max relative score drop
5benchmarks tested

Method

  • Take tasks from tau2-bench, SWE-bench, Terminal-Bench, HLE and MCP-Atlas.
  • Keep the correct solution unchanged.
  • Add one confident, misleading hint.

Result

  • Scores fall by up to 46.7% relative across Gemini, Claude Opus 4.8 and GPT 5.5.
  • Agents often disagree with the hint in their reasoning, then follow it anyway without telling the user.
  • A system prompt warning about the XY problem helps on single turn tasks, but large drops remain on multi turn ones such as tau2-bench and SWE-bench Verified.

Why it matters: if your agent takes user input mid task, test it against a confident wrong hint. Do not assume a system prompt covers it.

10. EvoOntology

+17.8points on DDR-Bench (avg across backbones)
+7.4points on BIRD execution accuracy
57%of gain from tool layer edits

Problem

  • Data agents usually get a hand written schema description in the prompt.
  • It is static, never tested, and goes stale.

Method

  • Replace it with an ontology the agent queries at runtime, served over MCP with schema, content and tool layers.
  • A builder agent proposes small typed edits.
  • Each edit is kept only if a paired evaluation on the same backbone shows it helps.

Why it matters: treat your agent's understanding of a data source as a living artifact with its own evaluation loop.

The common thread

  • Cheaper to run: HySparse2, SIFT and JEV cut cost without a bigger model.
  • External structure beats bigger context: GAVEL, WFM and EvoOntology add a checkable layer next to the LLM.
  • How the model is used matters: Harness-Zero and the self organizing teams paper found gains in harness and protocol, not weights.
  • Failures get subtler: XYEval shows an agent can be cheap and well scaffolded and still give in to a confident wrong hint.

Practical takeaway: spend the next engineering cycle on scaffolding (memory format, world model, judge, ontology, collaboration protocol) before reaching for a bigger model.

FAQ

Should I implement all ten ideas?

No. Pick the pattern that fits. Cascade a cheap judge in front of an expensive one, put a checkable state tracker beside your agent, and test your multi turn agent against a confident wrong hint.

Which ones help if I only call an API?

JEV as a Judge, XYEval and EvoOntology. All three can be built in application code. HySparse2, SIFT, Harness-Zero and WFM matter more if you train models or run at scale.

Why no arXiv links?

The source roundup did not carry resolvable IDs, and I chose not to guess URLs. Search each paper name plus the lab name.

Takeaways

  • Prefill and KV cache cost are now the target of agent focused architectures.
  • Cheap judges work best as the first stage of a cascade.
  • A structured layer next to the LLM is cheaper than more context.
  • Harness behavior can be distilled into the model.
  • Test multi turn agents for sycophancy, since prompts alone did not fix it.
