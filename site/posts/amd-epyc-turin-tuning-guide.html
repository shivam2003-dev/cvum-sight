Tuning AMD EPYC "Turin" (5th Gen) for your org — in plain words.

devops amd-epyc turin performance bios

TL;DR — A new EPYC "Turin" server doesn't run its fastest out of the box — the safe defaults leave performance on the table. The biggest wins come from a handful of BIOS switches (NUMA layout, SMT, determinism, power/TDP) plus a few Linux settings (CPU governor, NUMA pinning, hugepages). The single most important rule: tune for your workload — a database, a web fleet, an HPC job, and an AI server all want different settings. This guide explains each knob in everyday language and gives ready recipes.

What "Turin" is, briefly

"Turin" is AMD's 5th-generation EPYC server chip (the EPYC 9005 family), built on the Zen 5 core. Versus the previous generation at the same power, it delivers roughly 20% more integer and 34% more floating-point performance on a 64-core part. It comes in two flavours: standard Zen 5 (up to 128 cores, best per-core speed) and dense Zen 5c (up to 192 cores, best total throughput). It uses 12 channels of fast DDR5 memory and the same SP5 socket as the prior generation.

Inside, the chip is built from several chiplets (AMD calls them CCDs) of cores around a central I/O die that talks to memory. That layout is why the tuning knobs below matter — they control how cores, cache, and memory are grouped and fed.

Fig 1 — Turin = many core chiplets (CCDs) around one I/O die. NUMA settings decide how this gets grouped for software.

Why tuning matters (and the one rule)

Server defaults are chosen to be safe and broadly OK, not fastest. They favour power saving and compatibility. Real workloads can gain 10–40%+ from correct settings — or lose performance from wrong ones. So the one rule above all:

There is no universal "fast" setting. Tune for the workload you actually run. Then measure — never trust a setting you didn't benchmark on your own job.

The BIOS knobs that matter most

These live in your server's BIOS/UEFI (often under "AMD CBS" or the vendor's performance menu). Each explained simply:

1. NPS — how memory is grouped (NUMA Nodes Per Socket)

The chip can present its memory as one big pool (NPS=1) or split into 2 or 4 smaller, closer pools (NPS=2 / NPS=4). Smaller pools mean each group of cores has memory right next to it — faster if your software is "NUMA-aware" and keeps work near its own memory.

  • NPS=1 — simplest, good default for mixed/cloud and software that isn't NUMA-aware.
  • NPS=4 — best for HPC and well-optimized databases that pin memory locally. Each quadrant gets its own slice of cores, cache, and memory channels.

2. SMT — two threads per core, on or off

SMT lets each physical core run two tasks at once (like hyper-threading). It usually helps total throughput, so leave it on for most servers. Turn it off for two reasons: pure HPC code that wants full, uncontended cores, or to cut software licence costs when a vendor charges per thread.

3. Determinism — steady vs maximum speed

"Power determinism" makes every chip behave identically (predictable, slightly slower). "Performance determinism" lets each chip run as fast as its power budget allows. For top speed pick Performance; for fleets where every node must match exactly, pick Power.

4. cTDP / Power limit — how much wattage the chip may use

Each Turin part has a configurable power range (cTDP). Setting it to the maximum lets the chip hold higher clocks under load — more performance, more heat and power draw. Only do this if your cooling and power supply can handle it.

5. Power profile / boost

Choose the high-performance power profile and keep Core Performance Boost enabled so cores can clock up. Energy-saving profiles trade speed for watts — fine for idle-heavy fleets, bad for latency-sensitive work.

6. A few more, quickly

  • LLC (L3) as NUMA — exposes each cache cluster as its own NUMA node; helps some latency-sensitive and HPC apps that benefit from cache locality.
  • APBDIS / fixed DF P-state — stops the internal fabric from dropping to low-power states, removing latency jitter (good for HPC/low-latency).
  • x2APIC + IOMMU — enable for high core counts and virtualization/device isolation.
  • Memory interleaving — leave at the auto/recommended value for your NPS choice.
Where to find exact names. BIOS labels differ by vendor (Dell, HPE, Lenovo, Supermicro) and on clouds you often can't touch BIOS at all — there you pick the right instance type instead (e.g. AWS Nitro EPYC instances expose NPS/SMT choices via instance family and CPU options). AMD publishes per-workload tuning guides with the precise setting names — linked at the end.

Linux settings (the other half)

BIOS sets the hardware; the OS decides how it's used. The high-value Linux changes:

CPU governor — tell Linux to run fast

# set all cores to the performance governor (no down-clocking)
sudo cpupower frequency-set -g performance
# verify
cpupower frequency-info | grep "governor"

Use tuned profiles (the easy button)

# RHEL/SLES ship workload profiles that set many knobs at once
sudo tuned-adm profile throughput-performance   # or: accelerator-performance
tuned-adm active

Keep work near its memory (NUMA pinning)

# see the NUMA layout your NPS choice produced
numactl --hardware
lscpu | grep -i numa
# pin a process to one NUMA node's CPUs + memory
numactl --cpunodebind=0 --membind=0 ./your_app

Hugepages for big-memory apps (databases, JVMs)

# transparent hugepages cut TLB misses for large working sets
cat /sys/kernel/mm/transparent_hugepage/enabled
# many DBs prefer explicit hugepages instead — set per vendor guidance

Other quick wins

  • IRQ affinity — spread network/storage interrupts across cores (or pin away from app cores) for steady latency.
  • Disable deep C-states for latency-critical apps (BIOS or kernel processor.max_cstate).
  • Security mitigations — leave on by default; only disable in isolated, trusted HPC clusters where you accept the risk for speed.
  • Recent kernel — newer kernels know Zen 5 better; use a current LTS for best scheduling and frequency behaviour.

How to verify you actually gained something

Tuning without measuring is guessing. The loop:

  1. Baseline first — record your real metric (requests/sec, query latency p99, job time) on defaults.
  2. Change one thing — one BIOS or OS setting at a time, so you know what did what.
  3. Re-run 5–10 times — clouds and servers vary; report the median, not one lucky run.
  4. Watch the side effects — power draw, temperature, and consistency, not just peak speed.

Quick sanity tools: sysbench (CPU/memory), stress-ng, and STREAM for memory bandwidth — but your own application under real load is the verdict that counts. (There's a whole playbook for benchmarking your own workload if you want the full method.)

common mistakes Changing many BIOS settings at once (you can't tell what helped) · maxing cTDP without checking cooling (the chip throttles and you lose the gain) · setting NPS=4 for software that isn't NUMA-aware (you add latency for nothing) · forgetting the Linux governor (a perfect BIOS still down-clocks if Linux says "powersave").

The org checklist

  • ☐ Identified the workload type for each server group
  • ☐ Picked the matching recipe (NPS / SMT / determinism / power)
  • ☐ Set Linux governor to performance + applied a tuned profile
  • ☐ Confirmed NUMA layout with numactl --hardware and pinned where needed
  • ☐ Baselined on defaults, then changed one knob at a time
  • ☐ Re-ran 5–10×, checked power/heat/consistency too
  • ☐ Documented the final settings as code/config so every node is identical
  • ☐ Scheduled a re-check after BIOS/firmware/kernel updates

// vocab

Turin / Zen 5▶
AMD's 5th-gen EPYC 9005 server CPUs, built on the Zen 5 core. ~20% more integer / 34% more FP than the prior gen at the same power.
CCD / chiplet▶
A small die of CPU cores. Turin packs several CCDs around one central I/O die — the reason NUMA settings exist.
NUMA▶
Non-Uniform Memory Access — cores reach their own nearby memory faster than far memory. "NUMA-aware" software keeps work near its memory.
NPS▶
NUMA Nodes Per Socket. NPS=1 = one big memory pool (simple). NPS=4 = four smaller, closer pools (faster for NUMA-aware apps).
SMT▶
Simultaneous Multithreading — two threads per physical core. Usually on (more throughput); off for pure HPC or per-thread licensing.
Determinism▶
Power = every chip behaves identically (predictable, a bit slower). Performance = each chip runs as fast as its power budget allows.
cTDP▶
Configurable Thermal Design Power — the wattage limit you allow the chip. Max it for more sustained clocks, if cooling/power can handle it.
CPU governor▶
Linux's frequency policy. "performance" keeps clocks high; "powersave" down-clocks. A great BIOS still loses if the governor saves power.
Hugepages▶
Larger memory pages that cut address-translation misses (TLB), helping big-memory apps like databases and JVMs.
