Branching Strategies at Big Tech, MNCs and Startups: What Each One Actually Does.

devops git ci-cd engineering-culture

Summary: There is no single "correct" branching strategy. Google, Meta and Netflix run trunk based development on a single branch with heavy automated testing and feature flags. Startups and Shopify use GitHub Flow: one main branch, short feature branches, deploy on merge. Large enterprises with versioned, shipped software often still use GitFlow or Microsoft's Release Flow, which both keep long lived branches around a release. The Linux kernel uses a fully distributed model with no shared branch at all. Pick based on release cadence, team size and how much test automation you actually have, not on what is trendy.

1. At a glance

"Branching strategy" really answers three practical questions: how long does a piece of in progress code live apart from everyone else's, how does it get back together with the rest of the codebase, and how does a specific version reach production. The five strategies below answer those three questions very differently, and the answer that fits a 2,000 person engineering org is rarely the answer that fits a 5 person startup.

3. Trunk based development

GoogleMetaNetflixAmazonUberMost high performing SaaS teams

Everyone commits to one branch, called trunk or main. If branches exist at all, they live for hours and exist only for code review and CI, not for feature development that spans days.

How it works

  • One long lived branch. No develop branch, no long lived feature branches.
  • Unfinished work merges to trunk hidden behind a feature flag, not left on a branch.
  • A flag can be rolled out gradually: internal staff first, then 1% of traffic, then 10%, watching error rates at each step.
  • Heavy investment in CI, automated tests and in some cases a custom build system (Google uses Bazel internally).

Company specifics

  • Google runs its entire codebase, used by more than 35,000 engineers, in one Perforce based monorepo called Piper. Most engineers work through CitC (Client in the Cloud), a cloud backed filesystem where only changed files live in your workspace and unmodified files are not copied locally.
  • Meta is commonly cited alongside Google and Netflix as a trunk based, feature flag heavy organization.
  • Netflix built Spinnaker, an open source continuous delivery platform, to manage canary releases, red/black deploys and rollbacks across its microservices.
  • Amazon pushes a production deploy on average every 11.6 seconds across its services. This comes from "two pizza teams", groups small enough to feed with two pizzas, usually 10 people or fewer, who own one service end to end and deploy it independently with no central approval queue.

Why this needs feature flags, and the catch

Trunk based development only works if unfinished code hidden behind a flag never actually breaks anything. Flags are cheap to add and expensive to remove, so they build up. Minware and GrowthBook both describe this as flag debt: a codebase that accumulates hundreds of active toggles, many for features that shipped months ago, each one adding an untested combination of code paths.

The $440 million case for cleaning up flags: in 2012, Knight Capital deployed new trading code to 7 of its 8 servers. The 8th server kept an 8 year old flag that used to trigger a retired algorithm called Power Peg. The new code reused that same flag number for an unrelated purpose instead of allocating a new one. Orders sent with the repurposed flag woke up the dead algorithm on the 8th server, which bought high and sold low for 45 minutes before anyone found it, losing the firm $440 million and leading to its acquisition within the year.

Uber's fix: a tool called Piranha scans source code, finds stale flags, and automatically generates a diff that deletes the dead code paths for review. Between December 2017 and May 2019 it generated cleanup diffs for 1,381 flags and removed 71,000 lines of code, with 65% of its generated diffs landing with no manual changes needed. It is open source and supports Java, Objective-C and Swift.

Pros

  • Few or no long merges, so merge conflicts stay small.
  • Deploys can happen many times a day.
  • Feature flags let you decouple shipping code from releasing a feature to users.

Cons

  • Needs strong CI and automated test coverage before it is safe.
  • Feature flag sprawl becomes its own maintenance problem if flags are never cleaned up.
  • Requires tooling investment most small teams do not have (Google and Meta built their own).

4. GitHub Flow

GitHubShopifyMost startups

One main branch that is always deployable. Every change gets a short branch, a pull request, review, then a merge to main that triggers a deploy.

How it works

  • Branch off main for any change, however small.
  • Open a pull request early so others can see and comment on the work.
  • Merge once it passes review and CI. Main is always the source of truth for production.
  • No release branches, no fixed release schedule. You ship when you merge.

Company specifics

  • Shopify runs a tweaked GitHub Flow where main is the state of production. Their Shipit tool batches 5 to 10 merged commits into a deploy at a time through a merge queue, which makes it easier to spot the exact commit that caused a problem and roll it back.
  • At Shopify, merging a pull request is close to the last human step. A deploy bot batches merges and triggers deploys on a schedule, so you do not log into a server to push code.

Pros

  • Simple to explain to a new hire in five minutes.
  • Works well with continuous deployment.
  • Low ceremony, no release branch bookkeeping.

Cons

  • No built in way to support multiple versions in production at once.
  • Still needs decent CI, or main breaks for everyone.
  • Does not fit products that ship on a fixed schedule to an app store or on physical media.

5. GitFlow

Published by Vincent Driessen, 2010Enterprise softwareSDKsRegulated industries

Two long lived branches, main and develop, plus supporting branches for features, releases and hotfixes.

How it works

  • develop holds work in progress for the next release.
  • Feature branches come off develop and merge back into it.
  • A release branch is cut from develop to stabilize a version, then merged into both main and develop.
  • Hotfix branches come off main for urgent production fixes, then merge back into both main and develop.
  • main only ever holds tagged, released versions.

Pros

  • Clear structure for supporting several released versions at once.
  • Good fit for software with scheduled, versioned releases: SDKs, firmware, desktop apps.
  • Easy to explain the state of any given commit: feature, release candidate, or shipped.

Cons

  • Long lived develop branch drifts far from main, so merges get painful.
  • GitLab's own documentation calls it "annoying" and full of unnecessary ceremony for teams that deploy often.
  • The --no-ff merge habit many teams pair with GitFlow produces a tangled commit history.
  • Most teams that ship web products many times a day have moved away from it.
Still a reasonable choice for: versioned SDKs, embedded or firmware projects, and regulated industries that must support several shipped versions in parallel for years. Not a good default for a typical SaaS web app in 2026.

6. GitLab Flow

GitLabTeams with staged environmentsCompliance heavy orgs

Takes GitHub Flow's single main branch and adds environment branches on top, such as pre-production and production.

How it works

  • Feature branches merge into main, same as GitHub Flow.
  • main is then merged downstream into one or more environment branches in order.
  • Code only reaches production after it has flowed through every environment branch in between.
  • Each environment branch must always be deployable to its matching environment.
  • A hotfix follows the same path as any other change. It is not allowed to skip straight to the production branch, which is the main difference from teams that quietly patch production directly and let it drift.

GitLab designed this model for its own product, where every merge request already runs through staged pipelines before a release. The appeal over plain GitHub Flow is that "deployable" is proven at each stage, not assumed. The cost is that a change takes longer to reach users, since it has to clear every environment branch in order rather than going straight from merge to production.

Pros

  • Gives you an explicit, auditable gate between each environment.
  • Keeps the simplicity of one main development branch.
  • Fits teams that need a paper trail for what went where and when.

Cons

  • More branches to keep green than plain GitHub Flow.
  • Promoting code through environment branches adds latency between merge and production.
  • Still needs discipline to stop environment branches from drifting apart.

7. Release Flow

Microsoft, Azure DevOps / VSTS team

Trunk based day to day, but with a dedicated release branch cut for each shipped release instead of deploying straight from main.

How it works

  • Developers work in short lived topic branches off main, same as trunk based development.
  • main stays buildable at all times.
  • When a team is ready to ship, usually at the end of a sprint, they cut a new release branch from main and name it after the release.
  • Release branches do not merge back into main. Important fixes are cherry picked back instead.
  • Unlike GitHub Flow, the team does not continuously deploy main straight to production. They release on a sprint cadence from the release branch.

Pros

  • Keeps the simplicity of trunk based development for daily work.
  • Gives a clean, named artifact for each release, useful for a scheduled release cadence.
  • Hotfixing a specific release is straightforward: branch from that release branch.

Cons

  • Cherry picking fixes back from a release branch is manual and easy to forget.
  • Not true continuous deployment, since production only updates when a release branch ships.
  • Needs a scheduling cadence (sprints) to make sense. Awkward for teams that ship whenever a change is ready.

8. Distributed maintainer trees

Linux kernel

No shared branch at all. Patches travel by email, reviewed on mailing lists, and pulled upward through a tree of maintainers.

How it works

  • Each subsystem has its own maintainer and its own git tree, plus a mailing list.
  • Contributors send patches as emails using git format-patch and git send-email, not pull requests.
  • A subsystem maintainer typically keeps two branches: one tracking Linus's tree for the current release, one for the next release.
  • Maintainers pull from other maintainers below them. For example the networking tree is built from patches collected first in driver specific trees. This chain is rarely longer than two or three links.
  • Linus Torvalds pulls from top level maintainers to assemble each release.
  • A new kernel release opens with a two week merge window where new work is pulled in, then goes through weekly release candidates, usually rc1 through rc7, that only accept fixes, not new features.

There is no equivalent of a pull request button and no single shared integration branch anyone writes directly to. The entire coordination mechanism is a chain of trust: Linus trusts his top level maintainers to only send him things their own reviewers have already checked, and so on down the tree.

Pros

  • Scales to thousands of contributors with no central write access needed.
  • Clear ownership: every subsystem has a named maintainer responsible for its tree.
  • Review happens in the open on public mailing lists.

Cons

  • Steep learning curve for anyone used to pull requests on GitHub.
  • Email based patch review tooling is unfamiliar to most engineers today.
  • Only works because of decades of process discipline. Hard to copy wholesale into a company.

9. Which one should you actually use

Your situationReasonable choice
Early stage startup, one small team, web appGitHub Flow
Growing SaaS company, strong CI, want to ship many times a dayTrunk based development with feature flags
Enterprise product with several supported versions in the fieldGitFlow, or Release Flow if you also want trunk based daily work
Regulated industry needing an audit trail between environmentsGitLab Flow
Sprint based team shipping on a fixed cadenceRelease Flow
Huge open source project with thousands of outside contributorsDistributed maintainer trees, Linux kernel style
You do not have reliable CI or automated tests yetDo not pick trunk based development yet. Fix testing first, use GitHub Flow in the meantime
Rule of thumb: the shorter your branches live, the more you depend on automated tests to catch problems instead of a human reviewing a big diff. Match your branching strategy to how much you trust your test suite, not to what a famous company does.
Why copying Google exactly usually fails: Google's trunk based model works because of roughly two decades of investment in Piper, CitC, Bazel, and a code review culture backed by a huge testing infrastructure team. A 15 person startup that adopts "one branch, no exceptions" without that infrastructure usually ends up with a trunk that is red half the time and a team that has quietly started avoiding merges, which is worse than GitHub Flow with real pull requests. Copy the principle, build the automated testing first, then earn the short branch lifetimes.

10. Moving from GitFlow to trunk based development

A common real world path. Do not flip the switch overnight. Order matters.

  1. Get CI green first. Every commit to main must run the full automated test suite before anyone touches branching. Skipping this step is how teams end up with a broken trunk and a worse experience than GitFlow gave them.
  2. Shrink your feature branches. Before removing develop, start merging feature work in smaller, more frequent pull requests. A branch that lives two days is a much smaller leap than one that lives two weeks.
  3. Introduce feature flags for anything unfinished. Pick one flag system (LaunchDarkly, GrowthBook, Unleash, or an in-house one) before you need ten of them.
  4. Retire develop. Merge it into main one last time, then stop creating new branches from it. New feature branches now come off main directly.
  5. Assign flag owners and expiry dates from day one. This is the step most teams skip, and it is exactly how flag debt builds up later.
  6. Keep a release branch strategy if you still need versioned releases. You can combine trunk based daily work with Microsoft's Release Flow pattern, cutting a release branch when you actually ship, instead of going all the way to continuous deployment on day one.

12. Monorepo versus polyrepo, and how it changes branching

The branching strategy a company can realistically run is tied to how its code is split across repositories.

MonorepoPolyrepo
ExampleGoogle's Piper, Meta's codebaseMost startups, one repo per service
Cross project changesOne commit can touch many projects at once and is tested togetherNeeds coordinated releases or careful versioning across repos
Trunk based developmentNatural fit. One trunk, one history, one CI run proves the whole tree still worksWorks, but each repo needs its own CI and its own discipline
Tooling neededCustom build systems at Google and Meta scale, or Bazel for smaller setupsStandard per-language tooling usually suffices
Access controlHarder to restrict who can see or change whatNatural repo level boundaries

A monorepo does not force trunk based development, and trunk based development does not require a monorepo. But in practice the two show up together often, because a monorepo removes a lot of the cross repository coordination that makes long lived branches tempting in the first place.

13. Signs your branching strategy is failing

Teams rarely change their branching model because the model is wrong in theory. They change it because a symptom becomes painful enough. The table below lists the symptoms that show up most often and what they usually point to.

SymptomWhat it usually meansWhat to try first
Merges take days and create many conflictsBranches live too long, so the codebase moves on underneath themShorten branch lifetime. Merge smaller pull requests more often, even before a feature is complete, behind a flag.
Main is often red and nobody trusts itCI is too slow, too flaky, or does not cover the paths people changeFix the test pipeline before changing the branching model. Quarantine flaky tests and track their count.
Production hotfixes never make it back to the main lineHotfixes go straight to the production branch and drift away from the rest of the codebaseRequire every hotfix to flow back through the same path as a normal change, even if that adds a few minutes.
Release day is stressful and gets delayedToo many changes accumulate between releases, and integration is left to the endShip more often in smaller releases. If you must keep a release branch, cut it earlier and cherry pick fixes deliberately.
Feature flags keep growing and nobody removes themFlags are created without owners or expiry datesAssign an owner and an expiry date at creation. Schedule removal as part of finishing each feature.
Engineers avoid merging because it is riskyTrust in the pipeline is low, so people batch changes and delay integrationAdd a merge queue to control the rate of change, and make rollbacks fast and routine so merging is no longer a commitment.

The pattern across these symptoms is consistent. Most branching pain is a feedback problem: changes wait too long to be integrated and tested. A strategy with long branches hides that problem until release. A strategy with short branches exposes it early, which is uncomfortable but cheaper to fix.

14. When a migration is worth the cost

Moving from one strategy to another has real costs: retraining, tooling changes, a period of mixed practices, and sometimes a temporary drop in velocity. A migration is worth it when the current model blocks something the business needs, not because a newer model sounds better. Three situations usually justify the cost.

  • Release frequency is capped by the branching model. If the team wants to ship daily but the process only allows monthly releases, the branching model is the constraint.
  • The number of supported versions has shrunk. A product that once needed several long lived release lines may now need only one. Keeping the old model then adds overhead with no benefit.
  • Integration problems dominate the incident log. When a large share of production incidents trace to merges and divergent branches, the cost of the current model is measurable.

If none of these apply, improving the existing strategy usually pays more. Tighter CI, faster reviews, and a disciplined flag lifecycle often give most of the benefit of a migration with much less disruption.

FAQ

Is trunk based development the same as continuous deployment?

No. Trunk based development is about where code lives before it merges. Continuous deployment is about what happens after it merges. You can do trunk based development and still deploy on a schedule, as Microsoft's Release Flow shows.

Can a big company use GitHub Flow?

Yes, Shopify does, with extra tooling (a merge queue and a deploy bot) layered on top to control the rate and safety of merges. The core model stays simple even as the company scales.

Why do people say GitFlow is outdated?

Most criticism targets using it for a web product that deploys often. A long lived develop branch drifts from main and merges get painful. It still fits products with multiple supported released versions, such as SDKs or firmware.

What do monorepo and branching strategy have to do with each other?

A monorepo makes trunk based development easier, since every team's code sits in one place and can be tested together on every commit. It is possible to use trunk based development with multiple repos too, but a monorepo like Google's Piper removes a lot of the coordination overhead.

Do I need feature flags to do trunk based development?

For anything beyond a small feature, yes. Without a flag, half finished work merged to trunk either ships to users before it is ready or has to wait on a branch, which defeats the point of trunk based development.

How do I stop feature flags from piling up?

Assign an owner and an expiration date to every flag when it is created, and treat flag removal as a normal part of finishing a feature, not optional cleanup. Uber's open source Piranha tool automates finding and removing stale flags for Java, Objective-C and Swift codebases.

Can I mix strategies, for example trunk based work with release branches?

Yes, this is exactly what Microsoft's Release Flow does. Day to day work is trunk based with short lived topic branches, but instead of deploying straight from main, a named release branch is cut per release and fixes are cherry picked back into it when needed.

What does the Linux kernel do differently from everyone else here?

Every other strategy in this article assumes one shared repository with write access controlled by permissions. The kernel has none of that. Patches move as emails, each maintainer owns their own tree, and the only thing holding it together is a chain of people who trust the reviewer below them. It works at a scale almost nothing else matches, but it took decades of process to get there.

Takeaways

  • Trunk based development (Google, Meta, Netflix) trades long branches for strong CI and feature flags.
  • GitHub Flow (GitHub, Shopify, startups) is the simplest model that still supports continuous deployment.
  • GitFlow still earns its keep for versioned SDKs and regulated software, but is a poor default for a fast moving web product.
  • GitLab Flow adds explicit environment gates on top of a simple main branch.
  • Microsoft's Release Flow keeps trunk based daily work but ships from a named release branch per cycle.
  • The Linux kernel shows a working model with no shared branch at all, built on mailing lists and maintainer trust.
  • Choose based on release cadence, team size and test automation maturity, not on which company is trendiest.
