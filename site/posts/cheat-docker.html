Docker — The Interview Cheatsheet.

docker containers devops interview-prep
Concepts Lifecycle Images Dockerfile CMD vs ENTRYPOINT Multi-stage Volumes Networking Compose Best practices Security Debug Interview Q&A
If you remember one thing: an image is a read-only template; a container is a running (writable) instance of it. Images are built in layers, each layer cached. Containers add a thin writable layer on top and are ephemeral — kill it and the writable layer is gone unless you used a volume.

1. Core concepts

TermWhat it is
ImageRead-only template (app + deps + filesystem), built from a Dockerfile, made of stacked layers.
ContainerA running instance of an image with a thin writable layer on top. Ephemeral by default.
LayerOne filesystem diff = one Dockerfile instruction. Cached and shared between images.
RegistryStore/distribute images (Docker Hub, ECR, GHCR). push/pull.
DockerfileRecipe of instructions to build an image.
VolumePersistent storage that outlives the container.
Daemon (dockerd)Background service that builds/runs containers. The CLI talks to it over a socket.

Architecture: the Docker client (docker) sends commands to the daemon (dockerd) via REST over a Unix socket; the daemon manages images, containers, networks, volumes, and pulls from registries. Under the hood it uses Linux namespaces (isolation: PID, NET, MNT, UTS, IPC, USER) and cgroups (resource limits: CPU, memory). That's the real answer to "how is a container different from a VM" — containers share the host kernel, VMs ship their own.

2. Container lifecycle

docker run -d --name web -p 8080:80 nginx   # detached, named, publish port
docker run -it ubuntu bash                  # interactive shell
docker run --rm alpine echo hi              # auto-remove on exit
docker ps                                   # running containers
docker ps -a                                # all (incl. stopped)
docker stop web        /  docker start web  /  docker restart web
docker kill web                             # SIGKILL (stop sends SIGTERM then SIGKILL)
docker rm web          /  docker rm -f web  # remove (force = stop+rm)
docker exec -it web sh                      # shell into running container
docker logs -f --tail 100 web               # stream logs
docker inspect web                          # full JSON state
docker stats                                # live CPU/mem/IO
docker cp web:/etc/nginx/nginx.conf .       # copy file out

3. Working with images

docker build -t myapp:1.0 .                 # build from ./Dockerfile
docker build -t myapp:1.0 -f Dockerfile.prod .
docker images            /  docker image ls  # list
docker pull node:20-alpine
docker tag myapp:1.0 registry.example.com/myapp:1.0
docker push registry.example.com/myapp:1.0
docker history myapp:1.0                    # see layers + sizes
docker rmi myapp:1.0                        # remove image
docker image prune -a                       # delete unused images
docker save -o app.tar myapp:1.0  /  docker load -i app.tar

4. Dockerfile instructions

InstructionPurpose
FROMBase image. First instruction (after optional ARG).
WORKDIRSet/create working dir for subsequent instructions.
COPYCopy files from build context into image.
ADDLike COPY + auto-extracts tar + can fetch URLs. Prefer COPY.
RUNExecute a command at build time → new layer.
ENVSet environment variable (persists at runtime).
ARGBuild-time variable (not in final image runtime).
EXPOSEDocument the port (doesn't publish — -p does).
VOLUMEDeclare a mount point for persistent data.
USERSet the user for following instructions + runtime.
HEALTHCHECKCommand Docker runs to test container health.
CMDDefault command/args (overridable at run).
ENTRYPOINTThe executable; CMD becomes its args.
 
# Example
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev          # cached unless package files change
COPY . .
EXPOSE 3000
USER node
CMD ["node", "server.js"]
Layer caching gotcha Copy dependency manifests and install before copying the rest of the source. If you COPY . . first, any code change busts the cache and reinstalls all deps every build. Order instructions least-changing → most-changing.

5. CMD vs ENTRYPOINT (classic trap)

CMDENTRYPOINT
RoleDefault command/argsThe fixed executable
Override at rundocker run img othercmd replaces itArgs after image name become args to entrypoint
Best forA sensible default you may swapContainer that always runs one binary

Common pattern: ENTRYPOINT ["python","app.py"] + CMD ["--port","8000"]. Running docker run img --port 9000 overrides only the CMD args. Always use exec form (JSON array) not shell form — shell form wraps in /bin/sh -c and breaks signal handling (your app won't get SIGTERM, so graceful shutdown fails).

6. Multi-stage builds

Build in a heavy image, copy only the artifact into a tiny final image. Cuts size massively.

FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd

FROM gcr.io/distroless/static    # no shell, no package manager
COPY --from=build /app /app
ENTRYPOINT ["/app"]

Result: final image holds just the binary — small, fast to ship, tiny attack surface.

7. Volumes & storage

TypeUse
Named volumeDocker-managed persistent data. -v mydata:/var/lib/db. Best for DB data.
Bind mountHost path → container. -v $(pwd):/app. Best for local dev (live code).
tmpfsIn-memory, never written to disk. Secrets / scratch.
 
docker volume create mydata
docker run -v mydata:/var/lib/postgresql/data postgres
docker volume ls  /  docker volume inspect mydata  /  docker volume prune

8. Networking

DriverBehaviour
bridgeDefault. Private network on the host; containers reach each other by name.
hostShare host network stack directly. No isolation, no port mapping needed.
noneNo networking.
overlayMulti-host network (Swarm). Containers across nodes talk.
 
docker network create appnet
docker run -d --network appnet --name db postgres
docker run -d --network appnet --name api myapi   # api reaches db at hostname "db"
docker run -p 8080:80 nginx                        # publish host:container
docker network ls / inspect / rm
DNS gotcha On a user-defined bridge network, containers resolve each other by name automatically. On the default bridge they do not — you'd need legacy --link. Always create your own network.

9. Docker Compose

services:
  api:
    build: .
    ports: ["3000:3000"]
    environment:
      - DATABASE_URL=postgres://db:5432/app
    depends_on: [db]
  db:
    image: postgres:16
    volumes: ["pgdata:/var/lib/postgresql/data"]
    environment:
      POSTGRES_PASSWORD: secret
volumes:
  pgdata:
docker compose up -d        # start
docker compose ps / logs -f / down
docker compose up --build   # rebuild images
docker compose down -v      # also remove volumes
depends_on gotcha depends_on waits for the container to start, not for the app inside to be ready. For "wait until Postgres accepts connections" use a healthcheck + condition: service_healthy.

10. Best practices

  • Small base images — alpine, slim, or distroless.
  • Multi-stage builds to drop build tools from the final image.
  • Add a .dockerignore (skip node_modules, .git) — smaller context, faster builds.
  • Order layers least → most volatile for cache hits.
  • One process per container; one concern per image.
  • Pin versions (node:20.11-alpine, not latest).
  • Run as non-root (USER).
  • Combine RUN steps + clean apt caches in the same layer.

11. Security

  • Non-root user — never run app as root inside the container.
  • --read-only root filesystem + tmpfs for writable paths.
  • Drop capabilities: --cap-drop ALL --cap-add NET_BIND_SERVICE.
  • --no-new-privileges to block privilege escalation.
  • Scan images (docker scout, Trivy) for CVEs.
  • Never bake secrets into images/layers (they persist in history). Use runtime env / secret mounts / BuildKit --secret.
  • Avoid --privileged unless you truly need it.

12. Debug toolkit

docker logs -f --tail 200           # what did it print?
docker exec -it  sh                  # poke around inside
docker inspect                       # config, mounts, network, exit code
docker stats                             # resource hogs
docker events                            # daemon event stream
docker system df                         # disk usage by images/containers/volumes
docker system prune -a --volumes         # reclaim space (careful)
docker top                           # processes in container
SymptomLikely cause
Container exits immediatelyMain process finished/crashed — check logs, exit code in inspect. No long-running foreground process.
Port not reachableForgot -p, app bound to 127.0.0.1 not 0.0.0.0, or wrong network.
Changes not reflectedRebuilt without --build, or stale layer cache.
"No space left"Dangling images/volumes — docker system prune.
Signals ignored / slow stopUsed shell-form CMD; PID 1 is /bin/sh, not your app.

13. Rapid-fire interview Q&A

  • Container vs VM?Containers share the host kernel (namespaces + cgroups), start in ms, are MBs. VMs virtualize hardware, ship a full OS, are GBs and slower. Containers = process isolation, not hardware isolation.
  • Image vs container?Image = read-only template (layers). Container = running instance with a writable top layer. Many containers from one image.
  • COPY vs ADD?COPY just copies. ADD also auto-extracts local tars and can fetch URLs. Prefer COPY — explicit, predictable.
  • CMD vs ENTRYPOINT?ENTRYPOINT = fixed executable; CMD = default args (overridable). Use both: ENTRYPOINT binary + CMD default flags.
  • How do you shrink an image?Multi-stage builds, alpine/distroless base, .dockerignore, fewer/combined layers, remove caches in the same RUN.
  • How does layer caching work?Each instruction is a cached layer keyed on the instruction + context. If a layer changes, it and all below rebuild. Order least-volatile first.
  • Bind mount vs volume?Bind = host path (dev, live code). Volume = Docker-managed (prod data, portable, backup-friendly).
  • How do containers talk to each other?On a user-defined network, by container name via Docker's embedded DNS.
  • EXPOSE vs -p?EXPOSE is documentation only. -p host:container actually publishes the port to the host.
  • What is PID 1 / why use an init?Your container's main process is PID 1; it must reap zombies and handle signals. Use exec-form CMD or an init (--init / tini) for proper signal handling.
  • Is data lost when a container dies?The writable layer is lost. Anything in a volume/bind mount persists.
  • Why not run as root?A container escape as root ≈ host root. Drop to a non-root USER and minimal capabilities.
