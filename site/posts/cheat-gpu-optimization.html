CHEATSHEET · GENAI · GPU PERFORMANCE

GPU Optimization — The Engineer's Cheatsheet.

gpu cuda performance ml-engineering
Almost every "slow GPU" is one of three things: you're memory-bandwidth bound (not compute), you're starving the GPU (data pipeline / CPU / sync), or you never enabled the fast path (Tensor Cores, fused kernels, the right dtype). Find which one before you touch a kernel.

1. The mental model

  • A GPU is many SMs (streaming multiprocessors). Each runs threads in groups of 32 — a warp. Thousands of warps hide latency by swapping in when one stalls on memory.
  • Throughput machine, not latency machine. You win by keeping it fed and busy, not by making one op fast.
  • The real wall is usually HBM bandwidth (moving data to/from global memory), not FLOPs. Modern accelerators have far more compute than bandwidth.

2. Memory hierarchy (fast → slow)

TierWhat / cost
RegistersPer-thread, fastest. Spilling to "local" memory (really global) kills perf.
Shared memory / L1Per-SM scratchpad (~tens–100s KB). The key to tiling — reuse data across a block.
L2 cacheChip-wide, a few MB. Shared by all SMs.
Global (HBM)GBs, high bandwidth but high latency. The bottleneck for most kernels.

Coalescing: threads in a warp should read contiguous addresses so loads merge into a few wide transactions. Strided/scattered access wastes bandwidth.

3. Memory-bound vs compute-bound (roofline)

  • Arithmetic intensity = FLOPs ÷ bytes moved. Low intensity (elementwise add, layernorm, activation) → memory-bound. High intensity (big GEMM, conv) → compute-bound.
  • Memory-bound kernels are fixed by fusion (do more per byte loaded) and better access patterns — not faster math.
  • Compute-bound kernels are fixed by Tensor Cores, better tiling, and lower precision.
most ML ops are memory-bound Attention, layernorm, GELU, softmax, residual adds — all memory-bound. That's why FlashAttention (fusion + no materialized N×N matrix) is a huge win and why torch.compile fuses pointwise chains. Stacking more FLOPs doesn't help these.

4. Precision — pick the right dtype

dtypeWhen / why
FP32Default but slow. Rarely needed end-to-end for DL.
TF32Ampere+ auto-mode for matmuls — ~FP32 accuracy, big speedup. Enable it.
FP16Half memory + Tensor Cores. Narrow range → needs loss scaling.
BF16Same exponent range as FP32 (no loss scaling), less mantissa. Default for modern training.
FP8Hopper+/Blackwell. Training & inference with per-tensor/per-block scaling. Biggest throughput, most fragile.
INT8/INT4Inference quantization (weights and/or activations). Memory + bandwidth win.
 
# PyTorch: enable the fast matmul paths
import torch
torch.set_float32_matmul_precision("high")   # TF32 for fp32 matmuls
torch.backends.cuda.matmul.allow_tf32 = True
torch.backends.cudnn.allow_tf32 = True

# Mixed precision (BF16 preferred on Ampere+)
with torch.autocast("cuda", dtype=torch.bfloat16):
    out = model(x)

5. Tensor Cores — the fast path

  • Dedicated matrix-multiply-accumulate units. They do the heavy GEMMs in FP16/BF16/FP8/INT8 — orders faster than CUDA cores in FP32.
  • They engage only with low precision and friendly shapes. Keep matmul dimensions multiples of 8 (FP16) / 16 — pad vocab sizes, hidden dims, batch.
  • Check they're actually used: Nsight Compute "Tensor" pipe utilization, or torch profiler kernel names (*s16816gemm*, *_tensor_*).

6. Fusion & kernels

  • Kernel launch overhead is real (~µs each). Thousands of tiny ops = death by launches. Fuse them.
  • torch.compile(model) — fuses pointwise chains, picks better kernels, reduces launches. First win to try.
  • FlashAttention — fused, IO-aware attention; never materializes the N×N score matrix → memory and speed win, longer contexts.
  • CUDA Graphs — capture a static sequence of launches, replay as one. Removes per-launch CPU overhead for small-batch inference.
  • Use fused optimizers (fused=True AdamW), fused layernorm/RMSNorm (apex / Triton).

7. Don't starve the GPU

DataLoader(ds, batch_size=B,
           num_workers=8, pin_memory=True,
           persistent_workers=True, prefetch_factor=4)
# move to device async, overlap with compute
x = x.to("cuda", non_blocking=True)
  • If nvidia-smi shows low GPU-util with spiky pattern → input pipeline or CPU preprocessing is the bottleneck, not the model.
  • Avoid host↔device syncs in the hot loop: .item(), .cpu(), print(loss), tensor.numpy(), Python if on a GPU value — each forces a stall.
  • Keep tensors on-GPU; accumulate metrics on device and sync once per N steps.
.item() in the training loop is a silent killer Calling loss.item() every step forces a device sync — the CPU waits for the GPU, breaking overlap. Log every N steps, or stash losses on-GPU and sync in a batch.

8. Fit a bigger model / batch

  • Gradient checkpointing — recompute activations in backward instead of storing them. Trade compute for memory; fits much larger models.
  • Gradient accumulation — simulate a big batch with several small forward/backward passes before step().
  • Activation/optimizer offload — push states to CPU/NVMe (ZeRO-Offload) when VRAM is tight.
  • PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True reduces fragmentation OOMs.
  • Free cache between phases with torch.cuda.empty_cache() (doesn't fix leaks, just fragmentation).

9. Multi-GPU & communication

  • Data parallel (DDP/FSDP) — each GPU a shard of the batch; gradients all-reduced. FSDP also shards params/optimizer states (ZeRO-style) to fit large models.
  • NCCL does the collectives (all-reduce, all-gather). Goal: overlap comms with compute so the network is hidden.
  • Topology matters: NVLink > PCIe > network. Check nvidia-smi topo -m. Cross-node needs fast fabric (InfiniBand/RoCE) or comms dominates.
  • Tune NCCL_* env (e.g. algorithms, buffer sizes) only after confirming comms is the bottleneck.

10. Profiling — measure, don't guess

nvidia-smi dmon -s pucvmet      # live: power, util, mem, clocks, throttle
nvidia-smi -q -d CLOCK,PERFORMANCE  # clocks + throttle reasons
nsys profile -o out python train.py   # timeline: kernels, gaps, syncs, NCCL
ncu --set full -k regex:gemm python x.py  # per-kernel: occupancy, mem, pipes
# PyTorch profiler — find the expensive ops
from torch.profiler import profile, ProfilerActivity
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             record_shapes=True) as p:
    model(x)
print(p.key_averages().table(sort_by="cuda_time_total", row_limit=20))
  • Nsight Systems (nsys) — timeline; spot gaps (starvation), syncs, CPU bottleneck, comms not overlapping.
  • Nsight Compute (ncu) — single-kernel deep dive; occupancy, memory throughput, Tensor pipe usage, stall reasons.

12. Interview Q&A

  • Memory-bound vs compute-bound — how do you tell?Arithmetic intensity (FLOPs/byte) and the roofline. Profiler shows high memory throughput + low compute (or vice versa). Elementwise/norm/attention = memory-bound; big GEMMs = compute-bound.
  • GPU-util is 100% but training is slow — why?Util just means a kernel is resident, not efficient. Could be a memory-bound kernel saturating bandwidth, tiny kernels with launch overhead, or no Tensor Cores. Profile with nsys/ncu.
  • GPU-util is low and spiky — why?Starvation: data pipeline too slow, CPU preprocessing, host↔device syncs (.item()), or small batch. Fix the feeder, not the model.
  • BF16 vs FP16 for training?BF16 has FP32's exponent range → no loss scaling, more stable. FP16 needs loss scaling to avoid underflow. On Ampere+ default to BF16.
  • What does FlashAttention actually optimize?It's IO-aware: tiles the computation in SRAM and never writes the N×N score matrix to HBM. Removes the memory bottleneck of attention → faster + far less memory → longer context.
  • How do you fit a model that doesn't fit in VRAM?Gradient checkpointing, gradient accumulation, mixed precision, FSDP/ZeRO sharding, optimizer/activation offload to CPU/NVMe, quantization for inference.
  • Why do matmul dims being multiples of 8/16 matter?Tensor Cores need aligned tile shapes; odd dims fall back to slower paths or waste lanes. Pad vocab/hidden/batch.
  • What is CPU steal / throttling on a GPU box?GPUs throttle on power/thermal limits — nvidia-smi shows the clock-throttle reason. Distinct from being compute-bound; check clocks before optimizing code.
  • How do you hide multi-GPU communication?Overlap NCCL all-reduce with backward compute (DDP buckets do this), use NVLink, and ensure cross-node fabric is fast. Confirm in an nsys timeline that comms sits under compute.
