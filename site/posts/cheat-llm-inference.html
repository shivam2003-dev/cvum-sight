LLM Inference — The Serving Cheatsheet.

inference llm vllm serving
LLM inference is two different jobs. Prefill (process the prompt) is compute-bound and parallel. Decode (generate tokens one at a time) is memory-bandwidth-bound — every token re-reads all the weights and the KV cache. Almost all serving tricks exist to make decode less wasteful.

1. Prefill vs decode

PrefillDecode
WhatEncode the whole prompt, build KV cacheGenerate one token per step, autoregressively
Bound byCompute (big parallel matmul)Memory bandwidth (read weights + KV each step)
MetricTTFT (time to first token)TPOT / inter-token latency

Latency a user feels = TTFT + (tokens × TPOT). Throughput = tokens/sec across all concurrent requests. You optimize them separately.

2. The metrics that matter

  • TTFT — time to first token. Dominated by prompt length + queue wait.
  • TPOT / ITL — time per output token. Dominated by model size, batch, bandwidth.
  • Throughput — total tokens/sec; what you pay for. Trades off against latency.
  • Goodput — throughput of requests that met their SLO. The honest number.

3. The KV cache (the real constraint)

  • Every generated token attends to all previous tokens — so you cache their Key/Value tensors to avoid recomputing.
  • KV size ≈ 2 × layers × kv_heads × head_dim × seq_len × batch × dtype_bytes. It grows linearly with context and concurrency, and it competes with weights for VRAM.
  • At long context / high concurrency, KV cache, not weights, is what OOMs you.
PagedAttention is why vLLM wins Naive serving pre-allocates a contiguous KV block for max length → huge fragmentation and waste. PagedAttention pages the KV cache like virtual memory (fixed blocks, no contiguity needed) → far higher batch sizes and throughput from the same VRAM.

4. Continuous batching

  • Static batching waits for the whole batch to finish — short requests block behind long ones (head-of-line blocking).
  • Continuous (in-flight) batching — add/evict requests at the token level each step. A finished sequence frees its slot immediately for a queued one. Massive throughput gain at high concurrency.
  • This is the default in vLLM / TGI / TensorRT-LLM. It's the single biggest serving lever after the KV cache.

5. Quantization (smaller, faster)

MethodWhat
Weight-only INT8/INT4 (GPTQ, AWQ)Shrink weights → less VRAM + bandwidth. Decode is bandwidth-bound, so this speeds it up. Tiny quality hit.
W8A8 / SmoothQuantQuantize weights and activations → use INT8 Tensor Cores. More speed, more care.
FP8Hopper+/Blackwell native; good quality/speed balance for serving.
KV-cache quantStore KV in INT8/FP8 → more concurrent sequences / longer context per GB.

Rule of thumb: for decode-bound serving, weight-only 4-bit (AWQ/GPTQ) is the easiest large win — memory and bandwidth drop, quality mostly holds.

6. Faster decoding

  • Speculative decoding — a small draft model proposes K tokens, the big model verifies them in one pass. Accepted tokens come "free" → lower latency, same distribution.
  • Prefix caching — reuse KV for shared prompt prefixes (system prompts, few-shot). Big win for chat / RAG with repeated context.
  • Chunked prefill — split long prompts so prefill and decode interleave; keeps TTFT bounded under load.
  • Multi-LoRA serving — many adapters on one base model in memory (S-LoRA style).

7. Fitting big models across GPUs

  • Tensor parallel (TP) — split each layer's matmuls across GPUs. Low latency, needs fast interconnect (NVLink). Within a node.
  • Pipeline parallel (PP) — split layers into stages across GPUs/nodes. Higher throughput, adds pipeline latency.
  • Expert parallel — for MoE models, route experts across GPUs.
  • Pick TP for latency on a single node; add PP to cross nodes for very large models.

9. Tuning knobs & serving math

# vLLM — the levers you actually touch
--max-model-len 8192               # cap context = cap KV per request
--gpu-memory-utilization 0.90      # fraction of VRAM for weights+KV
--max-num-seqs 256                 # concurrency cap
--tensor-parallel-size 2           # split across 2 GPUs
--quantization awq                 # 4-bit weights
--enable-prefix-caching            # reuse shared prefixes
  • VRAM budget ≈ weights + KV-cache pool + activation overhead. If you raise concurrency or context, you need more KV pool → lower other two or OOM.
  • Bigger batch → more throughput but higher TPOT. Set max-num-seqs to the point where p99 latency still meets SLO.

10. Quick reference

Latency = TTFT + tokens × TPOT
Prefill = compute-bound (prompt) → batch/chunk it
Decode  = bandwidth-bound (per token) → quantize, speculate, cache
KV cache grows with context × concurrency → the usual OOM
Levers: continuous batching, PagedAttention, AWQ/GPTQ 4-bit,
        prefix caching, speculative decoding, TP/PP

11. Interview Q&A

  • Why is decode memory-bound but prefill compute-bound?Prefill processes many prompt tokens in parallel — a big GEMM (compute). Decode does one token at a time, re-reading all weights + KV per step with little math → bandwidth-bound.
  • What does the KV cache cost and why does it matter?Grows linearly with context length × batch × layers × kv-heads. At scale it dominates VRAM and is usually what OOMs you, not the weights. It's the reason for PagedAttention and KV quant.
  • What is continuous batching?Schedule requests at the token level — add new ones and evict finished ones every step instead of waiting for a whole static batch. Removes head-of-line blocking, big throughput win.
  • How does speculative decoding keep the output correct?A small draft model proposes K tokens; the target model verifies them in one forward pass and accepts the longest matching prefix. The accepted tokens follow the target's exact distribution, so quality is unchanged.
  • Which quantization for a latency-sensitive decode workload?Weight-only 4-bit (AWQ/GPTQ): decode is bandwidth-bound, so shrinking weights directly cuts per-token time with minimal quality loss. Add KV-cache quant for long context.
  • TTFT is fine but throughput is low — what do you check?Batching strategy (static vs continuous), max-num-seqs, KV pool size limiting concurrency, and whether you're GPU-bound or queueing. Raise concurrency until p99 latency hits the SLO.
  • Tensor parallel vs pipeline parallel?TP splits each layer across GPUs (low latency, needs NVLink, single node). PP splits layers into stages (higher throughput, pipeline latency, crosses nodes). Combine for very large models.
  • How do you serve many fine-tunes cheaply?Multi-LoRA: keep one base model in VRAM and swap small LoRA adapters per request (S-LoRA). Avoids loading a full model per fine-tune.
  • What is prefix caching good for?Reusing KV for shared prompt prefixes — system prompts, few-shot examples, RAG context. Cuts prefill cost and TTFT for repeated heads.
