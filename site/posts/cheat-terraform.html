Terraform — The Interview Cheatsheet.

terraform iac devops interview-prep
Terraform is declarative IaC: you write desired state in HCL, it diffs against state (a JSON record of what it manages) and makes real infra match. The loop is init → plan → apply. Everything hard is about state.

Core concepts

TermWhat
ProviderPlugin for a platform (aws, google, kubernetes). Exposes resources.
ResourceA managed infra object (aws_instance).
Data sourceRead-only lookup of existing infra.
StateJSON mapping config → real resources. Source of truth for Terraform.
ModuleReusable group of resources (a folder of .tf).
BackendWhere state lives (local, S3+DynamoDB lock, TF Cloud).

Workflow

terraform init        # download providers, configure backend
terraform fmt         # format ; terraform validate  # check syntax
terraform plan        # preview diff (read this every time)
terraform apply       # make it so
terraform destroy     # tear down
terraform apply -target=aws_instance.web   # narrow (use sparingly)

HCL essentials

variable "region" { type = string  default = "us-east-1" }
locals { name = "app-${var.env}" }
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  tags = { Name = local.name }
}
output "ip" { value = aws_instance.web.public_ip }
data "aws_ami" "ubuntu" { most_recent = true  owners = ["099720109477"] }

Variable precedence: CLI -var > *.auto.tfvars > terraform.tfvars > env TF_VAR_* > default.

Meta-arguments

ArgUse
countN copies by index. Good for identical resources.
for_eachOne per map/set key — stable addresses, preferred over count.
depends_onExplicit ordering when there's no implicit reference.
lifecyclecreate_before_destroy, prevent_destroy, ignore_changes.
count vs for_each count keys by index — remove the middle item and everything after it shifts and gets recreated. for_each keys by name — stable. Prefer for_each for sets.

State management

terraform state list           # what's managed
terraform state show <addr>
terraform import <addr> <id>    # adopt existing resource
terraform state mv A B         # rename without recreate
terraform state rm <addr>       # stop managing (doesn't delete real infra)
terraform force-unlock <id>     # stuck lock (carefully)
remote state + locking Local state breaks teams. Use a remote backend (S3 + DynamoDB lock, or TF Cloud) so concurrent applies don't corrupt state.

Modules

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"
  cidr    = "10.0.0.0/16"
}
# reference outputs: module.vpc.vpc_id

Best practices

  • Remote, locked, versioned state backend.
  • Pin provider + module versions.
  • Never commit secrets/state to git; never hand-edit state.
  • plan in CI, gated apply; separate state per environment.
  • Prefer data sources + for_each over copy-paste; avoid provisioners (last resort).

Rapid-fire Q&A

  • What is state and why does it matter?JSON mapping config to real resources. It's how Terraform knows what exists, computes diffs, and avoids recreating things. Lose/corrupt it and TF loses track of your infra.
  • count vs for_each?count = index-keyed (shifts on removal); for_each = key-keyed (stable). Prefer for_each.
  • plan vs apply?plan previews the diff; apply executes it. Always read plan first.
  • How to manage existing infra?terraform import (or import blocks) to bring it under state.
  • How do teams share state safely?Remote backend with locking (S3+DynamoDB / TF Cloud) so applies serialize.
  • local vs variable vs output?local = computed value reused in config; variable = input; output = exposed value (and module return).
