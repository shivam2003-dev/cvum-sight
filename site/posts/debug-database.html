Debugging Database Issues — Queries, Pools, Deadlocks.

database sre postgres performance
Most "DB is slow" tickets: a query missing an index, the pool exhausted, lock/deadlock contention, or replication lag serving stale reads. Find the slow query, read its plan, check pool + locks. Examples lean Postgres; the shape is universal.

Slow queries

SELECT pid, now()-query_start AS dur, state, query
FROM pg_stat_activity WHERE state!='idle' ORDER BY dur DESC;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;     -- Seq Scan on big table = missing index

Fix. Add the index the plan wants; rewrite sargable; avoid SELECT *; use pg_stat_statements to rank worst queries.

EXPLAIN ANALYZE is the answer Don't guess — run EXPLAIN (ANALYZE, BUFFERS). Bad row estimates → run ANALYZE.

Connection pool exhaustion

SELECT count(*), state FROM pg_stat_activity GROUP BY state;
SHOW max_connections;

App instances × pool size > max_connections; leaked connections; long transactions. Fix: pooler (PgBouncer); size pools; release connections (try/finally); kill idle-in-transaction.

Locks & deadlocks

SELECT blocked.pid, blocking.pid, blocked.query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));

Fix. Short transactions; acquire locks in the same order; add indexes to narrow lock scope; retry on deadlock (transient).

Replication lag / stale reads

SELECT now() - pg_last_xact_replay_timestamp() AS lag;

Fix. Route read-after-write to primary; fix replica resource/network limits.

Quick reference

SELECT * FROM pg_stat_activity ORDER BY query_start;
EXPLAIN (ANALYZE, BUFFERS) <query>;
SELECT * FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
