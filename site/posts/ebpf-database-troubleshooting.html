eBPF Observability for Real-Time, Kernel-Level Database Troubleshooting.

devops ebpf observability bpftrace postgres linux

TL;DR — When a database is slow, the cause usually hides below the application: disk I/O, the network stack, the CPU run queue, or the scheduler. eBPF lets you ask the kernel exactly what's happening — with nanosecond precision and near-zero overhead — without patching the kernel or restarting the DB. This guide walks five tools (biolatency, fileslower, tcpretrans, runqlat, profile), the exact commands, real output from a live PostgreSQL + OpenTelemetry box, and how to read each result. The verdict of a healthy run: every layer green.

Why eBPF for database troubleshooting

Your dashboards say the database is slow. The query planner looks fine. CPU sits at 30%. So where is the time going? Traditional tools (top, iostat, vmstat) give you averages over seconds — they tell you that something is slow, never why. The "why" lives in the kernel: a block I/O that took 80 ms, a TCP retransmit on the replication socket, a thread stuck 2 ms in the run queue.

eBPF (extended Berkeley Packet Filter) runs small sandboxed programs inside the Linux kernel — no kernel rebuild, no modules, no DB restart. You attach a probe to a kernel function, the probe fires on every event, and you get histograms and per-event traces at nanosecond resolution with overhead low enough for production.

Environment for this guide: Ubuntu 24.04 · bpfcc-tools 0.29.1 · bpftrace 0.20.2. Target server 10.100.43.121 running PostgreSQL + an OpenTelemetry collector. Traced June 3, 2026.

Installation & prerequisites

Ubuntu / Debian:

# BCC tools (biolatency, runqlat, profile, ...)
sudo apt update
sudo apt install -y bpfcc-tools python3-bpfcc
# bpftrace (tcpretrans.bt, runqlat.bt, ...)
sudo apt install -y bpftrace
# verify
biolatency-bpfcc --version
bpftrace --version

RHEL / CentOS / Amazon Linux:

sudo dnf install -y bcc-tools bpftrace
# tools land in /usr/share/bcc/tools/ — add to PATH:
export PATH=$PATH:/usr/share/bcc/tools

Verify kernel support:

uname -r                       # need 4.9+ for BCC, 4.17+ for bpftrace
ls /sys/kernel/debug/tracing    # debugfs must be mounted
On Ubuntu 24.04 the BCC tools install with a -bpfcc suffix (biolatency-bpfcc, runqlat-bpfcc). On other distros they may be plain biolatency, runqlat. Adjust the command names to match.

01 · Disk I/O latency — biolatency

What it does: traces every block-device I/O request and builds a latency histogram in microseconds. The single fastest way to tell whether storage is your bottleneck. Slow WAL, slow checkpoints, slow reads of cold pages — all show up here as long tails.

# 5 intervals of 1 second each
sudo biolatency-bpfcc 1 5
# or bpftrace (no -bpfcc suffix needed)
sudo bpftrace /usr/sbin/biolatency.bt

Healthy threshold: all I/O under 1 ms (1000 µs) is excellent NVMe/SSD territory. Consistent hits at 100 ms+ mean a storage problem.

Actual output from our server:

Tracing block device I/O... Hit Ctrl-C to end.
     usecs               : count     distribution
         0 -> 1          : 0        |                                        |
        ...
       128 -> 255        : 0        |                                        |
       256 -> 511        : 9        |****************************************|
       512 -> 1023       : 2        |********                                |

Read it: all I/O clustered in 256–1023 µs (0.25–1 ms). Zero operations crossed 1 ms. Bars are short — few operations total, so the disk is idle most of the time.

✅ Verdict: storage healthy — NVMe/SSD-class latency.

02 · Slow file operations — fileslower

What it does: surfaces individual file read/write operations slower than a threshold (default 10 ms). This is the one that catches slow WAL writes, journal flushes, and fsync stalls — the events that block a commit but never show up in query stats.

# BCC version (may fail on newer kernels with kprobe attach errors)
sudo timeout 15 fileslower-bpfcc 10

# bpftrace inline version (works on all kernels)
sudo timeout 15 bpftrace -e '
kprobe:vfs_read  { @s[tid]=nsecs; @c[tid]=comm; }
kretprobe:vfs_read /@s[tid]/ {
  $l=(nsecs-@s[tid])/1000000;
  if($l>10){ printf("PID:%-6d COMM:%-20s OP:READ   LAT:%d ms\n",pid,@c[tid],$l); }
  delete(@s[tid]); delete(@c[tid]);
}
kprobe:vfs_write { @s[tid]=nsecs; @c[tid]=comm; }
kretprobe:vfs_write /@s[tid]/ {
  $l=(nsecs-@s[tid])/1000000;
  if($l>10){ printf("PID:%-6d COMM:%-20s OP:WRITE  LAT:%d ms\n",pid,@c[tid],$l); }
  delete(@s[tid]); delete(@c[tid]);
}'

What to look for: database processes (postgres, mysqld, mongod) doing slow writes = WAL/fsync bottleneck. java/python with frequent slow reads = app reading large config or log files.

Actual output: zero file operations exceeded 10 ms across the entire 15-second window. Only active processes were otelcol-contrib (lightweight reads) plus the tracing tools themselves. postgres had no slow file ops.

kernel gotchaOn kernels 5.15+ the BCC fileslower-bpfcc can fail with cannot attach kprobe because the compiler inlined the target function. The bpftrace inline version above is functionally identical and always works.

✅ Verdict: no slow file operations — filesystem responding instantly.

03 · TCP retransmissions — tcpretrans

What it does: hooks the kernel TCP stack and prints every retransmitted packet with source, destination, port, and TCP state. The go-to for diagnosing replication lag, connection drops, and app-to-database timeouts that look like "random" slowness.

# bpftrace version (recommended)
sudo timeout 30 bpftrace /usr/sbin/tcpretrans.bt
# BCC version
sudo timeout 30 tcpretrans-bpfcc

TCP states to watch:

StateMeaning
ESTABLISHEDactive connection dropping packets — serious
SYN_SENTcan't even connect — firewall or server down
CLOSE_WAITconnection teardown issues

Actual output: zero TCP retransmissions in the trace window. Every connection (SSH, database, telemetry) delivered packets on first attempt. Clean RTT, no packet loss between this node and its peers.

For production monitoring: run for 60–120 seconds during peak load. Even 1–2 retransmissions/minute on a database replication port warrants investigation — that's where silent lag is born.

✅ Verdict: network healthy — no retransmissions.

04 · Run-queue / scheduling latency — runqlat

What it does: measures how long threads wait in the CPU run queue before getting scheduled. This is the metric that reveals CPU saturation and noisy-neighbour effects on shared infrastructure — the slowness that exists even when per-core utilization looks fine.

# BCC version — 5 intervals of 1 second
sudo runqlat-bpfcc 1 5
# bpftrace version
sudo timeout 15 bpftrace /usr/sbin/runqlat.bt

Read the histogram:

  • 0–7 µs dominant → CPU almost always free when a thread wants to run ✅
  • 100–1000 µs dominant → CPU moderately loaded, some waiting
  • 1000 µs+ present → CPU saturation, threads waiting 1 ms+ to run ❌

Actual output (3 of 5 intervals):

     usecs               : count     distribution
         0 -> 1          : 126      |******************************          |
         2 -> 3          : 166      |****************************************|
         4 -> 7          : 18       |****                                    |
         8 -> 15         : 6        |*                                       |
        16 -> 31         : 1        |                                        |
        32 -> 63         : 1        |                                        |
     ... (interval 3 spike) ...
         0 -> 1          : 1082     |****************************************|
         2 -> 3          : 500      |******************                      |
         4 -> 7          : 31       |*                                       |

Read it: the overwhelming majority of scheduling delays sit at 0–3 µs (sub-microsecond to 3 µs). One outlier at 32–63 µs — negligible. The interval-3 spike to 1082 at 0–1 µs is a brief burst of many short-lived threads all scheduling instantly — likely the OTel collector scraping metrics.

✅ Verdict: no CPU saturation — scheduling is instant, no noisy neighbours.

05 · CPU flame profile — profile

What it does: samples the kernel + user stack of every running thread at a fixed frequency (99 Hz, deliberately off 100 Hz to avoid lock-step with kernel timers). Aggregated stacks show exactly where CPU time goes. Feed the folded output into a flame-graph generator for a visual.

# profile a specific PID at 99 Hz for 30s
sudo profile-bpfcc -F 99 -p <PID> 30

# system-wide, bpftrace version
sudo timeout 15 bpftrace -e '
  profile:hz:99 { @[comm, kstack] = count(); }
  END { print(@); clear(@); }'

# find the busiest PID first
ps -eo pid,pcpu,comm --sort=-pcpu | head -5

Flame graph (optional):

git clone https://github.com/brendangregg/FlameGraph
cd FlameGraph
sudo profile-bpfcc -F 99 -f 30 > out.stacks
./flamegraph.pl out.stacks > cpu_flame.svg

Kernel compatibility notes

On Ubuntu 24.04 with kernel 6.8+, some BCC tools fail with cannot attach kprobe because certain kernel functions were inlined by the compiler. The fallback is always the bpftrace .bt script versions:

# if biolatency-bpfcc fails:
sudo bpftrace /usr/sbin/biolatency.bt
# if fileslower-bpfcc fails: use the inline bpftrace script from section 02
# if tcpretrans-bpfcc fails:
sudo bpftrace /usr/sbin/tcpretrans.bt
# if runqlat-bpfcc fails:
sudo bpftrace /usr/sbin/runqlat.bt

Compiler warnings like warning: multiple identical address spaces specified are harmless — they come from the BCC JIT compiler processing kernel headers and don't affect output accuracy.

Takeaways

  • Trace below the app. When the DB is slow and the query plan is fine, the answer is in the kernel — eBPF is how you read it live.
  • One tool per dimension. biolatency = storage, fileslower = file/fsync, tcpretrans = network, runqlat = scheduling, profile = CPU. Run all five, get a full health picture in minutes.
  • bpftrace is the safety net. When BCC can't attach a kprobe on a newer kernel, the .bt equivalents always work.
  • Near-zero overhead. Safe to run on production — no restart, no module, no kernel patch.
