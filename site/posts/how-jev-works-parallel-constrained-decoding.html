How Jev Actually Works — Parallel Constrained Decoding, Reverse-Engineered.

ml inference structured-output open-source

TL;DR — My earlier piece on Jev flagged one big gap: TypeSafe never disclosed the architecture, only the input/output shape and the headline numbers. Since then, three independent, verifiable sources have filled most of that gap without any cooperation from TypeSafe. Niels Rogge published a step-by-step trace of the decode mechanism. Harsha Gundala open-sourced a working reproduction — Qwen2.5-1B-RLCD — under the name Parallel Constrained Decoding, with a public benchmark table. And Bespoke Labs shipped Nimble, a full open recipe (data, training, serving code) for a Jev-shaped model, benchmarked directly against Jev 1.13.0. None of this is an official TypeSafe disclosure — treat it as a well-evidenced reconstruction, not a confirmed spec — but it's specific enough to actually explain why Jev's numbers look the way they do.

The three sources this reconstruction is built from

The original Jev launch post described what the model takes in and what it returns, and it gave real cost and latency figures, but it explicitly withheld the model architecture — "details remain proprietary." That's a reasonable thing for a vendor to do at launch, and it's also exactly the kind of gap that a fast-moving open-source ML community doesn't leave alone for long. In the two weeks since launch, three people independently converged on the same underlying mechanism from three different angles:

Stacked together, these three sources cover the two things the original launch post left open: the inference mechanism (Rogge and Gundala) and the training approach (Bespoke Labs), plus — as a bonus — a credible intellectual lineage stretching back two years to a 2024 fact-checking paper that TypeSafe itself credits as foundational. This piece works through all of it in order.

Step by step: what actually happens inside a Jev call

Niels Rogge's explainer is built specifically around the Qwen2.5-RLCD model Harsha Gundala released, which he states directly is the basis for his explanation of how Jev works. The mechanism he traces has five steps, and the key idea running through all of them is this: replace token-by-token generation with one prefill pass plus one short, parallelizable forward pass per output field.

  1. Single prefill. The context (whatever text or state you're judging) and the JSON schema (the questions you've predefined) are run through the transformer decoder exactly once. The keys and values produced at every layer, for every token, are cached — this is the same KV-cache mechanism every modern LLM serving stack already uses, just stopped after one pass instead of continued token-by-token.
  2. Per-field forward pass, reusing the cache. For each field in the schema, only that field's suffix tokens (essentially, "now answer this question") are passed through the decoder again — but reusing the KV cache from step 1, so the expensive part (processing the full context) is never repeated. This is the step that makes multi-field scoring cheap: a 28-field schema doesn't mean 28 full passes over the context, it means one full pass plus 28 short passes over a few suffix tokens each.
  3. Final hidden state through the LM head. The last hidden state produced by that short forward pass goes through the model's standard language-modeling head — the same output layer any LLM uses to predict the next token — producing a score (a logit) for every token in the model's entire vocabulary.
  4. Mask to only the allowed tokens. Instead of looking at all ~150,000 vocabulary logits, the scorer looks only at the handful of tokens that correspond to valid answers for this specific field — for a boolean field, that might be just the tokens for "true" and "false"; for a category field, one token per allowed category. Those logits go through a softmax, turning raw scores into a probability distribution that sums to 1 across only the allowed answers.
  5. Take the highest-probability token. The typed answer is whichever allowed option got the highest probability, and the full probability distribution across every allowed option is returned alongside it — which is exactly the "typed answer plus a probability per option" shape both the original Jev launch post and Nimble's README describe.

Fig. 1 — Reconstructed from Niels Rogge's decode trace and Nimble's ParallelScorer implementation. One expensive pass over the context, then one cheap pass per field, all reusing the same cache — instead of one token-by-token pass per generated character of a JSON blob.

Compare this to what a standard LLM does when you ask it to "return JSON matching this schema": it generates the entire output autoregressively, token by token — {, then a newline, then ", then i, s, _, a… — with a full forward pass through the model for every single token, and no guarantee the result parses as valid JSON at the end. The mechanism above sidesteps that completely for a specific, narrower class of problem: when every output is a choice from a small, pre-declared set of options rather than open-ended text, you don't need to generate anything — you only need to score the handful of tokens that could possibly be the answer, and you can score every field's candidates in one short pass rather than accumulating them one token at a time.

The open proof of concept: Qwen2.5-1B-RLCD and "Parallel Constrained Decoding"

Harsha Gundala's release is the part of this story that turns the mechanism above from a plausible theory into something you can actually run and time yourself. The model card frames it directly: "every LLM has the ability to efficiently batch inference every key of a JSON at the same time and generate probabilities from a set of possible categories. No new training required, but it's easy to optimize if you need!" That "no new training required" line is worth sitting with — it means the core speedup doesn't come from a specially-trained model at all, it comes from a different way of using a stock instruction-tuned model's existing weights. Training on top (RLCD or otherwise) is an optional accuracy/calibration improvement layered onto a mechanism that already works on an off-the-shelf model.

The technique is named Parallel Constrained Decoding, and the model card describes it with the same shape as Rogge's trace, in more implementation-level terms: a single broadcast prefill of the context and schema into an MLX key-value cache, then that cache is broadcast across every schema field in parallel, and for each field only the candidate token IDs that belong to that field's valid answer set are looked at — a step the card calls sub-vocabulary logit slicing. The problem statement it's solving is stated plainly too: standard autoregressive structured generation needs somewhere between 150 and 500 sequential forward passes for a typical schema, each one a full round-trip through the accelerator, and total latency scales linearly with output length — T = Σ t_step(k) for k = 1…K generated tokens. Parallel Constrained Decoding collapses that sum into one broadcast prefill plus M small, independent, parallelizable field evaluations.

Scenario (Apple Silicon M4 Max, Qwen2.5-1.5B-Instruct-4bit)FieldsAutoregressive baselineParallel ConstrainedSpeedup
Fintech fraud routing4420 ms (120 tok/s)75 ms5.6×

High-cardinality tariff classification1 field, 255 choices500 ms (118 tok/s)89 ms5.6×
Enterprise support triage281,900 ms (130 tok/s)270 ms7.0×

Every scenario in that table also reports 100% schema validity, guaranteed — not "usually valid JSON," but structurally guaranteed, for the same reason described in the original Jev piece: a model that can only select from a pre-declared set of tokens per field cannot emit a malformed key, an invalid enum value, or broken JSON syntax, because those aren't in its output space to begin with. Note too that the 28-field enterprise-triage scenario shows the largest speedup (7.0× vs 5.6× for smaller schemas) — which is exactly what you'd expect from an architecture whose expensive part (the context prefill) is paid once regardless of field count, while the autoregressive baseline's cost keeps growing linearly with every additional field it has to generate tokens for.

Why this explains Jev's specific numbers

The earlier piece on this site flagged a specific bm-note: "What's not disclosed: TypeSafe's launch post explicitly withholds the model architecture itself… none of it has been independently verified." The mechanism reconstructed above doesn't officially close that gap — TypeSafe hasn't confirmed any of it — but it does make several of Jev's headline numbers stop looking like marketing claims and start looking like straightforward consequences of a specific, describable architecture:

Jev claimHow the reconstructed mechanism explains it
70–500 ms latencyOne context prefill (the expensive, unavoidable part) plus short, parallel per-field passes — not hundreds of sequential token-by-token forward passes.
Free output tokens / $0.042 per MTok input onlyThere's no generation step to meter output tokens for — the "output" is a softmax over a handful of cached logits, not a stream of newly generated tokens.
"Cannot produce malformed JSON" / structural 0% type-error rateThe output space is a closed set of pre-declared allowed tokens per field; "malformed" isn't a category the scorer can select from, matching Nimble's own "there is no generated JSON to parse" description.
Latency roughly flat across schema size (relative to a naive baseline)Field count adds cheap parallel short-passes on top of one fixed prefill cost, not additional sequential generation — matching the M4 Max benchmark table's growing speedup as field count rises.
What this still doesn't confirm: the reconstructed mechanism explains the shape of Jev's numbers well, but Jev's actual model size, base architecture, and serving infrastructure remain undisclosed by TypeSafe. Gundala's and Bespoke Labs' work independently arrived at the same general mechanism and it fits the evidence unusually well — but "a plausible, evidence-consistent reconstruction from independent open replications" is a different epistemic status than "TypeSafe confirmed this is what Jev does." Treat everything in this section as strong circumstantial evidence, not an official spec.

Nimble: Bespoke Labs' full open reproduction of "an open Jev"

Where Gundala's release demonstrates the inference mechanism, Nimble — released by Bespoke Labs on GitHub — goes a step further and open-sources the entire stack: training data curation, the training recipe, and production-grade serving code for both Apple Silicon and NVIDIA GPUs. The README states its purpose without hedging: "Data, Model, Recipe for an open Jev," and is explicit that it's inspiration, not extraction — "Note that we did not distill from Jev. The point of the repository is to show how to curate data, how to train, and to serve such a model, and encourage more research!" The base model is Qwen3.5-9B, fine-tuned with LoRA on a deliberately small, carefully curated dataset — 2,676 training examples and 324 held-out examples, spanning ten domains including commerce, education, and media.

The serving code matches the reconstructed mechanism exactly

Nimble's own description of how it scores a field lines up almost line-for-line with Rogge's trace and Gundala's card: "Each allowed answer has a code that is one token long. The scorer reads the model's logits for these codes… The scorer turns the logits into probabilities with the softmax function. Our Python code then builds the output from these probabilities, so there is no generated JSON to parse." On Apple Silicon specifically, Nimble's ParallelScorer "processes the shared context once and then scores all the fields in parallel" — the same single-prefill-then-broadcast pattern as Parallel Constrained Decoding, implemented independently by a different team. One useful implementation detail Nimble's docs make explicit that the other two sources don't: fields are scored independently of each other and cannot see one another's answers — there's no cross-field conditioning within a single call, which is a real constraint worth knowing if you need one field's answer to logically depend on another's (your application code has to enforce that consistency itself).

How close does an open, one-day build get to Jev itself?

ModelHeld-out accuracy (324 examples)
Qwen3.5-9B (base model, no fine-tuning)66.36%
Bespoke-Nimble-9B (fine-tuned)90.12%
Jev 1.13.093.21%

Three things worth noting in that table. First, fine-tuning on just 2,676 curated examples took a 9B open model from 66.36% to 90.12% — a 23.76-point jump, which says most of "being good at this task" comes from the training data and objective, not from parameter count or a proprietary architecture. Second, Jev still wins by 3.09 points on Bespoke Labs' own held-out set, which is a reasonable, not-embarrassing gap for a same-domain evaluation against a one-day open build. Third — and this is the fairer test — Bespoke Labs also published a public benchmark suite (credited to contributor Edgar Dyck) that runs both Nimble and Jev against 13 public, human-labeled subsets neither model was tuned on, specifically so the comparison isn't graded on Nimble's own home turf; the guide and results live in the repository's public-benchmarks documentation, linked below, for anyone who wants the out-of-domain picture rather than just the in-domain one.

The naming isn't an accident. Gundala names his model Qwen2.5-1B-RLCD — the same acronym TypeSafe uses for Jev's training objective (Reinforcement Learning for Calibrated Decisions). Read alongside his "no new training required" framing, the naming choice reads as a pointed technical claim: the RLCD-style training TypeSafe describes is a calibration/accuracy layer on top of a mechanism that works, at least at a basic level, on a stock instruction-tuned model with no RLCD training at all. That's consistent with Bespoke Labs' own numbers above — the base model already gets 66.36% with zero fine-tuning, before any calibration training is added.

Contrastive data curation: how Nimble teaches discrimination, not just format

The inference mechanism explains why this architecture is fast; it says nothing about why the resulting model would be accurate. That's a training problem, and it's the one part of this whole picture where Bespoke Labs publishes an actual, specific methodology rather than a withheld "proprietary" label. Nimble's training data is built through what the README calls contrastive data curation: "We write two examples that are almost the same. They differ in one relevant fact, and this difference changes the correct answer."

Concretely, the pipeline runs four checks before a training pair is accepted: verify that the decision rule genuinely can produce two different answers depending on the fact in question (so you're not manufacturing a distinction without a difference), build the evidence pair with a controlled, minimal edit between the two versions, validate both resulting examples independently through separate model calls, and only generate the final training label once every check passes. The reasoning behind this is a specific, well-known failure mode in classifier training: a model trained on ordinary, unpaired examples can learn to key off surface features that happen to correlate with the label in the training set — sentence length, specific phrasing, topic — without ever learning to actually locate and weigh the one fact that determines the correct answer. A contrastive pair, where everything is held constant except the one fact that flips the label, removes that shortcut: the only way to get both halves of the pair right is to actually find and use the deciding fact, because any other feature the model might have leaned on is identical in both examples.

This is a materially different and more specific claim than TypeSafe's own RLCD description, and it's useful for exactly that reason — the earlier piece on this site flagged, as the single most important open technical question in the whole Jev launch, that TypeSafe never published its calibration training methodology or where its ground-truth labels come from. Nimble's contrastive curation doesn't answer that question for Jev specifically, but it's a fully disclosed, independently reproducible answer to the more general question of "how would you actually train a model like this to be good," and Bespoke Labs' own accuracy jump (66.36% → 90.12%) is a real data point that this specific approach works, not just a plausible-sounding description.

The lineage: two years earlier than Jev, by TypeSafe's own account

The credits shared alongside Jev's launch material name Greg Durrett and Liyan Tang's work on MiniCheck specifically, describing it as work that "was two years early and laid the foundations" — and singles out Bespoke-MiniCheck, a follow-on model built jointly with Bespoke Labs, the same company behind Nimble. That's not a coincidence worth skipping past: the lineage from MiniCheck to Nimble runs through one continuous thread, with the same lab appearing at both ends.

The throughline across all three is the same core insight, applied to a widening scope: you don't need a frontier generative model's full sequential-decoding machinery to answer a narrow, well-defined question about a piece of text — a small model, trained on the right kind of contrastive or synthetically-adversarial data, can match a much larger model's accuracy on that narrow question at a small fraction of the cost. MiniCheck proved this specifically for "is this claim supported by this document." Nimble is the same bet generalized to arbitrary typed schemas — booleans, categories, and rating scales — which is a meaningfully broader claim, and one TypeSafe is implicitly making at much larger scale and, per the undisclosed-architecture caveat above, with resources and training data Nimble's one-day build simply doesn't have access to.

If you wanted to build one of these yourself

All three sources above converge on the same practical recipe, and it's worth spelling out as one, because it's genuinely buildable with tools that already exist rather than requiring anything proprietary:

  1. Pick a base model and confirm it exposes logits, not just sampled tokens. Any standard Hugging Face causal LM does this — you need access to the raw output of the LM head before sampling, which is standard in every mainstream inference library (transformers, MLX, vLLM, SGLang all expose this).
  2. Define your schema as flat fields with a fixed, single-token answer set per field. Nimble's constraint — no nested JSON, each allowed answer maps to exactly one token — isn't an arbitrary limitation, it's what makes the "mask to allowed tokens, then softmax" step work cleanly. A multi-token answer breaks the one-shot scoring trick, because you'd need to score a sequence, not a single position.
  3. Prefill once, cache the KV state, then run one short forward pass per field. This is the part every inference library already supports via its KV-cache API — you're not implementing new low-level infrastructure, you're just calling the existing cache-reuse path once per field instead of once per generated token.
  4. Slice the logits to your field's allowed token IDs, softmax, and take the argmax — a handful of lines of tensor indexing, not a new model component.
  5. If accuracy on your specific domain matters, fine-tune with contrastive pairs rather than ordinary labeled examples — Nimble's four-step curation pipeline (verify the rule can flip the answer, build a controlled minimal-edit pair, validate both halves independently, only then generate the label) is fully described in its docs and is the one part of this recipe that takes real curation effort rather than engineering effort.

What you'd end up with, following exactly this recipe, is functionally Nimble — which is exactly why Nimble is worth treating as more than a curiosity: it's a complete, working reference implementation of the recipe above, not just a description of it. If you're building a routing, moderation, or scoring function inside a larger agent or pipeline and currently paying full LLM latency and price for what's really a bounded, structured decision, this is the concrete starting point — clone the repo, point it at your own schema, and measure whether the accuracy on your domain clears whatever bar the frontier-LLM alternative currently sets, before deciding whether it's worth curating your own contrastive training set on top.

Frequently asked questions

Is Nimble literally the same model as Jev?

No, and Bespoke Labs is explicit about this: "we did not distill from Jev." Nimble is an independent reproduction of the same general approach — fast typed decisions via cached-context scoring — trained on its own curated data on top of a different base model (Qwen3.5-9B). It gets close to Jev's accuracy on Bespoke Labs' own held-out set (90.12% vs 93.21%) but that's evidence the approach generalizes, not evidence the two models share weights or training data.

Does this mean TypeSafe's RLCD is basically the same as Nimble's contrastive data curation?

They're solving related but not identical problems, and TypeSafe hasn't confirmed RLCD's actual mechanics, so this is necessarily speculative. TypeSafe frames RLCD as targeting calibration specifically — making a stated 90% confidence actually correct about 90% of the time. Nimble's contrastive curation targets discrimination — making sure the model actually keys off the deciding fact rather than a surface shortcut. Good calibration usually requires good discrimination as a prerequisite (you can't be well-calibrated about a decision you can't actually make correctly), so the two are complementary rather than the same technique, but without TypeSafe publishing RLCD's actual loss function this can't be confirmed either way.

Can I run this kind of model myself today?

Yes — that's the entire point of both open releases. Harsha Gundala's Qwen2.5-1B-RLCD is runnable via MLX on Apple Silicon with a few lines of Python, no fine-tuning required. Nimble is a full clone-and-run repository with quickstart instructions for both Apple Silicon and NVIDIA GPUs, plus the training data and recipe if you want to fine-tune your own domain-specific version. Links for both are in the references below.

Why does field count change the speedup so much (5.6× vs 7.0×) in Gundala's benchmark?

The prefill cost (processing the context once) is fixed regardless of how many fields you're scoring, while the autoregressive baseline's cost grows roughly linearly with total output tokens, which itself grows with field count. So as schema size increases, the fixed cost gets amortized over more fields in the parallel approach, while the sequential baseline keeps paying its per-token cost for every additional field — which is exactly why the 28-field enterprise-triage scenario shows the largest gap (7.0×) of the four benchmarked scenarios.

Takeaways

  • The core mechanism is now well-reconstructed from independent sources, even without TypeSafe's confirmation: one prefill of context + schema, then one short forward pass per field reusing that cache, masked to each field's allowed tokens, softmaxed into a probability distribution — no token-by-token generation at all.
  • This mechanism works on a stock model with no special training — Gundala's release explicitly needed none — which means TypeSafe's proprietary RLCD training is best understood as a calibration/accuracy layer on top of a mechanism that isn't itself the proprietary part.
  • Nimble is the most complete open evidence available: a fully disclosed training methodology (contrastive data curation), a fully disclosed serving implementation, and a direct, if in-domain, accuracy comparison against Jev 1.13.0 (90.12% vs 93.21%).
  • The lineage is real and vendor-acknowledged: MiniCheck (2024) → Bespoke-MiniCheck-7B → Nimble is one continuous thread through the same lab, and TypeSafe's own credits name MiniCheck as foundational prior work.
  • What's still genuinely unconfirmed: Jev's actual base model, parameter count, and the precise RLCD training objective. Everything in this piece is a well-evidenced reconstruction from independent replications, not an official TypeSafe specification — read it accordingly.
