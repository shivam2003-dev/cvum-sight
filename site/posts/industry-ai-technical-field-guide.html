How Industry Is Using AI, a Technical Field Guide.

ml industry mcp recommendation

Summary: Companies rarely use AI as one thing. They use it as a stack of patterns: a gateway that lets agents call internal tools, a ranker that replaces hand-built features, a model that reads machine sensor data, a system that reads contracts, an optimizer that plans routes. This guide walks through the main patterns, the engineering each one needs, and the places where the public record is strong or weak.

Why a field guide and not a list of logos

Every month brings a new headline about a bank, a steelmaker, or a retailer that has "deployed AI". Most of those headlines say very little about how the thing works. A press release names a vendor and a budget. It does not say how requests are routed, how a model is evaluated, what breaks at three in the morning, or who owns the failure. If you are an engineer trying to learn from industry, the headline is the least useful part.

This guide takes a different route. It groups real deployments into patterns, and for each pattern it explains the engineering that makes the pattern work. Where a company has published technical detail, the guide uses it. Where the public record is thin, the guide says so. The aim is to give you a mental model you can apply to a case you have not seen yet.

Three sources anchor the discussion. The first is Uber's engineering blog, which describes an internal gateway for AI agents. The second is a Netflix research paper on an LLM-backed ranker, arXiv 2608.10257, which I checked directly. The third is a set of industry case studies that are useful for context but are mostly press material, and that this guide treats with care.

One naming note before we start. This series has already covered a different GenRec, a generative recommendation paper from JD.com with arXiv identifier 2604.14878. The name is shared by two papers from two companies. When you search for GenRec, check the identifier and the organization.

The shape of an enterprise AI stack

Picture an insurance company that wants AI in its claims process. It has a document store with decades of policies. It has a claims system with its own API. It has a fraud team with a rules engine, a call-center team with a ticketing tool, and a finance team with a reporting database. Each system has an owner, a security model, and a change process. An AI assistant that is useful to the claims adjuster has to reach into several of them, and it has to do so without breaking anyone's rules.

That picture explains most of enterprise AI engineering. The model is rarely the hard part. The hard parts are connection, control, cost, and evaluation. The connection problem is how a model reaches the systems it needs. The control problem is who may call what, and with which data. The cost problem is what each call costs at scale. The evaluation problem is how you know the system is right, when the answer depends on the state of several systems at once.

The rest of the guide follows that stack. It starts with the connection layer, which is where Uber's gateway lives, then moves through the ranking, sensing, document, optimization, and discovery patterns that sit on top.

Pattern one: a gateway for agent tools

Start with the connection problem. In 2024 and 2025, many companies gave their AI systems tools: functions that let a model look up an order, create a ticket, or query a database. Each team wrote its own integration. Each integration had its own schema, its own authentication, and its own idea of what counts as a safe call. Within a year a large company has hundreds of these integrations, and nobody has a complete list.

The Model Context Protocol, usually called MCP, was an attempt to standardize that connection. It defines how a client discovers the tools a server offers and how it calls them. Standardizing the protocol does not, by itself, solve a company's problem. A company still has to decide which servers exist, who owns them, which tools are exposed, and how calls are logged and limited.

Uber's engineering team wrote about its answer, an MCP Gateway. The post describes the problem in the same terms. Teams had built many independent MCP integrations, which fragmented discovery and ownership. The gateway is a centralized service built to standardize that layer. According to the post, it has two main components. The first is a control plane, an MCP registry that holds a catalog of more than 800 MCP servers and more than 5,000 tools, and that acts as the single source of truth for discovery and ownership. The second is a data plane, a proxy that handles runtime requests and translates between MCP and the protocols that existing services already speak, including HTTP, gRPC, and TChannel, without asking those services to change.

That split between control and data is the first lesson. The registry answers questions like what exists, who owns it, and whether it is enabled. The proxy answers the question of what happens when a call is made. Keeping them separate means you can change the discovery rules without touching the request path, and you can scale the request path without rebuilding the catalog.

Discovery that does not expose everything

The post describes a component it calls AutoCrawler. It discovers APIs from Uber's interface definition registry and from native MCP servers, and it generates tool definitions in a disabled state by default. Service teams must then review and enable the tools they own. This is a safety pattern that matters more than it looks. A crawler that enables everything it finds turns a large internal API surface into a set of tools that any agent can call. A crawler that generates definitions but leaves them off turns discovery into a review queue, which keeps the owners in control.

The same design shows up in other places. Platform teams that expose internal services to AI agents tend to converge on a rule: discovery is automatic, exposure is explicit. The cost is a manual step. The benefit is that no tool becomes callable by accident.

Context bloat, the quiet cost

Tool use has a cost that most demos hide. Every tool an agent knows about has a schema, and the schema takes tokens. If an agent is offered five thousand tools, loading all their schemas into the prompt wastes most of the context window before the user has said anything. The model also gets worse at picking the right tool when the list is huge.

Uber's post describes three responses to this problem. The first is Omni MCP, a proxy server that supports incremental tool discovery, so an agent finds tools as it needs them rather than all at once. The second is response projection, which borrows the idea of field selection from GraphQL. The caller asks for the fields it needs, and the gateway trims the rest before the response reaches the model. The third is what the post calls Code Mode, a command-line integration that lets an agent invoke tools without loading full schemas into its context.

All three ideas come from one principle. A model's context is a scarce resource, like memory on a GPU. Anything that does not need to be in the context should be kept out of it. The projection idea is especially useful beyond tools. Many systems return far more data than a model needs, and trimming responses at the gateway saves tokens and reduces the chance that irrelevant details confuse the answer.

Security as a property of the path

The post also describes built-in security. Policies enforce access control at the level of individual tools, and responses are redacted for personal information before they reach the model. Those are two different defenses. Tool-level access control decides who may call what. Response redaction decides what the model is allowed to see after a call succeeds. A system that only has the first defense can still leak personal data through a permitted call. A system that only has the second can still let an agent take actions it should not take.

Security in an agent system lives on the path between the model and the backend. Every call is a decision point, and the gateway is the natural place to make those decisions, because it sees every call. That is the argument for putting the defenses in the gateway rather than in each tool.

What the public record does not say: the post does not give latency figures, cost figures, or failure rates for the gateway, and it does not describe how policies are authored or tested. Those are the questions a team evaluating a gateway should ask its own vendor or its own platform team.

Pattern two: rankers that read like language models

Recommendation has been the largest commercial use of machine learning for more than a decade. Streaming services, shopping sites, and social feeds all rank items for each user, and the ranking models were built from thousands of hand-engineered features. A feature might count how many times a user watched a certain genre in the last seven days, or how long an item sat in a shopping cart. Each feature needed a pipeline, a backfill, and a monitor. The system worked, but adding a new business goal meant adding more features.

Large language models changed the question. A language model already understands text, and a user's history can be written as text: the titles they watched, the order, and the time between. If a model can read that history, it may need fewer hand-built features. The question becomes whether a language model can be trained to rank items for a user, and whether it can do so cheaply enough to serve.

Netflix's GenRec paper answers yes, with caveats. The paper is titled "GenRec: An LLM-Backed Recommendation Ranker at Netflix", by a team of Netflix researchers. Its problem statement is the one just described: traditional recommendation systems rely on thousands of hand-engineered features and specialized architectures, which makes it hard to support new business needs. The method has two phases. In the first, an open-source language model is adapted to Netflix data so that it understands users and content. In the second, the model is post-trained for recommendation. That second phase uses verbalized user histories, a scoring head that knows about the catalog, reward signals, and a serving approach the paper calls prefill-only inference.

The result, according to the paper's summary, is a statistically significant improvement over the production baseline in large-scale A/B testing, with roughly a 1.6 percent offline lift in mean reciprocal rank. The paper also says the improvement came with substantially fewer training examples and input signals than the baseline used. That combination is the claim that matters for an engineer: less hand-built input, comparable or better output.

Why prefill-only serving matters

A language model that ranks items has an unusual cost profile. A generator writes a long answer, one token at a time, and its cost grows with the answer. A ranker needs a score, not a sentence. If the model can produce a score from a single pass over the input history, the expensive decode loop disappears. The cost is then mostly prefill, the pass over the input, which is parallel across tokens and suits the GPU well.

That is the reason the paper's serving approach matters. Prefill-only inference turns a language model into something close to a classifier at serving time. The history goes in, a score comes out, and there is no long answer to generate. For a service that ranks millions of items for millions of users, that difference decides whether the model is affordable.

The technique has a limit. A prefill-only ranker cannot explain itself in free text, and it cannot be checked by reading an output sentence. Evaluation has to come from offline metrics, A/B tests, and the reward signals used in training. A team adopting this pattern should expect its evaluation work to be the hard part.

The cache that user histories create

User histories have a useful property for serving. A user's history changes slowly. Between one visit and the next, most of the history is the same, with a few new items at the end. A system that caches the prefill of the stable part of the history, and only computes the new tail, can serve repeated requests far more cheaply. This is the prefix caching idea from the earlier articles in this series, applied to recommendations rather than chat.

The design question is how to structure the prompt so that the stable part comes first. If a timestamp or a session identifier sits at the top, nothing before it is shared, and the cache never matches. Ordering the input so that the slow-changing content comes first is a small change with a large effect on cost.

Pattern three: machine sensors and predictive maintenance

Factories, steel mills, and power plants are full of machines that fail in predictable ways. A bearing wears, a motor overheats, a pump starts to cavitate. For decades, maintenance followed fixed schedules: replace this part every six months, whether it needs it or not. Predictive maintenance replaces the calendar with a signal. Sensors record vibration, temperature, and current. A model learns what normal looks like and flags deviations that precede failure.

The public record is full of this pattern. Siemens has described its Senseye predictive maintenance product and its industrial copilot, and it has published a case with a dairy company, Sachsenmilch, about applying predictive maintenance in food and beverage production. An academic study from the University of Twente describes applying data-driven models to predict bearing wear, with a steel company as the context. A steel-industry roundup lists several producers that have described AI-supported maintenance programs. I have not reviewed those pages in detail for this guide, so I describe the pattern rather than their numbers.

The engineering of predictive maintenance is less glamorous than its headlines. The hard problem is data. Sensors drift, they go offline, and they are installed on different machines in different ways. A model trained on one machine often fails on another of the same type, because the mounting, the load, and the environment differ. The practical work is in cleaning the data, aligning the time series, and labeling failures, which is often incomplete because machines are repaired before anyone records the cause.

A second problem is the cost of a false alarm. A model that flags too many false failures sends technicians to healthy machines, which costs labor and erodes trust. A model that misses a real failure costs far more, because the failure happens in production. The threshold is a business decision as much as a statistical one. A team should set it with the maintenance manager, not with a benchmark score.

Evaluating a model that predicts rare events

Failures are rare, which makes evaluation tricky. If a machine fails once a year and the model is checked daily, the positive cases are a tiny fraction of the data. Accuracy alone is misleading, because a model that never predicts failure is almost always right. The useful measures are precision and recall at the threshold the business chose, and the lead time between a flag and the failure. A flag that comes two days early is useful. A flag that comes two minutes early is not.

Pattern four: reading contracts and documents at scale

Banks, insurers, and law firms sit on large archives of documents. Loan agreements, policy wordings, and regulatory filings are long, dense, and full of clauses that matter for a small set of decisions. A human reviewer reads a few hundred pages a day. A system that can find the clauses that matter, and flag the ones that differ from a standard, saves time and reduces errors.

JPMorgan Chase is the most cited example. Public accounts describe its COiN contract intelligence system, which analyzes commercial loan agreements. A widely repeated figure says the system reduced hours spent on that review by a large amount each year, but I have not verified that figure in a primary source, so this guide does not rely on it. The pattern is the important part. The system reads the document, extracts the relevant fields, and gives a human a structured view to check.

The technical core is extraction with grounding. A good document system does not just answer a question. It points to the text that supports the answer, so a reviewer can check the source in one click. Without grounding, an answer that looks right can be wrong in a way that is expensive to find later.

Retrieval before reading

Most document systems use retrieval. A large archive cannot fit in one prompt, so the system first selects the passages that might answer the question, then passes only those to the model. The quality of the answer depends heavily on the retrieval step. If the right clause is not retrieved, the model cannot cite it, and it may invent a plausible but wrong answer from nearby text.

This is why document systems invest in chunking, indexing, and evaluation of retrieval separately from generation. A team should measure whether the right passage is in the top results for a set of real questions. That number is easier to improve and easier to trust than a final answer score.

Where a wrong answer costs the most

In legal and financial work, a wrong answer is not a shrug. A missed termination clause can cost a company its contract. A misread interest rate can change the value of a loan. The design response is to route high-stakes answers through human review, to keep the audit trail of which passage supported which answer, and to avoid letting the model make the decision itself. The model's job is to make the human faster and better informed, not to replace the signature.

Pattern five: optimization that plans routes

Not every industrial use of AI is a language model. Some of the largest savings come from classical optimization, sometimes combined with machine learning for prediction. Route planning is the classic case. A delivery company has to decide which driver goes where, in what order, with which constraints: time windows, vehicle capacity, traffic, and the rules about breaks.

UPS's ORION system is the widely cited example. Public write-ups describe it as an AI-assisted route optimizer, which considers many routing options and uses traffic and weather information. Press figures on fuel and cost savings circulate widely, and I have not verified them against a company source, so this guide does not repeat them. The lesson holds regardless of the numbers. Route planning at scale is a search problem with millions of possible plans, and a good heuristic found in seconds beats a perfect plan found after hours.

Predicting, then planning

Modern route systems often combine two stages. A model predicts the quantities the planner needs: how long a stop will take, how busy a road will be at a given hour, how likely a delivery is to fail. The planner then uses those predictions to build routes. The two stages should be evaluated separately. A better predictor does not always produce a better plan, because the planner may be sensitive to errors in the places where the predictor is least accurate.

Pattern six: energy, exploration, and operations

Energy companies run some of the largest physical systems on Earth. Their AI use spans seismic interpretation, drilling optimization, refinery control, and trading. Public material from Shell, ExxonMobil, and others describes AI work across exploration, operations, and retail. Shell's India business has also described AI programs aimed at energy output and productivity. The sources in the reading list cover those programs at the level of press and industry commentary.

The engineering in energy follows the sensing pattern. Physical measurements are noisy and sparse, so models must be combined with physics, and the cost of a wrong decision is high. Seismic models produce images of the subsurface that experts interpret, and the model's output is a proposal, not a verdict. Refinery control models run inside safety envelopes that engineers define, and they can only act within those limits.

The pattern to take from energy is that AI often sits inside a larger safety system. The model proposes, a rule or an engineer disposes, and the boundary between the two is written down. Teams in other industries should copy that discipline, even when the stakes feel lower.

Pattern seven: discovery in drug development

Drug discovery is a slow search through an enormous space of molecules, and the cost of a bad guess is measured in years. Generative models can propose candidate molecules, and predictive models can score their likely properties. Pharmaceutical companies have announced partnerships with AI-native firms and with large model providers, and a sector tracker covers many of them. Those deals describe access and collaboration, and they say little about whether a given molecule will work in patients.

The honest engineering picture is that generation is the easy part. A model can propose ten million molecules in an afternoon. The hard parts are the scoring, the synthesis, the testing in the lab, and the clinical trials that follow. A pipeline that generates more candidates has to be matched by a pipeline that filters them more cleverly, or the bottleneck just moves downstream.

What the patterns share

Read across the patterns and a few engineering habits repeat. Each one is worth stating, because they are the part of industry AI that transfers to your own work.

Cost is an architecture decision

In every pattern, the cost of serving shapes the design. A gateway that loads five thousand schemas wastes tokens, so it projects and discovers lazily. A ranker that generates long answers is too expensive, so it scores in a single pass. A maintenance model that runs on every sensor every second is too expensive, so it samples and aggregates. The model choice is often driven by the cost curve, not by the leaderboard.

Control is the product

In enterprises, the question is not only whether the model is accurate. It is who may use it, on which data, with what logging, and with what fallback when it is unavailable. Uber's gateway puts control in the path. Document systems put control in the review step. Energy systems put control in the safety envelope. A team that treats control as an afterthought will find that its AI system cannot get past the security review.

Evaluation is the hard part

Evaluation is the most common place where industry AI stalls. A recommendation ranker needs offline metrics and A/B tests. A maintenance model needs a threshold tied to a business cost. A document system needs retrieval recall and grounded citations. A route planner needs plan quality measured in real miles and minutes. Each pattern needs its own measurement, and none of them is solved by a single generic benchmark.

Context is scarce

Whether the resource is GPU memory, the model's context window, or an analyst's attention, scarcity drives design. The gateway trims responses. The document system retrieves passages instead of loading archives. The ranker turns a history into a compact prompt. The planner works with a short list of candidate routes. In each case, the engineer decides what the model sees, and that decision is one of the most important in the system.

A learning path through the field

If you want to learn industry AI engineering rather than read about it, a practical path helps. Start with the connection layer, because almost every enterprise system needs it. Read the MCP specification, then read Uber's post on its gateway, and build a small server with two tools and a policy that allows one and blocks the other. The exercise teaches discovery, schemas, and authorization in a few hours.

Next, study a ranker. Read the GenRec paper for the method, then read the earlier JD.com GenRec article on this site for a contrasting design. Build a toy version: a small language model that scores items from a user's history, served with a single forward pass. Measure the cost per request against a generative version. The difference is the lesson.

Then take a sensing problem. Find a public machine dataset, or simulate one with a known failure mode. Practice cleaning the time series, labeling events, and choosing a threshold with a cost table. The modeling is the easy part of this exercise. The discipline is what you should be building.

Finally, build a document system with grounding. Index a set of public documents, retrieve passages for real questions, and measure whether the right passage is in the top results. Only after retrieval works should you add a model on top. This order prevents the most common mistake in document AI.

Mistakes that repeat across industries

Several mistakes appear again and again, and they are worth naming. The first is treating a demo as a deployment. A demo answers a handful of hand-picked questions. A deployment must handle the long tail of real traffic, failures, and changing data. The gap between the two is usually where the budget goes.

The second is measuring the wrong thing. A system that improves a benchmark while degrading the business metric is not an improvement. Tie every measurement to a decision someone has to make.

The third is skipping the owner. A tool, a sensor, or a document belongs to someone. If the owner is not in the loop, the system will be switched off the first time it causes trouble.

The fourth is ignoring cost until the invoice arrives. The cost of a model call, a sensor stream, or a retrieval step adds up fast at scale. Track it per request from the start.

Where this is heading

The next few years will likely bring more agents that act across systems, more rankers built on language models, and more of the infrastructure that makes those systems safe to run. The gateway is an early example of that infrastructure. The most useful skill for an engineer is not knowing one model. It is knowing how to connect, control, measure, and afford a system that uses many.

Industry will also keep producing headlines faster than it produces detail. The discipline of reading past the headline, checking the primary source, and asking for the setup behind each number is the habit this guide hopes to build.

Frequently asked questions

Is an MCP gateway necessary for a small team?

Not at first. A small team with two or three tools can connect them directly. A gateway starts to pay off when many teams expose tools and you need one place for discovery, policy, and logging.

Can a language model really replace a feature-heavy ranker?

The Netflix paper reports gains with fewer hand-built inputs, in an A/B test at Netflix scale. That is evidence for the approach, not a guarantee for your product. Test it against your own baseline.

Why do the numbers in press releases differ so much from papers?

Press releases describe outcomes for a business, often over a long period, with many changes at once. Papers describe a method against a stated baseline. Read both, and trust the one that states its setup.

Which pattern should I learn first?

Start with the connection layer and document retrieval. Both teach discipline that transfers to every other pattern, and both can be built on a laptop.
