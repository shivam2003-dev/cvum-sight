The year ends with a default that is also a test

Across the year, a steady number of features became defaults: asynchronous scheduling in January, speculative decoding version 2 in May, the cache manager version 2 in August, and now the runner for every model in September. Each default flip is a claim that the new path is good enough for everyone who does not configure something else. September's flip is the broadest, because it covers all models rather than dense models or a subset. When a runner becomes the only path, the bugs that it hides are the bugs every user meets.

A default is also a test. The engine's users are the test suite for the default, and the bugs they find are reported in the notes that follow. That is why the September known-issues lists matter as much as the feature lists. TensorRT-LLM's release candidate on September 9 described a silent failure for a specific adapter setup, and its later candidates described memory estimates that were too conservative. Those are not crashes. They are behaviors that users would have to notice on their own.

The lesson for a team at the end of the year is to treat the default as a moving target. The configuration you tested in March is not the configuration the engine runs by default in September. A quarterly review of defaults, with a short list of settings that matter to your product, is the most reliable way to keep up. It is also cheaper than discovering a silent change in an incident report.

Model Runner V2 for every model

vLLM v0.29.0 on September 9 brought 594 commits from 277 contributors and completed the rollout of Model Runner V2 to all models. The runner had first become the default for dense models in July, and pooling models before that. The v0.29 notes add CUDA graph memory profiling for automatic KV cache sizing, batch-sharded sampling that reduces per-step logits memory by a factor of the tensor parallel degree, prompt embeds, and support for extracting hidden states during speculation.

Batch-sharded sampling deserves a closer look, because it is an example of the memory budget from January applied to a part of the pipeline most people do not think about. The logits for a batch are large: one row per request, one column per vocabulary entry. When the model is tensor parallel, sharding the sampling across the tensor parallel group divides the logits memory per device. For models with large vocabularies and large batches, that is a real saving, and it frees memory for the cache, which is where the capacity question always ends up.

The CUDA graph memory profiling is the other half of the same story. Automatic cache sizing has to know how much memory the graphs will need, and it used to rely on conservative guesses. Profiling the graph memory directly lets the engine size the cache closer to the real limit. The trade is startup time, since profiling runs a warm-up pass. For a long-running server that is a good trade, and for a short-lived job it may not be.

vLLM v0.30.0 on September 22 brought 762 commits from 315 contributors, the largest count of the year. It added DeepSeek-V4.1-Flash, which the notes say stores its whole KV cache in MXFP8 through a FlashMLA path on SM100 hardware. Storing the whole cache in a low-precision block format is a memory decision with a quality question attached, and it should be tested the way the May quantization tests were. The release also added a DeepSeek-V4 CPU backend with vectorized kernels for its sparse attention, indexer, and compressor, and GLM-5.3-Flash with expert load balancing.

Correctness bugs in the release candidates

TensorRT-LLM's September candidates disclosed bugs that are worth a close read, because they are the kind that do not fail a test suite. The rc26 notes on September 9 say that LoRA adapters targeting the routed experts of Qwen3 mixture-of-experts models are silently ignored, so the output is the base model's output. Adapters targeting attention layers behaved correctly. The same notes list a memory estimate for the V2 cache manager that is too conservative, so a server can fail to start with an insufficient-memory error even when enough GPU memory is free.

A silent adapter bug is a serious one. A team that serves a customer-specific adapter, and gets the base model's answer instead, may not notice for days. The failure does not show up as an error rate or a latency change. It shows up as a customer reporting that the product ignores their settings. The defense is an adapter-level test that compares the adapted output to a known-good reference, run on every deployment of the adapter, not only on the first.

The memory estimate bug is the opposite kind of problem. The server refuses to start while memory sits unused. That is a capacity problem that looks like an out-of-memory error, and a team that responds by buying more GPUs has spent money to fix a conservative estimate. The useful response is to measure free memory after startup and compare it with what the estimate predicted, then set an explicit cache size if the estimate is consistently off.

The rc26 notes also mentioned GPT-OSS with an Eagle draft model among the known issues. Speculative decoding with a learned draft head is a combination that appears in many of these notes, and each combination needs its own test. The pattern across the year is that the combinations are where bugs live, and the engines are only now covering them in a systematic way.

TensorRT-LLM removes AutoDeploy

TensorRT-LLM v1.3.0rc29 on September 29 removed the AutoDeploy integration and its public entry points, labeled as a breaking change. The July candidate had announced the deprecation, with the reasoning that agent-driven porting to the PyTorch backend would close the gap. This release carries out the removal. The notes also removed an obsolete CMake build option, which is another breaking change for source builds.

A removal that was announced in July and carried out in September is the pattern to expect from a mature project. The notice gave two months of warning, which is enough for a team to plan a migration if it watched the notes. A team that did not watch will see its deployment fail at the next upgrade, which is the worst time to discover the dependency. The lesson from June applies again: inventory the backends and integrations you use, and map each one to its replacement before the removal lands.

The same candidate added a long list of model items, including Qwen3.5 checkpoints with global FP8 scales, a vision rotary embedding change for Gemma 4 that avoids a matrix multiply, a CuTeDSL MoE backend for Kimi K3 NVFP4, and extended piecewise CUDA graphs for MiniMax-M3. The breadth of the list shows how much of the runtime is now shared across model families.

SGLang: Qwen3.8 and the 2.4-trillion-parameter model

SGLang v0.5.19 on September 5 brought 786 pull requests from 214 contributors, and its headline model was Qwen3.8 at 2.4 trillion total parameters with 95 billion active, listed in the notes as an autoregressive model with a dense 27 billion parameter sibling. The naming is the notable part for a practitioner: the active parameter count, not the total, determines per-token compute, and the total determines the memory needed to hold the weights. A model with 2.4 trillion parameters and 95 billion active is a memory problem first and a compute problem second.

SGLang v0.5.20 on September 18 brought 713 pull requests and added GLM-5.3-Flash, Tencent's Hy4-Preview, and Qwen3.8-Flash-Next. The pace of model additions is steady, and the engine's release notes read more like a model catalog than a feature list. For a team choosing an engine, the useful question is which models the engine supports well on the hardware it has, and how quickly new models arrive after release. The notes give a partial answer, and the cookbook links in each release give the rest.

A large model with a small active set raises a specific question for serving: where do the weights live? A model that does not fit in one node's GPU memory must be sharded across nodes, and the cost of expert communication across nodes becomes the limit. Offload to host memory helps for the cache, but weights that must be read on every token cannot sit in slow memory. The memory budget thinking from January now applies to weights as well as cache.

Ollama adds decision models

Ollama v0.35.0 on September 28 introduced decision models through a new endpoint called systemone. The notes say the endpoint is based on the Jev API from TypeSafe. Decision models return choices, probabilities, and scores instead of generated text, and the examples given are ticket triage, model routing, and content classification. Two models are listed, Nimble from Bespoke Labs and Tev1 from Together AI, and both are pulled with the normal Ollama command.

This is a different kind of model from the ones earlier in the series. A text generator produces a long sequence token by token, and its cost grows with output length. A decision model produces a short structured answer, a choice and a score, and its cost is closer to a single forward pass. That changes the serving economics. A routing decision that costs one forward pass can run in front of a large generator, deciding which model to call, which is a common pattern in cost-sensitive products.

The interface matters as much as the model. Returning probabilities and scores instead of text means the caller can apply thresholds, log calibration, and compare decisions over time. A text answer requires parsing before any of that is possible. For a team building a classifier or a router on a local runner, the endpoint is a simpler integration path than prompting a generator to emit a label and parsing the result.

A note of caution applies. Any scored decision needs calibration testing, meaning a check that a score of 0.8 is right about 80 percent of the time on your data. Uncalibrated scores look precise and mislead. The endpoint gives you the number. It does not tell you whether the number means what you think on your traffic.

Ollama v0.34.x ran from September 5 to September 23, with several patch releases, and v0.33.3 on September 2 added image and audio input for Gemma 4 on the MLX engine, reported cached prompt tokens, and honored default parameters defined in GGUF files. Reporting cached prompt tokens is a small change with a large effect on cost tracking: it makes the prefix cache's benefit visible to the application, which is the first step to managing it.

llm-d v0.10.0: operational hardening

llm-d v0.10.0 on September 29 set its themes in plain language: operational hardening, to make the production path safe and boring, with rollouts, high availability, and failure behavior that operators can trust, and production readiness, to move the flagship paths from working to default. The notes also describe container build changes and a stated aim to move community changes upstream into the engine projects.

The word boring deserves attention. In infrastructure, boring is a goal. A boring deployment is one where the rollout does what it says, a failed node is replaced without a page, and an upgrade does not require a meeting. llm-d's themes show the project moving from features to reliability, which is the same arc that the engines followed earlier in the year. The fleet layer is catching up with the engine layer.

The move of changes upstream is a sign of consolidation across the ecosystem. Projects that once carried their own patches for the engine are now pushing those patches back into the engine projects, which reduces the cost of maintaining forks. For a team running llm-d, the practical effect is that the engine version and the fleet version become more tightly coupled, and upgrades should be planned as a pair, as the earlier months recommended for framework and kernel.

The llm-d themes also match what a fleet team should watch for in production. Rollouts that do not drop requests, failover that keeps the cache usable, and failure behavior that degrades gracefully are the properties that a platform team is paid to deliver. A release that names them as goals is a release that the team expects operators to hold it to.

LMDeploy: DeepEP v2 and a Mooncake connector

LMDeploy v0.17.0 on September 1 integrated DeepEP v2, a communication library for mixture-of-experts dispatch, and added Kimi K2.6 support on its PyTorch path. It also added a KV connector for the Mooncake store, which means LMDeploy can use the same storage layer that vLLM and LMCache use. The connector is a sign that the storage layer is becoming a shared standard across engines, which makes it easier to move a cache between them.

LMDeploy v0.18.0 on September 28 followed. The release notes for that version were not part of this issue's detailed reading, so this section does not describe its contents. The point to keep is the timing: v0.17.0 and v0.18.0 landed four weeks apart, and the connector work follows the same storage direction as the rest of the ecosystem.

llama.cpp and the MoE reduction

llama.cpp published a build on September 1 with a CUDA change that fuses the weighted reduction of mixture-of-experts outputs. The commit message explains the mechanism: the combine step wrote weighted expert outputs to global memory before reducing them, and that intermediate traffic was the main cost. The fused path runs one kernel where the baseline ran two. This is a memory-traffic optimization, the same family as FlashAttention's tiling, applied to the expert combine step.

Memory traffic is the constraint that matters most for decode, because each generated token must move the weights and the intermediate results. Fusing two kernels into one removes a round trip through global memory, and that saving repeats for every layer and every token. For local users on consumer GPUs, where bandwidth is the limit, that kind of change can be the difference between a usable and an unusable speed.

The release cadence continued at a high pace in September, with a batch of builds on September 30 alone. Teams that depend on llama.cpp directly should pin a build and test it, for the same reason as in August.

FlashAttention 4 reaches beta 33

The FlashAttention repository published fa4 betas 29 through 33 in September, with the latest on September 30. Beta 29 on September 2 was a compilation speedup for scalar mask generation on SM100 hardware. The later betas continued the steady cadence of the year. By the end of September the fa4 line had run for most of 2026, from beta 0 in March to beta 33 in late September, and it has not yet been declared a stable tag in the data this series tracks.

That long beta period is itself a lesson about kernels. A kernel that serves many shapes, hardware generations, and precision modes takes a long time to harden, and the team is right to keep the beta label until the coverage is broad. Teams that adopted the betas early should have a test matrix of their own shapes, and should move to a stable tag only after the matrix passes on it.

xDiT 0.6 and 0.7

xDiT released version 0.6.0 on September 1 and version 0.7.0 on September 25. The 0.7.0 notes are mostly bug fixes: a diffusion output type that wrapped empty video in a list, callback handling for negative embeddings in several image models, a fix to argument forwarding in ring attention for FA3, and a timing fix for performance measurement across ranks. The fixes are the kind that matter when a team benchmarks a parallel diffusion setup and trusts the numbers.

The timing fix deserves a note. Performance measurements across several ranks are wrong if each rank starts its clock at a different moment, because the slowest rank sets the real finish time. Taking the start time of all ranks into account corrects the measurement, and a benchmark that ignored the issue would overstate some speeds. The lesson applies to every parallel benchmark in this series.

Ray in September

Ray had no release in September in the data this series tracks. The last Ray Serve LLM and Ray Data changes were in August, covered in that section. A quiet month for a project is not a sign of stagnation. For an operator, it is a window to test the August release in staging, because the next release will bring its own changes and the August behavior is the baseline.

Closing the year: what the series shows

Nine months of release notes leave a clear picture, even though no single month tells the whole story. The first months were about making the engine stop waiting. The middle months were about making memory and routing shared across machines and across layers. The later months were about removing old paths, testing the agreements between components, and hardening the defaults that most users now run. The arc is a common one for infrastructure software. It moves from speed, to scale, to reliability, and the notes give a dated record of each step.

A few numbers recur across the months and are worth keeping. Commit counts for the largest vLLM releases rose from about 660 in January to 762 in September, while the contributor count went from 251 to 315. The growth reflects a project that is still expanding even as it consolidates. The number of model families that arrived on day zero also grew. Each of these is a signal, but none is a measure of quality on your workload, which is the one number the notes cannot give you.

The most consistent theme of the year is the gap between a feature and a default. Features arrive in one release, become optional, then become defaults, and each step is a point where a team's assumptions can break. A team that tracks each step, and tests at each step, carries less risk into the next default flip. A team that tracks only the feature headlines finds out about defaults in incidents.

The practical habit that the series recommends for next year is simple to state. Keep a short list of the settings that matter to your product. Keep a replay of your traffic. Keep a long-output test and a recall test. Run them on every candidate and every default flip. Then read the release notes with the list in hand. The notes will say what changed, and the tests will say whether it changed your product.

Concepts this month adds

September adds three concepts. The first is the calibrated decision. A decision model returns a score, and a score is useful only when it is calibrated against outcomes on your data. Calibration is a testable property, and it should be tested before a threshold is set. The endpoint makes decision models cheap to run, which makes calibration testing more important, not less.

The second concept is the silent failure. A silently ignored adapter or a silently wrong cache estimate does not raise an error and does not move a latency metric. The defense is an end-to-end check against a known-good reference, which must be kept current as the engine changes. Silent failures are the category of bug most likely to reach customers before the team sees them.

The third concept is the active parameter count. For mixture-of-experts models, the total parameter count sets the memory needed for weights, and the active count sets per-token compute. A 2.4 trillion parameter model with 95 billion active is a memory problem and a compute problem in different measures. Planning from one number alone will mislead the capacity plan.

What to check this month

  1. Test LoRA adapters end to end. For any adapter that targets experts in a mixture-of-experts model, compare the adapted output to a known-good reference on every deployment, not only the first.
  2. Check cache sizing after startup. If the engine refuses to start on a conservative estimate, measure free memory and set an explicit cache size if the estimate is consistently off.
  3. Plan the TensorRT-LLM AutoDeploy migration. If you used the AutoDeploy path, the removal has landed in rc29. Verify your replacement before the next stable release.
  4. Calibrate decision scores before setting thresholds. For any decision model, measure whether the scores match outcomes on your data before using them to route traffic.
  5. Use reported cached tokens for cost tracking. If your runner reports cached prompt tokens, log them per request so the prefix cache's benefit is visible.
  6. Review llm-d upgrades as a pair with the engine. Version the fleet layer and the engine together, following the coupling from the earlier months.
  7. Run a year-end default review. List every default that flipped this year for your engines, and confirm each setting you rely on still does what you expect.

Frequently asked questions

Is a runner that handles every model the same as a faster runner?

Not necessarily. It is a more uniform runner, which means fewer special cases and fewer silent fallbacks. Speed depends on the model and hardware. Test the speed on your models, and test the correctness on your adapters.

Should I trust a silent-failure fix without a test?

No. A fix for a silent failure should be verified with an end-to-end check that would have caught the original bug. Otherwise the fix is a claim, not a result.

Does a decision model replace a classifier?

It can, for some tasks. It returns structured scores that a classifier also returns. The choice depends on whether the model's training matches your labels, which you must test on your own data.

Why is a quiet month worth noting?

Because it is a window to validate the previous release. Use the quiet time to test the current baseline, so the next release can be compared against something verified.

Common mistakes this month

The first mistake is assuming a flipped default is tested for your models. A default is tested on the engine's own suite and on early users. Your models may hit a path nobody tested. Run your own suite before the default reaches production.

The second mistake is ignoring known-issue lists in release candidates. The lists are the most honest part of a candidate's notes. A silent adapter bug in a candidate can reach production if the candidate is promoted without reading the list.

The third mistake is treating a decision score as a probability without checking calibration. A score can rank well and still be miscalibrated, which breaks any threshold set on it.

The fourth mistake is planning capacity from total parameters alone. The active count decides compute, and the total decides weight memory. Both belong in the plan.

The fifth mistake is upgrading the fleet layer without the engine. The coupling between them means one upgrade can invalidate the other. Plan them together and test the pair.

The cache becomes shared state

Earlier in this series, the cache was an engine detail. A single process owned its blocks, and the router only knew which worker to pick. Through the spring and summer, the cache spread outward. It moved to host memory, then to peers, then to shared stores. August shows the next step: the cache is now part of the request protocol itself. The router asks what each replica holds, the ingress tokenizes once and passes tokens along, and the engine is told about lifecycle events so every replica sees the same picture.

That shift changes who is responsible for correctness. When a cache lives in one process, only that process can get it wrong. When the cache is shared, the router's view, the engine's state, and the client's retries have to agree. A cancelled request that leaves half a cache entry behind is a problem for every replica that reads the entry. A stale router view is a problem for every request routed on it. August's releases are largely about making those agreements explicit.

There is also a cost dimension. Every extra agreement is a message, and messages take time. A router that consults cache state for every request adds latency unless the state is cheap to read. The design choice in Ray Serve, tokenizing in the ingress and transmitting tokens out of band, is a way to avoid re-tokenizing in the engine and to keep the routing decision on the fast path. The question for any team is whether the agreement costs less than the recompute it saves.

Read against the earlier months, August is the point where the stack's pieces start to close their loops. The router uses cache state, the engine reports cache state, the client retries against cache state, and each loop has a failure mode that a single component could not produce on its own.

Ray Serve LLM: routing on KV state

Ray 2.58.0 on August 23 completed a feature that Ray 2.57 had previewed: KV cache and token aware request routing for Ray Serve LLM. The notes describe tokenization happening in process on the LLM router ingress replica, the routing decision being made there, tokens transmitted out of band so the engine does not tokenize again, and KV lifecycle events broadcast to every ingress replica. The design removes a repeated step, because tokenization is now done once and reused.

Why does a single extra tokenization matter? Tokenization is cheap per request, but at high request rates it adds up, and it adds latency at the moment a request enters the system. Moving it to the ingress and reusing the result means the engine receives tokens ready to process. The routing decision needs tokens anyway, because the prefix that matters for cache matching is in token space. Doing the work once and sharing the result is the sort of small change that shows up in latency percentiles.

Broadcasting cache lifecycle events to every ingress replica is the more interesting part. Each ingress replica needs to know which replica holds which prefix, or its routing decisions will be based on stale information. Broadcast keeps the view consistent across ingress replicas, which matters when a load balancer spreads requests across them. The cost is network traffic proportional to cache churn. A workload with heavy churn, many short-lived prefixes, will pay more for broadcast than a workload with stable prefixes.

The January section described cache-aware routing with a radix tree and the risk of a stale view. Ray's design is a production version of that idea, with the staleness problem addressed by broadcast rather than left to chance. A team evaluating it should measure two things: the realized cache hit rate across replicas, and the broadcast traffic at its peak churn. The first says whether routing helps. The second says whether the helping costs too much.

Ray 2.57.0 on August 11 had its own data-side change: DataSourceV2 became the default, so read calls use the new scan and listing infrastructure with row-group aware chunking, and Hash Shuffle V2 removed a pool of aggregator actors that had to be sized from an estimate of input size. For batch inference jobs, a shuffle that does not need up-front sizing is a relief, because a wrong estimate used to cause either wasted capacity or out-of-memory failures.

Restore points for cancelled prefills

Ollama v0.33.0 on August 21 included a set of caching changes that are worth reading slowly. The notes describe a fix for a hang in which agent clients cancel long prefills. They also say prefill restore points are now trustworthy by construction: when a prefill is cancelled, it keeps every restore point it passed, so a retry resumes from where it stopped. Before the change, a cancelled prefill could leave the system unable to reuse its own progress.

The notes give a concrete example. On models with recurrent layers, a resumed prefill recorded restore points that did not cover what they claimed. A request that matched 46,000 tokens out of 47,000 had to be reprocessed from zero. That is a severe penalty for a near-complete match, and it is the kind of bug that appears only when a client cancels and retries, which agent clients do often.

The lesson is about what a restore point means. A restore point is a promise that the cache holds state up to a given token. If the promise is false, the system must recompute, and in the worst case it recomputes everything. Making restore points true by construction means the system only records a point when the state behind it is complete. Correctness of the promise is what makes the saving real.

For agent workloads, which cancel and resume often, this matters a great deal. An agent that interrupts a long reasoning step and then continues should not pay for the same prefill twice. The cost of getting this wrong is paid in tokens and in user wait time, and both are easy to miss in a benchmark that never cancels.

Ollama v0.33.0 also added Claude Desktop configuration for Ollama as a third-party gateway provider. Together with the earlier launch work, the pattern is clear: the local runner is becoming a gateway that many agent clients can point at, and the caching behavior it provides is what makes those clients affordable to run.

Kimi K3 and the hybrid attention pattern

SGLang v0.5.17 on August 8 described Kimi K3 day-zero support. The model is a 2.8 trillion parameter multimodal system with a latent mixture-of-experts layout: 896 experts, top-16 routing, and a 3584-dimensional latent space. It has a one-million-token context. Its layer stack interleaves 69 linear-attention layers using a KDA mechanism with 24 layers of multi-head latent attention, and a vision tower named MoonViT3d. The release notes say it ships as a native MXFP4 checkpoint.

The layer mix is the detail to study. Linear attention layers have a state that stays fixed in size as the context grows, instead of a cache that grows with every token. Multi-head latent attention layers have a cache that grows, but compressed. Interleaving the two means most of the stack pays a constant cost per token, and only a minority of layers pay a growing one. That is the architectural answer to the memory budget from January. The cache is smaller because most layers do not keep one that grows. To see why linear attention behaves this way, compare it with standard attention. Standard attention compares each new query with every past key, so it must keep every past key and value. Linear attention rewrites the computation so that past tokens are summarized into a running state of fixed size, and each new token updates that state instead of scanning the history. The state does not grow with context length, which is what makes the per-token cost flat. The tradeoff is that a fixed-size summary cannot hold every detail, which is why hybrid stacks keep some full-attention or latent layers in the mix.

The number of layers of each kind is a design choice that trades memory against recall. More linear layers mean a smaller cache and cheaper long context, but a greater risk of losing a specific detail from far back in the window. More latent or full layers mean better recall and a larger cache. Kimi K3's split of 69 linear layers to 24 latent layers is one point on that curve, and it is why the recall test at several depths matters more for this model than the raw context size suggests.

This is why the hybrid cache work from May and July matters. An engine serving Kimi K3 must manage two different kinds of state at once: the fixed recurrent state of linear layers and the growing compressed cache of latent layers. The allocator and the prefix cache have to treat each kind correctly. A prefix hit that is valid for the attention layers may not be valid for the recurrent layers unless their state was captured at the same point. That is the same boundary problem that block-aligned Mamba caching solved earlier.

vLLM v0.27.0 on August 10 brought Kimi K3 support as a full stack in one release: core model files, kernels, Python and Rust frontends, and compressed-tensors quantized checkpoints. Its patch on August 11 added support for quantized DSpark Markov heads. vLLM v0.28.0 on August 26 went further, with Decode Context Parallel for Kimi K3, fused kernels for the linear attention decode and prefill path, and an adaptive speculative token budget that the notes credit with about 60 percent better time to first token under DSpark. Kimi K3 also ran on ROCm with the V2 runner.

The adaptive speculative token budget is a connection to the July section. DSpark sized its verification window from the draft's confidence. An adaptive budget sizes the number of speculative tokens under a shared limit, so a busy server spends its speculative budget where it pays. The benefit shows up in time to first token, which is where speculation is most valuable for interactive users.

A note on the one-million-token context: a long window is valuable only if the model uses it, and the way a team checks that is a recall test at multiple depths. A system that serves a million tokens quickly but misses facts in the middle is a fast system that answers wrongly. August's releases make the window practical to serve. They do not make recall automatic, and the evaluation remains the team's responsibility.

TensorRT-LLM: KV cache manager V2 by default

TensorRT-LLM v1.3.0rc25 on August 31 announced that its KV cache manager V2 is now the default for a long list of model families, including DeepSeek V3, R1, and V3 Lite, DeepSeek V3.2 and V4, GLM-5, GPT-OSS, Mistral Large 3, the Kimi K2 line including K3, MiniMax M2 and M3, the Nemotron H family, and Qwen3-Next, Qwen3.5, and Qwen3.8. A default change in the cache manager reaches the most sensitive layer of the engine. Cache policy decides what is kept, what is evicted, and how blocks are reused, so a bug there affects output correctness as well as speed. The right way to adopt the new default is to run the replay and the long-output tests from May and June before promotion, and to compare cache hit rates and output drift against the previous default.

The breadth of the list is informative. The model families that now default to the V2 manager cover nearly the whole recent lineup, which suggests the team considers the manager stable across dense, mixture-of-experts, and hybrid models. That stability is what allows a default flip, and it is also what makes a rollback plan essential, because the previous manager remains the fallback for a configuration that fails.

Mooncake and LMCache: the storage layer keeps moving

Mooncake v0.3.13 on August 26 and v0.3.13.post1 on August 31 added several fixes in its transfer engine and CI. A fix for a stale status in an io_uring path affects how transfers report completion, and a fix for a leak in a request map affects long-running processes. Leaks in transfer code are slow killers: they do not fail a test, but they exhaust memory over days of uptime. The post-release restored CUDA-free non-CUDA wheels, which matters for teams that install on machines without GPUs.

LMCache v0.5.5 release candidates arrived on August 28 and August 31, with builds for CUDA 12.9, ROCm, and Intel XPU alongside the standard wheel. A release that ships on several accelerator stacks at once is a sign that the cache library is being treated as portable infrastructure, not as a single-vendor component. A team with mixed hardware can now plan one cache layer across it, at least in principle, and should test each accelerator path separately.

LMCache's ROCm wheel in early August, for AMD MI300X and MI350 series hardware, was built to match the upstream vLLM ROCm container's torch version. That ABI match is the kind of detail that makes a wheel installable. Without it, an install can succeed and then fail at import time, which is a bad first experience for an operator. Check the install path on a clean container before you write it into a runbook, and record the exact engine image it was tested against, because the next image may not match.

The storage work in August also reflects a broader lesson about where failures hide. A transfer that reports completion too early, a request map that leaks a little on every failed transfer, and a wheel that imports on one stack and not another all look like normal operations until they are not. Each of those issues is easy to miss in a short test and easy to catch with a long-running soak test that mixes successes, failures, and cancellations.

llama.cpp reaches a release every few days

The llama.cpp project is the engine underneath much of local inference, and its build cadence matters more each month. In August alone, the repository published 38 tagged builds, several of them on August 31 in a single batch. The pace reflects an active project shipping small, targeted changes, and it is a reminder that the local inference stack moves faster than most server stacks.

When a local product uses Ollama, its quality and speed depend on a chain of upstream choices that the product team does not control, and that chain is worth monitoring.

The series has mostly covered language models, but the same concerns apply: parallel layout, communication cost, and the balance between compute and transfer. Reading August against the year so far

If you read this series from January, August looks different from the months before it. Early in the year, the questions were about speed inside one engine. Mid-year, they moved to memory, transfer, and retirement of old paths. August's questions are about agreement: between the router and the engine, between a cancelled request and its retry, and between a model's layer layout and the cache policy that serves it. Each of those agreements is easy to assume and hard to test, which is why August's releases spend so much effort making them explicit.

Agreement is also where teams get hurt in ways that dashboards do not show. A router that sends a request to a replica that no longer holds its prefix does not fail. It becomes slower by an amount that looks like normal variance. A restore point that overstates its coverage does not raise an error either. It forces a recompute that doubles the user's wait on one request in a thousand, and the average barely moves. The defense is to test the agreements directly: send a request that should hit, check that it hits, cancel a request on purpose, and check what the retry costs.

A second pattern is that the pieces increasingly come from different projects. Ray provides the routing, Ollama and llama.cpp the local runtime, vLLM and SGLang the server engines, and LMCache and Mooncake the storage. A team that stitches these together owns the seams. The release notes describe each piece well, but the seams are described by nobody in particular. Writing down, for your own stack, which component owns each agreement is the most useful architecture document a team can produce this year.

Finally, August shows that the frontier is moving toward very large models with very long contexts. Kimi K3 is a 2.8 trillion parameter model with a million-token window, and it arrived on day zero in an open engine. The gap between frontier research and what a team can serve is shrinking, but the cost of serving such a model is still high, and the decisions in this month's notes, about layer mix, cache policy, and speculation budgets, are what set that cost. A team that understands them can decide whether a frontier model is worth its price for its own product.

Concepts this month adds

August adds three concepts. The first is the restore point, a promise that a stored state is complete up to a given token. A false promise is worse than no promise, because it forces silent recomputation or silent errors. The correctness of the promise is what makes cache reuse safe after a cancellation.

The second concept is the mixed-state cache. Hybrid models, such as the Kimi K3 layer mix, hold two kinds of state: fixed recurrent state and growing cache. Each kind needs its own correctness rule, and a prefix hit is valid only when both kinds were captured at the same point. This is the general form of the boundary problem that began with Mamba states in March.

The third concept is the default flip for critical components. The TensorRT-LLM cache manager change shows that the most sensitive layer can flip its default after a period of known issues. A default flip for cache management is a change to correctness as much as to speed, and it should be treated with the same care as a model upgrade.

What to check this month

  1. Measure KV-aware routing on your churn. In Ray Serve LLM, record the realized cache hit rate and the broadcast traffic at peak churn before and after enabling the routing.
  2. Test cancellation and resume on agent traffic. Cancel long prefills on purpose and confirm the retry resumes from its restore point, not from zero.
  3. Compare KV cache manager V2 against the previous default. Use a replay and long-output tests, and compare hit rates and output drift before promoting.
  4. Test long-context recall for Kimi K3 class models. Serving a one-million-token window quickly is not the same as using it correctly. Run recall at several depths.
  5. Pin llama.cpp and Ollama versions in local products. A fast build cadence means unpinned output can drift between runs.
  6. Watch transfer leaks in long-running processes. Track memory over multi-day runs after upgrading Mooncake, since leaks do not fail tests.
  7. Re-run the cancellation test after every Ollama upgrade. Restore-point behavior is a recent change, so keep a test that cancels a long prefill and checks the retry cost.

Frequently asked questions

Is KV-aware routing worth it for a small fleet?

Usually not until the fleet has several replicas and repeated prefixes. With one or two replicas, the router has little to choose between. Measure the hit rate gain against the broadcast cost before enabling it.

Does a one-million-token context mean the model remembers everything?

No. It means the model can accept that many tokens. Recall depends on training and on the attention layout, and it must be tested at several depths in the context.

Should I adopt a new cache manager default right away?

Not without a replay. A default flip changes correctness-sensitive behavior for every deployment that did not set the flag, so test it first and keep the previous manager available for rollback.

Why do local runner releases matter for server teams?

Because local tools and agent clients are often where new behaviors first appear, such as cancellation patterns and restore points. The fixes often carry over to server engines.

Common mistakes this month

The first mistake is adding routing that depends on cache state without measuring churn. Broadcasting cache events is cheap when prefixes are stable and expensive when they turn over quickly. Measure the churn before enabling the routing.

The second mistake is assuming a cancelled request leaves no trace. A cancelled prefill can leave restore points, and a false restore point is worse than none. Test cancellation explicitly, rather than assuming cleanup.

The third mistake is equating a long context with a good long context. A window that accepts a million tokens still needs recall testing. Serving speed and answer quality are separate measurements.

The fourth mistake is ignoring leaks because the tests pass. Leaks in transfer code and request maps show up over days, not in unit tests. Watch memory over long runs.

The fifth mistake is running an unpinned local engine in a product. A build cadence of several releases a week means the product's behavior can change between two runs of the same prompt.

Deleting code as a feature

Most of the features in this series were additions. A new kernel, a new cache policy, a new routing method. July's most important engine change was a deletion. vLLM v0.25.0 says PagedAttention has been removed, and the legacy attention implementation is gone now that the newer backends are the standard path. Given that PagedAttention was the idea that made vLLM, the removal can look strange. It is not a retreat from the idea. The paging concept, managing the cache in fixed blocks, lives on inside the newer backends. What was removed is the older code that implemented it in one particular way.

Deleting a path is expensive to do well. The old implementation has users, edge cases, and tests that depend on its behavior. Keeping it alive costs maintenance on every change to the shared code. A project that has spent several months proving the new path on the common configurations can afford to remove the old one, and the removal makes every later change simpler. The risk is that some configuration still depended on the old path. A team that upgrades past this release has to check its configuration against the new default.

For operators, the lesson of a deletion is to read the removal notice as a forced migration. The change does not give an option to stay. Test the replacement path on your traffic before the upgrade, record any configuration that depended on the old behavior, and treat the upgrade as the moment to clean up those dependencies too.

July also shows that the engines have started to converge on a common set of paths. Several projects now run speculative decoding with overlap scheduling, put the runner on CUDA graphs, and manage the cache across hybrid layer types. When the paths converge, the differences between engines move from core mechanisms to tuning, cache policy, and operational tooling. That is good news for teams that want to switch engines, and it raises the stakes for the tuning work that remains.

DSpark: sizing the verify window by confidence

SGLang v0.5.16 on July 25 introduced DSpark, which the notes describe as confidence-driven speculative decoding. The earlier speculative methods in this series used a fixed draft length. The proposer guessed a set number of tokens, and the verifier checked all of them, whatever the proposer's confidence. A fixed length is simple, but it wastes work when the proposer is unsure, and it leaves speed on the table when the proposer is confident and the window is too short.

DSpark drafts in blocks, semi-autoregressively, and then sizes each verification window from the draft's own confidence. A confident draft gets a longer window, and an uncertain one gets a shorter window. The reported result is 383.7 tokens per second at an average accept length of about five, on DeepSeek V4 Pro at tensor parallel 8 on B300 hardware with batch size one. That number is a single configuration, and batch size one is the best case for speculation, because there is no batch to share the work with. Treat it as a demonstration of the mechanism rather than a forecast for a loaded server.

The idea of tying the window to confidence is a general one. Speculation pays only when accepted tokens outnumber wasted work. A confidence signal tells the system when a long draft is likely to be accepted and when it is likely to be wasted. The engineering challenge is to make the confidence signal cheap and well calibrated. A miscalibrated signal can be worse than a fixed length, because it can draft long when the proposer is wrong.

The release notes also mention an environment setting that changes how verification is batched in compact mode. That is a reminder that speculative methods have more knobs than their headline suggests, and the defaults may not match your traffic. Benchmark the method with the block size and verification mode you will run, and compare it with the simpler fixed-length method on the same workload.

SGLang v0.5.15 on July 10 made Spec V2 the default, with zero-overhead scheduling through CUDA-graphable draft extension, removed device-to-host and host-to-device synchronizations, and fused metadata operations. The notes also describe tuned GLM-5.2 NVFP4 serving on Blackwell at over 500 tokens per second per user on eight B300 GPUs at batch size one. The post-release v0.5.15.post1 on July 14 fixed several launch and accuracy issues for that model, including NaN outputs from a FlashInfer FP4 kernel on long inputs. That NaN fix is the kind of correctness work that matters more than the throughput headline.

CacheBlend under the hybrid manager

LMCache v0.5.2 on July 22 carried an important compatibility requirement. It must be used with vLLM version 0.26.0 and later. The release also made NIXL an optional extra, so it installs only when requested, and added MiniMax M3 support. The most technical change is that CacheBlend now works under vLLM's hybrid KV cache manager, with dual rotary position embedding support for sliding-window attention models.

CacheBlend is a method for reusing cached text that was computed in a different context. The usual prefix cache requires an exact match from the start of the prompt. CacheBlend aims to reuse cached blocks even when they appear at a different position, by correcting the positional encoding and recomputing a small part of the cache. Its value is highest for retrieval workloads, where the same document appears in many prompts but never at the same offset. Making it work under the hybrid manager means it can serve sliding-window models too, which previously were a poor fit.

Position is the subtle part. A rotary position embedding encodes where a token sits in the sequence, so a block cached at one offset carries the wrong position if it is reused at another. Dual rotary embedding support, in the release notes' phrasing, means the cache can handle the two positional schemes that sliding-window models use. Getting positional encodings right is the difference between a cache hit that is correct and one that quietly degrades the answer. Test reused-context answers against a fresh computation before trusting them.

The compatibility line is a practical one. A team running vLLM 0.25 cannot take LMCache 0.5.2 without checking the version pairing. The rule from earlier months still applies: pin the cache library and the engine together, and treat the pair as one release.

LMDeploy v0.15 and prefix hits with speculation

LMDeploy v0.15.0 on July 31 had a feature that connects two earlier themes. It supports long-context and multi-token-prediction prefix-cache hits, which means a prefix cached in a speculative configuration can still be reused. Speculation and prefix caching used to interact poorly in some engines, because the draft state complicated what counted as a reusable block. Making the hit work for both means a long shared prefix pays off even when speculation is on.

The release also added guided decoding support for speculative decoding. Guided decoding constrains output to a grammar, such as valid JSON or a schema. Combining it with speculation is harder than it looks, because the grammar must reject drafted tokens that would be invalid, and the verifier must agree with the constraint. A correct combination preserves the guarantee that the output matches the schema. A broken one can produce schema-invalid output that passes every latency test. For structured-output products, the schema validity rate is the number that must be tested.

LMDeploy's turbomind backend also gained a memory allocator, an object cache, and scheduler integration in this line, which continues the theme of the memory system becoming a product feature. A team evaluating LMDeploy should test its long-context behavior with speculation on and off, and should check schema validity under speculation before enabling it.

Mooncake: transport quality and spraying

The notes mention path diversity for RDMA queue pairs through UDP source ports and link aggregation balance, and enhanced quality of service and slice spraying for the TENT transfer engine. Spraying a transfer across several paths spreads load and avoids a single congested link, which matters when large cache blocks move between machines.

These changes are invisible to most users and critical to cache-heavy clusters. When many machines move large blocks at once, a single hot link becomes the limit, and the whole system waits on it. Spreading the traffic across paths, and giving priority to latency-sensitive transfers, keeps tail latency under control. The benefit is easiest to see on a busy cluster and hardest to see on a quiet one, so benchmark it under concurrent load.

The post-release also rebuilt the NPU wheel with stripped shared libraries to reduce its size, and updated documentation for the multiprocess interface used with vLLM and LMCache. Reading July against the earlier months

The months since February have a clear arc. February asked whether the pieces could run together. March asked whether they composed. April asked whether they survived failures. May and June asked whether memory and transfer could be shared across instances, and whether old paths could be retired. July asks whether the new paths can become the only paths, and whether each speed claim holds once the default flips. That is a late-stage question, and it changes the job of the reader. The release notes now describe what is standard, not what is possible.

That shift has a practical consequence for benchmarking. When a feature is optional, a benchmark compares it against the default. When the feature is the default, the comparison is against the previous default, which is usually the path that now has tests and history. A benchmark that compares a new default against a removed path is measuring a baseline that no longer exists in the codebase. Teams should save the old baseline numbers before the upgrade, so they can still compare after the removal.

The arc also changes the risk. A feature in beta risks a bug in one configuration. A default flip risks a regression in every deployment that did not set the flag. The response is the same as in earlier months, pin what matters, but the scale of the risk is larger. A default-flip review should list every setting the team relies on and confirm each one still does what it did before.

Concepts this month adds

July adds three concepts. The first is removal as maintenance. A deleted code path is a sign that the replacement has earned the default position. Teams should treat a removal as a forced migration, and should read the removal notice with the same care as a new feature.

The second concept is confidence as a control signal. DSpark ties the verification window to the proposer's confidence, rather than to a fixed number. The general pattern is that a system can allocate work based on how sure it is, and that pattern will appear in other places, such as adaptive batching and adaptive cache policies. The risk is miscalibration, which turns a helpful signal into a bad guess.

The third concept is position in cache reuse. Reusing a cached block at a different offset requires correcting its positional encoding, and getting that wrong degrades answers quietly. CacheBlend makes the reuse possible under the hybrid manager, and the test for it is a comparison against fresh computation, not a latency number.

The month cache stopped being local

For most of this series, the KV cache lived in one process on one machine. Offload moved blocks to host memory or disk on the same box. Mooncake and the early LMCache work moved blocks across machines, but usually through a shared store that every worker reads and writes. June's LMCache release introduced something different: direct transfers between peers. One instance can ask another whether it holds a block, and fetch it without going through a central store.

That changes the shape of the system. A central store is simple to reason about. Every block has one authoritative location, and the store decides what stays. A peer-to-peer design spreads that authority. Each instance knows what it holds, and the lookup protocol has to find the right peer, fetch the block, and confirm it is current. The benefit is lower latency for nearby blocks and no single bottleneck. The cost is protocol complexity and new failure modes, such as a peer that disappears mid-transfer.

The same month also brought the opposite move in the engine world. TensorRT-LLM announced that its TensorRT backend will be removed after one more release candidate. That is a retirement, and retirements are part of inference engineering. Every engine accumulates backends, kernels, and code paths over time, and each one costs maintenance. A healthy project removes paths that a newer design has replaced. A team that depends on a retiring path needs to plan the move while the old path still works.

Taken together, these changes show that the system is being rebuilt around fewer, better-understood paths, with cache and routing treated as first-class concerns. There is a useful comparison with the earlier months here. In January and February, a new feature was a reason to change the stack. By June, the more common reason is that the stack has become complex enough that someone must remove parts of it. Peer-to-peer KV transfer in LMCache

LMCache v0.5.0 introduced full peer-to-peer support for multiprocess mode. The notes list a P2P adapter, a transfer channel abstraction, and a new remote procedure call interface for peer lookup, along with an end-to-end example. The design separates three questions: how does an instance find a block on a peer, how does it transfer the block, and how does it fit the block into its own cache. Separating them lets each part change without rewriting the others.

Why would a team want this? Consider a fleet of replicas serving the same system prompt and the same retrieved documents. Without peer lookup, each replica computes its own copy of the shared prefix, and the fleet pays that prefill cost many times. With peer lookup, a replica that is missing a prefix can fetch it from a peer that already has it. The transfer costs network bandwidth, but it is usually much cheaper than recomputing a long prefill, provided the network is fast and the block is large enough to matter.

A useful way to frame the decision is as a cost comparison per request. Recomputing a prefix costs a fixed amount of GPU time, paid on the replica that receives the request. Fetching the prefix costs network time, paid across the cluster, and it also consumes bandwidth that other requests may need. A fleet with a busy network may find that fetching competes with its own traffic. A fleet with idle network capacity and busy GPUs will find fetching far more attractive. The measurement should include both the GPU time saved and the network time spent.

The break-even point is the important number. Recomputing a prefix costs compute time that scales with prefix length. Fetching it costs transfer time that scales with the cache size of that prefix, plus lookup overhead. For long prefixes on a fast network, fetching wins. For short prefixes, or on a slow network, recomputing can be cheaper. A team should measure both costs on its own hardware and network before enabling peer transfer, and should set a minimum prefix length below which the system recomputes.

Peer transfer also raises a trust and correctness question. A block fetched from a peer must match the model, the tokenizer, and the cache layout of the requesting instance. A mismatch can produce wrong output without any error. Production setups should version their cache entries with the model identity and the engine version, and should refuse to load blocks whose identity does not match. That check costs almost nothing, and it prevents the worst kind of silent failure.

MoE load balancing

SGLang v0.5.14 highlighted two MoE load-balancing methods, Waterfill and LPLB. The notes describe them as balancing mixture-of-experts load. The problem they address is that tokens do not spread evenly across experts. Routing sends some tokens to popular experts and few to others, so some GPUs in an expert-parallel layout work hard while others wait. The slowest GPU sets the pace for the whole step, which makes imbalance a direct tax on latency.

Load balancing can happen in two places. Static placement decides which experts live on which GPUs, based on expected load. Dynamic rebalancing moves experts or replicates popular ones as traffic changes. Each approach has a cost. Static placement is cheap at runtime but cannot follow shifts in traffic. Dynamic rebalancing follows the traffic but moves weights, which takes time and bandwidth. The methods in the release presumably sit at different points on that tradeoff, and the notes do not give the internal design, so read the linked documentation before choosing one.

The measurement that matters is the spread of work across GPUs at each step, not just the average. A deployment with a good average and a bad spread still pays for the slowest GPU. Log the per-GPU token count at each step, look at the maximum against the mean, and use that ratio as the signal for whether load balancing is worth enabling. A ratio close to one means the router already spreads work well, and balancing will not help much.

The same logic applies to vLLM v0.23.0's work on DeepSeek V4. Concepts this month adds

June adds three concepts. The first is the break-even point for transfer. Fetching a cached block from a peer costs time and bandwidth, and recomputing it costs compute. The right choice depends on prefix length, network speed, and the hardware, and the threshold should be measured, not assumed. This is the same kind of decision as the offload question from April, now applied across machines.

The second concept is spread. Mixture-of-experts load is uneven, and the slowest device sets the step time. The ratio of the maximum device load to the mean is the number to track. Balancing methods reduce that ratio, and the value of a method depends on how much the ratio was costing before.

The third concept is the deprecation window. Engines retire backends, and each retirement is a migration with a deadline. A deployment inventory that lists the backend, the kernel, and the cache policy in use is the tool that makes the deadline manageable. Without it, the removal arrives as an incident.

What to check this month

  1. Measure the transfer break-even for peer cache. Compare recomputing a long prefix against fetching it from a peer on your own network, and set a minimum prefix length.
  2. Version cache entries with model and engine identity. Refuse to load blocks whose identity does not match, so a peer cannot inject stale or incompatible blocks.
  3. Inventory your TensorRT backend usage. If any deployment uses the TensorRT backend, plan the migration before the removal lands, and test the replacement on a replay.
  4. Log MoE load spread. Record the maximum and mean token count per GPU each step, and enable balancing only if the ratio is costing latency.
  5. Test sliding-window prefix retention. If you serve hybrid long-context models, verify that prefix reuse behaves as expected when the window rolls forward.
  6. Judge speculation on your content mix. For Ollama and other auto-tuned drafting, benchmark the content types your users actually send.
  7. Check data pipeline defaults after the Ray 2.56 upgrade. Confirm the logical memory and batch size settings match what your jobs need.

Frequently asked questions

Is peer transfer always faster than recomputing?

No. It depends on prefix length, network speed, and lookup overhead. Short prefixes or slow networks can make recomputation the cheaper choice. Measure both before enabling it.

Why is a backend removal a big deal if it still works today?

Because the next release will not include it, and every upgrade after that will fail to find it. The migration is much easier with time to test than under a forced upgrade.

Does load balancing help a small deployment?

Usually not much. Balancing matters when expert parallelism spreads a model across many GPUs and traffic is skewed. On a small layout, the router may already spread work evenly.

Should a local user trust the 90 percent figure?

Only for work that looks like the benchmark. Coding agents may see large gains. Chat and creative writing may see smaller ones. Test your own workload.

When memory management becomes a product feature

Through March and April, most engine work aimed at speed or at keeping a single feature from breaking others. May shows a different priority. The memory system itself, the part that decides which cache blocks live where, became something engines compete on and something operators configure deliberately. Memory is no longer a background detail that the engine handles quietly. It has policies, backends, and interactions with every other feature.

That change follows from the models. Long-context and reasoning models hold far more state per request, and that state has different lifetimes. A reasoning trace may be needed for a few thousand tokens and then discarded. A system prompt may be needed for every request in a session. A sliding-window layer only needs the most recent tokens, while a full-attention layer needs everything. An allocator that treats all of that state the same wastes memory. An allocator that understands the differences can keep more useful state in the same GPU.

The practical result is that teams now have to choose a memory configuration, not just a model and a batch size. A memory configuration is also harder to review than a model choice, because its effects show up under load, at the tail, and only for the request mix that triggers them. A team that writes its memory settings down, with the reason for each one, can revisit them when the traffic changes. A team that leaves them at defaults will discover the consequences during an incident. The choice includes the eviction policy, the offload tier, the quantization format of the cache, and how those interact with the scheduler. Each option has a cost in latency and a benefit in capacity, and the right mix depends on the workload. May is the month that made those choices visible in the release notes.

KV offload meets the hybrid memory allocator

vLLM v0.21.0 says its KV offloading subsystem now integrates with the Hybrid Memory Allocator, including scheduler-side support for sliding-window groups and full HMA enablement. The phrase hybrid here refers to models whose layers have different cache needs. Some layers keep every past token. Others keep a sliding window of recent tokens. A single allocator that manages both kinds of layer can avoid reserving full-length memory for the sliding layers, which is the kind of waste the paged design from January was built to remove.

Offloading adds a second dimension. Once blocks can move to host memory, the allocator must know which blocks are cold and which are needed soon. For sliding-window layers, that question is simpler, because the window moves forward and old blocks expire on a known schedule. For full-attention layers, every block may be needed again, so the offload decision depends on reuse patterns. Integrating the two means the scheduler can reason about both kinds of layer when it decides what to move.

The mental model is a budget with two layers. The GPU holds the blocks that the next step needs. The host holds blocks that might be needed later. The allocator's job is to keep the GPU budget aligned with the next few steps and to move everything else out of the way. Integrating offload with a hybrid allocator means that budget is computed per layer type, which avoids moving blocks that are about to expire anyway.

A useful check for a team is to measure how much of the GPU cache is held by sliding-window layers versus full-attention layers in their model. The answer depends on the architecture, and it determines how much a hybrid-aware allocator can save. If sliding layers dominate, the savings can be large. If full-attention layers dominate, the gain comes mostly from better offload policy.

Budgets, stop sequences, structured output constraints, and logprob requests all depend on the exact token stream the user sees. Speculation produces tokens in bursts and sometimes rejects them, so the accounting has to be done on accepted tokens. A bug in that accounting does not show up as a crash. It shows up as a reasoning answer that stops too early or runs too long.

Then measure the latency effect on answers with long thinking, since that is where speculation helps most and where budget bugs do the most damage.

Three engines supporting one model within two months is a sign that the model's features are now well understood. For a team, the implication is that the choice of engine for DeepSeek V4 is a performance and operations decision, not a feature decision. SGLang's v0.5.12 notes also describe HiSparse, a mechanism for offloading inactive KV cache to CPU memory, and a later addition of hierarchical caching under a unified radix tree. The phrase inactive is doing work. Sparse attention means many cached tokens are not read at each step, so the cache for those tokens can sit in host memory until a query needs it. That is a natural pairing of sparse attention and offload, and it is one reason long-context serving of sparse models is becoming practical on fewer GPUs.

The W4A4 MegaMoE kernels in the same release are also notable. W4A4 means four-bit weights and four-bit activations. The notes say the change is faster with a negligible accuracy drop. That claim needs the same scrutiny as any quantization claim: measure accuracy on the tasks you serve, and do not accept a general statement as a guarantee for your domain.

KV cache quantization in LMDeploy

LMDeploy v0.13.0 on May 12 added TurboQuant support for KV cache quantization, with a quant policy value of 42 in its notes. Quantizing the cache is different from quantizing the weights. Weights are fixed after loading, so their quantization error is set once. Cache entries are written at every decode step, and their quantization error accumulates over the sequence. The design problem is to keep that error small enough that answers stay correct across long outputs.

The payoff is capacity. From the worked memory budget in January, a cache stored in 8-bit precision holds twice as many tokens as one stored in 16-bit, for the same memory. Quantizing to a lower bit width does more, but accuracy risk grows with it. The right choice depends on task sensitivity. A summarization workload may tolerate a lot of cache error. An extraction task that copies exact identifiers may not.

LMDeploy's release also integrated cuBLAS grouped batched GEMM for Qwen 3.5 mixture-of-experts inference on Blackwell, and added a refactored tool parser for its API server. Those are less dramatic than the cache work, but they show that the engine is spending effort on the path from model output to tool call, which is where many agent products break.

For evaluation, the test is long-output fidelity. Generate long answers with and without cache quantization, using the same seed where the engine supports it, and compare factual content and identifiers. A short benchmark will miss drift that appears only after thousands of tokens. Include a long-output case in every quantization test.

Decode-side caching for disaggregated serving

SGLang v0.5.11 made decode-side prefix caching work under prefill-decode disaggregation. The notes say that recovers radix-cache hit rates and time-to-first-token savings for long shared prefixes in disaggregated deployments. In January, radix trees were a routing structure at the gateway. This release applies the same reuse logic to the decode workers, which means a shared prefix can be found and reused where the decoding actually happens.

The reason this matters is that disaggregation separated the phases and, in doing so, broke the locality that prefix caching depended on. A prefix computed on a prefill worker had to be transferred, and decode workers did not benefit from prefixes seen elsewhere. Restoring a radix cache on the decode side brings back reuse without giving up the separation. The gain depends on how often prefixes repeat across requests that land on the same decode worker, which the router's policy influences.

This is a good example of the pattern from earlier months: a feature that solves one problem creates a second problem, and the next release solves that one. Disaggregation solved interference between phases. Its cost was lost cache locality. Decode-side radix caching restores locality. The next question will likely be how to keep locality across many decode workers at once, which connects to cache-aware routing from January.

SGLang v0.5.11 also made CUDA 13 and PyTorch 2.11 the default, following the same base shift that vLLM made in April. Two major engines moving their build defaults in the same window is a strong signal that the ecosystem is consolidating on that base. Teams should plan their driver and image upgrades around it, because the base change is the largest single source of upgrade risk in this period.

Treat a preprocessing change as a data migration, not a release detail.

The GGUF support also matters for the series. Local runners that accept arbitrary community formats widen the set of models a developer can run, and they widen the set of quantization schemes in use. Every quantized model is a small experiment in accuracy, and local users rarely run the evaluations that teams run. The eviction policy is the storage counterpart of the pluggable policy in vLLM's offload. Once a storage backend evicts, the master must learn about it, or lookups will point at blocks that no longer exist. Batch notification keeps that consistent without a chatty protocol.

A cache store that lives across many machines has a consistency problem that a single engine does not. Blocks come and go, and the index must reflect that. Time-to-live flags are one answer, because they bound how stale an entry can be. Eviction notifications are another. Together they keep the index honest without requiring every lookup to verify the block exists, which would cost a round trip per lookup.

Concepts this month adds

May adds three concepts. The first is the hybrid allocator. Models with mixed layer types need memory managed per layer type, because the lifetime of state differs by layer. The allocator becomes a policy engine that understands sliding windows, full attention, and state-space layers, and it decides what to keep and what to move. This is the memory counterpart of the hybrid model architectures that are now common.

The second concept is accepted-token accounting. Speculation produces tokens in bursts and discards some of them, so any feature that counts tokens must count accepted tokens only. Budgets, stop conditions, and logprob requests all depend on this accounting. It is a small detail in the code and a large one in the product, because a wrong count shows up as a wrong answer length.

The third concept is locality recovery. Disaggregation separated phases and lost cache locality. Decode-side radix caching restores it. The pattern repeats across the series: a separation creates a cost, and a later release recovers the lost benefit inside the new structure. Teams should expect this cycle, and should measure each separation with its full cost, including what it breaks.

What to check this month

  1. Pin the allocator and offload configuration explicitly. If you use a hybrid model, record which allocator, eviction policy, and offload tier are active, so a future default change is visible.
  2. Test thinking budgets with speculation on and off. Use a fixed seed and compare stop behavior and accepted-token counts.
  3. Check the C++20 and Transformers v5 requirements. Source builds and older Transformers pins will break on vLLM v0.21.0. Test the build pipeline before upgrading.
  4. Verify the driver version for llm-d and CUDA 13 images. Driver 580 or later is required for the llm-d CUDA 13.0.2 images.
  5. Run long-output tests for cache quantization. Compare identifiers and facts across long generations before enabling a quantized cache.
  6. Re-check decode-side caching hit rates. After moving to a disaggregated layout, measure whether shared prefixes are reused on decode workers.
  7. Treat the embedding preprocessing change as a migration. If your embedding inputs changed case handling, plan a re-embed and compare retrieval quality before and after.

Frequently asked questions

Should I turn on KV cache quantization for everything?

No. Start with the tasks where long-output fidelity matters least, measure drift on each, and expand only after the tests pass. Identifier-heavy tasks need the strictest checks.

Does a hybrid allocator help pure transformer models?

Less. Its benefit comes from mixed layer types. A pure full-attention model still gains from offload policy, but the allocator's sliding-window logic has little to act on.

Is it safe to run two local engines in one runner?

It is convenient, but test each model on each engine you expect to use. The same model name can produce different results across engines, and reproducibility depends on knowing which engine answered.

Why does a default change matter so much?

Because most deployments never set the flag, so a default flip changes their behavior without any code change on their side. Read the default diff for every upgrade, and pin the settings that matter to you.

Common mistakes this month

The first mistake is tuning the memory system without measuring the layer mix. A team that does not know how much of its cache belongs to sliding-window layers will guess at the allocator's benefit, and the guess is often wrong in one direction or the other. Count the layer types first.

The second mistake is counting drafted tokens against user-facing budgets. The user sees accepted tokens. Any budget or stop logic should use the same count, and a test should confirm it under speculation.

The third mistake is upgrading drivers as an afterthought. The llm-d change makes the driver a hard requirement. A cluster with mixed drivers will fail on the nodes that were not upgraded, often in the middle of a rollout.

The fourth mistake is treating eviction as invisible. A storage backend that evicts without notifying the index will serve stale pointers. Verify that your storage layer's eviction notifications and time-to-live settings match your lookup pattern.

The fifth mistake is quantizing the cache and checking only short prompts. Drift accumulates over long outputs. A short benchmark can pass while a long answer drifts, so include long-output cases in every quantization test.

The month the engine learned to lose a GPU

Most inference engineering writing assumes that every GPU in the deployment stays healthy. Real clusters do not behave that way. A GPU can fall over in the middle of a request, a host can drop off the network, or a memory error can take one worker out while the others keep running. In a dense model served with tensor parallelism, losing one GPU usually means losing the whole replica. In a mixture-of-experts model, the picture is different, because the experts live on different GPUs and the failure touches only the experts on the lost device.

SGLang's v0.5.10 entry on elastic expert parallelism addresses exactly that case. The notes say that when a GPU fails, the system redistributes expert weights and keeps serving without a full restart. That is a shift from treating failure as a restart event to treating it as a degraded mode. The blog post the notes link describes the design in more detail, and the core idea is that the router and the expert placement can be updated while traffic continues.

Partial failure tolerance is also a cost decision. A full restart of a large MoE deployment can take many minutes, including weight loading and warmup. During that time every request either queues or fails. A degraded mode that serves at reduced capacity trades a drop in throughput for continuity. Whether that trade is worth it depends on your traffic, your service level commitments, and how often failures happen. A team with stable hardware may never use the feature. A team running a large fleet on mixed hardware probably will. In either case, the first step is to know how the system behaves today when a GPU disappears, because most teams have never tested it on purpose.

Zero-bubble overlap for speculative decoding

In January, asynchronous scheduling overlapped the CPU bookkeeping for step N plus one with the GPU work for step N. Speculative decoding was the hard case, because the verification result of one step decides what the next step proposes. vLLM v0.19.0 says asynchronous scheduling now supports speculative decoding with zero-bubble overlap. The term zero-bubble means the GPU has no idle gap between the end of one step and the start of the next, at least in the common case where the proposal and verification overlap cleanly.

The notes give no single end-to-end number for this change, only that it significantly improves throughput. Treat that as a direction. The gain depends on how much of the step was idle before, which depends on batch size, proposal cost, and acceptance rate. A method with a cheap proposer and high acceptance has more to gain than one where the proposal is expensive. The right test is the same as in January: profile the gap between kernel batches, then compare throughput with the change on and off for your traffic.

There is also a correctness side. Overlapping steps means some state is computed before the previous step's result is final. The engine has to roll back or discard speculative work when a token is rejected. Any change in that area deserves extra tests, especially for sampling modes that depend on exact token sequences. A correct overlap preserves the output distribution. A subtly wrong one can shift it in ways that only appear under specific sampling settings.

Model Runner V2 gained piecewise CUDA graphs for pipeline parallelism, plus a speculative decoding rejection sampler that supports greedy decoding and log probabilities, and multimodal embeddings for speculation. Each of those closes a gap in the runner that had forced a fallback path. The combined effect is that more of the feature matrix runs on the same runner code, which makes the matrix easier to test.

A general CPU offload for the KV cache

vLLM v0.19.0 added what the notes call a simple yet general CPU KV cache offloading mechanism for its V1 engine, with a pluggable cache policy and block-level preemption handling. In January, the offload idea appeared mostly in the LMCache and Mooncake context, as a separate storage system. Putting a general offload inside the engine changes the design. The engine can decide, block by block, what to keep on the GPU, what to move to host memory, and what to evict when a new request needs space.

Pluggable policy is the important phrase. The policy decides which blocks are cold. A least-recently-used policy is simple and works well when reuse is recent. A policy that accounts for prefix sharing can keep blocks that many requests reference, even if they were last used a while ago. The right policy depends on the traffic. Agent workloads with shared prefixes benefit from policies that protect shared blocks. Chat workloads with unique prompts gain less from any policy and more from simply having enough GPU memory.

Block-level preemption is the other half. When the engine runs out of GPU memory, it can preempt a request, which means pausing it, moving its blocks out, and resuming later. Earlier versions preempted whole requests, which wastes the work done so far. Block-level handling means only the blocks that must move are moved, and the rest of the request keeps its place. That is a fine-grained control over memory, and it reduces the cost of the memory pressure that every long-context deployment eventually hits.

The offload path also connects to the tiering picture from February. The engine's CPU tier is one level in the hierarchy. If the CPU tier fills, blocks can be pushed further to disk or to a remote store through LMCache or Mooncake. An inference team should think of these as layers that can be enabled one at a time. Start with the engine's own offload, measure the hit rate and the added latency on reload, and only add a remote tier when the local tier is saturated.

Concepts this month adds

April adds three concepts. The first is degraded mode. A serving system that can lose a component and keep running at reduced capacity has a different failure model from one that restarts. The key quantities are how fast the system detects the failure, how fast it redistributes work, and how much capacity remains. Those numbers should be part of any capacity plan for a large deployment, because they determine how much headroom you need.

The second concept is the pluggable policy. Cache management is a set of decisions about which blocks stay and which move. Making the policy pluggable means the engine stops hard-coding one answer and lets the operator pick the answer that fits the traffic. The cost is that the policy becomes a configuration surface that must be tested. A policy that works well for one workload can thrash on another, so the choice belongs in the benchmark plan.

The third concept is correctness under overlap. Zero-bubble scheduling, piecewise graphs, and offload all run work earlier or in parallel. Each optimization creates new states that must be consistent. The KV cache corruption fix in TensorRT-LLM is a reminder that consistency bugs are the most expensive ones to find, because they hide behind plausible output. Every overlap feature deserves a correctness test, not only a speed test.

Reading April against March

March was about making features compose. April is about what happens when the composed system meets reality: new model families, partial hardware failures, and storage that has to hold state for long periods. The shift is from "does this work together" to "does this keep working when something goes wrong." That is a more demanding question, and it changes what a good release looks like. A release that adds a feature with a clean test is useful. A release that adds a feature and documents what happens when it fails is more useful still.

The two months also differ in their risk surface. March's risk sat in seams between components. April's risk sits in the edges: the first hours of a new model family, the moment a GPU drops, the boundary where a cache block moves to a slower tier. Edge risks are harder to test in advance because they depend on timing and on the state of the system at the moment of the event. The practical response is to inject failures on purpose, in staging, and watch what the system does. A chaos test that kills one GPU in a replica is worth more than another benchmark.

April also shows a shift in the cadence of model arrivals. Gemma 4 and DeepSeek V4 both landed as engine features within days or weeks of their release. The engine has become a path that new architectures take into production, and the lag between a model release and a usable engine release is now a planning input. Teams that plan around new models should expect a stabilization period of several patch releases, and should budget test time for it.

Finally, April was the first month in this series where correctness fixes were a large share of the headlines. A KV cache corruption fix, a token leakage fix, a streaming parser fix, and an illegal memory access fix all appear in these notes. None of them is glamorous. All of them protect the output a user sees. A team that reads only the performance entries will miss the fixes that matter most for trust in the product.

Latency, tail behavior, and the April features

Averages hide the problems that users feel, and April's features mostly target tail behavior. Zero-bubble overlap reduces idle gaps, which helps most when the system is near saturation, where small stalls compound into queueing delay. Degraded mode keeps the tail from exploding when a component drops, because requests keep moving instead of piling up behind a restart. A pluggable offload policy can protect hot prefixes, which keeps time to first token steady for the requests that reuse them.

When you evaluate these features, measure percentiles, not averages. Track p50, p95, and p99 time to first token, and p95 and p99 time per output token, under a realistic load that includes bursts. A feature that improves the mean by a few percent and cuts p99 in half is a good feature for most products. A feature that improves the mean but leaves p99 unchanged may not be worth the complexity.

Load shape matters too. A steady load test will not show the effect of an autoscaler reacting to bursts, or the effect of a cache eviction during a traffic spike. Build a load profile with at least one burst, one long-context tail, and one period of mixed short and long requests. Run each candidate configuration against the same profile, and compare the tails. That profile is the most useful artifact a team can keep from an evaluation, because it makes next month's comparison fair. Store it in the repository next to the deployment config, version it with the engine release, and reuse it every month. A profile that changes between evaluations makes the results impossible to compare, and a profile that stays fixed turns each release into a measurement you can trust over time.

Tail latency also has a human side. Users notice a response that takes twice as long more than a response that is a few milliseconds slower on average, and they remember the slow ones. A single bad minute during a launch can define how a product feels for weeks, which is why tail targets belong in the same review as cost and throughput targets. A product team that agrees on the tail target in advance, such as p99 time to first token under two seconds, can judge every engine release against that target, instead of arguing about benchmark numbers that answer a different question.

What to check this month

  1. Upgrade the environment as one image. Driver, CUDA, PyTorch, Transformers, and the engine should move together. Test the image end to end before promotion.
  2. Test streaming tool calls with the shipped model. Use the exact model and client you ship. Include partial-token cases such as split numbers and booleans.
  3. Measure zero-bubble gain on your traffic. Compare throughput with speculation overlap on and off, at your batch sizes and acceptance rates.
  4. Pick an offload policy by measurement. Compare hit rate and reload latency across two policies on a replay of real prefixes before choosing a default.
  5. Plan for degraded capacity. If you run large MoE deployments, measure detection and redistribution time under a simulated GPU failure, and size headroom for the degraded state.
  6. Patch TensorRT-LLM to v1.2.1 if you use that line. The KV cache corruption fix is a correctness issue, not a performance one.
  7. Test autoscaling on GPU stages. Watch backlog and GPU utilization together during a batch job, and check whether scale-up lags the queue.

Frequently asked questions

Is degraded mode a replacement for redundancy?

No. It keeps serving when a component fails, at reduced capacity. Redundancy keeps full capacity. For critical services, you still need spare capacity, and degraded mode buys time until the replacement arrives.

Should I enable the CPU offload by default?

Not until you measure reload latency and hit rate on your traffic. Offload trades GPU memory for transfer time. It helps when reuse is high and hurts when the transfers do not pay back.

Is day-zero support safe to ship?

It is safe to test. Day-zero support often needs patch releases in the first weeks, as the Gemma 4 streaming fixes show. Wait for the first stable patch, or run your tool-calling tests before you adopt it.

Does a CUDA 13 default mean I must upgrade the driver?

Check the driver compatibility matrix for your CUDA version before upgrading. The notes recommend a cu129 backend for teams still on CUDA 12.9, which avoids a driver change.

Common mistakes this month

The first mistake is treating day-zero model support as a finished feature. The first weeks after a new family lands are full of parser and template fixes. Build the test suite around tool calls and streaming before the family reaches production.

The second mistake is upgrading the base in pieces. Changing the CUDA version, the PyTorch version, and the engine version in separate steps multiplies the number of combinations you test. Move them together and test the result as one unit.

The third mistake is enabling overlap features without a correctness test. A speed test can pass while the output distribution shifts. Add a fixed-seed comparison against a reference run for any overlap or offload feature.

The fourth mistake is planning capacity for the healthy state only. If a failure drops you to a degraded state that cannot serve peak traffic, the outage happens at peak. Test the degraded state under peak load.

The fifth mistake is ignoring the KV cache corruption class of bug. A corrupted cache can produce plausible wrong answers that no latency dashboard will flag. Patch those fixes first, and keep a small set of golden prompts to catch drift.

The month the runner became the product

In v0.17.0, it reached a set of milestones that were previously missing from it: pipeline parallelism, decode context parallelism, Eagle3 speculative decoding with CUDA graphs, pooling model support, and piecewise and mixed CUDA graph capture. A runner rewrite matters because it sits between the scheduler and the kernels. Every optimization in January and February had to pass through it. Asynchronous scheduling needed the runner to accept a batch before the previous one finished. Pipeline parallelism needed it to pass activations between stages. Speculative decoding needed it to run draft and verify steps as one unit. A runner that handles all of these natively means fewer special cases, and fewer special cases means fewer ways for a configuration to break silently.

Runner rewrites are also hard to see from outside. A changelog line such as "pipeline parallel is now supported" hides months of work on memory layout, buffer reuse, and synchronization. Users see the line. Maintainers see a set of corner cases that had to be closed one by one, and each closed case removes a class of bug that would otherwise surface in someone's production traffic. Reading the release with that in mind helps you value the change correctly, even when the headline sounds modest.

The lesson for a team is to read runner milestones as stability signals. When a runner stops being a list of exceptions and becomes a single path, the features you enable are tested together rather than in isolation. That is the point where a serving stack becomes boring in the good sense, and boring is what a production team wants.

FlashAttention 4 and the kernel generations

FlashAttention is the attention kernel that most modern engines use. The original paper by Tri Dao and colleagues (arXiv 2205.14135) showed how to compute exact attention with far less memory traffic by tiling the computation so the working set fits in fast on-chip memory. FlashAttention 2 improved parallelism and work partitioning. FlashAttention 3 (arXiv 2407.08608, by Jay Shah and colleagues) targeted Hopper hardware with asynchrony and low-precision support. Each generation chased the hardware it ran on, and the gains came from matching the kernel to the memory system and the tensor units of a specific chip.

FlashAttention 4 is the next step in that line, and March's signal is that it reached the point where serving engines could adopt it. The FlashAttention repository published a series of beta releases for version 4.0.0 between March 5 and March 25, labeled fa4-v4.0.0.beta0 through beta6. vLLM v0.17.0 listed FlashAttention 4 support as a backend. Beta releases of a kernel are a normal part of the cycle: the kernel is correct on the tested cases, and the team uses the betas to collect failures on shapes and hardware they did not test.

Why does a new attention kernel matter for an inference team? Attention cost grows with context length, and at long contexts it can dominate decode time. A kernel that moves less data per step or runs its tensor units more fully changes the cost of every long-context request. The catch is that kernel gains are hardware-specific. A benchmark on one GPU generation may not hold on another, and a beta kernel may not cover every head dimension or cache layout your model uses. Check the kernel's supported shapes against your model config before you assume it applies.

The PyTorch 2.10 upgrade in the same vLLM release is related. Kernels are compiled against a specific framework version, and a framework upgrade can change dispatch, compilation, and memory allocation. Teams often treat the framework as a fixed base and the kernel as a plug-in, but the two are coupled. Upgrade them as a pair, test them as a pair, and keep the previous pair available for rollback.

Separating preprocessing from GPU inference

vLLM v0.18.0 introduced vllm launch render, a command for GPU-less preprocessing and rendering. The notes describe it as a way to separate multimodal preprocessing from GPU inference. The idea is simple to state. A vision or audio model needs CPU work before the GPU sees anything: decoding images, resizing, tiling, tokenizing prompts with special placeholders, sometimes running a feature extractor. That work competes with inference for CPU time and memory, and it scales differently from the GPU stage.

When preprocessing lives in the same process as the GPU worker, the two compete for the same host resources. A burst of large images can stall decode for every request sharing the process. Splitting the render stage into its own service lets the team scale CPU preprocessing separately from GPU inference, and it lets a GPU worker spend its time on the parts of the request that need the GPU. The cost is an extra hop and a serialized intermediate representation between the two stages.

The same logic appears in the disaggregation idea from January and in SGLang's EPD work from February. Encoding, prefill, and decode have different resource profiles, and a system that treats them as one unit wastes whichever resource is not the bottleneck at a given moment. Separating stages is a way to match hardware to work. The engineering question is whether the handoff cost is smaller than the idle time you recover, and that depends on request size.

For a team building a multimodal product, the practical check is simple. Measure how much of each request's wall time falls in preprocessing versus GPU inference, under realistic image sizes. If preprocessing is a large share, a render split is worth prototyping. If it is small, leave the stages together and spend the effort elsewhere.

GPU n-gram speculation and the cost of proposing

Speculative decoding has two costs: the verification pass and the proposal step. Methods that use a draft model pay a real forward pass for the proposal. Methods that use n-gram lookup pay almost nothing, because they guess the next tokens by matching recent text against earlier text in the same context. That makes n-gram speculation attractive for workloads with repetition, such as code editing, retrieval answers that quote the source, and structured outputs.

vLLM v0.18.0 moved NGram speculative decoding onto the GPU and made it compatible with the async scheduler. The notes say this significantly reduces speculative decoding overhead. The reason it mattered is that a CPU-side proposal step sits on the critical path. Every decode step waits for the CPU to finish matching before the GPU can verify. Moving the matching to the GPU removes that wait and lets it overlap with the rest of the step, which is the same overlap idea that powered the January async headline.

The useful question is acceptance rate, not raw speed. An n-gram proposer helps only when the next tokens repeat earlier ones often enough that verification accepts several of them. On open-ended creative text, acceptance is low and the method adds overhead. On code diffs and quoted retrieval, acceptance can be high. Measure the accepted tokens per verification step on your traffic before deciding, and keep speculation off for workloads where it does not pay.

LMCache's multiprocess shift and prefetch

LMCache v0.4.0 on March 10 was described by its maintainers as the point where the project matured and shifted toward the multiprocess mode. The release list includes an L2 prefetch controller integrated with the storage manager. Prefetch is the cache equivalent of read-ahead in an operating system. If the system can predict that a block will be needed soon, it can move that block from a slow tier to a fast one before the request asks for it.

The mental model is worth spelling out, because prefetch only helps if prediction is good. Consider an agent that resends a long conversation every turn. The next turn's prefix is almost certain, because it is the previous turn plus new tokens. A prefetcher can warm those blocks from disk or remote storage while the current turn is still generating. For a random one-shot prompt, there is nothing to predict, and prefetch wastes bandwidth. The payoff depends on how predictable the traffic is.

The multiprocess mode itself, which January and February introduced in pieces, is now the main path. Separating the cache manager from the engine means the cache can survive engine restarts and be shared across workers. The cost is coordination: locks, free-list management, and consistency across processes. The v0.4.0 release adds an API for freeing locks in the multiprocess mode, which is the kind of detail that shows where the hard edges are.

Mooncake's March release, v0.3.10 on March 19, adds a related piece. Its notes mention etcd wrapping for master service high availability, and copy and move client support for stored objects. High availability for the metadata service matters because a cache store that loses its master loses track of where blocks are. A cache layer is only as useful as its ability to answer lookups during failures, so the availability work is part of the performance story.

Concepts this month adds

March adds three concepts. The first is the runner boundary. The runner is the code that executes a scheduled batch on the GPU. A runner that natively supports pipeline stages, speculative decoding, and CUDA graph capture is a runner where those features compose. The practical effect is that combinations which used to need special cases become normal paths, and the engine's test matrix shrinks. When you read a runner milestone, ask which special cases it removed.

The second concept is the CUDA graph. A CUDA graph records a sequence of GPU operations once and replays it, which removes the CPU overhead of launching each kernel separately. For decode, where each step runs many small kernels, graph replay can cut overhead a lot. The complication is that graphs need fixed shapes. Piecewise graph capture, which vLLM v0.17.0 extended to mixed batches, captures the parts of a step that have stable shapes and runs the rest eagerly. That balance is why piecewise capture is a common default.

The third concept is prefetch. Prefetch moves cache blocks from a slow tier to a fast one before they are requested. It is the same idea as read-ahead in storage systems, applied to attention state. It works only when the next access is predictable, which is why agent traffic with repeated prefixes is a strong fit and random prompts are not. Measuring predictability, meaning the fraction of blocks that a prefetcher would have guessed correctly, is a cheap way to decide whether to turn it on.

Reading March against February

February asked whether a feature was supported. March asked whether the supported features work together. That shift is the signature of a maturing stack. In February, a team could enable async scheduling with pipeline parallelism and find that it was a supported combination. In March, the question became whether that combination still holds when the runner also handles context parallelism, speculative decoding with CUDA graphs, and a new attention backend. Composition is harder to test than any single feature, and it is where the bugs that matter most tend to live.

The two months also differ in where the risk sits. February's risk was mostly in coupling between stages: a stall in one place showed up in another. March's risk is in the seams between components that were built separately. A new attention kernel must agree with the cache layout. A new speculation path must agree with the async scheduler. A render split must agree with the request format the GPU worker expects. Each seam is a place where a version bump can change behavior without a single line of your code changing.

The practical response is to test by composition. Pick the three or four configurations that matter most to your product, such as a long-context chat route, a speculative code route, and a multimodal route, and run each one through an upgrade before rolling it out. A matrix of two or three configurations catches most of what a full sweep would catch, at a fraction of the cost. It is also easier to explain to the rest of the team, which keeps the test plan alive.

March also shows a shift in who the features serve. Several entries, including the render split, the gRPC route, and the Ollama MLX preview, widen the set of places inference can run. A server, a laptop, a sidecar preprocessing service, and a gRPC client are all now first-class targets. That widening means a team's definition of the serving stack is growing. The useful habit is to write down, for each route, where inference runs and which engine version it uses, so the picture stays accurate as the set grows.

Finally, March rewards teams that read the candidate and beta notes. The TensorRT-LLM candidates that preceded v1.2.0, and the FlashAttention betas, told a story months before the stable releases. Teams that followed those notes arrived at March with a tested plan. Teams that waited for the stable tag had to do the testing under deadline. The cost of tracking pre-releases is attention, and the return is time.

Scale and cost, revisited

The worked memory budget from January still applies in March, but the inputs move. Kernels like FlashAttention 4 change how much time each token costs, not how much memory it occupies. Cache tiers and prefetch change where the blocks sit, which changes how much GPU memory the cache needs to hold. Speculation changes how many tokens each verification step yields. Each of these moves one term in the cost equation, and the cost per million tokens depends on all of them together.

A simple way to keep the picture honest is to track three numbers each month: GPU memory used for cache, tokens produced per GPU-second at your target latency, and the share of requests served from a warm cache. When a release claims a speedup, check which of the three it moved. A kernel that speeds up attention should move tokens per GPU-second. A cache change should move the warm share. A speculation change should move tokens per verification step. A release that moves none of your three numbers is worth reading, but it is not worth a rollout by itself.

Cost also depends on idle capacity. A faster engine on an underutilized fleet saves little, because the fleet was already waiting on traffic. The gains from March's kernels and runners pay off most on busy fleets, and on fleets where autoscaling keeps replicas warm. For a small deployment with bursty traffic, the bigger lever may be keeping cold starts short, which connects back to the cache warmup point from February.

There is also a quality side to cost. A cheaper token that is wrong is not a saving. Speculative methods preserve the target distribution when verification is correct, but any approximation in a kernel or a sparse path can shift outputs. If your product depends on exact answers, measure quality on the same tasks before and after a change. A cost reduction that moves quality is a tradeoff, and it should be accepted explicitly, not discovered later.

  1. Test FlashAttention 4 on your shapes. Confirm the head dimensions, GQA ratio, and cache layout in your model config are covered by the kernel before enabling it. Run long-context quality checks, not only speed.
  2. Upgrade framework and kernel as a pair. If you move to vLLM v0.17.0, plan the PyTorch 2.10 change together with any kernel change, and keep the previous environment ready for rollback.
  3. Measure preprocessing share. For multimodal products, record how much wall time goes to rendering before GPU inference. Only split the stages if that share is large.
  4. Measure acceptance for n-gram speculation. Count accepted tokens per verification step on real traffic. Turn speculation off for workloads where acceptance stays low.
  5. Test disaggregated scale events. If you use TensorRT-LLM disaggregation, test scale-up and scale-down under load. Service discovery failures show up there.
  6. Check prefetch predictability. If you run LMCache, measure how often the next prefix matches the prefetched blocks before tuning the prefetch policy.
  7. Apply the patch releases. Ray 2.54.1 and the vLLM point releases carry fixes. Test them and roll them out on a schedule.

Frequently asked questions

Is a beta FlashAttention kernel safe for production?

Only behind a test gate you control. Betas are for collecting failures across shapes and hardware. Run your own accuracy and long-context tests, and keep the previous kernel available for rollback until the release is stable.

Should I split preprocessing into a separate service?

Only if measurement says preprocessing is a large share of request time under realistic inputs. The split adds a hop and a serialized handoff, which costs time, so it has to pay for itself.

Does n-gram speculation help chat assistants?

Usually less than it helps code or quoted retrieval, because open-ended text repeats less. Measure acceptance on your traffic. If acceptance is low, the overhead can exceed the gain.

Is the MLX preview a reason to switch local stacks?

It is a reason to test. The preview changes the performance profile on Apple silicon, but it is still a preview. Compare on your own tasks and quality bar before moving a workflow.

Common mistakes this month

The first mistake is enabling a kernel without checking its supported shapes. A beta kernel that covers most head dimensions may still fall back or fail on the one your model uses, and the fallback can be slower than the old path. Read the supported-shape list before the benchmark, not after.

The second mistake is measuring speculation on the wrong workload. A method that doubles speed on code can slow down chat. Report acceptance and speed per workload, and set the policy per route rather than globally.

The third mistake is treating prefetch as free. Prefetch uses bandwidth and tier capacity. On unpredictable traffic it can evict blocks that would have been reused, which lowers the hit rate it was meant to raise. Track the hit rate with prefetch on and off.

The fourth mistake is upgrading the framework without the kernels. A kernel built against one framework version may not match a newer one, and mismatches can show up as slow paths rather than errors. Treat the pair as one release.

The fifth mistake is ignoring the patch releases. Teams that defer every patch end up with a large, risky jump later. Schedule patch upgrades on a short cycle, and keep them small.

That third direction is easy to skip, but it matters for anyone who trains and serves the same model. RLHF loops repeatedly generate rollouts from the current policy, then update weights and push them back to the inference engine. Syncing those weights quickly, without restarting the server, turns a multi-minute stall into a short pause. This is a case where the inference engine has become part of the training loop, and the performance questions change: weight transfer time now sits next to decode throughput on the critical path.

The realtime API is a different kind of change. An interactive voice agent cares about time to first audio and about keeping the connection open across turns. A WebSocket route fits that pattern better than repeated HTTP requests, because the server can stream partial outputs and accept new input without a new connection each turn. For an inference engineer, the point is that the request lifecycle is no longer always one prompt in, one completion out. Sessions now carry state across turns, and that state is mostly KV cache.

What SGLang shipped

SGLang v0.5.9 on February 24 had a short highlights list with three entries that matter here. The first is loading LoRA weights concurrently with computation. Adapters are small, but loading them can stall a batch, and the notes report that overlapping the load reduces time to first token by roughly 78% and time per output token by about 35% on large adapters. Those numbers describe the case where the load was a visible stall. If your adapters are already resident, the gain is smaller.

The second entry integrates TensorRT-LLM kernels for native sparse attention in DeepSeek V3.2. The notes say this boosts performance by three to five times on Blackwell with a minor accuracy drop, and they name separate prefill and decode backend flags. The third entry adds FlashInfer's all-to-all dispatcher for mixture-of-experts expert parallelism. Together these show where the engine work is going: specialized kernels per phase, and communication patterns designed for routing tokens to experts.

The sparse attention entry deserves its own explanation, because sparse attention is one of the big themes of 2026 and it changes the cache. In standard attention, each new token attends to every past token. Sparse attention selects a subset of past tokens for each query, using an indexer or a fixed pattern. That lowers the compute for long contexts, but it does not remove the need to store the whole cache. The kernel reads only the selected entries. So the performance win comes from the attention step, while the memory budget from the worked example still applies. A team should expect sparse attention to change compute cost more than memory cost, and should measure both.

Concept: sparse attention and the cache layout

Dense attention has a simple cost model. For a context of length L, each new token does work proportional to L, so long contexts get slower to decode as they grow. Sparse attention attacks that slope. If each query reads only k selected past tokens, decode work per step is proportional to k instead of L. For very long contexts, that difference is large.

The hard part is selection. The model has to pick which past tokens matter for the current query, and the selection itself costs something. Methods differ in how they choose, from fixed windows and block patterns to learned indexers that score past blocks. What they share is a need for the kernel to gather scattered cache entries rather than read one contiguous region. That gather pattern is harder to make fast on GPUs, which is why kernel support arrives as a separate integration with its own tuning, rather than as a flag that works everywhere.

For the memory side, nothing about the sparse selection removes the need to keep past keys and values. An indexer usually needs its own small structure, and the main cache stays in GPU memory or gets offloaded. So a long-context deployment still has to budget for the full cache, even if each step touches only part of it. This is why sparse attention is often paired with the offload and tiering ideas covered in January. The cache is large, reads are selective, and the system needs to keep cold blocks somewhere cheaper until a query needs them.

The accuracy caveat in the SGLang note is important. Sparse selection can drop tokens the dense model would have used, so output can shift slightly. A minor accuracy drop is acceptable for some products and not for others, such as legal or medical extraction. The right test is an evaluation on your own tasks, with long-context recall measured explicitly, rather than trusting a single benchmark score.

The fleet layer: llm-d v0.5.0

llm-d is a Kubernetes-native project for serving LLMs across a cluster, and its v0.5.0 release, dated February 3 in the notes, sets its core objectives in one line: reproducible benchmarking, scaling the KV cache, autoscaling improvements, and a better metrics and tracing story. It also made breaking infrastructure changes, upgrading the Gateway API, Istio, and KGateway versions. The release reads more like a platform maturity milestone than a single feature.

The reason this matters for inference is that a serving cluster has a different bottleneck from a single engine. A single engine's limit is its GPU memory and scheduler. A cluster's limit includes how requests are routed, when new replicas start, and how much cache each replica holds. Autoscaling a model server is harder than autoscaling a stateless web service, because a new replica starts with an empty cache and serves its first requests slowly. Scaling the KV cache across replicas, and routing requests to replicas with useful cache, reduces that cold-start penalty. This connects directly to the cache-aware routing theme from January.

Reproducible benchmarking is the least glamorous objective and possibly the most valuable. A cluster benchmark depends on the gateway version, the engine version, the model, the traffic shape, and the autoscaler's timing. If any of those changes between runs, the numbers are not comparable. A project that makes benchmarks reproducible is making it possible for teams to trust a comparison. When a release says it targets reproducibility, read that as a signal that the team expects users to make decisions from measurements.

Concept: the KV cache as a shared service

In a single engine, the KV cache belongs to the engine process. In a cluster, it becomes something closer to a shared service. Mooncake's February release, v0.3.9, shows that direction. Its notes list fixes to the offset allocator, a feature that enables Ascend fabric memory mode in the store, support for batch publish with tensor-parallel awareness, and documentation for a dummy client that lets SGLang's hierarchical cache use the store. Those are storage-layer details, but they point to one idea: cache blocks are moved, published, and looked up across processes and machines.

LMCache v0.3.14 on February 17 contributed a related piece. Its notes mention a new L1 manager for the multiprocess storage manager. A multiprocess design separates the cache manager from the engine process, so several engine workers can share one cache layer. That separation has costs. Every lookup crosses a process boundary, and the manager must handle concurrency and eviction across all of them. The benefit is that cache survives individual worker restarts and can be shared, which matters when a fleet scales up and down.

The mental model is a hierarchy. The hottest blocks live in GPU memory, next in CPU memory, and then on local or remote storage. A lookup goes down the hierarchy until it finds the block, and a hit at a lower tier costs more time than a hit at a higher one. Good systems keep the most reused prefixes near the GPU and push the long tail down. The right policy depends on reuse distance, which is the time between uses of the same block. Long reuse distances favor cheap storage, short ones favor memory.

Data pipelines and model servers both scale on demand, and when a data stage starves the GPU stage, the GPUs idle while the cost keeps running. Concepts this month adds

February adds three concepts to the January set. The first is the LoRA loading stall. A LoRA adapter is a small set of low-rank weight matrices that customize a base model for a task or a customer. Serving many adapters on one base model is attractive, because the base weights are shared and each adapter is cheap. The cost appears when an adapter is not already in memory. Loading it blocks the batch, which hurts the latency of every request sharing that batch. Overlapping the load with computation hides the stall, which is why the SGLang reduction in time to first token is large for large adapters.

The second concept is the reinforcement learning weight sync. Training and serving share a model, and the serving engine must receive new weights after each update. Syncing through a fast collective path, and allowing the engine to pause and resume, means training and generation can alternate without rebuilding the engine. The bottleneck moves from load time to transfer time, and the transfer uses the same interconnect as tensor parallelism. Teams running RL loops should measure sync time as a first-class metric, because it sets how often the policy can update.

The third concept is speculative decoding generalization. Eagle3 support for new architectures shows the technique is spreading across model families. The principle is the same as in January: a cheap proposer and a parallel verifier. The practical question is acceptance rate on your traffic, which depends on how well the draft head has learned the target model's distribution for your prompts. A draft head trained on general text may underperform on code or on domain text.

Reading the month as a set of tradeoffs

February's releases share one pattern: each gain was bought with a new kind of coupling. Async scheduling with pipeline parallelism couples two stages that used to be independent, so a stall in one stage now shows up in the other. Sparse attention couples the attention kernel to a selection step, which means a bug in the indexer can look like a model quality problem. Cache tiers couple latency to reuse patterns, so a traffic shift can make a previously fast tier slow without any code change. Autoscaling with shared cache couples replica count to cache state, so scale events have a lagging effect on performance.

Reading an engine release well means asking what got coupled. The question tells you where to look when something breaks. If a pipeline-parallel deployment slows down after an upgrade, the first suspect is the overlap between stages, not the model. If sparse attention drifts on a long-document task, the first suspect is selection quality on that document type, not the decoding loop. If a cache-backed fleet slows during a traffic spike, the first suspect is cold replicas, not a regression in the router.

Tradeoffs also differ by team size. A large platform team can absorb the complexity of tiered caches, multiprocess managers, and sparse kernels, because it has people to tune and monitor each layer. A small team gains more from the simpler path: keep the default scheduler, use the engine's built-in prefix cache, and skip the offload tier until the numbers justify it. The right stack is the smallest one that meets your latency target, and February's features are mostly useful once that target is hard to meet.

The release cadence itself is a tradeoff. vLLM and SGLang both shipped monthly-scale feature releases, and TensorRT-LLM ran a long candidate train. Faster cadence brings fixes sooner and forces more frequent upgrades. Slower cadence means fewer upgrades and longer waits for fixes. The honest answer is to pick a rhythm your team can test, then hold to it.

Operational notes for a February upgrade

If you run an engine in production and plan to move to a February release, a few operational steps reduce surprises. Start by diffing the defaults. The vLLM v0.16.0 scheduler path is now supported with pipeline parallelism, which means a configuration that previously kept it off may now turn it on in a new version, depending on how your flags are set. Read the diff of default values for your engine version, not only the list of new features.

Next, rebuild your cache expectations. A version change can alter eviction behavior or cache layout, so the hit rate you measured last month may not hold. Run a replay with the same prompts before and after the upgrade. A stable hit rate is the sign that the change is safe; a drop means investigate before rolling out.

Then check the adapter path if you serve LoRA. The SGLang overlap change reduces stalls on large adapters, but the gain depends on loading the adapter during compute. If your deployment loads adapters on demand from remote storage, the overlap helps, but storage latency still sets a floor. Measure cold load time from your actual storage, not from a local disk.

Finally, keep a rollback plan. Engines ship patch releases frequently, and a rollback path should name the exact previous version, the config file that worked with it, and the test that proves the rollback is healthy. The point is to make rollback boring, so the team uses it without debate when a metric moves the wrong way.

What to check this month

  1. Re-test async scheduling with pipeline parallelism. If your deployment uses pipeline parallelism, the v0.16.0 note makes it a supported path. Run your own throughput and time-per-output-token test with your parallel layout before and after.
  2. Measure adapter load time. If you serve LoRA adapters, record how long a cold adapter load takes and how often it happens. If the stall is visible in p99 latency, overlapping loads is the fix to evaluate.

Frequently asked questions

Does a fully supported async scheduling path mean I should turn it on everywhere?

Supported means the team tests it and considers it safe for that configuration. It does not mean it wins for every workload. Keep the default unless your own test shows a regression, and keep the escape hatch ready.

Are sparse attention kernels safe to use for accuracy-sensitive tasks?

Only after you test them on the tasks that matter. The note reports a minor accuracy drop, and the size of that drop varies by task. Long-context recall and your own evaluation set are the right gate.

Why does a cluster release mention benchmarking?

Because a fleet decision needs repeatable numbers. A benchmark that cannot be reproduced across gateway and engine versions cannot guide a scaling or purchasing decision, so reproducibility is a feature in its own right.

Is Ollama now a production serving tool?

It is a strong local runner and a launcher for agent tools. For multi-tenant production serving, the usual engines in this series remain the reference, but Ollama's direction matters for developer workflows and for understanding agent-shaped traffic.

Common mistakes this month

The first mistake is treating a percentage gain as a property of the engine instead of the setup. A 30 percent gain on a pipeline-parallel test with long prompts is a fact about that test. Your deployment may have shorter prompts, a shallower pipeline, or a different request mix. The fix is to reproduce the setup before budgeting for the gain.

The second mistake is evaluating sparse attention with perplexity or a single benchmark score. Those measures can hide the failure mode that matters, which is missing a specific fact buried deep in a long context. Recall tests at multiple depths expose it directly.

The third mistake is scaling replicas without accounting for cache warmup. A new replica with an empty cache serves its first requests slowly, and if the autoscaler reacts to queue depth alone, it may keep adding replicas that never catch up. Warm the cache, route to warm replicas, or scale on a metric that reflects cache state.

The fourth mistake is ignoring the cost of weight sync in RL loops. Teams often measure generation throughput and forget that every policy update pauses generation. The sync time caps how often the policy can improve, so it belongs on the same dashboard as tokens per second.

The fifth mistake is pinning a release candidate because its notes look good. Release candidates change, and the cache manager in a candidate may behave differently from the one in the final release. Test the candidate you deploy, and rerun the test when the candidate becomes stable.

Theme 1: stop the GPU from waiting for the CPU

To see why asynchronous scheduling matters, you need the basic loop of an LLM server. Each step, the scheduler decides which requests run. It builds the batch, launches GPU kernels, waits for the new tokens, and processes the results on the CPU. If that CPU work runs in series with the GPU work, the GPU sits idle during every scheduling pass. For small batches and fast models, that idle time is a large share of each step. The GPU spends real time doing nothing while Python prepares the next batch.

Asynchronous scheduling overlaps the two. While the GPU runs step N, the CPU prepares step N plus one. The result is fewer idle gaps, which shows up as higher throughput and lower time per output token, especially at moderate batch sizes. The gain is largest when the model is fast relative to the Python overhead around it. When batches are huge and the GPU is saturated, little idle time exists to recover, and the gain shrinks.

Overlapping is hard when the next step depends on the result of the current one. That happens in pipeline parallelism, where one stage's output feeds the next, and in some speculative decoding methods, where draft tokens decide what gets verified. This is why the v0.14.0 exclusion list named pipeline parallelism, and why v0.15.0 matters: it removed that exclusion. An engine's async story is always a list of supported configurations, and the list grows release by release.

Check it on your own system: profile one decode step and measure the gap between the end of one GPU kernel batch and the start of the next. If the gap is a meaningful fraction of the step, asynchronous scheduling is directly relevant. If the gap is tiny, the feature will barely change your numbers.

Theme 2: send each request where its cache already lives

The SGLang gateway release is a clean example of routing treated as a cache problem. A single engine caches the prefixes of prompts it has seen. A second request that shares a long system prompt or a document can skip most of its prefill. With one worker, that reuse is automatic. With many workers behind a load balancer, round-robin routing scatters requests across them, and each worker rebuilds the same cache. The hit rate collapses even when the total cache capacity across the fleet is large.

Cache-aware routing fixes this by tracking which prefixes each worker holds and sending requests accordingly. The data structure matters for cost. A radix tree stores shared prefixes compactly, so the router's own memory and lookup time stay small as the number of cached prefixes grows. The gateway's gain is a statement about that data structure. It says nothing about model speed, and you should not read it that way.

A router that trusts an outdated view sends requests to a worker that no longer holds the prefix, and the benefit disappears. Any production deployment should measure the realized hit rate, not the predicted one.

Theme 3: long context forces new parallelism

The SGLang chunked pipeline result and the vLLM pipeline work belong together. A context of one million tokens does not fit on one GPU, and the attention and KV cache for it must be split somehow. Pipeline parallelism splits the model's layers across GPUs, so each GPU holds some layers for the full context. Chunked pipeline parallelism splits the input into chunks that flow through the stages in order, so later stages start before earlier stages finish the whole prompt. The SGLang notes claim close to linear scaling for this case, meaning added stages keep cutting latency roughly in proportion.

Linear scaling is a strong claim, and it depends on the workload. Pipelining helps most when chunks are large enough to keep each stage busy and inter-stage communication is cheap. For short prompts, pipeline overhead can outweigh the benefit. For a team planning long-context serving, the question is whether the scaling holds at the context length and hardware you actually run.

Concepts you need for this series

Every month leans on the same small set of ideas. January touches nearly all of them, so it is a good place to pin them down.

Prefill and decode

An LLM request has two phases. Prefill processes the whole input prompt in one pass and produces the KV cache for every input token. Decode then generates output tokens one at a time. Each step reads the cache and appends one entry. Prefill is compute heavy and parallel across tokens, so it saturates the GPU's arithmetic units. Decode is memory bandwidth heavy and sequential, because each new token needs the whole cache read once. The two phases have different bottlenecks, which is why so many serving optimizations separate them, either by scheduling them differently or by running them on different hardware.

The metrics follow the phases. Time to first token is mostly prefill cost plus queueing. Time per output token is mostly decode cost. When a note says it cut time to first token, read that as a prefill or scheduling improvement. When it says it raised throughput at a fixed latency, the decode path or the batching policy is usually the source.

KV cache and PagedAttention

The KV cache stores the keys and values for every token in the context, so decode does not recompute attention over the whole history at each step. Its size grows with context length, batch size, layer count, and head dimension. For long contexts and large batches it is usually the largest memory consumer during serving, often larger than the weights themselves.

PagedAttention, introduced by Woosuk Kwon and colleagues in "Efficient Memory Management for Large Language Model Serving with PagedAttention" (arXiv 2309.06180), splits the cache into fixed-size blocks managed like virtual memory pages. Before paging, servers reserved a contiguous region per request, sized for its maximum possible length. Most of that memory sat unused on requests that stopped early. Blocks remove the fragmentation and let requests of different lengths share the GPU. Almost every block-level feature in the notes, including prefix caching and the Mamba block-alignment work in v0.15.0, builds on that idea.

Continuous batching

Static batching waits for a full batch to finish before starting another, so short requests sit idle behind long ones. Continuous batching, also called iteration-level scheduling, admits and removes requests at every decode step. It is now the default in every engine in this series. Asynchronous scheduling is a refinement of it: the bookkeeping for that loop overlaps with GPU work.

Prefix caching

When many requests share a prefix, such as a long system prompt or a retrieved document, the KV cache for that prefix can be computed once and reused. Prefix caching is the single-engine version of the routing idea in theme 2. Its benefit depends on how many requests repeat a prefix and on whether the cached blocks survive long enough to be reused before eviction.

Agent workloads fit well. Each turn resends a growing conversation, so most of each prompt repeats the previous turn. One-shot questions with unique prompts gain little. Hybrid models need a different rule, because state-space layers such as Mamba do not have a KV cache that behaves like pure attention. vLLM v0.15.0's block-aligned caching for Mamba states is the fix for that case.

Speculative decoding

Decode is sequential, so each output token normally costs one full pass through the large model. Speculative decoding uses a cheaper proposer, such as a small draft model or a lightweight head like Eagle, to guess several tokens ahead. The large model checks all the guesses in one parallel pass and keeps the ones that match what it would have produced. When verification is done correctly, the output distribution stays the same, which is why this is a speedup and not an approximation. The gain depends on acceptance rate. A proposer that matches the target model's style does far better than one that does not.

Disaggregation

Disaggregated serving runs prefill and decode, or other stages such as the vision encoder, on separate workers. DistServe, by Yinmin Zhong and colleagues (arXiv 2401.09670), is the standard reference for why this helps. Separating the phases removes interference, where a long prefill stalls every decode step sharing the GPU. The cost is moving the KV cache between workers, which is where Mooncake's transfer design comes in. SGLang's EPD work in v0.5.8 applies the same logic to a vision language model's encoder.

KV cache tiers and offload

GPU memory is the scarcest resource, so the cache does not have to stay there. Offloading moves cold blocks to CPU memory, local disk, or remote storage, and brings them back when a prefix is needed again. LMCache is built around this idea. Mooncake treats the KV cache as the central resource of a disaggregated cluster and moves it between machines. The tradeoff is latency: a block fetched from remote storage costs more than a block already in GPU memory. Offload pays when the reuse is high enough to cover the transfer.

A worked memory budget

Concepts stick better with numbers, so take a simple budget. Suppose a model has 32 layers, 8 key-value heads, a head dimension of 128, and stores its cache in 16-bit precision. Each token needs a key and a value per layer, so the cache per token is roughly 2 times 32 times 8 times 128 times 2 bytes, which is about 128 KB. A single request with a 32,000-token context therefore holds about 4 GB of cache. Ten such requests running at once need about 40 GB before counting weights, activations, or fragmentation.

That arithmetic explains almost every design choice in this series. It explains why a server admits requests by free cache blocks rather than by request count. It explains why prefix caching is worth so much: a shared 20,000-token system prompt, if reused, saves its own 2.5 GB on every concurrent request that shares it. It explains why quantizing the cache to 8-bit halves the budget, and why engines add offload when the budget still runs out. When a release note says it reduced memory per request, convert that into tokens per GPU. That is the number that decides your cost per million tokens.

Two details change the arithmetic. Models with grouped-query or multi-query attention store far fewer KV heads than attention heads, which is why modern open models are cheaper to serve per token than their parameter count suggests. Models with sliding-window or sparse attention may cap how many past tokens they keep, which changes the formula entirely. Always run the calculation with the architecture in the model's config file, not with a generic assumption.

How to read a release note

Release notes are written for maintainers and early adopters, and they mix three kinds of information. The first is new capability: a model, a kernel, a flag. The second is behavior change: a default that flipped, a parameter that now errors, a dropped quantization format. The third is limits: an experimental label, an exclusion list, a configuration marked unsupported. Most of the practical risk sits in the second and third kinds, and most of the headlines sit in the first.

A useful habit is to read the breaking changes section before the highlights, and the exclusion list before the feature. The v0.14.0 async scheduling note is a good example. The feature headline says throughput improves without configuration. The exclusion list says pipeline parallelism, the CPU backend, and some speculative decoding methods are not covered. Those two lines together tell you whether the feature applies to your deployment. The headline alone does not.

Benchmarks in notes need the same care. A router microbenchmark measures operations per second on a synthetic tree. An end-to-end benchmark measures tokens per second on a named model and hardware. A claim of 1.5x faster diffusion serving says nothing about text generation. Before you quote a number internally, write down the model, hardware, batch size, and context length it came from. If the note does not say, treat the number as a direction and not a measurement.

Finally, watch for the word "default." Defaults decide what most users run, and they change without much fanfare. When a default flips, the regression surface is every deployment that never set the flag. That is why an upgrade plan for inference engines should always diff the defaults, not only the new features.

Common mistakes this month

The first mistake is benchmarking with synthetic prompts that share no prefix. If every request in your test is unique, prefix caching and cache-aware routing look useless, and the test will undersell the engine in production. Build the benchmark from a replay of real traffic, or at least make the prompt-repetition rate in the test match the production rate. Otherwise you are measuring a different system.

The second mistake is measuring only throughput. A change that raises tokens per second by ten percent while doubling the time to first token may be a regression for an interactive product. Track time to first token and time per output token at the same time, with percentiles, not averages. Averages hide the long tail that users notice.

The third mistake is treating an experimental label as a warning to ignore rather than a schedule to watch. Experimental features often become defaults within a few releases. Teams that run a canary on experimental features catch regressions early, and teams that ignore them get surprised when the default flips during a routine upgrade.

The fourth mistake is assuming a router fixes a cache problem by itself. Cache-aware routing needs workers that actually keep useful prefixes, which means eviction policy and cache size matter too. A perfect router sending traffic to workers with a small or badly evicting cache will still miss. Look at the whole chain: prompt structure, cache size, eviction, routing, and then the engine.

The fifth mistake is ignoring prompt structure. Prefix caching only helps when the repeated part comes first. If the system prompt is placed after a timestamp or a random request ID, nothing before it repeats, and the cache never matches. A small change in prompt template order can move the hit rate more than any engine upgrade. This is cheap to test and easy to forget.

The last mistake is treating a month as a unit of progress on its own. Inference engineering changes in layers. A scheduler change in January becomes useful when a router change in March depends on it. Reading each month alone is fine for orientation, but the real value comes from tracking how the pieces combine over the year. That is why this page keeps every month in one place, newest first, with the same structure, so you can scan the pattern.

What to check this month

  1. Measure your CPU gap. Profile a decode step and check how much time the GPU is idle between kernel batches. If the gap is large, compare throughput with and without async scheduling.
  2. Check your exact combination. If you run speculative decoding with pipeline parallelism, confirm the release notes list your combination as supported. Before v0.15.0 it was on the exclusion list.
  3. Test the strict sampling change. vLLM v0.14.0 makes unsupported sampling parameters fail under speculative decoding. Run your integration tests before upgrading production.
  4. Replay routing on real traffic. Send a day of prompts through round robin and a prefix-aware policy. Compare realized cache hit rates and time to first token, not the router's own counters.
  5. Measure prefix repetition in your agents. Count how much of each turn's prompt repeats the previous turn. That number tells you how much prefix caching and offload can save.
  6. Pin engine versions. Track latest in staging, not production. TensorRT-LLM candidates in particular are still changing.

Frequently asked questions

Is asynchronous scheduling always faster?

No. The gain is largest when CPU scheduling time is a real fraction of each step, which happens at moderate batch sizes and fast models. With very large batches where the GPU is saturated, there is little idle time to recover. Measure on your own workload, and keep --no-async-scheduling in mind if something misbehaves.

Do I need the SGLang gateway for cache-aware routing?

You need some router that tracks where prefixes are cached. The SGLang gateway is one implementation. A simpler version uses consistent hashing on a stable prompt prefix. That needs no tracking state, but it cannot adapt when one prefix becomes very popular.

Should a small team care about any of this?

Yes, mainly for the concepts. A team running one engine on one GPU already gets continuous batching and prefix caching from the engine. Routing and pipeline changes matter once you scale to several workers or very long contexts. The vocabulary also makes the release notes faster to read.

Why does an inference series include Ollama?

Many developers run models locally through it, and its direction shows where local inference is heading. The agent loop in v0.14.0 and ollama launch in v0.15.0 change the workload profile. Agent traffic is many short sequential requests with growing context, which stresses prefix caching more than single-shot chat does.
