September 2026 the runner becomes the only path, two correctness bugs show how silent failures hide, and Ollama adds decision models

Summary: September closed the year with consolidation and with correctness work. vLLM made Model Runner V2 the default for every model, TensorRT-LLM disclosed a silent adapter bug and then removed its AutoDeploy integration, and Ollama added decision models that return scores instead of text.source ↗

The default is also the test

Imagine you are a user of an engine that changes its default. You did not ask for the change. You did not set the flag. Your configuration simply starts running a new path. If that path works, nobody notices. If it has a bug in a corner you depend on, you find out when a customer complains. The default is a test that every user runs whether they want to or not.

This year the defaults flipped one after another. Asynchronous scheduling in January, the newer speculative decoding path in May, the cache manager in August, and now the runner for every model in September. The September flip is the broadest, because it covers all models rather than a subset. When a runner becomes the only path, every bug it hides becomes a bug every user can meet. That is why a month's known-issue lists matter as much as its feature lists.

The practical advice is simple. Treat each default as a moving target. The configuration you tested in March is not the configuration the engine runs by default in September. A quarterly review of defaults, with a short list of the settings that matter to your product, catches silent changes before an incident does.

One runner for every model

vLLM v0.29.0, released September 9 with 594 commits from 277 contributors, finished the rollout of Model Runner V2 to all models.source ↗ The runner had first become the default for dense models in July, and for pooling models earlier. This release added kernel.">CUDA graph memory profiling for automatic decode does not recompute attention over the whole history.">KV cache sizing, which means the engine measures how much memory its graphs need rather than guessing. It also added batch-sharded sampling.

Batch-sharded sampling is worth a moment, because it shows the memory budget from January reaching into a part of the pipeline most people never think about. At every step, the engine computes a score for every possible next token, for every request in the batch. For a large vocabulary and a large batch, that table is big. When the model runs across several GPUs, sharding the sampling across them divides the table per device. The memory saved goes back to the cache, which is where capacity always ends up.

vLLM v0.30.0, released September 22, was the largest release of the year, with 762 commits from 315 contributors. It added DeepSeek-V4.1-Flash, which the notes describe as storing its whole KV cache in the MXFP8 block format on SM100 hardware. A low-precision cache is a memory win with a quality question attached, so it should be tested the way the May quantization checks were. The same release added a CPU backend for DeepSeek V4 with vectorized sparse attention kernels, and GLM-5.3-Flash with expert load balancing.

Bugs that do not crash

Some bugs announce themselves. A server crashes, an error rate spikes, a dashboard turns red. Others are quiet. TensorRT-LLM's September candidates included two of the quiet kind, and they are worth reading slowly.

The first, in rc26 on September 9, disclosed that LoRA adapters targeting the routed experts of Qwen3 mixture-of-experts models were silently ignored. The output came back as the base model's answer. Adapters that targeted attention layers behaved correctly, which made the bug harder to spot. A customer with a tuned adapter gets the generic model, and nothing in the logs says so. The defense is an adapter-level test that compares the adapted output against a known-good reference, run on every deployment of the adapter, not only the first.

The second bug is the opposite kind of problem. The same notes said the V2 KV cache manager could refuse to start with an insufficient-memory error, even while enough GPU memory was free, because its size estimate was too conservative. The server does not run, and the message suggests a capacity problem. A team that responds by buying more GPUs has paid to fix a guess. The useful response is to measure free memory after a startup, compare it with what the estimate predicted, and set an explicit cache size if the guess is consistently off.

Removing the AutoDeploy path

TensorRT-LLM v1.3.0rc29, released September 29, removed the AutoDeploy integration and its public entry points.source ↗ This was a breaking change, and it came two months after July's deprecation notice. A project that gives that much warning is being careful, and a team that was watching the notices had time to plan. A team that was not watching finds its deployment failing at the next upgrade. The lesson from June applies again: list the backends and integrations you use, and map each one to its replacement before the removal lands.

The same candidate listed many model items, including a fix for Qwen3.5 checkpoints with global FP8 scales, a vision rotary change for Gemma 4 that avoids a matrix multiply, and extended piecewise CUDA graphs for MiniMax-M3. That breadth tells you how much of the runtime is now shared across model families.

A very large model with a small active set

SGLang v0.5.19, released September 5, brought 786 pull requests from 214 contributors.source ↗ Its headline model was Qwen3.8, listed at 2.4 trillion total parameters with 95 billion active per token. The naming teaches a lesson. The active count sets the per-token compute, and the total sets the memory needed to hold the weights. A model like this is a memory problem first and a compute problem second.

That raises a serving question: where do the weights live? A model too large for one node must be split across nodes, and the cost of moving expert outputs between nodes becomes the limit. Offloading cache to host memory helps, but weights that every token reads cannot sit in slow memory. The memory budget from January now applies to the weights as well as to the cache.

SGLang v0.5.20, released September 18, brought 713 more pull requests and added GLM-5.3-Flash and Tencent's Hy4-Preview. The release notes read more like a model catalog than a feature list. For an engine, the useful question is which models it supports well on your hardware, and how quickly new models arrive after release.

Scores instead of sentences

Ollama v0.35.0, released September 28, introduced decision models behind a new endpoint.source ↗ The notes say the endpoint is based on the Jev API from TypeSafe. A decision model does not write prose. It returns choices, probabilities, and scores. The examples are ticket triage, model routing, and content classification. Two models are listed, Nimble from Bespoke Labs and Tev1 from Together AI, and both are pulled like any other Ollama model.

The cost profile is different from a text generator. A generator writes a long sequence token by token, and its cost grows with the answer. A decision model returns a short structured result, closer in cost to a single forward pass. That makes it practical to run a cheap decision in front of an expensive generator, which is a common pattern for cost-sensitive products. Returning scores also lets the caller set thresholds and log them over time, which a text answer does not allow without parsing.

A score is useful only if it is calibrated. Calibration means that a score of 0.8 is right about 80 percent of the time on your data. Uncalibrated scores look precise and mislead. The endpoint gives you the number. It does not tell you whether the number means what you think on your traffic, so test that before you set a threshold.

Ollama's September patches continued. v0.33.3, on September 2, added image and audio input for Gemma 4 on the MLX engine, reported cached prompt tokens, and honored defaults stored in GGUF files. Reporting cached tokens is a small change with a large effect, because it makes the prefix cache's benefit visible to the application for the first time.

Boring, on purpose

llm-d v0.10.0, released September 29, set its themes in plain language: operational hardening, which means rollouts, high availability, and failure behavior operators can trust, and production readiness, which means moving the flagship paths from working to default.source ↗ In infrastructure, boring is a compliment. A boring deployment is one where a rollout does what it says and a failed node is replaced without a page.

The release also moved changes upstream into the engine projects, which reduces the cost of maintaining forks. That ties the fleet layer more closely to the engine, so the two should be upgraded as a pair, as the earlier months recommended for kernels and frameworks.

Connectors and a DeepEP upgrade

LMDeploy v0.17.0, released September 1, integrated DeepEP v2, a communication library for mixture-of-experts dispatch, and added Kimi K2.6 support on its PyTorch path.source ↗ It also added a connector for the Mooncake store, so LMDeploy can use the same storage layer as vLLM and LMCache. A shared storage standard makes it easier to move a cache between engines.

A faster MoE combine

llama.cpp published a build on September 1 with a CUDA change that fuses the weighted sum of mixture-of-experts outputs into one kernel.source ↗ The commit message explains the mechanism. The combine step used to write each weighted expert output to global memory before summing them, and that traffic was the main cost. The fused path runs one kernel where the baseline ran two. Decode is limited by memory traffic, so removing a round trip through global memory helps on every layer of every token. For local users on consumer GPUs, that can be the difference between usable and not.

FlashAttention 4 reaches beta 33

The FlashAttention repository published fa4 betas 29 through 33 in September, the last on September 30.source ↗ Beta 29 sped up mask generation on SM100 hardware. By the end of the month, the fa4 line had run for most of 2026 without a stable tag. A kernel that must serve many shapes, hardware generations, and precisions takes a long time to harden, and teams that adopted it early should keep their own test matrix of shapes until a stable tag is out.

Parallel diffusion fixes

xDiT released 0.6.0 on September 1 and 0.7.0 on September 25.source ↗ The 0.7.0 notes are mostly bug fixes, including a timing correction. Performance measured across several ranks is wrong if each rank starts its clock at a different moment, because the slowest rank sets the real finish time. Taking the start of all ranks into account corrects the number, and a benchmark that ignored it would overstate some speeds.

A quiet month for Ray

Ray had no release in September. The last changes were in August. A quiet month is a window to test the August release in staging, because the next release will bring new changes and the August behavior is the baseline to compare against.

The concepts September adds

September adds three ideas to the set, and each one is easy to get wrong.

The first is calibration. A decision model is only as useful as its scores are honest. Test calibration before you set a threshold, because a score can rank well and still be miscalibrated.

The second is the latency metric, such as an ignored adapter. Only an end-to-end check against a known-good reference catches it.">silent failure. A silently ignored adapter does not show up as an error rate or a latency change. The defense is an end-to-end check against a reference, kept current as the engine changes.

The third is the active parameter count. A model with 2.4 trillion parameters and 95 billion active is a memory problem and a compute problem measured in different units. Plan from both numbers.

What to check this month

  1. Test LoRA adapters end to end. Compare adapted output to a known-good reference on every deployment.
  2. Check cache sizing after startup. Measure free memory and set an explicit cache size if the estimate is off.
  3. Plan the AutoDeploy migration. The removal is in rc29, so verify your replacement before the next stable release.
  4. Calibrate decision scores before using thresholds. Check the scores against outcomes on your data.
  5. Log cached prompt tokens. Track the prefix cache's benefit per request.
  6. Upgrade the fleet layer with the engine. Plan them as a pair.

Frequently asked questions

Is a runner that handles every model the same as a faster runner?

Not necessarily. It is more uniform, which means fewer special cases and fewer silent fallbacks. Speed depends on the model and hardware, so test speed on your models and correctness on your adapters.

Does a decision model replace a classifier?

For some tasks, yes. It returns structured scores, as a classifier does. Whether its training matches your labels is something only your own data can answer.

August 2026 Kimi K3 arrives on day zero, routers start reading cache state, and a cancelled request keeps its progress

Summary: August was the month the cache became shared state. Ray Serve LLM completed routing that reads the cache, Ollama made cancelled prefills resume instead of restarting, and SGLang v0.5.17 served Kimi K3 from its first day.source ↗

The cache is no longer a private notebook

For most of this series, the KV cache was a private notebook. One engine process wrote it, read it, and threw it away. A router only needed to know which worker to pick. Over the spring and summer, the notebook was passed around: first to host memory, then to peers, then to shared stores. August shows the next step. The cache became part of the request protocol itself. The router asks what each replica holds. The ingress tokenizes once and hands the tokens along. The engine tells every interested party when a block is created or removed.

That changes who is responsible for correctness. When the cache lives in one process, only that process can get it wrong. When the cache is shared, the router's view, the engine's state, and the client's retries all have to agree. A cancelled request that leaves half a cache entry behind is now a problem for every replica that reads it. A stale router view sends every request routed on it to the wrong place. August's releases are mostly about making those agreements explicit.

A router that reads the cache

Ray 2.58.0, released August 23, completed a feature that Ray 2.57 had previewed: KV-aware routing for Ray Serve LLM. Tokenization now happens once, at the ingress replica, and the tokens travel out of band so the engine does not repeat the work. KV lifecycle events are broadcast to every ingress replica, so each one sees the same picture of who holds what.

The small saving of tokenizing once matters at high request rates, because it happens at the moment a request enters the system. The bigger idea is the broadcast. Several ingress replicas each route requests. If each one has a different view of the cache, they make different decisions, and some of those decisions are wrong. Broadcasting keeps the views in step. The cost is network traffic that grows with how fast blocks come and go. A workload with heavy churn pays more than one with stable prefixes.

Ray 2.57.0, released August 11, made DataSourceV2 the default for reading data, with row-group aware chunking, and replaced the old hash shuffle's aggregator pool with a version that does not need its size guessed up front. That guessing used to cause either wasted capacity or out-of-memory failures in batch jobs.

Remembering how far you got

Picture an agent that is writing a long report. It sends a huge prompt, the prefill starts, and then the user clicks cancel. The engine stops, but the work it did is still in the cache, partly. When the agent retries, a good system resumes from where it stopped. A bad system starts over and repeats all of the work.

Ollama v0.33.0, released August 21, fixed a hang where agent clients cancel long prefills, and it made prefill restore points trustworthy. A cancelled prefill now keeps every restore point it passed, so a retry resumes where it stopped. The notes give a sharp example. On models with recurrent layers, a resumed prefill recorded restore points that did not cover what they claimed. A request that matched 46,000 of 47,000 tokens had to be reprocessed from zero. That is a brutal penalty for a near-complete match, and it only appears when clients cancel and retry, which agent clients do often.

The lesson is about what a promise in a cache means. A restore point claims that the state is complete up to a token. If the claim is false, the system must recompute, and in the worst case it recomputes everything. Making the claim true by construction means a point is recorded only when the state behind it is complete. The release also added a Claude Desktop setting that lets the app use Ollama as a third-party gateway, which shows the runner becoming a gateway for other tools.

Kimi K3 on its first day

SGLang v0.5.17, released August 8, described Kimi K3 support on day zero.source ↗ The model has about 2.8 trillion parameters and a latent mixture-of-experts layout with 896 experts, using the top 16 for each token. It handles a one-million-token context. Its layer stack mixes 69 linear-attention layers with 24 multi-head latent attention layers, and it has a vision tower. The release says it ships as a native MXFP4 checkpoint.

The layer mix is the most interesting detail. A linear-attention layer keeps a running summary of the past. Its memory does not grow with the conversation. A latent attention layer keeps a cache that grows, but in a compressed form. Mix the two and most of the stack pays a flat cost per token, while only a minority of layers pay a growing one. That is the architectural answer to the memory budget from January. The cache is smaller because most layers do not keep a growing one.

The trade is recall. A fixed-size summary cannot hold every detail, so hybrid stacks keep some full-attention or latent layers to recover specifics from far back. The number of each kind is a design choice that trades memory against recall. Kimi K3's split is one point on that curve, and it is why a recall test at several depths matters more for it than the raw context size suggests.

vLLM v0.27.0, on August 10, brought the full Kimi K3 stack in one release, including Python and Rust frontends. vLLM v0.28.0, on August 26, added Decode Context Parallel for Kimi K3, fused kernels for its linear-attention decode and prefill, and an adaptive speculative token budget. That budget sizes the number of speculative tokens under a shared limit, and the notes credit it with about 60 percent better time to first token under DSpark.

KV cache manager V2 becomes the default

TensorRT-LLM v1.3.0rc25, on August 31, announced that its KV cache manager V2 is now the default for a long list of model families, including DeepSeek V3, V3.2, and V4, GLM-5, GPT-OSS, the Kimi K2 line, MiniMax, Nemotron H, and the Qwen3 line.source ↗ The candidate before it had listed a teardown failure among its known issues, which is a reminder that a default flip usually follows a stretch of known problems being fixed.

The cache manager decides what stays, what gets evicted, and how blocks are reused. A bug there affects output correctness as well as speed. The safe way to adopt the new default is to run the replay and the long-output tests, then compare hit rates and output drift against the old manager before promoting. Keep the old manager available for rollback.

The storage layer keeps moving

Mooncake v0.3.13, on August 26, and v0.3.13.post1, on August 31, fixed several things in its transfer engine.source ↗ One fix corrects a stale status in an io_uring path, which affects how transfers report completion. Another fixes a leak in a request map. Leaks are slow killers. They do not fail a test, but they exhaust memory over days of uptime. The post-release also restored CUDA-free wheels for machines without GPUs.

LMCache v0.5.5 release candidates arrived on August 28 and 31, with builds for CUDA 12.9, ROCm, and Intel XPU alongside the standard wheel. A cache library that ships on several accelerator stacks at once is being treated as portable infrastructure. Test each accelerator path separately, because a wheel can install cleanly and then fail at import time on the wrong stack.

Local builds, every few days

The llama.cpp project sits underneath much of local inference, and its build cadence matters more each month.source ↗ In August it published 38 tagged builds, several of them in a single batch on August 31. The pace reflects an active project shipping small, targeted changes. Local products that use it should pin a build and update on a schedule. Running whatever is current means the output of a model can change between two runs with no change on your side.

Ollama's engine changes track that upstream work, so a local product that uses Ollama inherits a chain of upstream choices it does not control. That chain is worth watching.

Parallel diffusion, briefly

xDiT released version 0.5.0 on August 31.source ↗ The project is a parallel inference framework for diffusion transformers, which spreads one image or video generation across several GPUs. Most of this series covers language models, but the same habits apply: pin the parallel layout, measure the tail, and test on the hardware you will run.

The concepts August adds

August adds three ideas that will be on the exam of every serving team.

The first is the restore point, a promise that a stored state is complete up to a given token. A false promise is worse than no promise, because it forces silent recomputation or silent errors.

The second is the mixed-state cache. Hybrid models hold two kinds of state: a fixed running summary and a growing cache. Each kind needs its own correctness rule, and a prefix hit is only valid when both were captured at the same point. This is the same boundary problem that block-aligned Mamba caching solved in March.

The third is the broadcast churn of shared state. When many routers depend on the same cache, the cost of keeping them in step grows with how fast the cache turns over. Stable prefixes are cheap to share, and fast-changing ones are expensive.

What to check this month

  1. Measure KV-aware routing on your churn. Record hit rate and broadcast traffic at peak churn before and after enabling it.
  2. Test cancellation and resume. Cancel long prefills on purpose and check that the retry resumes from its restore point.
  3. Compare the cache manager defaults. Replay traffic and compare hit rates and output drift before promoting.
  4. Test long-context recall for hybrid models. Speed over a million tokens means nothing if the facts are missed.
  5. Pin local builds. Track llama.cpp and Ollama versions in any local product.
  6. Watch for transfer leaks. Track memory over multi-day runs after upgrading Mooncake.

Frequently asked questions

Is KV-aware routing worth it for a small fleet?

Usually not until you have several replicas and repeated prefixes. With one or two replicas the router has little to choose between.

Does a million-token context mean the model remembers everything?

No. It means the model can accept that many tokens. Recall depends on training and layout, and it must be tested at several depths.

July 2026 the old attention path is deleted, speculation learns to size its own window, and agents move into the command line

Summary: July was the month the engines started deleting their old paths. vLLM v0.25.0 made Model Runner V2 the default for all dense models and removed the legacy PagedAttention implementation, while SGLang v0.5.16 added DSpark, a speculative method that sizes its verification window from the draft's own confidence.source ↗

The month the old road was closed

Every long-running project has a road that everybody still uses, even though a newer road was built beside it. Keeping both open is expensive. Each change to the shared code must be checked against the old road as well as the new one. In July, vLLM closed the old road. Its v0.25.0 release, on July 11, made Model Runner V2 the default for all dense models and removed the legacy decode does not recompute attention over the whole history.">KV cache in fixed-size blocks, like virtual memory pages, so requests share memory without waste.">PagedAttention implementation, because the newer backends are now the standard path.

That sentence can alarm a reader who remembers PagedAttention as the heart of vLLM. It is worth being precise. The idea of managing the cache in fixed blocks lives on in the newer backends. What was deleted is one particular implementation of that idea. A project can only delete code after the replacement has earned its place through months of testing on common setups. The removal is therefore a sign of confidence, and it is also a deadline for anyone whose configuration depended on the old code.

The same release made the Transformers modeling backend as fast as native vLLM, and added FP8 mixture-of-experts support to it. A team can now run a new architecture through the Transformers code and get close to native speed. The native path may still carry model-specific tuning, so compare on the models you actually run.

Sizing the window by confidence

Think of speculation as sending a scout ahead to guess the next few steps on a trail. In the fixed-length method, the scout always goes the same distance, whether the trail is clear or not. If the scout is unsure, the distance wastes effort. If the scout is confident and the distance is short, the group walks slower than it could.

SGLang v0.5.16, released July 25, introduced DSpark, which it describes as confidence-driven speculative decoding. The draft is produced in blocks, and each verification window is sized from the draft's own confidence. A confident scout gets a longer leash, and an uncertain one comes back sooner. The reported result is 383.7 tokens per second at an average accept length of about five, on DeepSeek V4 Pro with tensor parallel 8 on B300 hardware at batch size one.

Batch size one is the best case for speculation, because there is no crowd to share the work with. Treat the number as proof that the mechanism works, and then test it at the batch sizes you actually run. A miscalibrated confidence signal can be worse than a fixed length, because it can send the scout too far when the trail is bad. The hard engineering problem is making that signal cheap and well calibrated.

SGLang v0.5.15, on July 10, had made Spec V2 the default, with zero-overhead scheduling through graph-friendly draft extension and fewer synchronizations between device and host. The same release described GLM-5.2 NVFP4 serving on Blackwell at over 500 tokens per second per user on eight B300 GPUs at batch size one. A post-release on July 14 fixed NaN outputs from a FlashInfer FP4 kernel on long inputs, which is the kind of correctness fix that matters more than any headline latency, or it means little.">throughput.

Reusing text that moved

Normal prefix caching has a strict rule: a cached block only helps if the request starts with exactly the same prefix. But a retrieval system often inserts the same document at a different position in each prompt. The document is the same, the offset is different, and the cache misses.

LMCache v0.5.2, released July 22, brought CacheBlend under vLLM's hybrid memory manager. CacheBlend reuses cached text computed in another context, corrects its position, and recomputes a small part of the cache to keep the answer right. The subtle part is position. A block cached at one offset carries the wrong position if it is reused at another. The release adds support for the two positional schemes that sliding-window models use. Test reused-context answers against a fresh computation before you trust them, because a positional error does not throw an exception. It just gives a slightly wrong answer.

The same release made NIXL an optional install, and it needs vLLM 0.26 or later. Pin the cache library and the engine together, as one unit.

A deprecation with a reason

TensorRT-LLM v1.3.0rc21, on July 15, announced that its AutoDeploy backend is being deprecated.source ↗ The notice gives its reasoning in plain language. The team is working on agent-driven porting to the PyTorch backend, and it cites MiniMax M3 functional support delivered within the first week of that model's release as an early sign. The bet is that porting can become fast enough that a single primary backend covers the need.

That reasoning describes a real tension. Teams want new models quickly, and a backend that loads models without hand-written code is valuable for exactly that. Keeping several backends alive has a cost. The project is betting that the cost of porting is falling, and the next few months of notes will show whether that bet holds.

The command that became an agent

Ollama v0.32.0, released July 11, changed the meaning of its simplest command.source ↗ Running plain ollama now starts an interactive agent that can help with code and delegated tasks, and the example uses a cloud model. The release also renamed the Codex app integration to ChatGPT and simplified how a launch chooses its integration.

The change matters because it changes what a local runner is for. An agent sends a stream of requests with a growing context, tool calls, and sometimes web search. That is the traffic profile of an agent workload, which is full of repeated prefixes. A runner's speed now depends on how well it handles that pattern, not just on single prompts. Ollama's v0.32.5 patch on July 27 fixed an MLX bug that reduced output quality for NVFP4 models, a reminder that quality checks belong in local workflows too.

Prefix hits even when speculating

LMDeploy v0.15.0, on July 31, supported long-context and multi-token-prediction prefix-cache hits.source ↗ Speculation and prefix caching used to interact badly in some engines, because the draft state muddied what counted as a reusable block. Making the hit work for both means a long shared prefix pays off even when speculation is on.

The same release added guided decoding for speculative decoding. Guided decoding forces output into a grammar, such as valid JSON. Combining it with speculation is harder than it sounds, because the grammar has to reject drafted tokens that would be invalid. For structured-output products, the schema validity rate is the number to test, because a broken combination can pass every latency test while producing invalid output.

Moving big blocks across busy links

Mooncake v0.3.12, on July 23, added transport-level work.source ↗ Its notes mention path diversity for RDMA queue pairs through UDP source ports, link aggregation balance, and quality of service with slice spraying for its transfer engine. Spraying splits one transfer across several paths, so a single hot link cannot become the limit.

These changes are invisible to most users, and critical to a cache-heavy cluster. When many machines move large blocks at once, the busiest link sets the speed, and the whole system waits on it. Spreading the traffic keeps tail latency under control, and the benefit is easiest to see under concurrent load, so benchmark it there.

Early warnings from a memory monitor

Ray 2.56.1, on July 17, fixed regressions that the 2.56 release had introduced in Ray Data's conversion to pandas, including an overflow crash and a crash on empty tensor columns.source ↗ It also added early detection of memory pressure on system slices, where the memory monitor takes snapshots of usage. Early detection is valuable because an out-of-memory kill destroys work in progress. A monitor that notices pressure building lets the system shed load or spill data while the work can still be recovered.

The concepts July adds

July adds three ideas that make the stack easier to reason about.

The first is removal as maintenance. A deleted path is a sign that its replacement has earned the default. Treat a removal as a forced migration, and read its notice as carefully as a new feature.

The second is confidence as a control signal. A system that knows how sure it is can allocate work to match. The pattern will appear in batching and cache policy too. The risk is miscalibration.

The third is position in cache reuse. A block is only useful at the position it was computed for, unless the system corrects it. The test is a comparison against fresh computation, not a latency number.

The break-even question

Two kinds of memory in one house

Cache that moves by policy

Splitting the work before the GPU

Picture a multimodal request. A user uploads a photo, and before the model sees a single token, a lot of work happens on the CPU. The cost of guessing

Think of speculative decoding as a student who writes an answer quickly and then has a teacher check it in one pass. The student's guess is cheap. The check is what costs time. If the teacher accepts most of the guesses, the class finishes faster. If the teacher rejects most, the student wasted effort.

For an n-gram proposer, the student is a pattern-matcher. It looks at the last few words, finds the same words earlier in the text, and copies what came next. That works on code diffs and on quoted passages, where repetition is common. It fails on creative writing. The story of a GPU that kept waiting

Picture a busy inference server on a Tuesday morning. Hundreds of users are chatting with a model, and the GPU is the most expensive thing in the room. It should be working all the time. Each wait is short, a few milliseconds, but there are thousands of them every minute, and together they eat a real share of the machine.

That waiting is the story of January 2026. The engineers who build vLLM and SGLang had been staring at profiles like this for years. The GPU was fast. The bottleneck was the loop around it. Every decode step, the scheduler decides which requests run, builds the batch, launches the work, waits for the tokens, and processes the results. Done one after another, the CPU steps and the GPU steps take turns, and the GPU spends a surprising amount of time doing nothing.

The fix is simple to describe and hard to build. You let the CPU prepare the next step while the GPU is still busy with the current one. The engineers call this asynchronous scheduling. On January 20, vLLM v0.14.0 made it the default. Users who saw problems could turn it off, and the release notes listed the setups that were not yet covered: pipeline parallelism, the CPU backend, and some speculative decoding methods. Why this matters more than it sounds

It helps to see the cost in numbers. Suppose one decode step takes 20 milliseconds of GPU time, and the CPU work around it takes 5 milliseconds in series. The GPU sits idle for a quarter of the step. The concepts behind the story

Every month in this series leans on the same small set of ideas, and January touches nearly all of them. Here they are as a story you can follow.

The first idea is the split between prefill and decode. A request arrives with a prompt. Prefill reads the whole prompt once and builds the cache. Decode then writes the answer one token at a time, and each token needs the whole cache read again. Prefill is a sprint through many tokens at once. Decode is a slow walk with a heavy bag. Almost every serving trick is a way to stop the two from fighting over the same resources.

The second idea is the cache itself. The KV cache is the memory of the conversation, and it is usually the largest consumer during serving. A useful way to picture it is a notebook where the model writes a note for every token it has seen. Long conversations fill the notebook fast. The PagedAttention paper, from the team behind vLLM, changed the notebook from one long page per request into small pages that can be shuffled around, much like virtual memory in an operating system. That single change let many requests share one GPU without wasting space.

The third idea is continuous batching. In the old way, a batch waited for its slowest member. A short question sat idle behind a long essay. Continuous batching lets a new request join the batch at the next step, and lets a finished one leave. Asynchronous scheduling is the next refinement: the bookkeeping for that loop now overlaps with the GPU work.

The fourth idea is prefix caching. Imagine a company support bot whose system prompt is two thousand tokens long. Every customer conversation starts with that same prompt. If the cache for that prompt is kept, each new customer skips the most expensive part of the first step. The gain depends on how often a prefix repeats and how long the cache survives before it is evicted.

The fifth idea is speculative decoding. Decode is sequential, so each token normally costs a full pass through the big model. A small draft model proposes a few tokens, the big model verifies them together, and the ones that match are kept. The output is the same as the big model would have produced, so the speedup is real, not an approximation. The gain depends on how often the draft is accepted, which is why its acceptance rate matters more than its raw speed.

A memory budget you can do on a napkin

Let's make the cache concrete. Take a model with 32 layers, 8 key-value heads, a head size of 128, and 16-bit values. Each token needs a key and a value per layer. That comes to roughly 128 kilobytes of cache per token. A single request with a 32,000-token context holds about 4 gigabytes. Ten such requests at once need about 40 gigabytes before the weights, the activations, and the fragmentation are counted.

That arithmetic explains a lot. It explains why a server admits requests by free cache blocks instead of by how many requests it has. It explains why a shared 20,000-token system prompt is worth caching: reused across many concurrent requests, it saves gigabytes. It explains why an 8-bit cache holds twice the tokens of a 16-bit one. When a release note says it reduced memory per request, convert that into tokens per GPU. That is the number that sets your cost.

What to check this month

  1. Measure your idle gap. Profile a decode step and see how much time the GPU waits between kernel batches.
  2. Check your exact combination. Speculative decoding with pipeline parallelism was on vLLM's exclusion list in v0.14.0. Confirm your setup is covered before you upgrade.
  3. Watch the strict sampling change. vLLM v0.14.0 makes unsupported sampling parameters fail under speculative decoding instead of ignoring them.
  4. Replay routing on real traffic. Compare round-robin with a prefix-aware policy using realized cache hit rates and time to first token.
  5. Pin your engine versions. Track the latest release in staging, and promote to production on a schedule.

Frequently asked questions

Is asynchronous scheduling always faster?

No. The gain is largest when CPU scheduling time is a real share of each step, which happens at moderate batch sizes and fast models. With very large batches the GPU is already saturated, and there is little idle time to recover.

Do I need the SGLang gateway for cache-aware routing?

You need some router that knows where prefixes are cached. The gateway is one implementation. A simpler approach hashes a stable prompt prefix to a fixed replica, which needs no tracking but cannot adapt when one prefix becomes very popular.

Common mistakes in 2025

The first mistake of the year was assuming a rewrite would be fast. The V1 work went from a testable alpha in January to a default in March to a full removal of V0 in October. Teams that planned a short migration found that the old and new engines coexisted for much longer than they expected. Plan migrations in quarters, and keep the old path available until the new one has been tested on your workload. A migration plan that names an owner, a test, and a rollback step for each stage is the difference between a smooth year and an emergency every quarter.

The second mistake was treating a release-candidate or alpha label as a signal to stop checking. Pre-release builds carry the most change per week, and a team that adopted one without a test matrix had to absorb every change as it arrived. A pre-release is a place to test, not a place to depend on.

The third mistake was confusing a gateway with a cache. The SGLang gateway shipped in late 2025 as a routing layer, and teams that expected it to manage cache state directly were disappointed until the later routing work arrived. Know which component owns which decision before you write the architecture down.

The fourth mistake was ignoring the storage layer when upgrading the engine. LMCache and Mooncake changed their interfaces during the year, and an engine upgrade that did not also upgrade the store could break the cache path silently. Version the storage layer with the engine, and run a cache correctness test after every change to either.

The fifth mistake was running local models without pinning. Ollama's pace of 59 releases in 2025 meant that a model that answered one way in January could answer slightly differently in September. Reproducible local results require a pinned runtime and a recorded model digest.

The second is cache offload, the movement of cold blocks to host memory and disk, which appeared in LMDeploy and was built into the LMCache and Mooncake layers.

What 2025 teaches an operator

  3. Stable interfaces are worth more than fast ones. TensorRT-LLM's 1.0 label is a contract. Pin to the stable line when the interface matters to your application.

  5. Treat storage as part of the engine. LMCache and Mooncake changed how cache moves between machines. Test cache correctness whenever you change the storage layer.

Multi-step scheduling trades latency granularity for overhead.

The third mistake was upgrading across a licence change without review. TGI v1.0 changed the licence, and an upgrade that did not check it changed the terms of use without anyone noticing.

The fourth mistake was leaving a cluster dashboard exposed. The 2023 Ray dashboard fixes are a reminder that a management interface needs the same access control as any other sensitive service.

The 2023 year also shows how much the vocabulary has changed. Terms that now appear in every engine's documentation, such as prefill, decode, continuous batching, and speculative decoding, were either absent from the 2023 notes or used in a narrower sense. A reader who starts with the glossary in this page and then reads a 2023 note will find the early notes describing the same systems with different words. Learning to translate between the two vocabularies is a useful skill for anyone reading the history of the field. The translation matters for search as well. A team looking for early work on a technique will miss it if it searches only for the modern term, so keep a list of the older names for each idea you care about. A short personal glossary, kept next to the notes you read, saves that search every time.
