Inference Engineering, Monthly 2026.

ml inference vllm sglang

This page is the running log of inference engineering for 2026. Each month gets one section. The newest month sits at the top, and each section stays collapsed until you open it. Every section follows the same shape: the important changes in the engines, the concepts that explain them, practical checks, and reading links. Release notes are the source for what shipped. Anything beyond the notes is interpretation, and I mark it that way.

March 2026 FlashAttention 4 arrives, Model Runner V2 matures, stable TensorRT-LLM disaggregation, Ollama on MLX

Summary: March was the month the new generation of kernels and runners became usable. vLLM v0.17.0 (March 7) added FlashAttention 4 as a backend and upgraded to PyTorch 2.10, and its Model Runner V2 gained pipeline parallelism and decode context parallelism. vLLM v0.18.0 (March 20) added gRPC serving, a GPU-less render command, and GPU-based n-gram speculative decoding. TensorRT-LLM v1.2.0 (March 12) became a stable release with disaggregated serving service discovery and multi-token prediction for DeepSeek V3.2. LMCache v0.4.0 (March 10) marked its shift to the multiprocess mode, and Ollama v0.19.0 (March 27) put an MLX-based preview on Apple silicon.

The month the runner became the product

Kernels get the attention, but March's most consequential change was about the runner, the part of the engine that turns a scheduled batch into GPU work. vLLM's Model Runner V2 has been in development for a while. In v0.17.0, it reached a set of milestones that were previously missing from it: pipeline parallelism, decode context parallelism, Eagle3 speculative decoding with CUDA graphs, pooling model support, and piecewise and mixed CUDA graph capture. Each item removes a reason a team would have to stay on the older path.

A runner rewrite matters because it sits between the scheduler and the kernels. Every optimization in January and February had to pass through it. Asynchronous scheduling needed the runner to accept a batch before the previous one finished. Pipeline parallelism needed it to pass activations between stages. Speculative decoding needed it to run draft and verify steps as one unit. A runner that handles all of these natively means fewer special cases, and fewer special cases means fewer ways for a configuration to break silently.

Runner rewrites are also hard to see from outside. A changelog line such as "pipeline parallel is now supported" hides months of work on memory layout, buffer reuse, and synchronization. Users see the line. Maintainers see a set of corner cases that had to be closed one by one, and each closed case removes a class of bug that would otherwise surface in someone's production traffic. Reading the release with that in mind helps you value the change correctly, even when the headline sounds modest.

The lesson for a team is to read runner milestones as stability signals. When a runner stops being a list of exceptions and becomes a single path, the features you enable are tested together rather than in isolation. That is the point where a serving stack becomes boring in the good sense, and boring is what a production team wants.

FlashAttention 4 and the kernel generations

FlashAttention is the attention kernel that most modern engines use. The original paper by Tri Dao and colleagues (arXiv 2205.14135) showed how to compute exact attention with far less memory traffic by tiling the computation so the working set fits in fast on-chip memory. FlashAttention 2 improved parallelism and work partitioning. FlashAttention 3 (arXiv 2407.08608, by Jay Shah and colleagues) targeted Hopper hardware with asynchrony and low-precision support. Each generation chased the hardware it ran on, and the gains came from matching the kernel to the memory system and the tensor units of a specific chip.

FlashAttention 4 is the next step in that line, and March's signal is that it reached the point where serving engines could adopt it. The FlashAttention repository published a series of beta releases for version 4.0.0 between March 5 and March 25, labeled fa4-v4.0.0.beta0 through beta6. vLLM v0.17.0 listed FlashAttention 4 support as a backend. Beta releases of a kernel are a normal part of the cycle: the kernel is correct on the tested cases, and the team uses the betas to collect failures on shapes and hardware they did not test.

Why does a new attention kernel matter for an inference team? Attention cost grows with context length, and at long contexts it can dominate decode time. A kernel that moves less data per step or runs its tensor units more fully changes the cost of every long-context request. The catch is that kernel gains are hardware-specific. A benchmark on one GPU generation may not hold on another, and a beta kernel may not cover every head dimension or cache layout your model uses. Check the kernel's supported shapes against your model config before you assume it applies.

The PyTorch 2.10 upgrade in the same vLLM release is related. Kernels are compiled against a specific framework version, and a framework upgrade can change dispatch, compilation, and memory allocation. Teams often treat the framework as a fixed base and the kernel as a plug-in, but the two are coupled. Upgrade them as a pair, test them as a pair, and keep the previous pair available for rollback.

Separating preprocessing from GPU inference

vLLM v0.18.0 introduced vllm launch render, a command for GPU-less preprocessing and rendering. The notes describe it as a way to separate multimodal preprocessing from GPU inference. The idea is simple to state. A vision or audio model needs CPU work before the GPU sees anything: decoding images, resizing, tiling, tokenizing prompts with special placeholders, sometimes running a feature extractor. That work competes with inference for CPU time and memory, and it scales differently from the GPU stage.

When preprocessing lives in the same process as the GPU worker, the two compete for the same host resources. A burst of large images can stall decode for every request sharing the process. Splitting the render stage into its own service lets the team scale CPU preprocessing separately from GPU inference, and it lets a GPU worker spend its time on the parts of the request that need the GPU. The cost is an extra hop and a serialized intermediate representation between the two stages.

The same logic appears in the disaggregation idea from January and in SGLang's EPD work from February. Encoding, prefill, and decode have different resource profiles, and a system that treats them as one unit wastes whichever resource is not the bottleneck at a given moment. Separating stages is a way to match hardware to work. The engineering question is whether the handoff cost is smaller than the idle time you recover, and that depends on request size.

For a team building a multimodal product, the practical check is simple. Measure how much of each request's wall time falls in preprocessing versus GPU inference, under realistic image sizes. If preprocessing is a large share, a render split is worth prototyping. If it is small, leave the stages together and spend the effort elsewhere.

GPU n-gram speculation and the cost of proposing

Speculative decoding has two costs: the verification pass and the proposal step. Methods that use a draft model pay a real forward pass for the proposal. Methods that use n-gram lookup pay almost nothing, because they guess the next tokens by matching recent text against earlier text in the same context. That makes n-gram speculation attractive for workloads with repetition, such as code editing, retrieval answers that quote the source, and structured outputs.

vLLM v0.18.0 moved NGram speculative decoding onto the GPU and made it compatible with the async scheduler. The notes say this significantly reduces speculative decoding overhead. The reason it mattered is that a CPU-side proposal step sits on the critical path. Every decode step waits for the CPU to finish matching before the GPU can verify. Moving the matching to the GPU removes that wait and lets it overlap with the rest of the step, which is the same overlap idea that powered the January async headline.

The useful question is acceptance rate, not raw speed. An n-gram proposer helps only when the next tokens repeat earlier ones often enough that verification accepts several of them. On open-ended creative text, acceptance is low and the method adds overhead. On code diffs and quoted retrieval, acceptance can be high. Measure the accepted tokens per verification step on your traffic before deciding, and keep speculation off for workloads where it does not pay.

TensorRT-LLM v1.2.0 and stable disaggregation

TensorRT-LLM v1.2.0 on March 12 was a stable release, not a candidate, after a long run of v1.2 release candidates in January and February. Its highlights list covers a wide model range, with beta support for K-EXAONE, Nemotron Nano V3, Qwen3-Next, and Qwen3-VL, and improved validation for GPT-OSS, GLM, DeepSeek V3.2, and Mistral Large 3. Its hardware list names B300, GB200, GB300, and several Blackwell and Ampere paths. Its speculative decoding entry enables multi-token prediction greater than one for DeepSeek V3.2.

The disaggregated serving entry is the one with operational weight. The notes add a service discovery mechanism for dynamic scaling. In a disaggregated deployment, prefill and decode workers are separate pools, and the router needs to know which workers exist and what they can do. Service discovery means the pools can grow and shrink while the system runs, rather than requiring a fixed topology set at startup. That is the difference between a disaggregated demo and a disaggregated service.

Stability matters here. A candidate train tells you the design is still moving. A stable release tells you the team considers the interface settled enough to build on. For TensorRT-LLM users, March is the first month where a disaggregated setup is a reasonable production target without pinning a candidate. Even so, pin the exact version, and test the service discovery path under scale-up and scale-down events, because that is where failures hide.

LMCache's multiprocess shift and prefetch

LMCache v0.4.0 on March 10 was described by its maintainers as the point where the project matured and shifted toward the multiprocess mode. The release list includes an L2 prefetch controller integrated with the storage manager. Prefetch is the cache equivalent of read-ahead in an operating system. If the system can predict that a block will be needed soon, it can move that block from a slow tier to a fast one before the request asks for it.

The mental model is worth spelling out, because prefetch only helps if prediction is good. Consider an agent that resends a long conversation every turn. The next turn's prefix is almost certain, because it is the previous turn plus new tokens. A prefetcher can warm those blocks from disk or remote storage while the current turn is still generating. For a random one-shot prompt, there is nothing to predict, and prefetch wastes bandwidth. The payoff depends on how predictable the traffic is.

The multiprocess mode itself, which January and February introduced in pieces, is now the main path. Separating the cache manager from the engine means the cache can survive engine restarts and be shared across workers. The cost is coordination: locks, free-list management, and consistency across processes. The v0.4.0 release adds an API for freeing locks in the multiprocess mode, which is the kind of detail that shows where the hard edges are.

Mooncake's March release, v0.3.10 on March 19, adds a related piece. Its notes mention etcd wrapping for master service high availability, and copy and move client support for stored objects. High availability for the metadata service matters because a cache store that loses its master loses track of where blocks are. A cache layer is only as useful as its ability to answer lookups during failures, so the availability work is part of the performance story.

Ollama on MLX and the local-first stack

Ollama v0.19.0 on March 27 made a platform change: on Apple silicon, Ollama is now built on Apple's MLX framework in preview, to take advantage of unified memory. Unified memory means the CPU and GPU share one memory pool, so the cost of moving data between them drops, and large model weights do not need to be copied across a bus. For local inference on a laptop, that changes which models fit and how fast they run.

The release also fixed a status bug where the app showed a model as out of date incorrectly, and added a web search plugin to the Pi launch path. v0.18.0 on March 14 improved performance for OpenClaw and cloud models, reporting up to 2x faster speeds with Kimi-K2.5, and made Ollama selectable as a provider during OpenClaw onboarding. The pattern from February continues: Ollama is becoming the local hub for agent tools, and its performance story now spans local hardware and cloud models.

For the series, the MLX change matters because it shows a common split. Local inference on Apple silicon increasingly uses a framework designed for that memory architecture, not the same CUDA-first path as servers. Benchmarks from a server GPU do not transfer to a laptop, and the right optimizations differ. When you compare local and server numbers, compare them on the same task and quality bar, not on raw tokens per second alone.

Ray 2.54.1 and the data path

Ray released a patch, 2.54.1, on March 25. The February article covered 2.54.0 and its data-side work. A patch release like this usually carries fixes rather than features, and for an inference team the rule is simple: if you run Ray for batch inference or serving, take the patch once your tests pass, because fixes in the data and scheduling layers affect every job. Patches are where stability work accumulates, and skipping them makes later upgrades harder. A good rhythm is to read each patch's notes the day it lands, run the same replay you use for minor releases, and roll it out within the week. That keeps every upgrade small enough to reason about, and it means a real regression is caught while the change is still easy to revert.

Concepts this month adds

March adds three concepts. The first is the runner boundary. The runner is the code that executes a scheduled batch on the GPU. A runner that natively supports pipeline stages, speculative decoding, and CUDA graph capture is a runner where those features compose. The practical effect is that combinations which used to need special cases become normal paths, and the engine's test matrix shrinks. When you read a runner milestone, ask which special cases it removed.

The second concept is the CUDA graph. A CUDA graph records a sequence of GPU operations once and replays it, which removes the CPU overhead of launching each kernel separately. For decode, where each step runs many small kernels, graph replay can cut overhead a lot. The complication is that graphs need fixed shapes. Piecewise graph capture, which vLLM v0.17.0 extended to mixed batches, captures the parts of a step that have stable shapes and runs the rest eagerly. That balance is why piecewise capture is a common default.

The third concept is prefetch. Prefetch moves cache blocks from a slow tier to a fast one before they are requested. It is the same idea as read-ahead in storage systems, applied to attention state. It works only when the next access is predictable, which is why agent traffic with repeated prefixes is a strong fit and random prompts are not. Measuring predictability, meaning the fraction of blocks that a prefetcher would have guessed correctly, is a cheap way to decide whether to turn it on.

Reading March against February

February asked whether a feature was supported. March asked whether the supported features work together. That shift is the signature of a maturing stack. In February, a team could enable async scheduling with pipeline parallelism and find that it was a supported combination. In March, the question became whether that combination still holds when the runner also handles context parallelism, speculative decoding with CUDA graphs, and a new attention backend. Composition is harder to test than any single feature, and it is where the bugs that matter most tend to live.

The two months also differ in where the risk sits. February's risk was mostly in coupling between stages: a stall in one place showed up in another. March's risk is in the seams between components that were built separately. A new attention kernel must agree with the cache layout. A new speculation path must agree with the async scheduler. A render split must agree with the request format the GPU worker expects. Each seam is a place where a version bump can change behavior without a single line of your code changing.

The practical response is to test by composition. Pick the three or four configurations that matter most to your product, such as a long-context chat route, a speculative code route, and a multimodal route, and run each one through an upgrade before rolling it out. A matrix of two or three configurations catches most of what a full sweep would catch, at a fraction of the cost. It is also easier to explain to the rest of the team, which keeps the test plan alive.

March also shows a shift in who the features serve. Several entries, including the render split, the gRPC route, and the Ollama MLX preview, widen the set of places inference can run. A server, a laptop, a sidecar preprocessing service, and a gRPC client are all now first-class targets. That widening means a team's definition of the serving stack is growing. The useful habit is to write down, for each route, where inference runs and which engine version it uses, so the picture stays accurate as the set grows.

Finally, March rewards teams that read the candidate and beta notes. The TensorRT-LLM candidates that preceded v1.2.0, and the FlashAttention betas, told a story months before the stable releases. Teams that followed those notes arrived at March with a tested plan. Teams that waited for the stable tag had to do the testing under deadline. The cost of tracking pre-releases is attention, and the return is time.

Scale and cost, revisited

The worked memory budget from January still applies in March, but the inputs move. Kernels like FlashAttention 4 change how much time each token costs, not how much memory it occupies. Cache tiers and prefetch change where the blocks sit, which changes how much GPU memory the cache needs to hold. Speculation changes how many tokens each verification step yields. Each of these moves one term in the cost equation, and the cost per million tokens depends on all of them together.

A simple way to keep the picture honest is to track three numbers each month: GPU memory used for cache, tokens produced per GPU-second at your target latency, and the share of requests served from a warm cache. When a release claims a speedup, check which of the three it moved. A kernel that speeds up attention should move tokens per GPU-second. A cache change should move the warm share. A speculation change should move tokens per verification step. A release that moves none of your three numbers is worth reading, but it is not worth a rollout by itself.

Cost also depends on idle capacity. A faster engine on an underutilized fleet saves little, because the fleet was already waiting on traffic. The gains from March's kernels and runners pay off most on busy fleets, and on fleets where autoscaling keeps replicas warm. For a small deployment with bursty traffic, the bigger lever may be keeping cold starts short, which connects back to the cache warmup point from February.

There is also a quality side to cost. A cheaper token that is wrong is not a saving. Speculative methods preserve the target distribution when verification is correct, but any approximation in a kernel or a sparse path can shift outputs. If your product depends on exact answers, measure quality on the same tasks before and after a change. A cost reduction that moves quality is a tradeoff, and it should be accepted explicitly, not discovered later.

What to check this month

  1. Test FlashAttention 4 on your shapes. Confirm the head dimensions, GQA ratio, and cache layout in your model config are covered by the kernel before enabling it. Run long-context quality checks, not only speed.
  2. Upgrade framework and kernel as a pair. If you move to vLLM v0.17.0, plan the PyTorch 2.10 change together with any kernel change, and keep the previous environment ready for rollback.
  3. Measure preprocessing share. For multimodal products, record how much wall time goes to rendering before GPU inference. Only split the stages if that share is large.
  4. Measure acceptance for n-gram speculation. Count accepted tokens per verification step on real traffic. Turn speculation off for workloads where acceptance stays low.
  5. Test disaggregated scale events. If you use TensorRT-LLM disaggregation, test scale-up and scale-down under load. Service discovery failures show up there.
  6. Check prefetch predictability. If you run LMCache, measure how often the next prefix matches the prefetched blocks before tuning the prefetch policy.
  7. Apply the patch releases. Ray 2.54.1 and the vLLM point releases carry fixes. Test them and roll them out on a schedule.

Frequently asked questions

Is a beta FlashAttention kernel safe for production?

Only behind a test gate you control. Betas are for collecting failures across shapes and hardware. Run your own accuracy and long-context tests, and keep the previous kernel available for rollback until the release is stable.

Should I split preprocessing into a separate service?

Only if measurement says preprocessing is a large share of request time under realistic inputs. The split adds a hop and a serialized handoff, which costs time, so it has to pay for itself.

Does n-gram speculation help chat assistants?

Usually less than it helps code or quoted retrieval, because open-ended text repeats less. Measure acceptance on your traffic. If acceptance is low, the overhead can exceed the gain.

Is the MLX preview a reason to switch local stacks?

It is a reason to test. The preview changes the performance profile on Apple silicon, but it is still a preview. Compare on your own tasks and quality bar before moving a workflow.

Common mistakes this month

The first mistake is enabling a kernel without checking its supported shapes. A beta kernel that covers most head dimensions may still fall back or fail on the one your model uses, and the fallback can be slower than the old path. Read the supported-shape list before the benchmark, not after.

The second mistake is measuring speculation on the wrong workload. A method that doubles speed on code can slow down chat. Report acceptance and speed per workload, and set the policy per route rather than globally.

The third mistake is treating prefetch as free. Prefetch uses bandwidth and tier capacity. On unpredictable traffic it can evict blocks that would have been reused, which lowers the hit rate it was meant to raise. Track the hit rate with prefetch on and off.

The fourth mistake is upgrading the framework without the kernels. A kernel built against one framework version may not match a newer one, and mismatches can show up as slow paths rather than errors. Treat the pair as one release.

The fifth mistake is ignoring the patch releases. Teams that defer every patch end up with a large, risky jump later. Schedule patch upgrades on a short cycle, and keep them small.

February 2026 async scheduling with pipeline parallelism, sparse attention kernels, LoRA loading overlap, cache-aware fleets

Summary: February turned January's ideas into something teams can actually turn on. vLLM v0.16.0 (February 25) declared asynchronous scheduling with pipeline parallelism fully supported, and its notes report a 30.8% end-to-end throughput gain and 31.8% lower time per output token. SGLang v0.5.9 (February 24) integrated TensorRT-LLM kernels for DeepSeek V3.2's sparse attention and overlapped LoRA weight loading with computation. On the fleet side, llm-d v0.5.0 (February 3) focused on scaling the KV cache and autoscaling, and Ollama's February releases pushed its launch command into more coding and agent tools. The month's main lesson is that the boundary between engine, cache, and cluster is now the place where performance is won or lost.

The month the exclusion list shrank

In January, the most useful part of the vLLM note was the list of configurations asynchronous scheduling did not cover yet. February's most useful part is a sentence that removes an item from that list. vLLM v0.16.0 says asynchronous scheduling combined with pipeline parallelism is now fully supported. The release was branch-cut on February 8, so anything merged after that date is not in it. That detail matters. It tells you the release is a snapshot of a moving target, and any single version is a checkpoint in a longer effort.

Shrinking exclusion lists is the normal pattern for a serving feature. A new scheduler path starts narrow because each combination of parallelism, speculative decoding, and sampling creates a separate set of correctness questions. The team tests the common combinations first, ships the feature as default for them, and keeps the rest on a list. Each month the list gets shorter. When you read an engine's notes, the exclusions are a live roadmap of what is still risky, and the removals are a record of what the team has verified.

February also shows why headline performance numbers need a setup line. The 30.8% throughput and 31.8% time-per-output-token figures are real numbers from the notes, but they describe a specific model, hardware, parallelism layout, and load. A team with a different pipeline depth, a different batch distribution, or a short-prompt workload may see a smaller gain or none. The right move is to reproduce the setup that matches your traffic, not to quote the figure in a planning document.

What vLLM shipped

vLLM had two releases in February. v0.15.1 on February 4 was a patch. v0.16.0 on February 25 was the feature release, with 440 commits from 203 contributors, 7 of them new. Its highlights reveal three directions. The first is the scheduler story already discussed. The second is a WebSocket-based Realtime API for streaming audio interactions, which builds on the Voxtral streaming work that appeared in v0.15.0. The third is reinforcement learning from human feedback infrastructure: the notes mention a native NCCL-based weight syncing API, layerwise weight reloading for QeRL, and engine pause and resume.

That third direction is easy to skip, but it matters for anyone who trains and serves the same model. RLHF loops repeatedly generate rollouts from the current policy, then update weights and push them back to the inference engine. Syncing those weights quickly, without restarting the server, turns a multi-minute stall into a short pause. This is a case where the inference engine has become part of the training loop, and the performance questions change: weight transfer time now sits next to decode throughput on the critical path.

The realtime API is a different kind of change. An interactive voice agent cares about time to first audio and about keeping the connection open across turns. A WebSocket route fits that pattern better than repeated HTTP requests, because the server can stream partial outputs and accept new input without a new connection each turn. For an inference engineer, the point is that the request lifecycle is no longer always one prompt in, one completion out. Sessions now carry state across turns, and that state is mostly KV cache.

What SGLang shipped

SGLang v0.5.9 on February 24 had a short highlights list with three entries that matter here. The first is loading LoRA weights concurrently with computation. Adapters are small, but loading them can stall a batch, and the notes report that overlapping the load reduces time to first token by roughly 78% and time per output token by about 35% on large adapters. Those numbers describe the case where the load was a visible stall. If your adapters are already resident, the gain is smaller.

The second entry integrates TensorRT-LLM kernels for native sparse attention in DeepSeek V3.2. The notes say this boosts performance by three to five times on Blackwell with a minor accuracy drop, and they name separate prefill and decode backend flags. The third entry adds FlashInfer's all-to-all dispatcher for mixture-of-experts expert parallelism. Together these show where the engine work is going: specialized kernels per phase, and communication patterns designed for routing tokens to experts.

The sparse attention entry deserves its own explanation, because sparse attention is one of the big themes of 2026 and it changes the cache. In standard attention, each new token attends to every past token. Sparse attention selects a subset of past tokens for each query, using an indexer or a fixed pattern. That lowers the compute for long contexts, but it does not remove the need to store the whole cache. The kernel reads only the selected entries. So the performance win comes from the attention step, while the memory budget from the worked example still applies. A team should expect sparse attention to change compute cost more than memory cost, and should measure both.

Concept: sparse attention and the cache layout

Dense attention has a simple cost model. For a context of length L, each new token does work proportional to L, so long contexts get slower to decode as they grow. Sparse attention attacks that slope. If each query reads only k selected past tokens, decode work per step is proportional to k instead of L. For very long contexts, that difference is large.

The hard part is selection. The model has to pick which past tokens matter for the current query, and the selection itself costs something. Methods differ in how they choose, from fixed windows and block patterns to learned indexers that score past blocks. What they share is a need for the kernel to gather scattered cache entries rather than read one contiguous region. That gather pattern is harder to make fast on GPUs, which is why kernel support arrives as a separate integration with its own tuning, rather than as a flag that works everywhere.

For the memory side, nothing about the sparse selection removes the need to keep past keys and values. An indexer usually needs its own small structure, and the main cache stays in GPU memory or gets offloaded. So a long-context deployment still has to budget for the full cache, even if each step touches only part of it. This is why sparse attention is often paired with the offload and tiering ideas covered in January. The cache is large, reads are selective, and the system needs to keep cold blocks somewhere cheaper until a query needs them.

The accuracy caveat in the SGLang note is important. Sparse selection can drop tokens the dense model would have used, so output can shift slightly. A minor accuracy drop is acceptable for some products and not for others, such as legal or medical extraction. The right test is an evaluation on your own tasks, with long-context recall measured explicitly, rather than trusting a single benchmark score.

The fleet layer: llm-d v0.5.0

llm-d is a Kubernetes-native project for serving LLMs across a cluster, and its v0.5.0 release, dated February 3 in the notes, sets its core objectives in one line: reproducible benchmarking, scaling the KV cache, autoscaling improvements, and a better metrics and tracing story. It also made breaking infrastructure changes, upgrading the Gateway API, Istio, and KGateway versions. The release reads more like a platform maturity milestone than a single feature.

The reason this matters for inference is that a serving cluster has a different bottleneck from a single engine. A single engine's limit is its GPU memory and scheduler. A cluster's limit includes how requests are routed, when new replicas start, and how much cache each replica holds. Autoscaling a model server is harder than autoscaling a stateless web service, because a new replica starts with an empty cache and serves its first requests slowly. Scaling the KV cache across replicas, and routing requests to replicas with useful cache, reduces that cold-start penalty. This connects directly to the cache-aware routing theme from January.

Reproducible benchmarking is the least glamorous objective and possibly the most valuable. A cluster benchmark depends on the gateway version, the engine version, the model, the traffic shape, and the autoscaler's timing. If any of those changes between runs, the numbers are not comparable. A project that makes benchmarks reproducible is making it possible for teams to trust a comparison. When a release says it targets reproducibility, read that as a signal that the team expects users to make decisions from measurements.

Concept: the KV cache as a shared service

In a single engine, the KV cache belongs to the engine process. In a cluster, it becomes something closer to a shared service. Mooncake's February release, v0.3.9, shows that direction. Its notes list fixes to the offset allocator, a feature that enables Ascend fabric memory mode in the store, support for batch publish with tensor-parallel awareness, and documentation for a dummy client that lets SGLang's hierarchical cache use the store. Those are storage-layer details, but they point to one idea: cache blocks are moved, published, and looked up across processes and machines.

LMCache v0.3.14 on February 17 contributed a related piece. Its notes mention a new L1 manager for the multiprocess storage manager. A multiprocess design separates the cache manager from the engine process, so several engine workers can share one cache layer. That separation has costs. Every lookup crosses a process boundary, and the manager must handle concurrency and eviction across all of them. The benefit is that cache survives individual worker restarts and can be shared, which matters when a fleet scales up and down.

The mental model is a hierarchy. The hottest blocks live in GPU memory, next in CPU memory, and then on local or remote storage. A lookup goes down the hierarchy until it finds the block, and a hit at a lower tier costs more time than a hit at a higher one. Good systems keep the most reused prefixes near the GPU and push the long tail down. The right policy depends on reuse distance, which is the time between uses of the same block. Long reuse distances favor cheap storage, short ones favor memory.

Ollama's shift from runner to launcher

Ollama published thirteen releases in February, from v0.15.3 on February 1 to v0.17.4 on February 27, and the feature story is consistent. v0.16.0 on February 12 brought GLM-5 and MiniMax-M2.5 to the model library and introduced a new ollama command for launching apps with Ollama models. Its notes list Pi as one of the launch targets. v0.17.0 on February 21 added automatic installation and configuration of OpenClaw through ollama launch openclaw, and enabled web search for cloud models inside that setup. The same release mentions a tokenizer performance improvement.

Two things stand out for an inference engineer. The first is that models in the library now include very large mixture-of-experts systems. GLM-5 is listed at 744 billion total parameters with 40 billion active. A local runner that serves a model of that size relies on offload, quantization, or cloud routing, and the performance profile looks nothing like a small chat model. The second is that the launch pattern sends agent tools to Ollama as their backend. Agent tools make repeated calls with growing context, so the workload looks like the agent traffic described in January. Caching and tokenizer speed both matter more when the same conversation returns every few seconds.

The web search detail is a reminder that local-first tools now mix local and cloud execution. A request may start locally and call out to a search or a cloud model. For measurement, that means a single user action can produce several inference calls with different latency profiles. Benchmarks that look at one call miss the end-to-end cost.

TensorRT-LLM: the candidate train continues

TensorRT-LLM kept its release-candidate cadence through February. The v1.3.0 line moved from rc2 on February 3 through rc3 on February 12, rc4 on February 17, and rc5 on February 24. There were also v1.2.0 post-release patches on February 5. The rc3 notes show the kinds of changes this line carries. Support for LoRA BF16 checkpoints with a Llama 3.3 70B FP8 model. Eagle3 speculative decoding for Nemotron-H. A new default for continuous usage statistics in streaming responses, changed to follow the OpenAI protocol. Integration of a KV cache manager v2 into the runtime. Support for a programmatic dependent launch path in the MoE all-to-all kernels.

The KV cache manager v2 entry is the one to track. Cache managers are where memory policy lives, and a version change there can shift latency in ways no single kernel benchmark reveals. The release-candidate status means the design is still being shaken out. Teams that depend on TensorRT-LLM should test each candidate against their own traffic, because cache behavior is one of the first things to change and one of the last things to show up in a microbenchmark.

Eagle3 support for a hybrid model like Nemotron-H is also worth noting. Speculative decoding with a learned draft head needs the target model's hidden states, and hybrid architectures with state-space layers make those states less uniform. Support for a new architecture family in speculative decoding is a sign that the technique is moving from standard transformers to the broader model zoo, which broadens its value but also multiplies the test matrix.

Ray and data-side checkpointing

Ray 2.54.0 landed on February 18. Its notes are dominated by Ray Data, the data processing library, with new checkpointing support, expression operations, aggregations, and autoscaler metrics on the data dashboard. For an inference team, the relevance is indirect but real. Batch inference jobs, such as embedding a corpus or running evaluations across a large dataset, depend on data pipelines that must survive failures. Checkpointing in the data layer means a long job can resume rather than restart, which saves GPU hours when a node fails partway through a run.

The autoscaler metrics on the data dashboard also point to a shared problem. Data pipelines and model servers both scale on demand, and when a data stage starves the GPU stage, the GPUs idle while the cost keeps running. Exposing autoscaler decisions as metrics lets an operator see whether the bottleneck is the data side or the model side. Most inference cost waste comes from exactly that mismatch.

Concepts this month adds

February adds three concepts to the January set. The first is the LoRA loading stall. A LoRA adapter is a small set of low-rank weight matrices that customize a base model for a task or a customer. Serving many adapters on one base model is attractive, because the base weights are shared and each adapter is cheap. The cost appears when an adapter is not already in memory. Loading it blocks the batch, which hurts the latency of every request sharing that batch. Overlapping the load with computation hides the stall, which is why the SGLang reduction in time to first token is large for large adapters.

The second concept is the reinforcement learning weight sync. Training and serving share a model, and the serving engine must receive new weights after each update. Syncing through a fast collective path, and allowing the engine to pause and resume, means training and generation can alternate without rebuilding the engine. The bottleneck moves from load time to transfer time, and the transfer uses the same interconnect as tensor parallelism. Teams running RL loops should measure sync time as a first-class metric, because it sets how often the policy can update.

The third concept is speculative decoding generalization. Eagle3 support for new architectures shows the technique is spreading across model families. The principle is the same as in January: a cheap proposer and a parallel verifier. The practical question is acceptance rate on your traffic, which depends on how well the draft head has learned the target model's distribution for your prompts. A draft head trained on general text may underperform on code or on domain text.

Reading the month as a set of tradeoffs

February's releases share one pattern: each gain was bought with a new kind of coupling. Async scheduling with pipeline parallelism couples two stages that used to be independent, so a stall in one stage now shows up in the other. Sparse attention couples the attention kernel to a selection step, which means a bug in the indexer can look like a model quality problem. Cache tiers couple latency to reuse patterns, so a traffic shift can make a previously fast tier slow without any code change. Autoscaling with shared cache couples replica count to cache state, so scale events have a lagging effect on performance.

Reading an engine release well means asking what got coupled. The question tells you where to look when something breaks. If a pipeline-parallel deployment slows down after an upgrade, the first suspect is the overlap between stages, not the model. If sparse attention drifts on a long-document task, the first suspect is selection quality on that document type, not the decoding loop. If a cache-backed fleet slows during a traffic spike, the first suspect is cold replicas, not a regression in the router.

Tradeoffs also differ by team size. A large platform team can absorb the complexity of tiered caches, multiprocess managers, and sparse kernels, because it has people to tune and monitor each layer. A small team gains more from the simpler path: keep the default scheduler, use the engine's built-in prefix cache, and skip the offload tier until the numbers justify it. The right stack is the smallest one that meets your latency target, and February's features are mostly useful once that target is hard to meet.

The release cadence itself is a tradeoff. vLLM and SGLang both shipped monthly-scale feature releases, and TensorRT-LLM ran a long candidate train. Faster cadence brings fixes sooner and forces more frequent upgrades. Slower cadence means fewer upgrades and longer waits for fixes. The honest answer is to pick a rhythm your team can test, then hold to it.

Operational notes for a February upgrade

If you run an engine in production and plan to move to a February release, a few operational steps reduce surprises. Start by diffing the defaults. The vLLM v0.16.0 scheduler path is now supported with pipeline parallelism, which means a configuration that previously kept it off may now turn it on in a new version, depending on how your flags are set. Read the diff of default values for your engine version, not only the list of new features.

Next, rebuild your cache expectations. A version change can alter eviction behavior or cache layout, so the hit rate you measured last month may not hold. Run a replay with the same prompts before and after the upgrade. A stable hit rate is the sign that the change is safe; a drop means investigate before rolling out.

Then check the adapter path if you serve LoRA. The SGLang overlap change reduces stalls on large adapters, but the gain depends on loading the adapter during compute. If your deployment loads adapters on demand from remote storage, the overlap helps, but storage latency still sets a floor. Measure cold load time from your actual storage, not from a local disk.

Finally, keep a rollback plan. Engines ship patch releases frequently, and a rollback path should name the exact previous version, the config file that worked with it, and the test that proves the rollback is healthy. The point is to make rollback boring, so the team uses it without debate when a metric moves the wrong way.

What to check this month

  1. Re-test async scheduling with pipeline parallelism. If your deployment uses pipeline parallelism, the v0.16.0 note makes it a supported path. Run your own throughput and time-per-output-token test with your parallel layout before and after.
  2. Measure adapter load time. If you serve LoRA adapters, record how long a cold adapter load takes and how often it happens. If the stall is visible in p99 latency, overlapping loads is the fix to evaluate.
  3. Evaluate sparse attention on recall, not only speed. For any sparse attention path, run a long-context recall test that places facts at different depths. Speed gains mean little if the model misses the fact you need.
  4. Track autoscaler decisions against GPU idle time. Plot scaling events next to GPU utilization. A replica that scales up with an empty cache adds cost before it adds throughput.
  5. Pin candidate builds for TensorRT-LLM. Test each release candidate against a replay of production traffic before moving a deployment forward. Cache manager changes are the first thing to check.
  6. Count inference calls per user action. For agent and assistant products with cloud fallback, measure how many model calls a single user action triggers, and add their latencies together.

Frequently asked questions

Does a fully supported async scheduling path mean I should turn it on everywhere?

Supported means the team tests it and considers it safe for that configuration. It does not mean it wins for every workload. Keep the default unless your own test shows a regression, and keep the escape hatch ready.

Are sparse attention kernels safe to use for accuracy-sensitive tasks?

Only after you test them on the tasks that matter. The note reports a minor accuracy drop, and the size of that drop varies by task. Long-context recall and your own evaluation set are the right gate.

Why does a cluster release mention benchmarking?

Because a fleet decision needs repeatable numbers. A benchmark that cannot be reproduced across gateway and engine versions cannot guide a scaling or purchasing decision, so reproducibility is a feature in its own right.

Is Ollama now a production serving tool?

It is a strong local runner and a launcher for agent tools. For multi-tenant production serving, the usual engines in this series remain the reference, but Ollama's direction matters for developer workflows and for understanding agent-shaped traffic.

Common mistakes this month

The first mistake is treating a percentage gain as a property of the engine instead of the setup. A 30 percent gain on a pipeline-parallel test with long prompts is a fact about that test. Your deployment may have shorter prompts, a shallower pipeline, or a different request mix. The fix is to reproduce the setup before budgeting for the gain.

The second mistake is evaluating sparse attention with perplexity or a single benchmark score. Those measures can hide the failure mode that matters, which is missing a specific fact buried deep in a long context. Recall tests at multiple depths expose it directly.

The third mistake is scaling replicas without accounting for cache warmup. A new replica with an empty cache serves its first requests slowly, and if the autoscaler reacts to queue depth alone, it may keep adding replicas that never catch up. Warm the cache, route to warm replicas, or scale on a metric that reflects cache state.

The fourth mistake is ignoring the cost of weight sync in RL loops. Teams often measure generation throughput and forget that every policy update pauses generation. The sync time caps how often the policy can improve, so it belongs on the same dashboard as tokens per second.

The fifth mistake is pinning a release candidate because its notes look good. Release candidates change, and the cache manager in a candidate may behave differently from the one in the final release. Test the candidate you deploy, and rerun the test when the candidate becomes stable.

Summary: January was about two things. The first was getting the engine to stop waiting on itself. vLLM v0.14.0 made asynchronous scheduling the default. The second was making a cluster smarter about where each request lands. The SGLang Model Gateway v0.3.1 rebuilt its cache-aware router and reports a 10 to 12 times speedup with 99% less memory per tree node. Around those two changes, SGLang v0.5.8 pushed diffusion and long-context pipeline parallelism, vLLM v0.15.0 extended prefix caching to hybrid models, and Ollama began turning from a local model runner into an agent and tool platform.

Why January matters more than it looks

Most months in inference engineering produce a long list of model support announcements. January produced fewer of those and more changes to how the engine works internally. That is the kind of change that lasts. A new model architecture is useful for a few weeks. A change to the scheduler or the cache changes the performance of every model that runs on that engine afterward.

It also helps to know who is building these changes. Most of the core work in this list comes from open-source maintainers who work across companies, with large model labs and inference-focused startups contributing kernels, model support, and benchmarks. That mix is why the notes are so detailed: maintainers write for other maintainers, and they assume you can follow the mechanism. Reading them well is a skill, and the rest of this section tries to build it.

So this section spends most of its length on the mechanisms. The release notes are a map. The concepts are the terrain, and once you know them, you can read any future note and tell which part of the stack it touches and what it should do to your numbers.

The same release required PyTorch 2.9.1, removed several deprecated quantization schemes, and made unsupported sampling parameters fail under speculative decoding instead of being silently ignored. It also added a gRPC entrypoint and a --max-model-len auto option that sizes the context window to fit available memory.

The two engine changes that matter most are that --async-scheduling now works with pipeline parallelism, and that Mamba and other hybrid models get block-aligned prefix caching. The notes report about a 2x speedup from caching Mamba states directly.

Theme 1: stop the GPU from waiting for the CPU

To see why asynchronous scheduling matters, you need the basic loop of an LLM server. Each step, the scheduler decides which requests run. It builds the batch, launches GPU kernels, waits for the new tokens, and processes the results on the CPU. If that CPU work runs in series with the GPU work, the GPU sits idle during every scheduling pass. For small batches and fast models, that idle time is a large share of each step. The GPU spends real time doing nothing while Python prepares the next batch.

Asynchronous scheduling overlaps the two. While the GPU runs step N, the CPU prepares step N plus one. The result is fewer idle gaps, which shows up as higher throughput and lower time per output token, especially at moderate batch sizes. The gain is largest when the model is fast relative to the Python overhead around it. When batches are huge and the GPU is saturated, little idle time exists to recover, and the gain shrinks.

Overlapping is hard when the next step depends on the result of the current one. That happens in pipeline parallelism, where one stage's output feeds the next, and in some speculative decoding methods, where draft tokens decide what gets verified. This is why the v0.14.0 exclusion list named pipeline parallelism, and why v0.15.0 matters: it removed that exclusion. An engine's async story is always a list of supported configurations, and the list grows release by release.

Check it on your own system: profile one decode step and measure the gap between the end of one GPU kernel batch and the start of the next. If the gap is a meaningful fraction of the step, asynchronous scheduling is directly relevant. If the gap is tiny, the feature will barely change your numbers.

Theme 2: send each request where its cache already lives

The SGLang gateway release is a clean example of routing treated as a cache problem. A single engine caches the prefixes of prompts it has seen. A second request that shares a long system prompt or a document can skip most of its prefill. With one worker, that reuse is automatic. With many workers behind a load balancer, round-robin routing scatters requests across them, and each worker rebuilds the same cache. The hit rate collapses even when the total cache capacity across the fleet is large.

Cache-aware routing fixes this by tracking which prefixes each worker holds and sending requests accordingly. The data structure matters for cost. A radix tree stores shared prefixes compactly, so the router's own memory and lookup time stay small as the number of cached prefixes grows. The gateway's gain is a statement about that data structure. It says nothing about model speed, and you should not read it that way.

Routing policyCache hit behaviorMain cost

Consistent hashing on prefixSame prefix goes to the same worker, with no tracking stateUneven load if one prefix is very popular

The stale-view problem deserves attention. A router learns what each worker caches from the requests it has sent. Workers evict entries under memory pressure without telling the router right away. A router that trusts an outdated view sends requests to a worker that no longer holds the prefix, and the benefit disappears. Any production deployment should measure the realized hit rate, not the predicted one.

Theme 3: long context forces new parallelism

The SGLang chunked pipeline result and the vLLM pipeline work belong together. A context of one million tokens does not fit on one GPU, and the attention and KV cache for it must be split somehow. Pipeline parallelism splits the model's layers across GPUs, so each GPU holds some layers for the full context. Chunked pipeline parallelism splits the input into chunks that flow through the stages in order, so later stages start before earlier stages finish the whole prompt. The SGLang notes claim close to linear scaling for this case, meaning added stages keep cutting latency roughly in proportion.

Linear scaling is a strong claim, and it depends on the workload. Pipelining helps most when chunks are large enough to keep each stage busy and inter-stage communication is cheap. For short prompts, pipeline overhead can outweigh the benefit. For a team planning long-context serving, the question is whether the scaling holds at the context length and hardware you actually run.

Concepts you need for this series

Every month leans on the same small set of ideas. January touches nearly all of them, so it is a good place to pin them down.

Prefill and decode

An LLM request has two phases. Prefill processes the whole input prompt in one pass and produces the KV cache for every input token. Decode then generates output tokens one at a time. Each step reads the cache and appends one entry. Prefill is compute heavy and parallel across tokens, so it saturates the GPU's arithmetic units. Decode is memory bandwidth heavy and sequential, because each new token needs the whole cache read once. The two phases have different bottlenecks, which is why so many serving optimizations separate them, either by scheduling them differently or by running them on different hardware.

The metrics follow the phases. Time to first token is mostly prefill cost plus queueing. Time per output token is mostly decode cost. When a note says it cut time to first token, read that as a prefill or scheduling improvement. When it says it raised throughput at a fixed latency, the decode path or the batching policy is usually the source.

KV cache and PagedAttention

The KV cache stores the keys and values for every token in the context, so decode does not recompute attention over the whole history at each step. Its size grows with context length, batch size, layer count, and head dimension. For long contexts and large batches it is usually the largest memory consumer during serving, often larger than the weights themselves.

PagedAttention, introduced by Woosuk Kwon and colleagues in "Efficient Memory Management for Large Language Model Serving with PagedAttention" (arXiv 2309.06180), splits the cache into fixed-size blocks managed like virtual memory pages. Before paging, servers reserved a contiguous region per request, sized for its maximum possible length. Most of that memory sat unused on requests that stopped early. Blocks remove the fragmentation and let requests of different lengths share the GPU. Almost every block-level feature in the notes, including prefix caching and the Mamba block-alignment work in v0.15.0, builds on that idea.

Continuous batching

Static batching waits for a full batch to finish before starting another, so short requests sit idle behind long ones. Continuous batching, also called iteration-level scheduling, admits and removes requests at every decode step. It is now the default in every engine in this series. Asynchronous scheduling is a refinement of it: the bookkeeping for that loop overlaps with GPU work.

Prefix caching

When many requests share a prefix, such as a long system prompt or a retrieved document, the KV cache for that prefix can be computed once and reused. Prefix caching is the single-engine version of the routing idea in theme 2. Its benefit depends on how many requests repeat a prefix and on whether the cached blocks survive long enough to be reused before eviction.

Agent workloads fit well. Each turn resends a growing conversation, so most of each prompt repeats the previous turn. One-shot questions with unique prompts gain little. Hybrid models need a different rule, because state-space layers such as Mamba do not have a KV cache that behaves like pure attention. vLLM v0.15.0's block-aligned caching for Mamba states is the fix for that case.

Speculative decoding

Decode is sequential, so each output token normally costs one full pass through the large model. Speculative decoding uses a cheaper proposer, such as a small draft model or a lightweight head like Eagle, to guess several tokens ahead. The large model checks all the guesses in one parallel pass and keeps the ones that match what it would have produced. When verification is done correctly, the output distribution stays the same, which is why this is a speedup and not an approximation. The gain depends on acceptance rate. A proposer that matches the target model's style does far better than one that does not.

Disaggregation

Disaggregated serving runs prefill and decode, or other stages such as the vision encoder, on separate workers. DistServe, by Yinmin Zhong and colleagues (arXiv 2401.09670), is the standard reference for why this helps. Separating the phases removes interference, where a long prefill stalls every decode step sharing the GPU. The cost is moving the KV cache between workers, which is where Mooncake's transfer design comes in. SGLang's EPD work in v0.5.8 applies the same logic to a vision language model's encoder.

KV cache tiers and offload

GPU memory is the scarcest resource, so the cache does not have to stay there. Offloading moves cold blocks to CPU memory, local disk, or remote storage, and brings them back when a prefix is needed again. LMCache is built around this idea. Mooncake treats the KV cache as the central resource of a disaggregated cluster and moves it between machines. The tradeoff is latency: a block fetched from remote storage costs more than a block already in GPU memory. Offload pays when the reuse is high enough to cover the transfer.

A worked memory budget

Concepts stick better with numbers, so take a simple budget. Suppose a model has 32 layers, 8 key-value heads, a head dimension of 128, and stores its cache in 16-bit precision. Each token needs a key and a value per layer, so the cache per token is roughly 2 times 32 times 8 times 128 times 2 bytes, which is about 128 KB. A single request with a 32,000-token context therefore holds about 4 GB of cache. Ten such requests running at once need about 40 GB before counting weights, activations, or fragmentation.

That arithmetic explains almost every design choice in this series. It explains why a server admits requests by free cache blocks rather than by request count. It explains why prefix caching is worth so much: a shared 20,000-token system prompt, if reused, saves its own 2.5 GB on every concurrent request that shares it. It explains why quantizing the cache to 8-bit halves the budget, and why engines add offload when the budget still runs out. When a release note says it reduced memory per request, convert that into tokens per GPU. That is the number that decides your cost per million tokens.

Two details change the arithmetic. Models with grouped-query or multi-query attention store far fewer KV heads than attention heads, which is why modern open models are cheaper to serve per token than their parameter count suggests. Models with sliding-window or sparse attention may cap how many past tokens they keep, which changes the formula entirely. Always run the calculation with the architecture in the model's config file, not with a generic assumption.

How to read a release note

Release notes are written for maintainers and early adopters, and they mix three kinds of information. The first is new capability: a model, a kernel, a flag. The second is behavior change: a default that flipped, a parameter that now errors, a dropped quantization format. The third is limits: an experimental label, an exclusion list, a configuration marked unsupported. Most of the practical risk sits in the second and third kinds, and most of the headlines sit in the first.

A useful habit is to read the breaking changes section before the highlights, and the exclusion list before the feature. The v0.14.0 async scheduling note is a good example. The feature headline says throughput improves without configuration. The exclusion list says pipeline parallelism, the CPU backend, and some speculative decoding methods are not covered. Those two lines together tell you whether the feature applies to your deployment. The headline alone does not.

Benchmarks in notes need the same care. A router microbenchmark measures operations per second on a synthetic tree. An end-to-end benchmark measures tokens per second on a named model and hardware. A claim of 1.5x faster diffusion serving says nothing about text generation. Before you quote a number internally, write down the model, hardware, batch size, and context length it came from. If the note does not say, treat the number as a direction and not a measurement.

Finally, watch for the word "default." Defaults decide what most users run, and they change without much fanfare. When a default flips, the regression surface is every deployment that never set the flag. That is why an upgrade plan for inference engines should always diff the defaults, not only the new features.

Common mistakes this month

The first mistake is benchmarking with synthetic prompts that share no prefix. If every request in your test is unique, prefix caching and cache-aware routing look useless, and the test will undersell the engine in production. Build the benchmark from a replay of real traffic, or at least make the prompt-repetition rate in the test match the production rate. Otherwise you are measuring a different system.

The second mistake is measuring only throughput. A change that raises tokens per second by ten percent while doubling the time to first token may be a regression for an interactive product. Track time to first token and time per output token at the same time, with percentiles, not averages. Averages hide the long tail that users notice.

The third mistake is treating an experimental label as a warning to ignore rather than a schedule to watch. Experimental features often become defaults within a few releases. Teams that run a canary on experimental features catch regressions early, and teams that ignore them get surprised when the default flips during a routine upgrade.

The fourth mistake is assuming a router fixes a cache problem by itself. Cache-aware routing needs workers that actually keep useful prefixes, which means eviction policy and cache size matter too. A perfect router sending traffic to workers with a small or badly evicting cache will still miss. Look at the whole chain: prompt structure, cache size, eviction, routing, and then the engine.

The fifth mistake is ignoring prompt structure. Prefix caching only helps when the repeated part comes first. If the system prompt is placed after a timestamp or a random request ID, nothing before it repeats, and the cache never matches. A small change in prompt template order can move the hit rate more than any engine upgrade. This is cheap to test and easy to forget.

The last mistake is treating a month as a unit of progress on its own. Inference engineering changes in layers. A scheduler change in January becomes useful when a router change in March depends on it. Reading each month alone is fine for orientation, but the real value comes from tracking how the pieces combine over the year. That is why this page keeps every month in one place, newest first, with the same structure, so you can scan the pattern.

What to check this month

  1. Measure your CPU gap. Profile a decode step and check how much time the GPU is idle between kernel batches. If the gap is large, compare throughput with and without async scheduling.
  2. Check your exact combination. If you run speculative decoding with pipeline parallelism, confirm the release notes list your combination as supported. Before v0.15.0 it was on the exclusion list.
  3. Test the strict sampling change. vLLM v0.14.0 makes unsupported sampling parameters fail under speculative decoding. Run your integration tests before upgrading production.
  4. Replay routing on real traffic. Send a day of prompts through round robin and a prefix-aware policy. Compare realized cache hit rates and time to first token, not the router's own counters.
  5. Measure prefix repetition in your agents. Count how much of each turn's prompt repeats the previous turn. That number tells you how much prefix caching and offload can save.
  6. Pin engine versions. Track latest in staging, not production. TensorRT-LLM candidates in particular are still changing.

Frequently asked questions

Is asynchronous scheduling always faster?

No. The gain is largest when CPU scheduling time is a real fraction of each step, which happens at moderate batch sizes and fast models. With very large batches where the GPU is saturated, there is little idle time to recover. Measure on your own workload, and keep --no-async-scheduling in mind if something misbehaves.

Do I need the SGLang gateway for cache-aware routing?

You need some router that tracks where prefixes are cached. The SGLang gateway is one implementation. A simpler version uses consistent hashing on a stable prompt prefix. That needs no tracking state, but it cannot adapt when one prefix becomes very popular.

Should a small team care about any of this?

Yes, mainly for the concepts. A team running one engine on one GPU already gets continuous batching and prefix caching from the engine. Routing and pipeline changes matter once you scale to several workers or very long contexts. The vocabulary also makes the release notes faster to read.

Why does an inference series include Ollama?

Many developers run models locally through it, and its direction shows where local inference is heading. The agent loop in v0.14.0 and ollama launch in v0.15.0 change the workload profile. Agent traffic is many short sequential requests with growing context, which stresses prefix caching more than single-shot chat does.

Glossary

TermMeaning
PrefillThe pass over the full input prompt that builds the KV cache.
DecodeStep-by-step generation of output tokens, reading the cache each step.
KV cacheStored keys and values for past tokens, reused so decode avoids recomputing attention.
PagedAttentionStoring the KV cache in fixed-size blocks, like virtual memory pages.
Continuous batchingAdmitting and removing requests at every decode step rather than per batch.
Async schedulingPreparing the next step on the CPU while the GPU runs the current one.
Prefix cachingReusing the KV cache of a shared prompt prefix across requests.
Radix treeA prefix tree that stores shared prefixes compactly.
Speculative decodingA cheaper proposer guesses tokens that the large model verifies in one pass.
DisaggregationRunning prefill, decode, or encoder stages on separate workers.
Pipeline parallelismSplitting model layers across GPUs so each stage handles a subset of layers.
KV offloadMoving cold cache blocks to CPU memory, disk, or remote storage.
