1. Kubernetes on EKS

Hands-on debugging questions. Interviewers care about your method: describe, events, logs, then metrics.

A pod is stuck in Pending. How do you find out why? easy

Run kubectl describe pod and read the Events at the bottom. The scheduler writes its reason there. The usual causes:

  • Not enough room. No node has enough unreserved CPU or memory. The scheduler looks at requests, not live usage.
  • Taints with no matching toleration, or a nodeSelector or affinity rule that matches no node.
  • A PersistentVolumeClaim that is not bound (wrong StorageClass, or the volume lives in another AZ).
  • A ResourceQuota or LimitRange that rejects the pod.
  • On EKS, nodes that have run out of pod IPs, which shows as "Too many pods".

Fix by lowering oversized requests, adding capacity (Cluster Autoscaler or Karpenter), correcting selectors and tolerations, or fixing the volume.

kubectl describe pod <pod> -n <ns> | sed -n '/Events:/,$p'
kubectl get events -n <ns> --sort-by=.lastTimestamp | tail -20
kubectl describe node <node> | grep -A8 'Allocated resources'
A container restarts with exit code 137. What does it mean, and how do you tell OOMKilled from CPU throttling? easy

137 is 128 plus 9, which is SIGKILL. In Kubernetes it is most often the kernel OOM killer: kubectl describe pod shows Last State: Terminated, Reason: OOMKilled. The memory limit is a hard ceiling, and crossing it kills the container.

CPU is different. A CPU limit never kills anything, it throttles the container through the CFS quota. The symptom is latency, not restarts. Check container_cpu_cfs_throttled_periods_total divided by container_cpu_cfs_periods_total. Many teams therefore set CPU requests but leave CPU limits off for latency-sensitive services, while always setting a memory limit equal to the memory request.

A pod is in CrashLoopBackOff. Walk through your debugging steps. easy
  1. kubectl logs <pod> --previous shows the crashed container's output, not the fresh restart.
  2. kubectl describe pod gives the exit code, the last state and any probe failures.
  3. Check the obvious: a missing ConfigMap or Secret, a wrong command or args, a bad env var, a dependency (database, Kafka) that is unreachable at startup.
  4. Check whether a liveness probe is killing a slow-starting app. Add a startup probe if so.
  5. If the image has no shell, use kubectl debug -it <pod> --image=busybox --target=<container> to attach an ephemeral container.

The back-off delay doubles up to five minutes and resets after the container has run cleanly for ten minutes.

Liveness, readiness and startup probes: what does each do, and what goes wrong? easy

Readiness decides whether the pod receives traffic: fail it and the pod is removed from Service endpoints, but not restarted. Liveness decides whether the container is restarted. Startup holds off the other two until a slow app has booted.

The classic mistake is a liveness probe that checks a dependency (database, downstream API). When the dependency blips, every pod fails liveness at once, restarts, and you turn a small outage into a restart storm. Liveness should answer only "is this process stuck?". Put dependency checks in readiness, and keep them cheap.

How does a pod get an IP on EKS, and what limits pods per node? medium

The AWS VPC CNI gives each pod a real VPC IP address taken from the node's network interfaces. A node can only attach a fixed number of ENIs, and each ENI holds a fixed number of IPs, so the instance type caps pod density:

max pods = ENIs x (IPv4 addresses per ENI - 1) + 2

Two other limits bite. The subnet can run out of free IPs, and pods then sit in Pending or ContainerCreating. To relax both: enable prefix delegation (each IP slot holds a /28 prefix, which multiplies capacity), use bigger or secondary CIDR subnets, or use custom networking so pods draw from a separate range.

Explain QoS classes. Which pods are evicted first under node memory pressure? medium

Kubernetes assigns each pod a class from its requests and limits:

  • Guaranteed: every container has CPU and memory requests equal to limits.
  • Burstable: at least one request or limit is set, but not equal everywhere.
  • BestEffort: nothing is set.

Under memory pressure the kubelet evicts BestEffort pods first, then Burstable pods that exceed their requests, and Guaranteed pods last. The kernel's OOM score follows the same order. So critical workloads should have honest requests, and a node full of BestEffort pods is a node that falls over unpredictably.

How do you get zero-downtime rolling updates? medium

Several pieces have to line up:

  • maxUnavailable: 0 and a sensible maxSurge so capacity never dips (the default for both is 25 percent).
  • A real readiness probe, so new pods get traffic only when ready.
  • A preStop sleep of a few seconds plus a terminationGracePeriodSeconds long enough to drain, because the endpoint removal and the SIGTERM race each other.
  • The app handles SIGTERM: stop accepting new work, finish in-flight requests, then exit.
  • A PodDisruptionBudget so node drains and upgrades cannot take too many replicas at once.
  • Behind an AWS load balancer, match the target group deregistration delay to your drain time.
HPA, VPA, Cluster Autoscaler and Karpenter: how do they differ? medium

HPA changes the replica count from metrics (CPU utilisation is measured against requests, so wrong requests give wrong scaling). It needs metrics-server for resource metrics. VPA adjusts requests and limits, and is best used in recommendation mode. Cluster Autoscaler adds or removes nodes in a node group when pods are Pending or nodes are underused. Karpenter skips node groups and launches the right instance type directly for the pending pods, and consolidates nodes afterwards.

For event-driven workloads, KEDA scales on external signals such as Kafka consumer lag, which usually matches load better than CPU.

How do pods call AWS APIs safely? Compare IRSA with the node role. medium

If you leave it to the node's instance role, every pod on that node gets the same permissions, which is far too broad. IRSA (IAM roles for service accounts) uses the cluster's OIDC provider: a Kubernetes service account is annotated with a role ARN, and AWS trusts tokens for that account only. Each workload gets its own least-privilege role. EKS Pod Identity achieves the same result with a node agent and less OIDC plumbing. Either way, block pod access to the node's instance metadata, or require IMDSv2 with a hop limit of 1.

Describe how you would upgrade an EKS cluster with no downtime. medium
  1. Read the release notes, and scan for removed APIs (tools such as kubent or pluto, or check API server deprecation metrics).
  2. Upgrade lower environments first and run the real test suite.
  3. Upgrade the control plane one minor version at a time.
  4. Upgrade add-ons: VPC CNI, CoreDNS, kube-proxy, the EBS CSI driver, and your own controllers.
  5. Roll the node groups (managed node groups roll for you, or recycle Karpenter nodes). PDBs and good readiness probes protect traffic during the drain.
  6. Stay inside the supported node version skew, and do not sit on an old version: clusters past standard support cost about five times more per hour in extended support.
A node shows NotReady. What do you check? medium

Start with kubectl describe node and its Conditions: MemoryPressure, DiskPressure, PIDPressure, Ready. Then check the instance in the AWS console (status checks), SSH or SSM into it, and read journalctl -u kubelet and the container runtime logs. The common culprits are a full disk (images and logs), memory exhaustion, a dead CNI plugin, kubelet unable to reach the API server (security group, networking), or a failed instance. Cordon the node, drain it, and replace it rather than nursing it, but keep the evidence first if you need a root cause.

Service names resolve slowly or intermittently inside the cluster. What could be wrong? hard

Three usual suspects. First, ndots:5 in each pod's resolv.conf: an external name like api.example.com is tried with every search domain before the absolute lookup, multiplying DNS queries. Use fully qualified names with a trailing dot, or lower ndots. Second, CoreDNS is undersized or throttled: check its CPU, restarts and the coredns_dns_request_duration_seconds metric, and scale it with the cluster (proportional autoscaler). Third, UDP conntrack races on busy nodes. NodeLocal DNSCache fixes most of these by caching on every node and talking TCP upstream.

2. CI/CD and GitOps

Pipelines, Argo CD, secrets, rollbacks. Expect "what would you do?" more than definitions.

What is GitOps, and how does Argo CD implement it? easy

GitOps keeps the desired state of the system in Git and uses an agent to make reality match. The agent pulls from the repo, so the cluster never needs inbound credentials from CI. Argo CD continuously compares the manifests in Git with live objects and reports the difference. With automated sync it applies the change, with self-heal it reverts manual edits. You get review through pull requests, a full audit trail, and rollback by reverting a commit.

Why should image tags be immutable, and why avoid latest? easy

latest is a moving target: two nodes can run different images under the same tag, a rollback is impossible, and you cannot tell what is deployed. Tag images with the commit SHA (or a semantic version) and never overwrite a tag. Build once, then promote the same image from dev to staging to production. Where possible deploy by digest, and enable tag immutability in the registry.

Chef or Puppet versus Ansible. What is the difference? easy

Chef and Puppet usually run an agent on each node that pulls and converges configuration on a schedule. Ansible is agentless: it pushes tasks over SSH (or WinRM) from a control node and is easy to start with. All three aim for idempotent, declarative state. Today most teams provision with Terraform, bake images or use containers, and keep Ansible for the configuration that remains, so a hands-on answer is "I use Ansible, and I understand why the agent model exists."

In Argo CD, what is the difference between Synced and Healthy? Why does an app stay OutOfSync? medium

Sync status compares Git to live state (Synced or OutOfSync). Health is whether the resources work (Healthy, Progressing, Degraded, Missing, Suspended). They are independent: an app can be Synced and Degraded.

A permanent OutOfSync is almost always something else mutating the object: an HPA changing spec.replicas, a mutating webhook injecting sidecars, defaulted fields, or an operator writing status. Fix it by removing the field from Git (do not set replicas if an HPA owns them) or with ignoreDifferences for that path.

What do self-heal, prune, sync waves and hooks do? medium
  • Self-heal: if someone edits a live resource, Argo CD reverts it to Git.
  • Prune: resources deleted from Git are deleted from the cluster. Without it, orphans linger.
  • Sync waves (annotation argocd.argoproj.io/sync-wave) order resources inside a sync, for example namespace, then CRD, then the app.
  • Hooks (PreSync, Sync, PostSync) run jobs at a phase, such as a database migration before the new version rolls out.

Turn on prune carefully in production, and protect stateful resources with Prune=false.

App-of-apps or ApplicationSet? medium

App-of-apps is a parent Application whose manifests are child Applications. It is simple and explicit but you maintain each child by hand. ApplicationSet generates Applications from a template plus a generator (list, Git directories, clusters, pull requests). It scales better for many clusters or many similar services and is the usual answer for fleet management.

How do you handle secrets in a GitOps workflow? medium

Never commit plain Secrets. Options: External Secrets Operator (or the CSI driver) that reads from AWS Secrets Manager or Parameter Store, so Git holds only a reference; Sealed Secrets or SOPS, where encrypted values live in Git and only the cluster (or KMS) can decrypt; or Vault with an injector. Whichever you use, prefer short-lived credentials, scope access per namespace, and rotate on a schedule. Remember that Kubernetes Secrets are only base64, so enable encryption at rest with KMS for etcd.

How do you roll back in a GitOps setup? medium

The clean way is a git revert of the bad commit, because Git stays the source of truth and the rollback is reviewed and recorded. Argo CD also has a rollback to a previous synced revision, but it cannot be used while automated sync is enabled (the next sync would just reapply Git). For fast mitigation use feature flags or Argo Rollouts to abort a canary. Database changes need the expand and contract pattern so an app rollback never needs a schema rollback.

A pipeline takes 40 minutes. How do you speed it up? medium

Measure first, then fix the longest stage. Typical wins: cache dependencies and Docker layers (and the Gradle or Maven build cache), run independent stages in parallel, build and test only what changed in a monorepo, split slow end-to-end tests to run after merge, use bigger or warm runners, and fail fast by running cheap checks (lint, unit tests) first. Keep an eye on flakiness, because retries hide waste.

How would you secure the CI/CD pipeline itself? hard
  • Replace long-lived cloud keys with OIDC federation: the pipeline assumes a short-lived role scoped to one repo and branch.
  • Least privilege per job, protected branches, required reviews, and signed commits where practical.
  • Pin third-party actions, plugins and base images by digest. Pipeline plugins are a supply-chain risk.
  • Scan dependencies, images and IaC, produce an SBOM, and sign images (for example with cosign) and verify the signature at admission.
  • Isolate runners, keep secrets out of logs, and never run untrusted pull-request code with production credentials.
What does progressive delivery look like with Argo Rollouts? hard

A Rollout replaces the Deployment and shifts traffic in steps, for example 5 percent, 25 percent, 50 percent, 100 percent, pausing between steps. An AnalysisTemplate queries Prometheus (error rate, latency) at each step and aborts and rolls back automatically if the SLO is violated. Blue-green is also supported. The result is that a bad release hurts a small slice of users and is reverted without a human at 3 a.m.

3. AWS fundamentals

EKS, EC2, IAM, load balancers and VPC, the pieces every role in this space expects you to know cold.

IAM user, role and policy: what is the difference, and what wins when policies conflict? easy

A user has long-lived credentials. A role has no credentials of its own: something (a service, another account, a federated identity) assumes it and receives temporary ones. A policy is a JSON document of allow and deny statements attached to either. Evaluation is: default deny, an explicit Deny always wins, otherwise an Allow is needed. Prefer roles for everything automated, and use permission boundaries or SCPs to cap what teams can grant.

You get AccessDenied from an AWS API call. How do you debug it? medium

Read the exact error: it names the action and often the resource. Then work through the layers: the caller's identity (aws sts get-caller-identity), the identity policy, any permission boundary, a service control policy, the resource policy (S3 bucket, KMS key), and session policies. CloudTrail shows the denied call and the principal. The IAM policy simulator and Access Analyzer help. Cross-account and KMS cases are the usual traps, because both sides must allow.

Security group versus network ACL? easy

A security group is stateful, attached to an ENI, allow-only, and can reference other security groups. A NACL is stateless, applies to a whole subnet, has numbered allow and deny rules, and needs rules for return traffic. Use security groups for almost everything and keep NACLs coarse.

Explain public and private subnets, NAT and VPC endpoints. medium

A subnet is public if its route table sends 0.0.0.0/0 to an internet gateway. Private subnets reach the internet outbound through a NAT gateway in a public subnet. NAT charges an hourly fee plus per-GB processing, so it is a common cost surprise. Gateway endpoints for S3 and DynamoDB are free and keep that traffic off the NAT. Interface endpoints (PrivateLink) reach other AWS services privately but cost per hour per AZ.

ALB versus NLB: when do you choose each? medium

ALB is layer 7: host and path routing, redirects, header rules, WebSockets, authentication integration, and WAF. NLB is layer 4: very high throughput, static IPs per AZ, preserves the client source IP, and handles non-HTTP protocols. On EKS the AWS Load Balancer Controller provisions both. A rule of thumb is ALB for HTTP services, NLB for TCP or when you need fixed IPs. Use target-type ip to send traffic straight to pods.

Targets are unhealthy behind a load balancer. What is your checklist? medium
  1. Is the health check path and port correct, and does it return the expected code quickly?
  2. Do the target's security group rules allow the load balancer's security group on the traffic and health check ports?
  3. Is the app actually listening on that port and bound to 0.0.0.0, not 127.0.0.1?
  4. Is the timeout or the unhealthy threshold too strict for a slow-starting app?
  5. On EKS, does the pod's readiness gate or the Service selector match?

Also look at the target group's reason code in the console, which is usually specific.

An EC2 instance fails a status check. What do you do? medium

There are two checks. A system status failure is a problem on the AWS side (host hardware, networking): stop and start the instance to move it to new hardware, or enable auto-recovery. An instance status failure is inside the OS (kernel panic, full disk, bad network config): look at the console output and screenshot, then fix via SSM, or attach the root volume to a rescue instance. Design so that losing one instance never matters: Auto Scaling groups, health checks and immutable images.

gp3 versus gp2, and how do you grow a volume without downtime? medium

gp3 is about 20 percent cheaper per GB than gp2, and gives a baseline of 3,000 IOPS and 125 MiB/s regardless of size, with IOPS and throughput adjustable independently. gp2 ties IOPS to size. Converting gp2 to gp3 is online and free of downtime. To grow a volume, modify the size (Elastic Volumes), then extend the partition and filesystem inside the OS (growpart and resize2fs or xfs_growfs). A volume can only be modified again after a cooldown.

Why does cross-AZ traffic matter on EKS, and how do you reduce it? hard

Traffic between AZs in a region is billed per GB in each direction, and chatty services (replication, scraping, Kafka, service-to-service calls) can quietly create large bills. Spreading pods across AZs is good for availability but each call may then cross a zone. Reduce it with topology-aware routing or trafficDistribution: PreferClose where your Kubernetes version supports it, rack awareness for Kafka consumers (fetch from the closest replica), keeping tightly coupled pairs together, and watching the cross-AZ usage type daily.

Design a production VPC for an EKS cluster. hard

Use three AZs. Put nodes and pods in private subnets sized generously (pods consume VPC IPs), and put load balancers in public subnets tagged for the AWS Load Balancer Controller. Plan the CIDR so it does not overlap with other networks you will peer. Add gateway endpoints for S3 and ECR image layers, and interface endpoints for the services you call heavily. Decide NAT per AZ (resilient, costs more) versus a shared NAT (cheaper, a single point of failure). Lock down the API endpoint, use separate node security groups, and send VPC flow logs to the cheapest suitable destination.

4. Observability: Prometheus, Grafana and Elasticsearch

Metrics, logs, traces and the alerting habits that keep on-call sane.

How does Prometheus collect metrics, and what are exporters? easy

Prometheus pulls (scrapes) an HTTP /metrics endpoint on a schedule, using service discovery to find targets. Pull makes it easy to see that a target is down (the up metric is 0). Software that does not expose metrics is covered by exporters, for example node_exporter for hosts, kube-state-metrics for Kubernetes objects, and Kafka or Elasticsearch exporters. On Kubernetes, the Prometheus Operator's ServiceMonitor and PodMonitor describe what to scrape. Short-lived jobs use the Pushgateway.

Metrics, logs and traces: when do you use each? easy

Metrics are cheap numbers over time: they tell you that something is wrong and drive alerts. Logs are event detail: they tell you what happened in one instance. Traces follow one request across services: they tell you where the time went. A good workflow is alert on a metric, jump to a trace through an exemplar, then read the matching logs.

Counter, gauge, histogram: what are they, and why is average latency misleading? medium

A counter only goes up (requests, errors) and you always look at it through rate(). A gauge goes up and down (memory, queue length). A histogram buckets observations so you can compute percentiles on the server with histogram_quantile. The average hides the tail: a service with a 50 ms average can still have a 3 second p99 that real users feel. Alert and set SLOs on percentiles.

# error ratio over 5 minutes
sum(rate(http_requests_total{code=~"5.."}[5m]))
  / sum(rate(http_requests_total[5m]))

# p99 latency
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# CPU used per pod, in cores
sum by (pod) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))
How does Alertmanager reduce noise? medium

Prometheus decides when a rule fires (use the for: clause so a one-minute blip does not page). Alertmanager then groups related alerts into one notification, routes by label to the right team, inhibits lower-level alerts when a higher one is firing (do not page for every pod when the node is down), and lets you silence during maintenance. Alert on symptoms users feel (errors, latency, saturation) rather than on every cause, and attach a runbook link to each alert.

What are SLIs, SLOs, error budgets and burn rate alerts? medium

An SLI is a measurement, such as good requests divided by valid requests. An SLO is the target for it, for example 99.9 percent over 30 days. The error budget is what remains: 0.1 percent, or about 43 minutes a month. A burn rate measures how fast you spend the budget. The standard multi-window alert pages when you burn at about 14.4 times the allowed rate over both 1 hour and 5 minutes (that spends 2 percent of the monthly budget in an hour), and opens a ticket for slower burns. It catches real problems quickly and ignores blips.

Prometheus is using huge memory. What is cardinality, and how do you fix it? medium

Every unique combination of label values is a separate time series, and the head block keeps active series in memory. A label with unbounded values (user ID, request ID, full URL path, pod name with churn) creates millions of series. Find the offenders on the TSDB status page or by counting series per metric, then drop or rewrite labels with metric_relabel_configs, fix the instrumentation, add recording rules, and set sample limits per scrape. Scaling up memory only delays the problem.

An Elasticsearch cluster is yellow or red. What does that mean and what do you do? medium

Green: all shards assigned. Yellow: all primaries are assigned but some replicas are not (often a single-node cluster, or a lost node). Red: at least one primary shard is unassigned, so some data is unavailable. Run GET _cluster/health, then GET _cluster/allocation/explain to see exactly why a shard is stuck. The most frequent cause is disk watermarks: at 85 percent used Elasticsearch stops allocating new shards to a node, at 90 percent it relocates shards away, and at 95 percent it makes indices read-only. Free or add disk, delete old indices, then clear the read-only block if it was applied.

curl -s localhost:9200/_cluster/health?pretty
curl -s localhost:9200/_cluster/allocation/explain?pretty
curl -s 'localhost:9200/_cat/shards?v&h=index,shard,prirep,state,node,unassigned.reason'
How do you size and manage an Elasticsearch cluster for logs? hard

Keep shards in the tens of gigabytes and avoid thousands of tiny shards, because every shard costs heap and file handles. Give each node a JVM heap of at most about half its RAM and under roughly 31 GB so compressed object pointers stay on. Use index lifecycle management: roll over daily or by size, move older indices to cheaper warm or cold nodes, then delete. Use data streams, tune the refresh interval for heavy ingest, and put a queue (Kafka) in front so ingest bursts do not overwhelm the cluster.

What does distributed tracing add, and what is sampling? medium

A trace is a tree of spans showing one request crossing services, so you can see which hop is slow or failing. Instrument with OpenTelemetry and store in a backend such as Tempo. Tracing every request is expensive, so you sample: head sampling decides at the start (cheap but may drop the interesting ones), tail sampling decides after the trace finishes (keeps errors and slow traces). Exemplars attach a trace ID to a metric sample, so a latency spike on a graph links to a concrete slow trace.

Nagios versus Prometheus: what changed? easy

Nagios style monitoring runs checks that return OK, warning or critical, and was built for fairly static hosts. Prometheus collects dimensional metrics and lets you query and alert on them, which suits dynamic, containerised systems where hosts come and go. Checks tell you the state; metrics tell you the trend and let you build SLOs. Many teams still use blackbox probes for simple "is it up" checks, but inside Prometheus.

What makes a dashboard useful at 3 a.m.? medium

One top-level view per service built on the golden signals (latency, traffic, errors, saturation), or RED for services (rate, errors, duration) and USE for resources (utilisation, saturation, errors). Put the SLO and error budget first, then drill-down panels, with consistent variables (cluster, namespace, service) and deploy markers so you can see if a release caused the change. Keep dashboards in code (JSON or Terraform) so they are reviewed and reproducible.

5. Apache Kafka

Topics, partitions, consumer groups, lag, and what to do when things fail.

Explain topics, partitions, offsets and consumer groups. easy

A topic is a named log split into partitions. Each partition is an ordered, append-only sequence and each record has an offset. Ordering is guaranteed only within a partition, and records with the same key go to the same partition. A consumer group shares the work: each partition is read by exactly one consumer in the group at a time, so parallelism is capped at the partition count. Different groups read the same data independently and track their own committed offsets.

What is consumer lag, and how do you monitor it? easy

Lag is the log-end offset minus the group's committed offset, per partition: how far behind the consumers are. Check it with the CLI, or export it continuously with a lag exporter into Prometheus. Alert on lag that keeps growing (a positive trend over several minutes) rather than a fixed number, since a busy but healthy consumer can show a large steady lag, and watch time lag as well as message count.

kafka-consumer-groups.sh --bootstrap-server broker:9092 \
  --describe --group orders-service
# GROUP TOPIC PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG CONSUMER-ID ...
Consumer lag keeps growing. Walk through the causes and fixes. medium
  • Consumers are too slow: slow processing, a slow downstream call, GC pauses. Profile, batch writes, add concurrency.
  • Not enough consumers: scale the group up, but only to the partition count. Beyond that extra consumers sit idle.
  • Hot partition: a skewed key sends most traffic to one partition. Change the key or add salting.
  • Rebalance churn: consumers repeatedly leave and rejoin, so little work is done (see next question).
  • Poison message: one record fails and is retried forever, blocking the partition. Use retries with a limit and a dead-letter topic.
  • Producer surge: input rate simply exceeds capacity. Scale, or add partitions.

Check the per-partition view first. Lag on one partition points to skew or a poison message, lag on all points to capacity or the downstream.

What causes rebalance storms, and how do you reduce them? medium

A rebalance happens when a consumer joins or leaves, or is considered dead. The usual triggers are processing that takes longer than max.poll.interval.ms, a missed heartbeat past session.timeout.ms (long GC, CPU starvation), and rolling deployments that restart pods one after another. Reduce them by processing smaller batches (max.poll.records), tuning the timeouts, using static membership (group.instance.id) so a restart does not trigger a rebalance, and the cooperative sticky assignor so only the moved partitions pause.

How does Kafka replicate data? Explain ISR, acks and min.insync.replicas. medium

Each partition has a leader and followers. The in-sync replicas (ISR) are the followers that are caught up. With acks=all, the leader waits for every ISR member, and min.insync.replicas sets the minimum ISR size that must exist for a write to succeed. The common production setup is replication factor 3, min.insync.replicas=2 and acks=all: you survive one broker loss without losing acknowledged data or availability. Keep unclean.leader.election.enable=false so an out-of-date replica never becomes leader. Alert on under-replicated partitions.

kafka-topics.sh --bootstrap-server broker:9092 --describe --under-replicated-partitions
How should a consumer handle failures without losing or duplicating data? medium

Kafka is normally at-least-once: commit offsets after processing, so a crash causes a reprocess, not a loss. Make processing idempotent (upsert by a unique ID) so duplicates are harmless. Retry transient errors with backoff, and send records that keep failing to a dead-letter topic with the error attached, so one bad message cannot block the partition. On the producer side use enable.idempotence=true and acks=all. True exactly-once across systems needs transactions and a transactional sink.

How do you choose the number of partitions? Can you change it later? medium

Start from target throughput divided by the throughput one partition can handle, and from the maximum consumer parallelism you want, then add headroom. More partitions mean more open files, more replication work and longer failovers, so do not over-provision. You can increase partitions but never decrease them, and increasing changes which partition a given key maps to, which breaks per-key ordering for existing data. Plan the number up front for keyed topics.

A broker's disk is almost full. What do you do? medium

Find which topics use the space (kafka-log-dirs.sh, or the disk metrics per topic). Short term, reduce retention on the heaviest topics (retention.ms or retention.bytes), which frees segments at the next cleanup, or move partitions off the broker with the reassignment tool. Longer term add storage or brokers and rebalance, and alert on disk well before it is full, because a broker that runs out of disk can stop and risk a cascade.

You need to reprocess data from yesterday. How do you reset offsets? medium

Stop the consumers first, because the group must be inactive. Preview with --dry-run, then execute. You can reset to the earliest offset, to a timestamp, or by a shift. Make sure the consumer is idempotent, since it will see old records again.

kafka-consumer-groups.sh --bootstrap-server broker:9092 --group orders-service \
  --topic orders --reset-offsets --to-datetime 2026-10-26T00:00:00.000 --dry-run
# then replace --dry-run with --execute
What happens when a broker dies, and how do clients react? hard

The controller (a KRaft quorum on newer clusters, ZooKeeper before it was removed in Kafka 4.0) notices the failure and elects new leaders from the ISR for each affected partition. Producers and consumers get a metadata error, refresh their metadata and retry against the new leader, so with sensible retry settings clients see a short blip. Partitions with replication factor 1, or with the ISR below min.insync.replicas, become unavailable for writes. When the broker returns it catches up and rejoins the ISR, and preferred leader election moves leadership back.

6. Aerospike

Working knowledge: the data model, scaling, and how to reason about performance. Exact setting names vary by server version, so always check the docs for yours.

Describe the Aerospike data model. easy

The hierarchy is namespace (the top-level container, with its own storage and replication settings), set (an optional grouping, a bit like a table), record (identified by a key) and bins (named values inside a record, like columns). Records are looked up by key, and the key is hashed to a 20-byte digest used for placement. It is a distributed key-value store built for low-latency reads and writes at scale, not a general query engine.

How does Aerospike distribute data and route requests? medium

The cluster is shared-nothing. Each namespace is divided into 4,096 partitions, and the partitions (primary and replica copies, according to the replication factor) are spread across nodes. The key's digest decides the partition. A smart client keeps the partition map and sends each request straight to the right node, so there is no central router. When nodes join or leave, partitions migrate automatically to rebalance.

What lives in memory, and how do you size a cluster? medium

The primary index is always in RAM, at about 64 bytes per record. Data itself can be stored in memory, on SSD (usually raw devices), or on persistent memory, per namespace. A first sizing check is the primary index memory: records x 64 bytes x replication factor, divided across nodes, plus the data if it is in memory. Leave headroom for growth and for the loss of a node (the survivors take its partitions), and keep disk usage and memory usage below the thresholds that trigger eviction.

What happens when you add or remove a node? medium

The cluster re-forms and partitions migrate so each node holds its share again. Migrations use network, disk and CPU, and can raise latency, so they are throttled by settings such as migrate-threads, and there are options to delay migrations after a node leaves (migrate-fill-delay, check your version). Add nodes during quieter periods, one at a time, and watch the remaining migrations statistic until it reaches zero before the next change. Do the same discipline for rolling restarts.

How do TTL and eviction work, and what is stop-writes? medium

Each record can carry a TTL (time to live), with a namespace default, and a background process (nsup) removes expired records. If memory or disk use crosses a high-water threshold, the server can evict records that are closest to expiry to make room. If usage climbs further to the stop-writes threshold, the namespace rejects writes to protect itself, and clients see errors while reads continue. Names of these settings changed between versions, so check yours. Alert before the thresholds, and treat a stop_writes flag as an incident.

Which commands do you use for day-to-day operations and checks? medium

asadm (the admin tool) gives a cluster view, and asinfo queries a single node. aql runs simple queries for inspection. Useful checks are cluster size and namespace summaries, the latency histograms, namespace statistics (memory, disk, stop-writes, migrations), and the logs.

asadm -e "info"                                  # cluster and namespace overview
asadm -e "show latencies"                        # read/write latency histograms
asadm -e "show statistics namespace like migrate" # migration progress
asinfo -v "namespace/<ns>"                       # one node, one namespace
Latency spikes on one node. How do you investigate? hard

Compare nodes with the latency histograms to confirm it is one node and one operation type. Then look for: a hot key (one record hit far more than others, so its node saturates), large records, a device that is slow or at its IOPS limit, defragmentation or migrations running, a noisy neighbour or CPU steal, network issues, and clients that are scanning or running heavy batch calls. Mitigate hot keys with client-side caching or by splitting the record, throttle migrations, and fix capacity. Check the OS metrics (iostat, network) alongside the Aerospike ones.

Availability versus consistency: how does Aerospike behave, and what is XDR? hard

By default a namespace favours availability: during a partition each side can keep serving, and conflicts are resolved afterwards. Aerospike also offers a strong consistency mode, which uses a roster of nodes, guarantees no lost or stale reads for committed writes, and makes affected partitions unavailable rather than risk inconsistency. XDR (cross datacenter replication) ships changes asynchronously to another cluster for disaster recovery or geographic distribution. In an interview, show that you know the trade-off and choose per use case.

7. Infrastructure and configuration as code

Terraform state, safe changes, Ansible and Python.

What is Terraform state, and why is a remote backend with locking important? easy

State maps your configuration to real resources and records their attributes, which is how Terraform computes a plan. Keep it in a remote backend (for example S3 with encryption and versioning) so the team shares one source of truth, with locking so two applies cannot run at once (a DynamoDB table historically, and newer Terraform versions can lock directly in S3). State can contain secrets, so restrict access and encrypt it.

How do you detect and fix drift? medium

Drift is real infrastructure that no longer matches the code, usually from manual console changes. terraform plan (or plan -refresh-only) shows it, and a scheduled plan in CI with an alert on a non-empty diff catches it early. Then decide: update the code to match the change, or apply to revert it. The real fix is cultural and technical: restrict console write access and make the pipeline the only path.

count versus for_each? medium

count creates resources by numeric index, so removing an item from the middle shifts every later index and Terraform plans to destroy and recreate them. for_each keys resources by a stable string or ID, so adding or removing one item affects only that item. Prefer for_each for anything that is not a simple on or off switch.

How do you rename or move a resource without destroying it? medium

Use a moved block (or terraform state mv) so the state follows the new address, and an import block (or terraform import) to adopt an existing resource. Always run a plan and confirm it shows no destroy before applying. For critical resources add lifecycle { prevent_destroy = true } so an accidental plan fails loudly.

moved {
  from = aws_db_instance.main
  to   = module.database.aws_db_instance.main
}
The state lock is stuck after a failed run. What do you do? medium

First make sure no apply is really still running, since forcing the lock while one runs can corrupt state. Then use terraform force-unlock <lock-id> with the ID from the error, and run a plan to verify the state is consistent. Prevent it by running Terraform in CI with timeouts and a single concurrency group per state.

How do you structure Terraform for a team? medium

Split state by blast radius and change rate: networking, clusters, and applications in separate states, not one giant file. Write small versioned modules, pin provider and module versions, and keep one environment per directory or workspace with clear variable files. Run plan on every pull request and require review, then apply from CI only. Scan the code (tflint, checkov or similar) and keep secrets out of variables files.

What makes an Ansible play idempotent, and how do you test one? medium

Use modules that describe a desired state (package present, file with content, service started) instead of raw shell commands. A second run should report no changes. Test with --check --diff for a dry run, run the playbook twice and assert the second run changes nothing, and use Molecule for role testing. Use handlers to restart a service only when its config actually changed, and Ansible Vault (or an external secret store) for secrets. A dynamic inventory built from AWS tags avoids stale host lists.

Where does Terraform end and Ansible begin? medium

Terraform provisions things with APIs (networks, instances, databases, IAM). Ansible configures what runs inside them (packages, files, services). A modern preference is to push most configuration into images and containers, so each is built once and replaced rather than patched, and to keep Ansible for the leftover cases and for orchestration tasks.

8. Linux fundamentals

The commands and mental models that solve most "the server is slow" problems.

Load average is high but CPU looks idle. How is that possible? easy

On Linux, load average counts tasks that are runnable and tasks in uninterruptible sleep (state D), usually waiting on disk or network storage. So a slow disk or a hung NFS mount can show a huge load with idle CPU. Check vmstat 1 (the wa column and the b blocked count), iostat -xz 1 for device utilisation and await time, and ps -eo state,pid,cmd | awk '$1=="D"' for stuck processes.

free shows almost no free memory. Is there a problem? easy

Probably not. Linux uses spare RAM as page cache and gives it back when applications need it. Look at the available column, not free. A real problem is low available memory plus swapping (vmstat si and so) or OOM kills. Confirm with dmesg -T | grep -i 'out of memory' and journalctl -k.

The disk is full but df shows free space, or df shows full but du finds little. Why? medium

Several causes. Inodes can run out while blocks remain (df -i), usually from millions of tiny files. A deleted file still held open by a process keeps its space until the process closes it (lsof +L1 lists them, restart or truncate via /proc). The space may be in another mount hidden under a directory, or reserved blocks on ext filesystems. Containers add overlay layers and logs: check /var/lib/docker or the container runtime directory.

You see "too many open files". How do you diagnose and fix it? medium

Every socket and file consumes a descriptor. Check the process limit in /proc/<pid>/limits and the count in ls /proc/<pid>/fd | wc -l, and find leaks with lsof -p. Raise the limit where the process actually gets it: for a systemd service set LimitNOFILE (shell ulimit does not apply), and for containers set it in the runtime. Raising the limit hides a leak, so also find out why descriptors are not being closed.

Outline your network debugging order for "service A cannot reach service B". medium
  1. Name resolution: dig or getent hosts.
  2. Reachability and routing: ping (may be blocked), mtr or traceroute.
  3. Port and listener: nc -vz host port, curl -v, and on the target ss -tulpn.
  4. Firewalls: security groups, NACLs, iptables or nftables, Kubernetes NetworkPolicies.
  5. Packets: tcpdump on both ends to see where they stop.
  6. TLS: openssl s_client -connect for certificate and handshake errors.
SIGTERM versus SIGKILL, and what is a zombie process? medium

SIGTERM asks a process to shut down and can be handled for a clean exit. SIGKILL cannot be caught: the kernel just removes the process, with no cleanup. Orchestrators send SIGTERM, wait the grace period, then SIGKILL. A zombie is a finished process whose parent has not yet read its exit status, so it holds a process table entry. You cannot kill a zombie, you fix or stop the parent. In containers the process with PID 1 must reap children and forward signals, so use a small init such as tini if your app does not.

A process hangs. How do you find what it is doing without restarting it? hard

Check its state in ps or /proc/<pid>/status (D means stuck in I/O). Attach strace -p <pid> -f to see the last system call, for example blocked on a futex, a socket read or a disk call. Use /proc/<pid>/stack and wchan for the kernel side, lsof and ss for what it holds open, and a thread dump or a profiler for the language runtime (jstack, py-spy). Capture evidence before you restart.

Outbound connections fail intermittently through a NAT. What could be exhausted? hard

A NAT maps each connection to a source port, and the range of ports per destination is finite (about 64,000 per IP and destination). Many short connections to one destination can exhaust it, which shows as timeouts and as ErrorPortAllocation metrics on a NAT gateway. On a host, many sockets in TIME_WAIT (ss -s) show the same symptom. Fix with connection pooling and keep-alive, spreading across more NAT IPs, and gateway endpoints that bypass the NAT for AWS services.

9. Scripting: Python and Bash

Short, realistic tasks. Interviewers watch for error handling and clarity, not cleverness.

Write a Bash script safely. Which habits matter? easy

Start with strict mode, quote variables, and clean up on exit. A script that silently continues after an error is how you delete the wrong thing.

#!/usr/bin/env bash
set -euo pipefail            # exit on error, unset vars, and pipe failures
IFS=$'\n\t'

tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT    # always clean up

backup() { tar -czf "$tmp/backup.tgz" -C "$1" .; }
[[ $# -eq 1 && -d $1 ]] || { echo "usage: $0 <dir>" >&2; exit 2; }
backup "$1"
echo "ok: $(du -h "$tmp/backup.tgz" | cut -f1)"
List every pod that has restarted more than 5 times. medium

Use JSON output and jq, which is more robust than parsing the table.

kubectl get pods -A -o json | jq -r '
  .items[]
  | select(any(.status.containerStatuses[]?; .restartCount > 5))
  | "\(.metadata.namespace)/\(.metadata.name)"'
Total the Kafka lag for a consumer group in a script. medium

The CLI output has the lag in the sixth column. Skip headers and non-numeric rows.

kafka-consumer-groups.sh --bootstrap-server broker:9092 \
  --describe --group orders-service 2>/dev/null |
  awk 'NR>1 && $6 ~ /^[0-9]+$/ {sum += $6} END {print sum+0}'
Write a retry helper with exponential backoff and jitter in Python. medium

Retrying immediately makes an outage worse. Back off exponentially, add random jitter so clients do not retry in lockstep, cap the delay, and retry only errors that can succeed later.

import random, time
from functools import wraps

def retry(attempts=5, base=0.5, cap=30.0, exceptions=(ConnectionError, TimeoutError)):
    def deco(fn):
        @wraps(fn)
        def wrapper(*a, **kw):
            for i in range(attempts):
                try:
                    return fn(*a, **kw)
                except exceptions:
                    if i == attempts - 1:
                        raise
                    delay = min(cap, base * 2 ** i)
                    time.sleep(random.uniform(0, delay))   # full jitter
        return wrapper
    return deco

@retry()
def call_api():
    ...
Find unattached EBS volumes across a region with boto3. medium

Use a paginator, because a single call returns a limited page of results. Reviewing before deleting is the safe default.

import boto3

ec2 = boto3.client("ec2", region_name="ap-south-1")
paginator = ec2.get_paginator("describe_volumes")

total_gb = 0
for page in paginator.paginate(Filters=[{"Name": "status", "Values": ["available"]}]):
    for v in page["Volumes"]:
        total_gb += v["Size"]
        print(v["VolumeId"], v["Size"], "GiB", v["VolumeType"], v["CreateTime"].date())

print("unattached:", total_gb, "GiB")

10. SRE practice, on-call and cost

Reliability habits and awareness of cost, both of which come up in every loop.

SLI, SLO and SLA: what is the difference? easy

An SLI is a measured number (the fraction of requests served successfully under 300 ms). An SLO is the internal target for it (99.9 percent over 30 days). An SLA is a contract with consequences, usually looser than the SLO so you have room to react. Pick SLIs users actually feel, and use the error budget to decide between shipping features and fixing reliability.

What is toil, and how do you reduce it? easy

Toil is work that is manual, repetitive, automatable, reactive and that grows with the service without adding lasting value. Examples: restarting stuck jobs, manual deploys, hand-run capacity changes. Track it, cap it (a common target is under half of an engineer's time), and automate the biggest items first, starting with those that recur most often or wake people at night.

How do you run an incident, and what goes in a good postmortem? medium

Assign an incident commander, a communications lead and the people doing the fix, and give stakeholders updates on a fixed cadence in one channel. Mitigate first (roll back, shed load, fail over), diagnose second. Afterwards write a blameless postmortem: impact, timeline, root causes and contributing factors, what went well, what went badly, and concrete action items with owners and dates. The aim is to fix the system, not to find someone to blame.

On-call is noisy. How do you fix alert fatigue? medium

Audit every alert from the last month. Delete the ones nobody acted on, convert cause alerts into symptom alerts tied to SLOs, add a for: duration, group and deduplicate, and link a runbook to each page. Page only for things that need a human right now, and send the rest to tickets or a daily digest. Review the on-call load regularly as a team metric.

What are the biggest cost levers for Kubernetes on AWS? medium
  • Right-size requests and instances, using real usage (VPA recommendations or metrics). Oversized requests waste whole nodes.
  • Use Spot for stateless and fault-tolerant work, and Karpenter consolidation to remove idle nodes.
  • Buy Savings Plans only after right-sizing, for the steady baseline.
  • Cut data transfer costs: gateway endpoints, cross-AZ traffic, NAT usage.
  • Move gp2 volumes to gp3, delete unattached volumes and idle load balancers, and set retention on logs and snapshots.
  • Keep clusters on supported versions, since extended support is billed at a higher hourly rate.
  • Allocate cost by label or namespace (OpenCost or Kubecost) so teams see what they spend.
How do you decide between a rollback and a fix-forward during an outage? medium

If the change is recent, the cause is plausibly that change, and rollback is safe (no incompatible data migration), roll back: it is the fastest, most predictable way to restore service. Fix forward only when rollback is impossible or riskier (a destructive migration already ran) and the fix is small and well understood. Either way, decide quickly, say it out loud in the incident channel, and keep the change small.

11. Production scenarios

The questions that separate hands-on engineers from people who read documentation. Answer with a method and say what you would check first.

Consumer lag started growing right after a deployment. What do you check? hard
  1. Compare lag per partition. One partition points to skew or a poison message, all partitions point to capacity.
  2. Look for a rebalance storm in the consumer logs and the group's generation changes. A rolling deploy often triggers one.
  3. Diff the release: a changed batch size, a new slow dependency, a changed timeout (max.poll.interval.ms), a deserialisation change, fewer replicas or lower CPU limits.
  4. Check downstream latency (database, API) and consumer CPU throttling.
  5. Mitigate: roll back, or scale consumers up to the partition count. Add a dead-letter route if one record is looping.
New pods on EKS stay Pending or in ContainerCreating even though nodes have free CPU and memory. What is going on? hard

Suspect IP exhaustion: the subnet has no free addresses, or the node has hit its maximum pods for its instance type. The kubelet or CNI events say "failed to assign an IP" or "Too many pods". Check free IPs per subnet, the CNI logs on the node, and the awscni metrics. Fix with prefix delegation, larger or additional subnets (secondary CIDR with custom networking), or bigger instance types. Also check whether warm IP settings are reserving too many addresses.

An Argo CD application flips between OutOfSync and Synced after every HPA scale event. Fix it. hard

Git declares replicas: 3 but the HPA keeps changing the live value, so Argo CD sees a diff and, with self-heal on, fights the HPA. Remove spec.replicas from the manifest so the HPA owns it, or add ignoreDifferences for /spec/replicas on the Deployment (and enable RespectIgnoreDifferences when syncing). The same pattern applies to any field owned by a controller or webhook.

Prometheus restarts with out-of-memory errors every few hours. What is your plan? hard

Confirm it is series growth: the number of active series, and which metrics and labels contribute most (TSDB status page). Look for a recent change that added a high-cardinality label or a new exporter. Drop or rewrite labels with relabelling, remove unused metrics, add recording rules for heavy queries, and set per-scrape sample limits so one target cannot hurt everyone. Short term, raise memory to stabilise. Long term, shard by team or use a remote-write backend, and review cardinality in code review.

A site sees random 502s from the load balancer only during deployments. Why? hard

Two common causes. First, termination races: the pod gets SIGTERM and stops listening before the load balancer has deregistered it, so in-flight and new requests fail. Fix with a preStop sleep, a long enough grace period, graceful shutdown in the app, and a deregistration delay that matches. Second, keep-alive mismatch: if the app closes idle connections sooner than the load balancer's idle timeout (60 seconds by default on an ALB), the balancer reuses a connection the app already closed and returns a 502. Set the app's keep-alive timeout higher than the balancer's.

Latency rises on the key-value store when you add a node. Is that expected? What do you do? hard

Yes, to a degree. Partition migrations compete with live traffic for disk, CPU and network. Check the remaining migrations count and the latency histograms, then slow the migration rate for the duration, avoid adding capacity at peak traffic, and add one node at a time. If latency stays bad after migrations finish, look for hot keys, a node with a slow device, or an undersized cluster that was already near its limits.

Terraform wants to destroy and recreate a production database. What do you do? hard

Stop and do not apply. Read the plan to find which attribute forces replacement (it is marked in the output). Common causes are a renamed resource without a moved block, a changed immutable argument, or drift. Add moved or import so the state matches, revert the argument, or change to a supported in-place path. Protect it going forward with prevent_destroy, deletion protection on the database, final snapshots, and a required human approval for plans that contain a destroy.

Production is down because a TLS certificate expired. How do you prevent a repeat? hard

Automate issuance and renewal (cert-manager in Kubernetes, ACM for AWS load balancers), so no human renews anything. Add monitoring that does not trust the automation: probe real endpoints with the blackbox exporter and alert on probe_ssl_earliest_cert_expiry at 21, 14 and 7 days. Inventory certificates (including internal and mutual TLS ones), and include certificate expiry in your game days. In the incident review, ask why the renewal failed, not only why nobody noticed.

Nodes evict pods at 3 a.m. and nobody was alerted. What was missing? hard

Probably a disk or memory pressure condition with no alert on the cause. Add alerts on node conditions (kube_node_status_condition), on filesystem usage with a prediction (predict_linear shows disk that will fill in hours), on image and log growth, and on eviction events. Set ephemeral-storage requests and limits, configure log rotation and image garbage collection, and make sure the alert routes to someone and has a runbook.

A single user-facing endpoint is slow, but CPU and memory look normal everywhere. How do you find the bottleneck? hard

Use the golden signals and traces. Check the endpoint's latency histogram, then a trace to see which span dominates. A slow span points to a dependency (database query, cache miss, downstream API, Kafka produce), so look at that dependency's own metrics: connection pool saturation, lock waits, slow query logs, throttling. If no span stands out, check thread pool queues, DNS time, TLS handshakes and CPU throttling (limits can throttle without high usage). Reproduce with a load test once you have a hypothesis.

how to answer well

Interviewers in this space lean on live debugging stories ("a pod will not start," "lag is growing," "the deploy broke production") and on whether you can explain a trade-off. Answer debugging questions with a method: what you would look at first, what each result would tell you, and how you would mitigate before you fully diagnose. Mention cost and safety unprompted (blast radius, rollback, least privilege). For Kafka and the key-value store, show you understand failure modes and capacity, not just the commands. If you do not know a setting name, say so and explain the concept; it is better than guessing.

A one-week practice plan

  1. Day 1: break things on a local cluster (kind or minikube): OOMKill a pod, fail a probe, drain a node, and read the events each time.
  2. Day 2: install Argo CD, deploy an app, then force it OutOfSync and fix it with ignoreDifferences.
  3. Day 3: run Kafka locally, build a producer and consumer group, create lag on purpose, and use the CLI to inspect and reset offsets.
  4. Day 4: write a small Terraform module with a remote state, then rename a resource using a moved block.
  5. Day 5: run Prometheus and Grafana, write the error ratio and p99 queries, and add an alert with a runbook.
  6. Day 6: practise Linux triage on a loaded VM: top, vmstat, iostat, ss, strace, and df -i.
  7. Day 7: mock interview. Pick five scenarios from section 11 and answer each out loud in under three minutes.
