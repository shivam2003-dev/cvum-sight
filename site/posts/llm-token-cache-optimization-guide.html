Save tokens & cache on every LLM — the complete guide.

devops llm tokens claude-code cost-optimization

Every token you send and receive costs money and eats your context window. This is the complete, current guide to spending fewer of them across Claude (Claude Code), OpenAI Codex, and GitHub Copilot — and the three levers that beat everything else: prompt caching (50–90% off repeated context), the Batch API (50% off non-urgent jobs), and a tool-output proxy like RTK (60–90% off the command-output firehose). Plus the trending 2026 toolbelt — Caveman (output), Graphify (code exploration), Headroom (logs/RAG), memory layers — each attacking a different token sink. You'll get the billing model that actually matters, a provider-by-provider cache cheat-sheet, cache-friendly prompting rules, per-tool token tactics, and copy-paste macOS install commands for every CLI. Real numbers throughout; people have cut bills from $720 to $72 a month with the cache alone.

If you use AI coding tools seriously, two things creep up on you: the bill (or the rate-limit wall on a subscription) and the context window filling up until the model gets dumber and slower. Both have the same root cause — tokens. You pay per token in, per token out, and every token in the window is re-read on every turn. Most people just throw more money or bigger models at it. The people who actually run these tools cheaply do something smarter: they manage tokens deliberately and they exploit the cache.

This guide is the playbook, current as of mid-2026. It's tool-agnostic where the ideas are universal and tool-specific where they're not. Nothing here is theoretical — the techniques come straight from each provider's own docs and from teams who've measured the savings. Let's start with the thing nobody explains clearly: what you're actually paying for.

How LLM billing actually works (the part nobody explains)

There isn't one "token price." There are up to four, and the gap between them is where all the savings live:

Token typeWhat it isRough relative cost
Input (uncached)Everything you send — prompt, system message, files, history — read fresh.1× (baseline)
OutputEverything the model generates.3–5× input
Cache writeInput you ask the provider to store for reuse.1.25× input (Anthropic, 5-min)
Cache readInput served from that store instead of reprocessed.0.1–0.5× input

Three facts fall out of this table, and they drive everything else:

  • Output is the expensive one. Generated tokens cost several times more than input tokens. So "make the model write less" is a bigger lever than it sounds — verbose answers, giant diffs, and re-printing whole files are where output cost balloons.
  • Cached input is nearly free. A cache read can cost as little as 10% of normal input. If you're sending the same big context (a system prompt, a codebase, a CLAUDE.md) over and over, paying full price for it every time is the single most common waste.
  • The window is re-read every turn. In a chat or agent session, the entire conversation so far is sent again on each message. A 50-message session re-sends message #1 fifty times. This is why long sessions get expensive and slow — and why caching and pruning matter so much.

The big lever: prompt caching

If you remember one thing from this guide, remember this. Prompt caching is the highest-leverage cost reduction available, and most people leave it on the table.

How it works. When a model processes your prompt, it builds an internal representation of those tokens — a "KV cache" (key-value cache) of the computation. Normally that work is thrown away after the response. Prompt caching stores it, keyed on the exact prefix of your prompt. On your next request, if the beginning of your prompt is byte-for-byte identical to a cached one, the provider skips recomputing it and serves it from cache — for a fraction of the price and a fraction of the latency.

The catch is in the word prefix. Caching matches from the start of the prompt up to the first point where it differs. Change one token early in the prompt and everything after it is a cache miss. This is the single most important fact for using the cache well, and it drives all the rules below.

The numbers are not small. One engineer documented going from $720 to $72 a month — a 90% cut — just by enabling prompt caching on repeated context. A security tooling team reported a 59% reduction in total LLM cost. Anthropic measured an 85% latency drop on a 100K-token prompt (11.5s → 2.4s). Caching is rarely a marginal optimization; it's frequently the difference between viable and not.

Provider cache cheat-sheet

The three providers behind Claude, Codex, and Copilot handle caching differently. This table is the whole story:

ProviderHow to enableCached read discountMinimumLifetime
Anthropic (Claude)Manual — mark stable prefixes with cache_control breakpoints~90% off (0.1×)2,048 tok (Sonnet/Opus), 1,024 (Haiku)5 min, refreshed on each read; 1-hr option (2× write)
OpenAI (GPT/Codex)Automatic — no code, no extra fee~50% off cached input1,024 tokMinutes of inactivity (automatic)
Google (Gemini)Implicit (auto on 2.5) + explicit context caching~75% off (explicit)32,768 tok (explicit)Configurable TTL

Read this carefully, because it changes your strategy per tool:

  • OpenAI/Codex: caching is automatic and free. You don't enable anything — prompts ≥1,024 tokens are cached and you get ~50% off the repeated prefix with zero effort. Your only job is to not break the prefix (see rules below).
  • Anthropic/Claude: caching is manual but deeper. You (or the tool) place cache_control markers on the stable parts; in return you get a much bigger ~90% discount. The good news: Claude Code does this for you automatically — it caches your system prompt, CLAUDE.md, and tool definitions. Your job is to keep those stable.
  • Gemini: great for huge fixed contexts. The 32K minimum means it's built for "I have a 200-page document I query repeatedly," not for a small system prompt.
Cache write costs extra — so caching tiny, rarely-reused content loses money. On Anthropic a cache write is 1.25× normal input (5-min) or 2× (1-hr). It only pays off if the cached prefix is read again: once for the 5-minute cache, twice for the 1-hour cache. Cache the big stable stuff you'll reuse within minutes (system prompt, codebase context). Don't cache a one-off prompt you'll never send again.

Cache-friendly prompting: the rules that matter

Whether the caching is automatic (OpenAI) or managed for you (Claude Code), you control whether it hits. Four rules:

1. Stable content first, volatile content last

Structure every prompt so the parts that don't change come first: system instructions, rules files, tool definitions, the codebase or documents you're working over. Put the parts that change every turn — the user's new message, the latest tool output — at the end. The cache matches the longest stable prefix, so front-loading the stable stuff maximizes the cached region.

2. Never edit the prefix

Changing anything early in the prompt invalidates the cache for everything after it. A dynamic timestamp in your system prompt, a counter, a "current time" field near the top — each one silently busts your entire cache on every request. Keep early content byte-stable. If you need volatile values, push them to the very end.

3. Keep the cache hot

Caches expire (5 minutes on Anthropic by default, refreshed each time they're read). A steady stream of requests keeps a hot prefix alive indefinitely; long gaps let it expire and you pay the write again. For interactive coding this is usually automatic — you're sending messages regularly. For batch jobs, order your work so cached prefixes get reused before they cool.

4. Reuse the exact same context

The cache keys on exact-match prefixes. Two prompts that are "basically the same" but differ in whitespace, ordering, or a single word are two different cache entries. Be deliberate about reusing identical system prompts and context blocks rather than regenerating slightly-different ones each time.

The one-line version: put your big, stable context at the top, keep it identical run-to-run, and keep sessions active. Do that and the cache does the rest — 50% off automatically on OpenAI, ~90% off on Claude.

A worked example: same request, cached vs not

Here's the difference in concrete terms. Say you're querying a model over a 20,000-token codebase context, plus a small changing question each turn. Structured well (Anthropic-style, with a cache breakpoint after the stable block):

{
  "system": [
    { "type": "text",
      "text": "<20,000 tokens of stable codebase + rules>",
      "cache_control": { "type": "ephemeral" } }   // ← cache breakpoint here
  ],
  "messages": [
    { "role": "user", "content": "<the small, changing question>" }  // ← volatile, at the end
  ]
}

The math on ten such turns (illustrative, at "1× = normal input price"):

ApproachWhat you pay for the 20K context, ×10 turns
No caching20K × 10 × 1× = 200K-tokens-worth of input
With caching20K × 1.25× (one write) + 20K × 9 × 0.1× (nine reads) = 25K + 18K = 43K-tokens-worth

That's a ~78% reduction on the context portion — and it grows the more turns you run, because the one-time write cost amortizes across more cheap reads. The same shape holds on OpenAI automatically (at the smaller 50% discount), with no cache_control needed. The only requirement is that the 20K block is identical and comes first every turn.

The other half-price lever: Batch APIs

Caching is for repeated context. There's a second, separate discount for work that isn't urgent: batch processing. Both Anthropic and OpenAI offer a Batch API that runs your requests asynchronously (results within hours instead of seconds) for 50% off both input and output. It stacks with caching, and it applies to output too — which caching doesn't.

Use it for anything that doesn't need a real-time answer: bulk code review across a repo, generating test suites, large-scale data labeling, documentation generation, offline evals. If you'd be fine getting the results "sometime in the next few hours," batch it and halve the bill. It's the single biggest lever for non-interactive workloads, the way caching is for interactive ones.

Three levers, three situations. Interactive, repetitive context (a coding session, a chatbot over fixed docs) → caching. Non-urgent, high-volume jobs (batch generation, evals, bulk processing) → Batch API. Noisy command output flooding an agent's context → a tool-output proxy like RTK (next). Real pipelines use all three.

The third lever: compress tool output with a proxy (RTK)

Here's a cost most people never see. When a coding agent runs shell commands — git status, cargo test, npm run build, cat bigfile, ls -R — the entire raw output gets fed back into the model as input tokens so it can "read" the result. A single failing test run can be 25,000 tokens of stack traces and logs, 90% of which is noise. Across a session, this command-output firehose is frequently the largest single source of input tokens in agentic coding — and caching doesn't help it, because the output is different every time.

The fix is a different layer entirely: a proxy that compresses command output before it ever reaches the model. RTK ("Rust Token Killer") is the standout here — a single zero-dependency Rust binary that intercepts common dev commands and strips them down, cutting their token cost 60–90% (and reportedly 90–95% of input tokens on command-heavy work). It does it four ways:

  • Smart filtering — drops noise: comments, whitespace, boilerplate banners.
  • Grouping — aggregates similar items (files by directory, errors by type) instead of listing each.
  • Truncation — keeps the relevant context, cuts the redundant tail.
  • Deduplication — collapses repeated log lines into one line + a count.

The measured savings on real commands are large:

CommandRaw tokensWith RTKCut
git status~2,000~600−80%
git diff~10,000~2,500−75%
cargo test~25,000~2,500−90%
pytest~8,000~800−90%
cat / read~40,000~12,000−70%
30-min session~118,000~23,900−80%

The clever part is delivery: RTK installs a shell hook that transparently rewrites commands before they run — you (or the agent) type git status and the hook silently executes rtk git status, so the model receives the compact output with zero change to its behavior. The hook only touches bash tool calls; an agent's built-in Read/Grep tools bypass it. It covers 100+ commands across git, build/lint (cargo, pytest, eslint, tsc, go test), package managers, Docker/Kubernetes, AWS, and file ops.

Install on macOS

# Homebrew (recommended)
brew install rtk

# wire it into your agent's hooks (transparent command rewriting)
rtk init -g                     # Claude Code / Copilot (default)
rtk init -g --gemini            # Gemini CLI
rtk init -g --agent cursor      # Cursor
rtk init --agent cline          # Cline / Roo Code

# check it's working — token savings analytics
rtk gain                        # summary stats
rtk gain --graph                # last-30-days ASCII graph
rtk discover                    # find commands you're not yet optimizing
Why this stacks with everything else: caching discounts repeated input; RTK shrinks fresh input (command output) that caching can't touch; the Batch API halves non-urgent jobs. They operate on different parts of the bill, so you can run all three at once. For an agent that constantly shells out to build and test, a tool-output proxy is often the biggest win of the three — that noise is pure, uncacheable, full-price input.

The trending token-saving toolbelt (2026)

RTK isn't alone. Through 2026 a whole wave of tools appeared, and the smart way to think about them is: each one attacks a different token sink. Your context bill is the sum of several streams — code exploration, command output, model output, conversation memory — and there's now a specialised tool for each. Caveman — compress the model's output

Output is the priciest token type (3–5× input), and Caveman goes straight at it: it makes the agent answer in a terse, telegraphic "caveman" style — full technical accuracy, far fewer words. Benchmarked across 10 dev tasks it cut ~65% of output tokens (range 22–87%), and its caveman-compress rewrites your CLAUDE.md into the same compressed style for a persistent ~46% input saving on the memory file. A documented bonus: forcing brevity actually improved accuracy by 26 points on some benchmarks — concise models wander less.

# install (Node >= 18) — Claude Code / Codex / Gemini auto-activate
curl -fsSL https://raw.githubusercontent.com/JuliusBrussee/caveman/main/install.sh | bash

# usage, inside your agent:
#   /caveman full          → compress replies (levels: lite | full | ultra | wenyan)
#   /caveman-compress CLAUDE.md   → shrink the memory file
#   /caveman-stats         → measured tokens + USD saved this session
#   "normal mode"          → turn it off

It auto-activates on Claude Code, Codex, and Gemini; Cursor/Windsurf/Cline/Copilot get it via a --with-init rule file; 30+ other agents can trigger it manually. (Full disclosure: this very guide was drafted with caveman mode running.)

Graphify — explore code without grepping every file

One of the biggest hidden input costs in agentic coding is exploration: to answer "where is X handled?", an agent greps and reads file after file, dumping each into context. Graphify attacks that by building a queryable knowledge graph of your codebase up front — app code, SQL schemas, infra, even docs — so the agent looks up the answer in a compact graph instead of reading the whole tree. The measured difference is dramatic: a lookup costs roughly 1.7K tokens versus ~123K naively — about a 71× reduction on exploration.

# install (PyPI package name is graphifyy — double y)
uv tool install graphifyy
graphify install        # wires the /graphify command + hook into your agent
# then, inside the agent:  /graphify  "where is auth handled?"

It's a build-time tool: it produces a GRAPH_REPORT.md and a hook injection that Claude reads (an MCP version is on the roadmap). Works across Claude Code, Codex, Cursor, Gemini CLI, Copilot CLI, and more.

Headroom — a general compression layer (with MCP)

Headroom is the broader cousin of RTK: a compression layer that squeezes tool outputs, system logs, files, and RAG chunks before they reach the model, reporting 60–95% reduction with the answers kept just as accurate. It blew up in June 2026 (10K+ GitHub stars) largely because it ships in three forms — a library, a proxy, and an MCP server — so you can wire it into any MCP-capable agent (Claude Code, Cursor, etc.) without changing your code. Use RTK for shell commands specifically; reach for Headroom when you also want to compress logs, large files, and RAG context through one layer.

Memory layers — Mem0, Zep

For long-running assistants (not one-off coding sessions), the conversation history itself becomes the cost — it's re-sent every turn and only grows. Memory platforms like Mem0 and Zep replace raw history with structured retrieval: they extract discrete facts and serve back only what the current task needs, often using a knowledge graph of entities and relationships. Reported savings land around 40% at equal quality. Overkill for a quick coding task; valuable for a persistent agent that accumulates context over days.

Stack them by sink. These aren't competitors — they compress different streams, so a maxed-out setup runs several at once: Graphify for exploration input, RTK or Headroom for command/tool/log output, Caveman for the model's output and memory file, a memory layer for long-term history, and prompt caching underneath it all for the repeated prefix. Each shaves a different slice; together they routinely get teams past 90% total reduction.

Install on macOS

Anthropic's recommended path is the native installer — no Node.js needed, auto-updates in the background:

claude --version

Never sudo npm install. It breaks permissions on your npm directory and creates security problems. If you hit permission errors, fix the npm prefix or use the native installer instead.

Token tactics specific to Claude Code

Claude Code already caches your system prompt, CLAUDE.md, and tool definitions for you. Your job is to feed it well:

  • Keep CLAUDE.md under ~200 lines. It's sent on every single turn. A 5,000-token CLAUDE.md costs 5,000 tokens whether your session is 2 messages or 200. Include only essentials — commands, conventions, gotchas — not a novel. (It caches, but a bloated file still wastes the volatile budget and dilutes attention.)
  • /compact at natural breakpoints. When you finish a discrete sub-task, compact the conversation — it summarizes the history into a much smaller form, freeing the window. Add custom instructions about what to preserve. Compact after solid work, not mid-task.
  • /clear when switching tasks. Moving to unrelated work? Clear the context entirely. Stale context from the last task is re-read (and re-paid) on every new message until you do.
  • Right-size the model with /model. Sonnet handles most coding well and costs far less than Opus. Reserve Opus for genuinely hard architectural or multi-step reasoning. Switch mid-session as the task demands.
  • Use plan mode (Shift+Tab) before expensive operations. Claude outputs a step-by-step plan without touching files; you review and cut unnecessary steps before spending tokens executing them.
  • Delegate verbose work to subagents. Running a test suite, fetching docs, or grepping logs produces a flood of output. A subagent keeps that verbose output in its context and returns only a summary to your main session — huge window savings.
  • Be specific. "Add input validation to the login function in auth.ts" reads one file. "Fix the auth bug" triggers a broad, token-hungry scan of your whole project.

Other agents — Cursor, Cline, Windsurf & the rest

The same principles carry to every other coding agent, because they all sit on the same provider APIs underneath. Quick notes:

  • Cursor / Windsurf (IDE agents). These send your open files and a chunk of the codebase as context. Keep irrelevant files closed, use their "codebase indexing" so they retrieve specific snippets instead of dumping everything, and prefer their cheaper/auto model for routine edits — reserve the frontier model for hard tasks. They lean on provider caching automatically; your job is a stable, tight context.
  • Cline / Roo (open-source, bring-your-own-key). Here you pay the raw API bill, so every tactic in this guide hits your wallet directly. They support Anthropic prompt caching — enable it. Watch the per-request token readout they show; it's the most honest feedback loop of any tool.
  • Aider (terminal, git-native). Uses a repo map to give the model just enough context instead of whole files, and supports caching. Add only the files you're working on to the chat (/add), and drop them (/drop) when done — the equivalent of /clear.

Install commands shift over time, but the current pattern for the open ones is npm or pip:

No matter the tool, the hierarchy is identical: cache the stable context, prune the window, right-size the model, cap the output. The UI changes; the economics don't.

Cache-busting mistakes that quietly cost you

If your cache-read ratio is low when it should be high, one of these is almost always the culprit. Each one breaks the prefix and forces a full re-read every turn:

MistakeWhy it busts the cache
A timestamp or "current time" near the topChanges every request, invalidating everything after it. Put dynamic values at the end, never the start.
Reordering files or context blocksThe cache is exact-prefix. Same files in a different order = a brand-new, uncached prompt.
A changing counter, session ID, or UUID early onSame as a timestamp — any volatile token near the top defeats the whole cache.
Regenerating a "basically identical" system promptWhitespace or a one-word tweak makes it a different cache key. Reuse the exact string.
Editing a file that's in the cached contextLegitimate, but it does bust the cache from that file onward. Group edits so you're not re-caching every turn.
Letting the cache go coldGaps longer than the TTL (5 min on Anthropic) expire the entry; the next request pays the write again.

Diagnosing this is mechanical: look at cache_read_input_tokens across a few turns. If it's stuck near zero on a session where the big context hasn't meaningfully changed, something at the top is changing — bisect your prompt from the top down until the reads light up.

The universal token-saving playbook

These work everywhere — every tool, every provider, even raw API use. In rough order of impact:

TacticWhy it saves
1. Exploit the cacheStable-first prompts + identical context = 50–90% off repeated input. The biggest single lever for repeated context.
1b. Proxy your tool outputRTK-style command compression = 60–90% off the uncacheable command-output firehose. The biggest lever for shell-heavy agents.
2. Prune the window/compact and /clear. Every token in the window is re-paid every turn; a bloated session multiplies cost on each message.
3. Right-size the modelCheap model for routine work, expensive model only for hard reasoning. Often a 5–10× per-token difference.
4. Cap the outputOutput is 3–5× input. Ask for diffs not whole files, summaries not transcripts, "just the function" not the explanation.
5. Be specificPrecise requests read 1–2 files; vague ones scan the whole repo. Name the file and function.
6. Isolate verbose workSubagents for tests/logs/docs — the noise stays out of your main window; only the summary returns.
7. Exclude junk from contextLockfiles, build output, vendored deps, node_modules — keep them out of what the tool ingests.
8. Retrieve, don't dumpDon't paste a whole codebase "for context." Let the tool fetch the specific files it needs.
Output discipline is underrated. Because generated tokens cost several times more than input, trimming output is pure profit. Add "respond concisely, code only" to your rules; ask for a unified diff instead of the full file; tell the model to skip re-explaining what it just did. On a chatty session this alone can shave a third off the bill.

Putting it together: a cheap-by-default setup

Tactics are easy to forget mid-flow. The durable win is to bake the savings into your defaults so you save tokens without thinking. A setup that's cheap by construction:

  • A lean rules file. CLAUDE.md / AGENTS.md under ~200 lines, essentials only — commands, conventions, the handful of gotchas. It's stable (so it caches) and small (so it barely touches the volatile budget). Review it monthly and cut.
  • An ignore file for context. Exclude node_modules, build output, lockfiles, vendored code, large generated files, and data dumps. Most tools honor a .gitignore or have their own ignore config — set it once so junk never enters the window.
  • A default to the cheap model. Start every session on the cheaper model; escalate to the frontier model only when you hit something genuinely hard, then drop back. Make "expensive" the exception, not the default.
  • A concise-output instruction. Put "respond concisely; code/diffs only unless asked; don't re-explain completed work" in your rules. Output is the priciest token type — make terseness the default.
  • A pruning habit. /compact when a sub-task is done and solid; /clear when you switch to unrelated work. Tie it to your natural workflow breaks so it's automatic.
  • Batch for the non-urgent. Route bulk, can-wait jobs (mass review, test generation, evals) through a Batch API for the standing 50% discount.

Set those six up once and the expensive habits become hard to fall into. You're not optimizing each request by hand — the environment optimizes for you.

Measure it — you can't optimize what you can't see

Every tool exposes usage; check it before and after you apply this guide:

  • Claude Code: run /cost in-session for token and dollar usage; /context shows what's filling the window. The native usage dashboard breaks down input vs output vs cache.
  • Codex: the CLI reports token usage per turn; watch the context-window indicator and the cached-token share.
  • API users: every response includes a usage object — look for cache_creation_input_tokens and cache_read_input_tokens (Anthropic) or cached_tokens (OpenAI). A healthy cached-read ratio on a repetitive workload should be high; if it's near zero, your prefix is being broken.

The tell-tale sign caching is working: on a long session, your cache-read tokens should dwarf your fresh input tokens. If they don't, something near the top of your prompt is changing every turn — hunt it down (a timestamp, a counter, reordered files) and stabilize it.

FAQ

Does prompt caching make the model dumber or change answers?

No. The cache stores the computation of the prefix, not a canned answer. The model still runs normally on the full prompt — it just skips recomputing the part it already processed. Same outputs, lower cost, lower latency.

If OpenAI caching is automatic, why does Anthropic make me do it manually?

Trade-off: automatic (OpenAI) is zero-effort but a smaller discount (~50%); manual (Anthropic) takes a cache_control marker but gives a much bigger discount (~90%). And in practice Claude Code places those markers for you, so you get the deep discount without the manual work.

I'm on a subscription, not the API — does any of this matter?

Yes. Subscriptions have rate/usage limits, and tokens are how you hit them. Pruning the window, right-sizing the model, and capping output all stretch your limits further and keep sessions fast. Caching also reduces how much of your allowance each turn consumes.

What's the fastest single win?

Two things: (1) make sure your big stable context (system prompt, rules file, codebase) sits at the top of the prompt and never changes — so it caches; and (2) /clear or /compact when you switch tasks instead of dragging a stale window around. Those two cover most of the savings for most people.

Why does my long session get slow as well as expensive?

Same cause: the whole window is re-read every turn. More tokens in the window means more to process per message — higher latency and higher cost together. Compacting fixes both at once.

Takeaways

  • Four prices, not one. Output is 3–5× input; cached input is 0.1–0.5× input. Steer work toward the cheap quadrants.
  • Three levers do the heavy lifting. Caching (50–90% off repeated context), the Batch API (50% off non-urgent jobs), and a tool-output proxy like RTK (60–90% off command output). They hit different parts of the bill — run all three.
  • Never break the prefix. One changing token near the top busts the whole cache. Keep early content byte-stable; push volatile values to the end.
  • Prune relentlessly. /compact at breakpoints, /clear on task-switch. The window is re-paid every turn.
  • Right-size everything. Cheap model for routine work, tight output, specific asks, junk excluded from context, verbose work in subagents.
  • Measure. Watch your cache-read ratio. If it's low on a repetitive task, your prefix is leaking — find the changing token.

None of this requires new tools or a different model — just spending tokens the way you'd spend any other metered resource: deliberately. Set up the cache once, build the prune-and-right-size habits, and the same work that used to cost $720 a month quietly costs $72.
