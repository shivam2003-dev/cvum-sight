Operating System Concepts Chapter 10 — Virtual Memory.

operating-systemschapter-10virtual-memorypage-faultlruthrashing

// the one-minute version

Virtual memory lets a process run even if only part of it is in RAM. Pages are loaded on demand — only when actually touched — and a miss triggers a page fault that fetches the page from disk. When RAM is full, a replacement algorithm (ideally LRU) decides which page to evict. Push it too far and the system thrashes: it spends all its time swapping pages instead of working.

Your machine runs programs that together need more memory than it physically has, and somehow it works. The trick is a beautiful lie: give each process a huge address space, but keep only the pages it's actually using in RAM, parking the rest on disk. The program never knows. That's virtual memory.

01 Demand paging

Instead of loading a whole program into RAM at launch, demand paging loads each page only when the program first touches it. Most programs use only a fraction of their code and data at any moment, so this saves enormous memory and makes startup fast. Pages not yet needed simply stay on disk.

02 The page fault

Each page-table entry has a valid bit saying whether the page is in RAM. Touch a page that isn't, and the MMU raises a page fault — a trap to the OS. The OS finds the page on disk, reads it into a free frame, updates the page table, and restarts the instruction. To the program, nothing happened except a pause.

Fig 1 — Servicing a page fault. A disk read is ~100,000× slower than RAM, so faults must be rare for the illusion to feel fast.

watch outA page fault is cheap to handle but brutally slow — a disk fetch is tens of thousands of times slower than a RAM access. The whole scheme only works because faults are rare. A workload that faults constantly performs terribly even though nothing is broken.

03 Page replacement

When a fault hits and RAM is full, the OS must evict an existing page to make room. Which one? That's the page-replacement decision, and it matters enormously — evict a page that's about to be used again and you just create another fault.

FIFO

Evict the oldest-loaded page. Simple, but dumb — it can toss a heavily-used page just because it arrived early. Can even suffer Belady's anomaly (more frames → more faults).

Optimal (OPT)

Evict the page that won't be used for the longest time. Provably best — but it requires knowing the future, so it's only a benchmark, not implementable.

LRU — least recently used

Evict the page unused for the longest time, betting the recent past predicts the near future. Close to optimal in practice; real systems approximate it cheaply (e.g., a reference bit).

noteLRU is the practical sweet spot. True LRU is costly to track exactly, so hardware/OS use approximations — a "reference bit" set on each access and periodically cleared — that capture most of the benefit at a fraction of the cost.

04 Thrashing

If a process doesn't have enough frames to hold the pages it actively needs, it faults on almost every access, evicting pages it's about to need again. This is thrashing: the CPU sits nearly idle while the disk runs flat-out swapping pages. Throughput collapses. Counterintuitively, the fix is often to run fewer processes so each gets enough frames.

think of it likeThrashing is like a tiny desk with a huge filing cabinet. If the desk holds only two folders but your task needs five, you spend all day swapping folders to and from the cabinet and get no actual work done. Give the desk more room (frames) or work on fewer tasks at once.

05 The working-set model

The defense against thrashing is the working set: the set of pages a process has used recently — roughly, what it actually needs right now. If the OS keeps each active process's working set in RAM, faults stay rare. If the combined working sets exceed RAM, the OS should reduce the degree of multiprogramming rather than let everyone thrash.

06 Questions students actually ask

What is demand paging?

Loading each page into RAM only when the program first accesses it, rather than loading the whole program up front. Since programs use only part of their memory at a time, this saves RAM and speeds up startup.

What happens on a page fault?

The MMU traps to the OS because the page isn't in RAM. The OS reads the page from disk into a free frame, updates the page table, and restarts the faulting instruction. The program just experiences a pause.

Why can't we just use the optimal replacement algorithm?

It requires knowing which page will be used furthest in the future — knowledge we don't have. It's used only as a theoretical benchmark. LRU approximates it using recent history instead.

What causes thrashing and how do you stop it?

Too little RAM per process, so it constantly faults on pages it just evicted. Fix it by giving processes more frames or, often, running fewer processes so each one's working set fits in memory.

07 Key takeaways

  • Virtual memory runs programs with only part of them in RAM; the rest waits on disk.
  • Demand paging loads pages only when first touched.
  • A page fault fetches a missing page from disk — correct but very slow, so faults must be rare.
  • Replacement picks an eviction victim: FIFO (simple), OPT (ideal but impossible), LRU (practical).
  • Thrashing = constant faulting; the CPU idles while the disk thrashes.
  • The working-set model keeps each process's active pages resident to prevent it.

08 Wrapping up

Virtual memory is the OS's most impressive illusion: more memory than exists, conjured with paging and a disk. Which raises the question of what that disk actually is and how the OS drives it — the storage half of the book begins now. Next up: Mass-Storage Structure.
