Operating System Concepts Chapter 2 — Operating-System Structures.

operating-systemschapter-2ossystem-callskernelmicrokernel

// the one-minute version

An operating system shows two faces. To you, it offers services — run programs, open files, talk to the network. To programs, it offers system calls, the controlled doorways into the kernel. This chapter is about those services, the call interface beneath them, and the handful of ways people actually structure a kernel: one big blob, neat layers, a tiny microkernel, or loadable modules.

Chapter 1 said the OS sits between apps and hardware. Chapter 2 opens the box and asks: what services does it actually offer, how do programs reach them, and how is the thing itself built inside?

01 What services an OS provides

Some services exist to help the user: a way to run programs, do I/O, work with files, communicate between processes, and report errors. Others exist to keep the system efficient and safe: sharing resources fairly, accounting for who used what, and protecting one user's work from another's.

User-facing

Program execution, I/O, file manipulation, communication, error detection — the things that make the machine usable.

System-facing

Resource allocation, accounting, protection and security — the things that keep it efficient and safe to share.

02 The two interfaces: shell and system calls

People reach the OS through a user interface — a command-line shell or a GUI. Programs reach it through system calls. A system call is the only legitimate way for ordinary code to ask the kernel to do privileged work: it briefly flips the CPU into kernel mode, runs vetted OS code, and flips back.

noteMost programmers never write raw system calls. They call a friendly library function (like fopen), and the library makes the actual system call (open) underneath. The API you code against and the system call beneath it are two different layers.
think of it likeA system call is like a bank teller window. You can't walk into the vault (kernel mode) yourself. You slide a request through the window, a trusted teller does the privileged action, and hands the result back. The window is narrow on purpose.

03 Types of system calls

The book groups them into six families. Almost every call you'll ever meet fits one of these:

CategoryExamplesWhat it does
Process controlcreate, terminate, wait, execstart, stop, and coordinate programs
File managementopen, read, write, closework with files and directories
Device managementrequest, release, read, writeget and use hardware devices
Informationget/set time, get PIDread and set system data
Communicationpipe, send, recv, shared memorymove data between processes
Protectionchmod, set permissionscontrol who can access what

04 System programs

Around the kernel sits a layer of system programs (sometimes called system utilities): file managers, text editors, compilers, shells, status tools, background services. They aren't the kernel, but to most users they are "the operating system" because they're what you actually touch.

05 How the kernel itself is structured

There's no single right way to build a kernel. Four classic designs trade simplicity, speed, and reliability against each other:

Monolithic

Everything — scheduling, memory, filesystems, drivers — in one big kernel address space. Fast (no crossing costs) but huge and fragile: one bad driver can crash all of it. Classic UNIX.

Layered

Built as stacked layers, each using only the layer below. Clean and easy to reason about, but rigid and sometimes slow because requests pass through many layers.

Microkernel

Keep the kernel tiny — just scheduling, basic memory, and message passing. Push filesystems and drivers out to user-space servers. Very robust and modular, but message passing adds overhead.

Modular

A small core plus loadable kernel modules (drivers, filesystems) added at runtime. The mainstream compromise — flexible like microkernels, fast like monolithic. Linux and macOS work this way.

Fig 1 — Monolithic packs everything into the kernel; microkernel pushes most services out to user-space servers that communicate by messages.

watch outDon't read "microkernel = better." The famous Tanenbaum–Torvalds debate was exactly this. Microkernels are cleaner and more robust, but the message-passing overhead is real, which is why Linux stayed monolithic-with-modules and won the desktop and server world. Design is a trade-off, not a ranking.

06 Booting: how it all starts

When you power on, firmware (BIOS/UEFI) runs a bootstrap program from ROM. It finds the kernel on disk, loads it into memory, and jumps to it. The kernel initializes hardware, starts core services, and launches the first user process — which starts everything else.

07 Questions students actually ask

Why not let programs skip system calls and touch hardware for speed?

Because then any bug or attack would control the whole machine, and every program would need to know every device's details. The system-call wall is what makes the system safe and portable. The small overhead is the price of that safety.

Is the shell part of the kernel?

No. The shell is a system program that runs in user mode like any app. It just happens to be the program that reads your commands and asks the kernel (via system calls) to run them.

What's the difference between an API and a system call?

An API (like the C library's printf) is what your code calls. It's convenient and portable. Underneath, it may make one or more system calls (write) to actually do the privileged work. Coding to the API shields you from OS-specific call details.

Why do modular kernels dominate today?

They get the best of both worlds: a fast in-kernel core plus the ability to load and unload drivers and filesystems at runtime without rebuilding the kernel. Flexible like a microkernel, fast like a monolith.

08 Key takeaways

  • The OS offers services to users and a system-call interface to programs.
  • A system call is the controlled doorway from user mode into the kernel.
  • System calls group into six families: process, file, device, information, communication, protection.
  • System programs (shells, editors, utilities) wrap the kernel and are what users actually touch.
  • Kernel designs — monolithic, layered, microkernel, modular — trade speed, simplicity, and robustness.
  • Modern systems (Linux, macOS) are modular: a fast core plus loadable modules.

09 Wrapping up

Chapter 2 is the "how do I reach the OS, and how is it built" chapter. The system-call interface is the contract every program depends on; the kernel structure is an engineering choice with real trade-offs. Next up: Processes.
