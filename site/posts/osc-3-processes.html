Operating System Concepts Chapter 3 — Processes.

operating-systemschapter-3computer-sciencecompanion-notes
A process is a running program with its own state, memory view, and execution history. This chapter explains how the OS creates, tracks, and coordinates that unit of work.

1. Introduction

A program stored on disk is passive. A process is what that program becomes when it starts running. The OS turns code into a live execution unit with memory, registers, open files, and a current state.

This chapter matters because most operating-system work is process work: creating them, stopping them, switching between them, and letting them communicate safely.

2. Detailed explanation

What a process contains

A process includes program code, current CPU state, stack, data, heap, and resources such as open files. Two copies of the same program can become two different processes because each one has its own execution state.

Process states

A process usually moves through states such as new, ready, running, waiting, and terminated. These states help the OS decide what is runnable now and what is blocked on I/O or some event.

Process control block

The OS keeps a record for each process called a process control block, or PCB. It stores identity, current state, CPU register values, scheduling details, memory info, and open-resource data.

Context switching

When the CPU changes from one process to another, the OS must save the old state and load the new one. That step is a context switch. It is necessary, but it adds overhead because the CPU is doing management work rather than user work.

Process creation and termination

Processes can create child processes. The child may continue independently or may replace its memory image with another program. Processes also end normally, fail, or get terminated by the system or another authorized process.

Interprocess communication

Processes often need to share information. The two common models are shared memory and message passing. Shared memory can be fast, while message passing can be cleaner and easier to isolate.

Client-server idea

Many real systems use a client-server pattern. One process asks for a service, and another process provides it. Web servers, database systems, and local desktop services all work this way.

3. Key concepts

ConceptMeaning
ProcessA running program with its own state and resources.
PCBThe OS record that stores process metadata and execution state.
Ready queueThe set of processes waiting for CPU time.

Parent/childA relationship where one process creates another.

4. Real-world examples

Opening many browser tabs

Modern browsers may use multiple processes so one tab crash does not always crash the whole browser.

Running `ps` or Task Manager

These tools show live process data that the OS keeps in its internal tracking structures.

Web app to database

A web server process may send requests to a separate database process. That is client-server design in action.

5. FAQs

Is a process the same as a program?

No. A program is passive code. A process is the active running instance.

Why is a context switch expensive?

Because the OS must save and restore execution state, and caches may become less useful after the switch.

Why use multiple processes instead of one big one?

Multiple processes can improve isolation, reliability, and organization.

What is better: shared memory or message passing?

Neither is always better. Shared memory can be faster, while message passing can be simpler and safer.

6. Key takeaways

  • A process is the OS unit for a running program.
  • The OS tracks each process with a PCB.
  • Process states help the scheduler manage work.
  • Context switching enables multitasking but costs time.
  • IPC is necessary because processes rarely work alone.

7. Conclusion

Chapter 3 gives the core execution model for the rest of operating systems. Once you understand processes, later topics like threads, scheduling, synchronization, and memory management fit much more naturally.
