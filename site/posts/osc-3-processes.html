Operating System Concepts Chapter 3 — Processes.

operating-systemschapter-3processespcbipcfork

// the one-minute version

A process is a program in action — code plus its current memory, registers, and open files. The OS tracks each one with a process control block (PCB), moves it through a small set of states (ready, running, waiting), and switches between processes with a context switch. When processes need to cooperate, they use interprocess communication: shared memory or message passing.

A program sitting on disk is just a file. The moment it runs, it becomes a living thing with memory, a place in its execution, and resources it holds. That living thing is a process, and managing processes is one of the OS's core jobs.

01 Program vs process

A program is passive: bytes on disk. A process is active: that program loaded into memory and executing, with its own address space, a program counter saying where it is, registers, a stack, a heap, and a list of open files. Run the same program twice and you get two separate processes that don't share memory.

think of it likeA recipe is a program. The act of a cook actually making the dish — ingredients on the counter, current step, half-chopped onions — is a process. Two cooks following the same recipe are two processes.

02 Process states

At any instant a process is in one of a few states. It's created (new), becomes ready (waiting only for a CPU), gets picked to run, may drop to waiting if it needs I/O, and finally terminates.

Fig 1 — The process state cycle. The scheduler moves processes between ready and running; I/O sends a process to waiting and back.

noteOnly one process per CPU core is running at a time. Many can be ready (waiting for a turn) or waiting (blocked on I/O). The whole illusion of "many programs at once" is the OS shuffling processes between these states very fast.

03 The PCB: the OS's index card for each process

For every process, the kernel keeps a process control block — a record holding everything it needs to manage and resume that process: its state, process ID, program counter, register values, memory layout, open files, and accounting info. The PCB is the process, as far as the kernel is concerned.

04 Context switching

To switch the CPU from process A to process B, the kernel saves A's state into A's PCB and loads B's state from B's PCB. That's a context switch. It's pure overhead — during the switch no useful user work happens — so the OS tries to keep switches cheap and not too frequent.

watch outContext switches aren't free. Saving and restoring registers, flushing pipelines, and disturbing CPU caches all cost time. A system that switches too often spends its CPU shuffling paperwork instead of doing work — a real performance trap.

05 Creating processes

Processes form a tree: each process can create children, which can create their own children. On UNIX-like systems this uses two calls. fork() makes a near-copy of the calling process; exec() then replaces that copy's program with a new one. The parent can wait() for the child to finish.

noteThat fork-then-exec split feels odd but is powerful: between the two calls the child can adjust its environment (redirect files, change permissions) before loading the new program. It's exactly how a shell runs your commands.

06 Interprocess communication (IPC)

Processes have separate memory, so cooperating processes need a deliberate channel. There are two main models:

Shared memory

The OS sets up a region both processes can read and write. Fast (no kernel in the loop after setup), but the processes must coordinate access themselves to avoid races.

Message passing

Processes send and receive discrete messages through the kernel. Slower (each message crosses into the kernel) but cleaner and easier to get right, and works across machines.

Concrete IPC tools include pipes (a one-way byte stream, like ls | grep), sockets (endpoints that also work over a network), and remote procedure calls (making a function call run on another process or machine).

07 Questions students actually ask

Is a process the same as a program?

No. A program is the passive file on disk. A process is that program actively running, with its own memory and execution state. One program can become many processes.

What information lives in a PCB?

Process state, a unique process ID, the program counter, saved CPU registers, memory-management info, open-file list, and accounting data — everything needed to pause and later resume the process exactly.

Why is context switching considered overhead?

Because while the CPU saves one process's state and loads another's, it does no useful application work. Plus it disturbs CPU caches. Necessary for sharing, but something to minimize.

When should I use shared memory vs message passing?

Shared memory when you need maximum speed and the processes are on the same machine and can coordinate carefully. Message passing when you want simpler, safer code or need to communicate across machines.

08 Key takeaways

  • A process is a program in execution, with its own memory and state.
  • Each process lives in one state at a time: new, ready, running, waiting, terminated.
  • The PCB stores everything the kernel needs to manage and resume a process.
  • A context switch saves one process and loads another — necessary but pure overhead.
  • Processes form a tree via fork/exec; parents can wait on children.
  • Cooperating processes use IPC: shared memory (fast) or message passing (cleaner, networkable).

09 Wrapping up

Processes are the unit the OS schedules, protects, and accounts for. Get states, the PCB, and the context switch clear, and scheduling and synchronization fall into place. Next up: Threads & Concurrency.
