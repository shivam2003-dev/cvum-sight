Operating System Concepts Chapter 4 — Threads & Concurrency.

operating-systemschapter-4threadsconcurrencyparallelismmulticore

// the one-minute version

A thread is a single flow of execution inside a process. One process can run many threads that share its memory but each have their own stack and registers. Threads make programs faster on multicore CPUs and more responsive, but sharing memory is exactly what makes concurrent bugs possible. This chapter also separates two ideas people confuse: concurrency (making progress on many tasks) and parallelism (literally running at the same instant).

A process with one thread does one thing at a time. But a web browser wants to render a page, run scripts, and download images all at once — without spinning up a whole separate process for each. The answer is threads: many lanes of execution inside a single process, sharing its memory.

01 What a thread is

A thread has its own program counter, registers, and stack — but shares the process's code, heap, and open files with its sibling threads. That sharing is the whole point: threads can pass data through shared memory instantly, with no IPC needed.

Each thread owns

Program counter, CPU registers, and a stack of local variables and function calls.

Threads share

The code, the heap (dynamically allocated data), global variables, and open files of their process.

think of it likeA process is an office; threads are the workers in it. They each have their own desk (stack) and current task (program counter), but they share the office's files, supplies, and whiteboard (heap and globals). Sharing makes them fast to collaborate — and prone to scribbling over each other's notes.

02 Why bother with threads

Four classic benefits: responsiveness (one thread handles the UI while another does slow work), resource sharing (threads share memory for free, unlike processes), economy (creating a thread is far cheaper than a whole process), and scalability (threads can run on different cores in parallel).

03 Concurrency vs parallelism

These sound alike but aren't. Concurrency means dealing with many tasks that are all in progress — even on a single core, by interleaving. Parallelism means literally executing multiple tasks at the same instant, which needs multiple cores.

key ideaA single-core machine can be concurrent but never parallel. A multicore machine can be both. Concurrency is about structure (juggling tasks); parallelism is about execution (genuinely simultaneous). You can have one without the other.

04 User threads vs kernel threads

Threads come in two flavors. User-level threads are managed by a library in user space — fast to create and switch, but the kernel sees only one process, so one blocking call can stall them all. Kernel-level threads are managed by the OS — the kernel can schedule them on separate cores and one blocking won't freeze the rest, at the cost of more overhead.

05 Multithreading models

How user threads map onto kernel threads gives three classic models:

ModelMappingTrade-off
Many-to-onemany user threads → 1 kernel threadfast, but one block stalls all; no true parallelism
One-to-oneeach user thread → its own kernel threadreal parallelism & isolation; more overhead per thread
Many-to-manymany user threads → smaller pool of kernel threadsflexible balance; more complex to implement
noteMost modern systems (Linux, Windows) use the one-to-one model — every thread you create is a real kernel thread. It's simple and gives true multicore parallelism, and threads are cheap enough now that the overhead rarely matters.

06 Thread pools

Creating a fresh thread for every small task is wasteful and unbounded. A thread pool keeps a fixed set of worker threads alive and hands them tasks from a queue. It caps how many threads exist (protecting the system from overload) and skips repeated creation cost. This is how web servers handle thousands of requests.

watch outMore threads is not always faster. Past the number of cores, extra threads just add context-switching and contention. And the instant two threads write shared data without coordination, you get a race condition — a bug that appears only under certain timing. That problem is the entire subject of the next two chapters.

07 Questions students actually ask

What's the core difference between a thread and a process?

Processes have separate memory; threads inside one process share memory. That makes threads cheaper and faster to coordinate, but means a bug in one thread can corrupt data the others rely on.

Can I get parallelism on a single-core CPU?

No. A single core runs one instruction stream at a time, so you can only get concurrency (fast interleaving). True parallelism needs multiple cores.

Why do most systems use one-to-one threading?

Because it gives real multicore parallelism and keeps one blocked thread from freezing the others, and modern kernel threads are cheap enough that the overhead is acceptable.

Why use a thread pool instead of making threads on demand?

To cap the total number of threads (so a flood of work can't exhaust the system) and to avoid paying thread-creation cost over and over. The pool reuses a fixed set of workers.

08 Key takeaways

  • A thread is a flow of execution; threads in a process share its memory but own their stack and registers.
  • Threads add responsiveness, cheap sharing, low cost, and multicore scalability.
  • Concurrency = juggling many tasks; parallelism = running them at the same instant. Different ideas.
  • User threads are fast but kernel-blind; kernel threads get real scheduling at more cost.
  • Models: many-to-one, one-to-one (the common choice), many-to-many.
  • Thread pools bound and reuse workers. But shared memory means race conditions — the next chapters' problem.

09 Wrapping up

Threads are how a single program uses many cores and stays responsive. The power — shared memory — is also the danger, which is why synchronization is the very next topic. Next up: CPU Scheduling.
