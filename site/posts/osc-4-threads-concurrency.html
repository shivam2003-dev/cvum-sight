Operating System Concepts Chapter 4 — Threads and Concurrency.

operating-systemschapter-4computer-sciencecompanion-notes
A thread is the smaller execution unit inside a process. Concurrency makes programs faster and more responsive, but it also creates races, ordering problems, and shared-state bugs.

1. Introduction

A process can contain one or more threads. Threads share the same address space and resources of the process, but each thread keeps its own execution state such as program counter, registers, and stack.

Threads matter because modern programs want parallel work, responsive UIs, and efficient server handling. But shared memory also makes bugs easier to create.

2. Detailed explanation

Why threads exist

Threads make it easier to overlap work. One thread can handle input, another can compute, and another can wait on I/O. This can improve responsiveness and throughput.

User and kernel threads

Some threading work can be managed in user space, while some is visible to the kernel. The mapping between user threads and kernel threads affects performance and blocking behavior.

Threading models

Common models include many-to-one, one-to-one, and many-to-many. One-to-one is common in modern systems because it maps application threads more directly to OS scheduling.

Multicore programming

On multicore systems, threads can run at the same time on different cores. That is real parallelism, not just fast switching.

Concurrency hazards

If multiple threads update shared data without coordination, the result can depend on timing. This is the root of race conditions.

Thread libraries

Developers usually work through libraries such as Pthreads, Java threads, or language runtimes. These libraries provide creation, joining, synchronization, and management helpers.

3. Key concepts

4. Real-world examples

Web server worker pool

A server may use many threads so different requests can be handled together.

Desktop app responsiveness

A GUI thread can stay responsive while background threads do heavy work.

Data pipeline

One thread reads data, another transforms it, and another writes results out.

5. FAQs

Are threads lighter than processes?

Yes, because threads share process resources and usually cost less to create and switch.

Do threads always speed things up?

No. Too many threads can increase overhead and contention.

What is the main danger of threads?

Shared-state bugs such as races, deadlocks, and inconsistent data.

Is concurrency the same as parallelism?

No. Concurrency means overlapping progress; parallelism means true simultaneous execution.

6. Key takeaways

  • Threads are smaller execution units inside processes.
  • Threads improve responsiveness and scalability.
  • Multicore systems make thread-based parallelism more useful.
  • Shared memory makes concurrency bugs possible.
  • Threading design is a performance and correctness tradeoff.

7. Conclusion

Chapter 4 shows why modern systems rely on threads. It also prepares the ground for synchronization, where the OS and programmer must control the risks created by shared execution.
