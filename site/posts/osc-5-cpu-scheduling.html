Operating System Concepts Chapter 5 — CPU Scheduling.

operating-systemschapter-5schedulinground-robinsjfthroughput

// the one-minute version

When more processes are ready than there are CPUs, the scheduler decides who runs next. Different algorithms optimize different things — short waiting time, high throughput, or fairness — and they conflict, so there's no single best one. The big four: FCFS (simple, but slow jobs block fast ones), SJF (optimal average wait, but needs to predict the future), priority (important first, risks starvation), and round robin (fair time slices, the basis of interactive systems).

Your laptop has maybe 8 cores but hundreds of ready threads. Something has to decide, thousands of times a second, which one gets a core right now. That something is the CPU scheduler, and the choice it makes is the difference between a snappy machine and a sluggish one.

01 When scheduling happens

The scheduler runs when a process switches state — finishes, blocks on I/O, gets preempted by the timer, or a new process arrives. If the scheduler can yank a running process off the CPU before it's done, scheduling is preemptive; if a process keeps the CPU until it voluntarily gives it up, it's non-preemptive. Modern interactive systems are preemptive — that's what the timer interrupt is for.

02 What we're optimizing for

"Good scheduling" depends on what you measure. The classic criteria pull in different directions:

CriterionMeaningWant it to be
CPU utilizationfraction of time the CPU is busyhigh
Throughputprocesses finished per unit timehigh
Turnaround timetotal time from arrival to completionlow
Waiting timetime spent sitting in the ready queuelow
Response timetime from request to first responselow (interactive)
watch outThese goals fight each other. Maximizing throughput can starve interactive responsiveness; minimizing average wait can be unfair to long jobs. A scheduler always picks a compromise — there is no setting that wins on every metric at once.

03 The classic algorithms

FCFS — first come, first served

Run processes in arrival order. Dead simple and fair-by-arrival, but one long job makes everyone behind it wait — the convoy effect. Non-preemptive.

SJF — shortest job first

Run the process with the smallest next burst. Provably gives the lowest average waiting time — but you can't truly know burst lengths in advance, so it's estimated. Can starve long jobs.

Priority

Each process has a priority; highest runs first. Flexible, but low-priority jobs may starve forever. Fix: aging — slowly raise the priority of waiting jobs.

Round robin

Give each ready process a fixed time slice (quantum), then move to the next. Fair and responsive — the heart of time-sharing. The quantum size is the key tuning knob.

noteRound robin's quantum is a balancing act. Too big and it degrades into FCFS (long jobs hog the CPU). Too small and the CPU wastes time context-switching instead of working. Typical quanta are tens of milliseconds — long enough to do real work, short enough to feel instant.

04 Multilevel queues

Real systems don't use one algorithm; they use several at once. A multilevel queue splits processes into classes (interactive, batch, background), each with its own queue and policy. A multilevel feedback queue goes further: it moves processes between queues based on behavior — a job that uses its whole slice drops to a lower-priority, longer-slice queue, while an interactive job that blocks quickly stays high. This automatically favors responsive, short tasks without needing to know their lengths in advance.

think of it likeA multilevel feedback queue is like a hospital triage that keeps re-sorting patients. You're not labeled once — if your case turns out long and stable, you move to a slower lane; if you're a quick urgent thing, you stay up front. The system learns each job's nature from how it behaves.

05 Scheduling on multiple cores

With many cores, new questions appear: should one queue feed all cores, or one queue per core? Keeping a process on the same core (processor affinity) preserves its warm cache. Load balancing moves work off busy cores onto idle ones. The two goals tug against each other — moving a process balances load but throws away its cache warmth.

06 Questions students actually ask

Why isn't shortest-job-first just always used, since it's optimal?

Because it requires knowing each job's next CPU burst length ahead of time, which is impossible in general. Systems estimate it from past behavior, and even then it can starve long jobs, so it's rarely used raw.

What is the convoy effect?

Under FCFS, one long CPU-bound job at the front makes all the short jobs behind it wait a long time — like cars stuck behind one slow truck. It tanks average waiting time.

How does round robin stay fair?

It gives every ready process an equal, fixed time slice in rotation, so no single process can hog the CPU. That equal slicing is what makes interactive systems feel responsive.

What is starvation and how is it fixed?

Starvation is when a process never gets to run because higher-priority work keeps arriving. The standard fix is aging: gradually raise a waiting process's priority so it eventually runs.

07 Key takeaways

  • The scheduler picks which ready process runs when CPUs are scarce.
  • Preemptive scheduling can interrupt a running process; non-preemptive can't.
  • Criteria (throughput, waiting time, response time) conflict — every scheduler is a compromise.
  • FCFS is simple but suffers the convoy effect; SJF is optimal-but-unknowable; priority risks starvation; round robin is fair.
  • Multilevel feedback queues sort jobs by behavior, favoring short interactive tasks automatically.
  • Multicore adds affinity vs load-balancing trade-offs.

08 Wrapping up

Scheduling is where the OS's resource-manager role is most visible: pure, constant arbitration of a scarce resource. With many threads sharing the CPU and memory, the next problem is keeping their shared data correct. Next up: Synchronization Tools.
