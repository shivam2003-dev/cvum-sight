Operating System Concepts Chapter 6 — Synchronization Tools.

operating-systemschapter-6computer-sciencecompanion-notes
When many threads share data, we need rules and tools so updates happen safely. Synchronization is how the OS and programs control shared access.

1. Introduction

Concurrency creates useful speed and responsiveness, but it also creates shared-state bugs. If two threads update the same data at the same time, the result may be wrong.

This chapter introduces the basic tools used to avoid that problem.

2. Detailed explanation

Critical section problem

A critical section is code that accesses shared data. The challenge is to let only safe access happen there.

Requirements

A good solution usually wants mutual exclusion, progress, and bounded waiting. In plain terms: one thread at a time, no unnecessary blocking, and no starvation forever.

Hardware support

Modern CPUs provide atomic instructions such as compare-and-swap. These help build higher-level locks safely.

Mutex locks

A mutex is a simple lock: one thread acquires it, and others wait until it is released.

Semaphores

A semaphore is a counter with controlled wait and signal operations. It is more flexible than a simple mutex, but also easier to misuse.

Monitors and condition variables

Monitors package shared data and synchronization rules together. Condition variables let threads sleep until a condition becomes true.

3. Key concepts

ConceptMeaning
Critical sectionCode that touches shared state.
Mutual exclusionOnly one thread can enter a protected section at a time.
MutexA lock used to guard shared data.
SemaphoreA synchronization counter with controlled operations.
MonitorA structured way to combine data and synchronization.
Condition variableA tool that lets threads wait for a condition.

4. Real-world examples

Bank balance update

If two threads change the same balance without locking, one update may get lost.

Producer-consumer queue

One thread adds work and another removes it. The queue must be synchronized.

Request counter

A shared metrics counter may need atomic updates or locks.

5. FAQs

Why not lock everything?

Too much locking reduces parallelism and may create deadlocks.

Are semaphores better than mutexes?

Not always. Semaphores are more flexible, but mutexes are often simpler and safer for basic protection.

What is the main danger of bad synchronization?

Wrong data, race conditions, deadlocks, or starvation.

Why do monitors feel cleaner?

Because they keep synchronization logic close to the shared data it protects.

6. Key takeaways

  • Concurrency needs synchronization when state is shared.
  • Critical sections must be protected correctly.
  • Mutexes, semaphores, and monitors solve related but different problems.
  • Atomic hardware operations support higher-level synchronization.
  • Simple tools used carefully beat complex tools used badly.

7. Conclusion

Chapter 6 gives the base toolbox for safe shared execution. The next chapter shows these ideas in classic problems that appear again and again in real systems.
