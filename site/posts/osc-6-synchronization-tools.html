Operating System Concepts Chapter 6 — Synchronization Tools.

operating-systemschapter-6synchronizationmutexsemaphorerace-condition

// the one-minute version

When threads share data, interleaving their steps can corrupt it — a race condition. The fix is to make the dangerous code a critical section that only one thread enters at a time. This chapter is the toolbox for that: atomic instructions at the bottom, mutex locks and semaphores in the middle, and monitors as the high-level, harder-to-misuse wrapper.

Two threads both do count = count + 1. You'd expect count to go up by two. Sometimes it only goes up by one — and the bug shows up once in a million runs, on the customer's machine, never in your tests. Welcome to concurrency. This chapter is how we make shared data safe.

01 The race condition

count = count + 1 isn't one step — it's three: read count, add one, write it back. If two threads interleave those steps, both can read the same old value, both add one, both write back the same result. One increment vanishes. A race condition is exactly this: the outcome depends on the unpredictable timing of threads.

think of it likeTwo people editing the same shared document by hand. Both read "balance: $100", both subtract $30, both write "$70". Two withdrawals happened but the record shows one. Nothing crashed — the data is just silently wrong.

02 The critical-section problem

The code that touches shared data is the critical section. The goal: ensure only one thread is in it at a time. A correct solution needs three properties:

Mutual exclusion

If one thread is in its critical section, no other thread can be in theirs. The core guarantee.

Progress

If no one is in the critical section and some threads want in, one of them must be allowed in — no needless stalling.

Bounded waiting

A thread can't be made to wait forever while others repeatedly jump ahead. No starvation.

03 Atomic hardware instructions

Software-only solutions (like Peterson's algorithm) exist and are great for understanding, but real systems lean on the CPU. Modern processors provide atomic instructions — operations that complete as one indivisible step — such as test-and-set and compare-and-swap (CAS). These are the bedrock every higher-level tool is built on.

note"Atomic" means all-or-nothing: no other thread can observe the operation half-done. That indivisibility is precisely what plain count = count + 1 lacks, and what hardware atomic instructions provide.

04 Mutex locks

The simplest tool: a mutex (mutual-exclusion lock). A thread acquire()s the lock before the critical section and release()s after. If the lock is taken, other threads wait. Built on atomic instructions underneath.

watch outA naive mutex that loops while waiting is a spinlock — it burns CPU doing nothing until the lock frees. Spinlocks are fine when the wait is extremely short (and on multiprocessors), but for longer waits the OS should block the thread (put it to sleep) instead of spinning, so the CPU can do real work.

05 Semaphores

A semaphore is a counter with two atomic operations: wait() (decrement, block if it would go negative) and signal() (increment, wake a waiter). A binary semaphore (0 or 1) acts like a mutex. A counting semaphore tracks a pool of N identical resources — say, 5 available database connections — letting exactly five threads through at once.

06 Monitors

Semaphores are powerful but easy to misuse: forget a signal(), or call wait() in the wrong order, and you get deadlock or corruption. A monitor is a higher-level construct that bundles shared data with the procedures that touch it and automatically ensures only one thread is active inside at a time. Condition variables let a thread inside wait for some state to become true and be woken when it does. This is what languages expose as synchronized methods or lock objects.

key ideaThe progression is about safety, not just power: atomic instructions → locks → semaphores → monitors. Each level is easier to use correctly than the one below. Prefer the highest-level tool that fits — most concurrency bugs come from hand-managing low-level primitives.

07 Liveness hazards

Synchronization can fix races but introduce new troubles: deadlock (threads wait on each other in a cycle, covered in Chapter 8), starvation (a thread never gets the lock), and priority inversion (a high-priority thread stuck waiting on a low-priority one that holds the lock). Correct locking is necessary but not sufficient — you also have to avoid these.

08 Questions students actually ask

What exactly causes a race condition?

Shared data plus unsynchronized access where the result depends on timing. Operations that look atomic in source code (like incrementing a counter) are actually several machine steps that can interleave.

Mutex vs semaphore — what's the difference?

A mutex enforces single ownership of one resource (one thread in, one thread out). A counting semaphore tracks N interchangeable resources and lets up to N threads proceed. A binary semaphore behaves like a mutex.

When is a spinlock a bad idea?

When the wait might be long. Spinning burns CPU doing nothing. For short waits (or holding a lock briefly on a multiprocessor) it's fine; otherwise block the thread so the CPU can do useful work.

Why prefer monitors over raw semaphores?

Monitors automate the locking and keep the shared data and its operations together, so it's much harder to forget a release or order operations wrong. Fewer footguns, fewer concurrency bugs.

09 Key takeaways

  • A race condition = shared data + unsynchronized, timing-dependent access.
  • Protect the critical section so only one thread enters at a time.
  • Correct solutions need mutual exclusion, progress, and bounded waiting.
  • Atomic instructions (test-and-set, CAS) are the hardware foundation.
  • Mutexes guard one resource; semaphores count a pool; monitors wrap it all safely.
  • Even correct locking can hit deadlock, starvation, or priority inversion.
