Operating System Concepts Chapter 8 — Deadlocks.

operating-systemschapter-8deadlockbankers-algorithmpreventionresource-allocation

// the one-minute version

A deadlock is a cycle of waiting: each task holds a resource and waits for one another task holds, so nobody can move. It needs four conditions at once — mutual exclusion, hold-and-wait, no preemption, circular wait — and breaking any one prevents it. Systems handle deadlock four ways: prevent it by design, avoid it by checking each request, detect-and-recover after the fact, or just ignore it and reboot.

Two threads, two locks. Thread A grabs lock 1 and reaches for lock 2. Thread B grabbed lock 2 and reaches for lock 1. Both wait. Forever. Nothing crashed, nothing errored — the system is simply, permanently stuck. That's deadlock, and it's one of the nastiest bugs in systems because it depends on exact timing.

01 The four necessary conditions

Deadlock can only happen when all four of these hold simultaneously. That's good news — remove any single one and deadlock becomes impossible.

Mutual exclusion

At least one resource is held in a non-shareable way — only one task can use it at a time.

Hold and wait

A task holds at least one resource while waiting to acquire more.

No preemption

A resource can't be forcibly taken away; it's released only voluntarily by the holder.

Circular wait

A closed chain of tasks exists, each waiting for a resource the next one holds.

key ideaAll four are required together. Every deadlock-prevention strategy is just "pick one of these four and make it impossible." That's the whole conceptual core of the chapter.

02 Resource-allocation graphs

Draw tasks and resources as nodes; an arrow from a task to a resource means "waiting for it," and from a resource to a task means "held by it." A cycle in this graph signals possible deadlock. With one instance of each resource, a cycle is deadlock; with multiple instances, a cycle only means the danger is possible.

03 Strategy 1 — Prevention

Prevention designs the system so one of the four conditions can never hold. For example, attack hold-and-wait by requiring a task to request all its resources up front; attack circular wait by numbering resources and forcing acquisition in increasing order. Prevention is airtight but often wastes resources or hurts flexibility.

04 Strategy 2 — Avoidance and the Banker's Algorithm

Avoidance is less rigid: allow flexible requests, but before granting each one, check whether it could lead to trouble. This needs advance knowledge of each task's maximum future needs. A state is safe if there's some order in which all tasks can finish; the famous Banker's Algorithm grants a request only if the resulting state stays safe — like a banker who only lends if every client can still be fully funded.

think of it likeA cautious banker has limited cash and several borrowers, each with a credit limit. Before approving any withdrawal, the banker checks: "can I still satisfy everyone eventually?" If yes, approve; if it would risk leaving someone unfundable, make them wait. That foresight is deadlock avoidance.

05 Strategy 3 — Detection and recovery

Some systems let deadlocks happen, then run a detection algorithm periodically (looking for cycles in the wait graph) and recover by force: abort one or more tasks, or preempt their resources and roll them back. Databases do exactly this — detect a deadlock between transactions and kill the cheaper one to break the cycle.

06 Strategy 4 — Ignore it

The blunt option, the "ostrich algorithm": assume deadlocks are rare enough that handling them isn't worth the cost, and just reboot if the system hangs. Surprisingly, this is what most general-purpose operating systems actually do for ordinary resources — the overhead of prevention or avoidance isn't worth it for a rare event.

watch outDeadlock is not the same as starvation. In deadlock, a fixed set of tasks are all permanently blocked in a cycle. In starvation, the system keeps running but one unlucky task never gets served. Different problems, different fixes — don't conflate them.

07 The practical rule

In everyday multithreaded code you rarely run the Banker's Algorithm. You break circular wait by always acquiring locks in a consistent global order. Lock account A before account B by ID, always — then the cycle that causes deadlock simply can't form. Simple, cheap, effective.

08 Questions students actually ask

Do you need all four conditions, or just some?

All four must hold at the same time for deadlock to occur. That's why prevention works by eliminating just one of them — break a single link and the chain can't form.

Why not always prevent deadlocks?

Because prevention and avoidance cost real performance and flexibility — requesting all resources up front, or checking safety on every request, wastes resources. For rare deadlocks, that overhead often isn't worth it.

How do databases handle deadlock?

They use detection and recovery: detect a cycle between transactions, then abort and roll back the cheaper one so the other can proceed. The killed transaction is simply retried.

What's the easiest practical defense in my own code?

Always acquire locks in a consistent order across all threads. This kills the circular-wait condition and prevents the most common multithreaded deadlocks with almost no cost.

09 Key takeaways

  • A deadlock is a cycle of tasks each holding one resource and waiting for another.
  • It needs four conditions together: mutual exclusion, hold-and-wait, no preemption, circular wait.
  • Break any one condition and deadlock is impossible.
  • Prevention designs it out; avoidance (Banker's) checks each request; detection+recovery cleans up after; ignoring is common for rare cases.
  • Deadlock ≠ starvation.
  • Practical rule: acquire locks in a consistent global order.

10 Wrapping up

Deadlock closes out the process-and-concurrency half of the book: correctness can fail in the interaction between components even when each looks fine alone. Now the focus shifts to the other great resource — memory. Next up: Main Memory.
