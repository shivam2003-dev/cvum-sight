Parallel Constrained Decoding: A Technical Reference.

ml inference structured-output decoding

In one sentence: Parallel Constrained Decoding (PCD) answers a multi field schema with one prefill plus one short pass per field, instead of generating the output token by token. It only works when every field has a small fixed set of allowed answers.

5.6x to 7.0xfaster than autoregressive on the reference benchmark

100%schema valid output, by construction

1. At a glance

PCD answers one narrow question well: when a model call only ever needs to pick an answer from a small, known list, why pay for open ended text generation at all. The table below is the full specification in miniature. Everything after it is detail.

2. The problem it solves

Normal structured generation (JSON mode, function calling, grammar guided sampling) produces one token per forward pass:

[Context] -> "{" -> "\n" -> " " -> "risk" -> ":" -> " " -> "HIGH" -> ...
150 to 500 sequential forward passes for a typical schema

Total latency is the sum of every token step:

\[ T_{\text{autoregressive}} = \sum_{k=1}^{K} t_{\text{step}}(k) \]

Here \(K\) is the number of output tokens. It grows with every added field, so latency grows with schema size.

Two more problems come with this approach:

  • Syntax errors: one bad token can break the whole JSON. A missing closing brace or an unescaped quote anywhere in the output makes the entire response unparseable, even if every field value was correct.
  • Missing or invented keys: the model can skip a required field or make up a new one. Nothing in standard autoregressive decoding stops the model from emitting a field name that was never in the schema, or quietly dropping one it was asked for.

This matters most for agent and automation workloads, where a single step calls a model many times a request, for small decisions: is this ticket urgent, which of these eight categories, does this transaction look fraudulent. Paying the full cost of token by token generation, with its failure modes, for a decision that only ever has a few possible answers is the specific waste PCD targets.

3. The core idea

Each field value comes from a small known set. So do not generate it. Score every allowed answer from the model's own logits and pick the best one.

  • Read the context once.
  • Reuse that cached work for every field.
  • Look only at the tokens that are valid answers for the field.
  • Build the JSON in code from the chosen values.

A language model already computes, at every position, a score for every token in its vocabulary before it samples one. Normal decoding throws almost all of that away and keeps only the single sampled token. PCD keeps the scores instead of throwing them away, and only for the small set of tokens that could possibly be a valid answer.

Normal decodingPCD
Compute full vocabulary logitsCompute full vocabulary logits
Sample or pick top 1 tokenDiscard all but the schema's candidate tokens
Append token, repeatSoftmax over the kept candidates, pick the best
Stop on an end token or limitStop. One pass per field, done.

Fig. 1: The six stage pipeline. Stages 1 and 2 run once per request. Stages 3 to 5 run once per field, independently.

4. The algorithm

  1. Broadcast prefill. Put the context and the schema field descriptions through the model once. Store the KV cache.
  2. Cache broadcast. Share that one KV cache with all \(M\) fields. No field reprocesses the context.
  3. Logit slicing. For each field, run a short pass over its own suffix tokens. Read only the logits at that field's candidate token IDs. Ignore the rest of the vocabulary.
  4. Calibrated softmax. Turn the sliced logits into probabilities: \[ P(c_i) = \frac{\exp(z_i / T)}{\sum_{j=1}^{C} \exp(z_j / T)} \] \(z_i\) is the logit of candidate \(i\), \(C\) is the number of candidates, \(T\) is temperature.
  5. Token tree disambiguation. If candidates span several tokens and share a prefix, run extra steps on sliced cache states to tell them apart. No cache reallocation.
  6. Programmatic assembly. Build the output JSON in code from the chosen values. No parsing of generated text.

Why each stage exists

StageWhat breaks without it
1. Broadcast prefillEvery field would reprocess the full context. Cost grows with field count.
2. Cache broadcastAttention would be recomputed for the context on every field.
3. Logit slicingThe top token could be outside the schema. Nothing enforces valid answers.
4. Calibrated softmaxRaw logits are not probabilities. Code cannot threshold them.
5. Token tree stepCandidates with the same first token could not be told apart.
6. Programmatic assemblyGenerated JSON text can be malformed. Validity is lost.

Reference pseudocode

def parallel_constrained_decode(context, schema, model, T=1.0):
    # Stages 1-2: one prefill, one shared KV cache
    kv_cache = model.prefill(context + schema.render_descriptions())

    results = {}
    for field in schema.fields:              # independent, parallelizable
        # Stage 3: short pass reusing the cache, then slice logits
        logits = model.forward(field.suffix_tokens, cache=kv_cache)
        sliced = logits[field.candidate_token_ids()]

        # Stage 4: softmax over the slice only
        probs = softmax(sliced / T)

        # Stage 5: multi token candidates
        if field.has_multi_token_candidates():
            probs = resolve_token_tree(field, kv_cache, probs)

        results[field.name] = {
            "value": field.candidates[argmax(probs)],
            "prob": max(probs),
        }

    # Stage 6: build JSON in code
    return assemble_json(results)

Notes on the softmax

  • Normalized over the slice only. Probabilities sum to 1 across the field's candidates, not the full vocabulary. Do not compare them with full vocabulary probabilities.
  • Temperature changes confidence, not the answer. Softmax keeps the ranking, so the argmax is the same for any \(T > 0\). Only the reported probability changes.
  • Masking detail. Implementations often set non candidate logits to \(-\infty\) instead of gathering. The result is identical because \(\exp(-\infty) = 0\).
  • Ties are not covered by the public spec. Add your own tie break rule.

A worked example with two candidates. A boolean field has logits 4.1 for true and 1.8 for false. At \(T = 1\):

\[ P(\text{true}) = \frac{e^{4.1}}{e^{4.1} + e^{1.8}} \approx 0.91, \quad P(\text{false}) \approx 0.09 \]

At \(T = 2\), the same logits give a flatter result, around 0.76 and 0.24. The chosen answer, true, does not change at either temperature. Only how confident the returned number says the model is changes.

How candidate token IDs are found

Before any scoring happens, each field's allowed answers must be mapped to token IDs once, when the schema is built, not on every request:

  • Tokenize each candidate string with the model's own tokenizer.
  • If a candidate tokenizes to exactly one token, record that ID. This is the fast path logit slicing uses directly.
  • If a candidate tokenizes to more than one token, it needs the token tree step (stage 5) at scoring time, since a single logit lookup cannot resolve it.
  • Candidates sharing a first token, such as BILLING and BILLING_DISPUTE, are exactly the case stage 5 exists for.

5. Complexity

PropertyAutoregressivePCD
Sequential passes\(K\) (150 to 500 typical)1 (the prefill)

Growth with field countRoughly linearSub linear. Each field adds one small pass
Generated tokensLength of the JSON0
Syntax validityNot guaranteedGuaranteed by construction

In the reference benchmark, going from 4 fields to 28 fields raised the autoregressive output from about 148 tokens to about 312. The PCD speedup improved from 5.6x to 7.0x, because the fixed prefill is a smaller share of the alternative.

The "with full parallelism" condition in the table matters. If the hardware or runtime evaluates fields one after another instead of concurrently, total latency becomes \(t_{\text{prefill}} + \sum_i t_{\text{field}}(i)\), the sum over all fields rather than the slowest one. The published M4 Max numbers reflect whatever concurrency the MLX reference implementation actually achieves on that hardware, not a theoretical best case. Either way, the key property holds: field cost does not compound with generated token length the way autoregressive cost does.

Worked example

Published numbers for the 28 field triage scenario:

  • Autoregressive: 1,894.2 ms for 312 tokens, about 6.07 ms per token.
  • PCD: 268.4 ms total, one sequential pass.

A separate 3 field example response reports elapsed_ms: 74.5, prefill_ms: 52.1, suffix_eval_ms: 18.2. That is about 70% prefill and 24% field evaluation.

Applying that ratio to the 28 field run is an estimate, not a measurement: roughly 188 ms prefill and 65 ms for all fields, so about 2 to 3 ms per field. The published data has no per field timing for that scenario.

  • sequential_forward_passes: 1 means the whole request had one sequential dependency.
  • field_telemetry exposes the full distribution, so your code can apply its own confidence threshold.

A typical use of field_telemetry is routing low confidence answers to a human or to a larger model instead of trusting every automated decision equally:

result = run_parallel_generation(context, schema)
for name, field in result["parsed_json"].items():
    if field["prob"] < 0.75:
        send_for_human_review(name, field["value"], field["prob"])
    else:
        apply_automatically(name, field["value"])

This pattern, a confidence threshold deciding between automatic action and escalation, is the same cascade idea used by cheap LLM judges: accept confident answers, send the rest somewhere more expensive or more careful.

Why 148x fewer steps gives only 5.6x lower latency: one token step is cheap. Cutting 148 steps to 1 removes those steps, but the single prefill and the per field work still cost real time. The latency number is what matters for an SLA. The step count explains where the gain comes from.

What this means for throughput, not just latency

Latency per request is one axis. The other is how many requests a single machine can serve per second, which matters more for a high volume classification endpoint than for a one-off call. Because PCD replaces 148 to 312 sequential forward passes with 1, a server handling many concurrent requests spends far less total compute per request, which directly raises how many requests the same hardware can serve before it needs to scale out. The published benchmarks report single-request latency only; they do not report a throughput or requests-per-second figure, so treat the throughput gain as directionally implied by the step count reduction, not as a measured number.

9. Compared with other structured output methods

MethodHow it decodesValid syntaxSequential passes
Plain JSON promptingAutoregressive, unconstrainedNo\(K\)
Grammar constrained decodingAutoregressive, each token masked to grammar valid tokensYes for syntax\(K\)
PCDPrefill once, score candidates per fieldYes, by construction1, plus \(M\) independent field passes

Grammar constrained decoding still generates token by token. It limits what each token may be, but it still needs one forward pass per token. PCD removes the generation loop for field values.

The two can be combined in principle: PCD for bounded fields, another method for free text. The public PCD code does not support free text fields.

PCD versus speculative decoding

These solve different problems and are easy to confuse because both claim to cut the number of real forward passes.

Speculative decodingPCD
Output spaceOpen ended text, any lengthA fixed set of candidates per field

10. Building it yourself

None of this needs proprietary infrastructure. The pieces are standard parts of any modern inference stack:

  1. Pick a model that exposes logits, not just sampled text. Any local Hugging Face model, or an API that returns logprobs, qualifies.
  2. Tokenize every candidate answer once, at schema build time, and record which are single token and which need the token tree step.
  3. Prefill the context and keep the KV cache, using whatever cache API your inference library already exposes for normal autoregressive generation.
  4. For each field, run one short forward pass reusing the cache, slice the logits to the candidate IDs, and softmax.
  5. Assemble the output in code, never by asking the model to produce the final JSON string.

Harsha Gundala's repository and Bespoke Labs' Nimble are both working reference implementations of exactly this recipe, in Python, and are the fastest way to see it running before writing your own version.

11. When to use it

Your outputUse PCD?
All fields are booleans or fixed enumsYes. This is the target case.
Some fields need free textNot for those fields. Route them elsewhere.
One field's choices depend on another fieldNot in one call. Use two calls or filter the distribution in code.
Nested objects or arraysNo. Schemas must be flat.
More than 255 choices in one fieldNot directly. Bucket or split the decision.

Edge cases worth planning for

SituationWhat to do
None of the candidates actually fit the inputAdd an explicit "none of the above" or "not stated" choice to the field. Without one, the model is forced to pick the least-wrong option and the probability on it will usually be low, which your confidence threshold should catch.
A field's correct answer genuinely requires context from another fieldSplit into two calls: resolve the first field, then pass its value into the context for a second call that resolves the dependent field.
Candidate list changes often, such as a product catalogUse FieldDefinition with choices generated at request time rather than hard coding a static schema, and re-tokenize whenever the list changes.
You need an explanation alongside the decisionPCD cannot produce one. Log the full probability distribution and, if a reason is required, pair the decision with a separate, normal generative call only when needed.

12. Limits

  • No free text and no nesting in the reference implementation. A field that needs a short explanation, a summary, or a verbatim quote from the context cannot be expressed in this schema format at all.
  • No cross field conditioning inside one call. If field B's valid choices should depend on what field A returned, that dependency has to be enforced by your own code after the fact, or split into two sequential calls.
  • 255 choice ceiling per enum. Multi token choices need the extra token tree step, which costs more than single token choices, so a schema built entirely from long, multi-word candidate strings will not see the full benchmarked speedup.
  • Apple Silicon only in the published engine. The idea works on any stack that exposes logits and KV cache reuse, but the benchmark numbers are specific to MLX on an M4 Max and have not been reproduced on CUDA or other hardware in the public material this reference is built from.
  • Valid is not correct. PCD guarantees a valid output. It does not guarantee the chosen answer is right. The public benchmarks report latency and validity, not task accuracy, so accuracy on your own data needs its own evaluation.
  • No built in explanation. The output is a value and a probability, never a reason. If your workflow needs "why did it pick this," that has to come from a separate system, such as logging the full candidate distribution for later review.
Same pattern elsewhere: Bespoke Labs' Nimble uses the same idea. Its ParallelScorer on Apple Silicon processes the context once and scores all fields. Its CUDA scorer scores each field with the full prompt, so it skips the cache sharing. Nimble also says fields cannot see each other's answers.

How this relates to Jev

PCD is the mechanism several independent sources use to explain how TypeSafe's Jev model likely works internally, though TypeSafe itself has never confirmed an architecture. The match is based on matching behavior: Jev's 70 to 500 millisecond latency, its free output tokens, and its guaranteed valid output all follow directly from this kind of scoring based pipeline rather than generation. See How Jev Actually Works for the full reverse engineering writeup, including a side by side accuracy comparison against an open model trained the same way.

13. Glossary

TermMeaning here
PrefillThe forward pass over the input context, before any output is produced.
KV cacheThe stored key and value tensors from prefill, reused so later passes do not recompute attention over the same context.
LogitA model's raw, unnormalized score for one vocabulary token, before softmax.
Logit slicingKeeping only the logits at a chosen subset of token IDs and discarding the rest.
ArgmaxThe candidate with the highest probability or score.
CalibrationWhether a stated confidence, such as 90%, actually matches how often that answer is correct.

FAQ

Is this speculative decoding?

No. Speculative decoding speeds up open ended generation with a draft model. PCD does not generate field values. It scores a fixed set of candidates.

Can it return a value outside the schema?

No. Logits are sliced to the field's candidate token IDs, so the argmax can only be one of them. This guarantees schema validity. It says nothing about whether the value is correct.

Does more fields always improve the speedup?

In the four benchmarks, yes: 5.6x at 4 fields, 7.0x at 28. It is not unbounded. Each field still costs a small pass, and the benchmarks stop at 28 fields.

Where can I try it without installing?

The model card links a hosted demo: drinkmoonshine/parallel-constrained-decoding on Hugging Face Spaces.

Does the model need special training to support this?

No. The published technique runs on a stock instruction tuned model with no fine tuning. Training can improve accuracy and calibration on top of it, but the mechanism itself works on an off the shelf model.

What happens if two candidates get the exact same score?

The public specification does not define tie breaking behavior. In practice, floating point ties are rare but not impossible, especially at low temperature on a small model. Pick a deterministic rule, such as the first candidate in declaration order, and apply it consistently in your own code.

Is this the same as adding a classification head to the model?

No. A classification head is a separate trained layer bolted onto the model, specific to one task, usually requiring its own training run. PCD reuses the model's existing, general purpose language modeling head and vocabulary. The same base model can answer any new schema you define without retraining anything.

Takeaways

  • PCD swaps generation for scoring on bounded fields.
  • \(K\) sequential passes become 1 prefill plus \(M\) small independent passes.
  • Valid syntax is guaranteed. Correctness is not, so accuracy still needs its own evaluation on your data.
  • It is not grammar constrained decoding, which still loops per token, and it is not speculative decoding, which needs a second draft model.
  • No training is required to get the speedup. Training only improves accuracy and calibration on top of it.
  • field_telemetry's full probability distribution is what makes a confidence-threshold cascade to human review or a bigger model possible.
  • Limits: flat schema, no free text, no cross field dependency in one call, 255 choices per field, no built in explanation, and published benchmarks specific to Apple Silicon.
