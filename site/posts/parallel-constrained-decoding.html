Parallel Constrained Decoding — A Technical Reference.

ml inference structured-output decoding

Definition. Parallel Constrained Decoding (PCD) is an inference technique for schema-bounded structured generation that replaces token-by-token autoregressive decoding with one context prefill plus one short, independently-computed forward pass per output field. It applies when every output field's value is drawn from a small, pre-declared, enumerable candidate set (a boolean, or an enum with up to 255 choices) rather than open-ended text. The public reference implementation is Harsha Gundala's Qwen2.5-1B-RLCD release for Apple Silicon (MLX), evaluated against mlx-community/Qwen2.5-1.5B-Instruct-4bit. This is a specification and reference document — for the reverse-engineering context (how this connects to TypeSafe's Jev and Bespoke Labs' Nimble), see How Jev Actually Works.

1. Problem statement

Standard LLM structured generation — JSON mode, function calling, grammar-guided sampling — decodes autoregressively: each output token is produced by one full forward pass through the model, conditioned on every token generated so far.

[Context Prompt] -> "{" -> "\n" -> " " -> "risk" -> ":" -> " " -> "HIGH" -> ...
(requires 150 to 500 sequential forward passes for a typical multi-field schema)

Total latency is the sum of per-token step costs:

\[ T_{\text{autoregressive}} = \sum_{k=1}^{K} t_{\text{step}}(k) \]

where \(K\) is the number of output tokens. \(K\) grows with schema size (more fields, more JSON syntax, longer field names, longer enum-value strings), so latency scales linearly with schema size under this model. Two further properties of autoregressive structured generation motivate PCD specifically:

  • Syntax degradation: a sampling error at any single token position (a missed closing brace, a truncated string) can invalidate the entire output, regardless of how many tokens were correct before it.
  • Field omission and hallucination: nothing structurally prevents the model from skipping a required key or inventing a key not in the schema; grammar-guided sampling constrains the syntax token-by-token but does not, by itself, guarantee every declared field is populated with a value from its declared candidate set.

2. The structural property PCD exploits

In structured extraction and classification, field values belong to bounded candidate sets: a boolean field has exactly two valid values; an enum field has a fixed, pre-declared list of string choices (up to 255 in the reference implementation). This is a strictly narrower output space than open-ended text generation, and it makes a specific reformulation possible: instead of generating a field's value token by token, you can score every candidate value directly from the model's own next-token logits and select the highest-scoring one — with no generation step at all.

3. Algorithm

The pipeline as specified, in order:

  1. Single broadcast prefill. The context document and the schema's field descriptions are prefilled into the model exactly once, producing a KV (key-value) cache — the same caching mechanism every standard transformer inference stack already implements for autoregressive decoding, used here as the terminal step rather than the first of many.
  2. KV-cache broadcasting. The single KV cache from step 1 is broadcast across all \(M\) schema fields. No field re-processes the context; every field's evaluation starts from the same cached state.
  3. Sub-vocabulary logit slicing. For each field independently, a short forward pass (over that field's suffix/instruction tokens only, reusing the broadcast cache) produces logits over the model's full vocabulary. Only the logits at the token IDs corresponding to that field's valid candidate answers are read; every other vocabulary position is discarded (masked).
  4. Calibrated softmax. The sliced candidate logits are normalized into a probability distribution with a temperature-scaled softmax: \[ P(c_i) = \frac{\exp(z_i / T)}{\sum_{j=1}^{C} \exp(z_j / T)} \] where \(z_i\) is the logit for candidate \(i\), \(C\) is the number of valid candidates for that field, and \(T\) is a temperature parameter. This produces exact, normalized probabilities over only the declared candidate set — not an approximation.
  5. Token-tree disambiguation. Candidate choices whose string representation spans more than one token (e.g. a multi-word enum value) share a common token prefix. For these, the engine executes additional continuation steps using sliced cache states — reusing the already-computed cache rather than reallocating or recomputing it — to resolve which full multi-token candidate was selected.
  6. Programmatic assembly. The final output JSON is constructed directly, in code, from the verified per-field values and their probabilities — not by asking the model to emit JSON syntax and then parsing it. Because every value is drawn from a set already known to be valid for its field, the assembled output is syntactically valid by construction, with zero possibility of a JSON parse error.

3.1 Why each stage is necessary

StageWhat breaks if it's skipped
1. Broadcast prefillWithout a single shared prefill, every field's evaluation would need to reprocess the full context independently — turning an \(O(1)\)-prefill, \(O(M)\)-field-evaluation system back into an \(O(M)\)-context-processing system, which is exactly the cost PCD exists to avoid.
2. Cache broadcastAttention layers compute keys and values as a function of all preceding tokens. Reusing the cached keys/values means a field's forward pass only needs to compute attention for its own (short) suffix against the already-cached context — not recompute the context's own self-attention. Skipping this forces exactly that recomputation per field.
3. Logit slicingWithout slicing to the candidate token IDs, the argmax would be taken over the full ~150k-token vocabulary, which can select a token that isn't even a valid answer for the field — the model's raw top prediction is not constrained to the schema at all until this step is applied.
4. Calibrated softmaxRaw logits are unbounded and not comparable across fields or across requests. Softmax-normalizing only the candidate slice is what turns "field X's answer scored higher than field Y's" into an actual probability your calling code can threshold, compare, or log.
5. Token-tree disambiguationIf a candidate spans multiple tokens and this step is skipped, only the first token of each multi-token candidate could be scored — which under-determines the choice whenever two candidates share a first token (e.g. "BILLING" and "BILLING_DISPUTE" as separate enum values).
6. Programmatic assemblyIf the model were asked to emit the final JSON itself instead of code assembling it from verified values, every syntax-validity guarantee from steps 1–5 would be void — you'd be back to trusting generated text to be well-formed.

3.2 Numerical notes on the masked softmax

Two properties of stage 4's formula are worth being explicit about, since they're easy to get subtly wrong in a from-scratch reimplementation:

  • The normalization is exact only over the sliced set. \(P(c_i)\) sums to 1 across the \(C\) candidates for that field, not across the full vocabulary. This is the entire point — it's what turns an arbitrary logit magnitude into a genuine probability conditioned on "given that the answer is one of these \(C\) options" — but it also means these probabilities are not directly comparable to a full-vocabulary softmax probability from a different, unconstrained generation, and shouldn't be treated as if they were.
  • Temperature \(T\) changes calibration sharpness, not the argmax. Because softmax is monotonic in the logits for any \(T > 0\), the selected candidate (the argmax) is identical for any temperature — only the reported confidence value changes. Low \(T\) sharpens the distribution toward the top candidate (higher reported confidence, same selection); high \(T\) flattens it. If downstream code thresholds on the reported probability (e.g. "only escalate if requires_escalation.prob > 0.9"), the temperature setting directly determines how many results clear that bar, even though it never changes which candidate is selected.

3.3 Reference pseudocode

def parallel_constrained_decode(context, schema, model, T=1.0):
    # Stage 1-2: broadcast prefill, single KV cache for the whole request
    kv_cache = model.prefill(context + schema.render_descriptions())

    results = {}
    for field in schema.fields:               # independent; parallelizable
        # Stage 3: short forward pass reusing kv_cache, then slice logits
        logits = model.forward(field.suffix_tokens, cache=kv_cache)
        candidate_ids = field.candidate_token_ids()   # len == C
        sliced = logits[candidate_ids]                # discard all other vocab

        # Stage 4: calibrated softmax over the slice only
        probs = softmax(sliced / T)                    # sums to 1 over C candidates

        # Stage 5: resolve multi-token candidates via sliced-cache continuation
        if field.has_multi_token_candidates():
            probs = resolve_token_tree(field, kv_cache, probs)

        results[field.name] = {
            "value": field.candidates[argmax(probs)],
            "prob": max(probs),
            "distribution": dict(zip(field.candidates, probs)),
        }

    # Stage 6: assemble directly from verified values -- never parse generated text
    return assemble_json(results)

Two implementation details this pseudocode elides but matter in practice: masking (stage 3) is typically implemented by setting non-candidate logit positions to \(-\infty\) before the softmax rather than by physically gathering only the candidate indices, which keeps the operation a fixed-shape tensor op rather than a variable-length gather — a performance detail, not a semantic one, since \(\exp(-\infty) = 0\) removes those positions from the normalization identically either way. And argmax ties (two candidates with numerically identical top probability) are not addressed in the public specification; a production implementation needs its own explicit tie-breaking rule.

4. Complexity

PropertyAutoregressiveParallel Constrained Decoding
Sequential forward passes\(K\) (one per output token, 150–500 typical)1 (the broadcast prefill only — field evaluations are independent of each other, not sequential with respect to one another)
Total latency\(T = \sum_{k=1}^{K} t_{\text{step}}(k)\)\(T \approx t_{\text{prefill}} + \max_i\, t_{\text{field}}(i)\) under full parallelism, or \(t_{\text{prefill}} + \sum_i t_{\text{field}}(i)\) if fields are evaluated one after another on hardware without parallel field evaluation
Scaling with field count \(M\)Roughly linear — every additional field adds output tokens to generateSub-linear in practice — prefill cost is fixed and amortized; each additional field adds one small, cheap forward pass
Output token countEqual to the generated JSON's token lengthZero — no tokens are generated; values are selected, not produced
Syntax validityNot guaranteed; degrades with schema complexityGuaranteed by construction (step 6)

The measured effect of this scaling difference: in the reference benchmark, going from a 4-field schema to a 28-field schema increased the autoregressive baseline's cost from ~148 output tokens to ~312 (roughly 2.1×), while PCD's speedup over that baseline actually improved, from 5.6× to 7.0–7.1×, because the fixed prefill cost is a smaller fraction of a larger field count's total autoregressive alternative.

4.1 Worked example, from the published numbers

Using the 28-field support-triage scenario's own reported figures: the autoregressive baseline took 1,894.2 ms for 312 tokens, implying an average \(t_{\text{step}} \approx 6.07\) ms per token. PCD's total for the same request was 268.4 ms, all within 1 sequential pass.

The §6 example response (a separate, 3-field incident-triage request) reports a prefill/suffix split directly: elapsed_ms: 74.5, prefill_ms: 52.1, suffix_eval_ms: 18.2 — meaning prefill was ~70% of total latency and per-field suffix evaluation (for all fields combined) was ~24%, with the remainder assembly and rounding overhead. Applying that same ratio as a rough estimate to the 28-field, 268.4 ms scenario: prefill would account for roughly 188 ms, leaving roughly 65 ms split across all 28 fields' independent short passes — on the order of 2–3 ms per field once the shared prefill is already paid for. This is an estimate, extrapolated from a different scenario's measured ratio, not a directly reported 28-field breakdown; the published data doesn't include a per-field timing split for the support-triage benchmark specifically. But it's consistent with the complexity model in §4's table: the marginal cost of one more field is small and roughly constant, while the marginal cost of one more autoregressive output token is not — it's paid on top of every token already generated for the fields ahead of it in the sequence.

4.2 When this technique applies

Your output shapePCD applicable?
Every field is boolean or a fixed enum, known at schema-design timeYes — this is exactly the case the technique targets.
One or more fields need free-text (a summary, an explanation, extracted verbatim text)No, for those fields — the public implementation has no mechanism for open-ended output. A mixed system would need to route text fields to a different generation path entirely.
A field's valid choices depend on another field's value in the same call (e.g. "sub-category" options change based on "category")Not within a single call — §5 and §9 both note fields are scored independently; this needs either two sequential PCD calls or application-level filtering of the returned distribution.
Schema needs nested objects or arraysNo — schemas must be flat in the reference implementation.
An enum field could plausibly have more than 255 valid valuesNot directly — would need bucketing, hierarchical decomposition, or a different technique.

The latency speedup is the number that matters for a production SLA; the step-reduction number explains mechanistically where that speedup comes from.

8. Comparison with related structured-output techniques

TechniqueDecoding patternGuarantees valid syntaxSequential passes for a schema with \(M\) fields
Plain JSON-mode promptingAutoregressive, unconstrainedNo — model can emit invalid JSON\(K\) (one per output token)
Grammar-constrained decoding (e.g. a CFG/FSM-based sampler)Autoregressive, but each token is masked to only grammar-valid continuations before samplingYes, for syntax — the grammar guarantees well-formed structure; it does not by itself guarantee every field is populated with a semantically valid enum member unless the grammar itself encodes the exact candidate set per field\(K\) — still one forward pass per output token; the constraint is applied to logits at each step, decoding remains sequential
Parallel Constrained DecodingOne prefill, then one independent scored evaluation per field — no autoregressive generation of field values at allYes — every field's value is selected from its declared candidate set by construction1 (prefill), plus \(M\) independent, parallelizable evaluations — not chained to each other

The distinction that matters: grammar-constrained decoding (the family PCD is most often confused with) still generates output autoregressively — it constrains what each next token is allowed to be, but a full forward pass is still required per output token, and total latency still scales with output length. PCD removes the autoregressive generation step for the field-value portion of the output entirely, replacing it with a scoring operation. The two techniques are not mutually exclusive in principle — a system could use PCD for its bounded-candidate fields and fall back to grammar-constrained or unconstrained generation for any genuinely open-ended text fields in a mixed schema — but the public PCD implementation reviewed here does not support open-ended fields at all (see §5's constraint table).

9. Stated limitations

  • No free-text or open-ended fields. Every field must resolve to a member of a pre-declared candidate set. A field like "summarize this in one sentence" is out of scope for this technique entirely.
  • No nested schemas. Fields are flat; the reference implementation does not support nested objects or arrays within a single schema.
  • No cross-field conditioning within one call. Because every field is scored independently against the same broadcast cache, a field cannot be made to depend logically on another field's selected value inside the same request — that consistency has to be enforced by the calling code, if needed, typically by issuing a second call once the first field's value is known.
  • 255-choice ceiling per enum field in the reference implementation, and single-token-per-choice is the fast path — choices whose string spans multiple tokens require the extra token-tree disambiguation step (§3, step 5), which adds cost relative to a single-token choice.
  • Platform-specific reference implementation. The published engine targets Apple Silicon via MLX specifically; the technique itself (prefill once, score candidates via logit slicing) is platform-agnostic and implementable on any inference stack that exposes raw logits and KV-cache reuse (CUDA, for instance — see Nimble's separate CUDA scorer path in the note below), but the benchmarked numbers in §7 are MLX/M4-Max-specific and should not be assumed to transfer directly to other hardware or frameworks.
  • Base model dependency. Accuracy (as opposed to latency and syntax validity, which are structural guarantees) depends entirely on how well the underlying model's logits actually rank the correct candidate — PCD guarantees the output is valid, not that it's correct. The reference benchmarks report latency and syntax validity; they do not report task accuracy for the base 1.5B-Instruct-4bit model on the four preset scenarios.
Cross-implementation note: Bespoke Labs' Nimble implements the same core pattern independently, with two scorer variants — a ParallelScorer for Apple Silicon that, like the reference implementation here, processes the shared context once and scores all fields in parallel, and a separate CUDA scorer that scores each field on its own with the full prompt each time (i.e., without the cache-broadcast optimization of §3, step 2, on that code path). Nimble's docs state explicitly that fields "cannot see other fields' answers" within a call — the same independence constraint as §5's cross-field-dependency limitation above, arrived at independently.

Frequently asked questions

Is this the same as speculative decoding?

No. Speculative decoding still produces open-ended autoregressive output; it speeds up generation by having a small draft model propose several tokens that a larger model verifies in one pass, but the output space is still unconstrained token sequences. PCD is specific to bounded-candidate-set fields and doesn't generate tokens for field values at all — it scores pre-declared candidates directly.

Can PCD produce an answer that isn't in the declared candidate set?

No — that's the structural guarantee in §3, step 6. Because every field's value is selected from logits sliced to only that field's candidate token IDs, an out-of-schema value is not in the space the argmax is taken over. This guarantees syntactic and schema validity; it says nothing about whether the selected in-schema value is the semantically correct one for the given context.

Does adding more fields always help the speedup ratio?

In the four benchmarked scenarios, yes — the ratio improved from 5.6× at 4 fields to 7.0–7.1× at 28 fields, because the fixed prefill cost is amortized over more field evaluations while the autoregressive baseline's cost keeps growing with each additional field's output tokens. This isn't unbounded, though: per-field evaluation still has a real (small) cost, and very large field counts would eventually be bottlenecked by that sum rather than by the fixed prefill — the reference benchmarks don't test schemas larger than 28 fields.

Takeaways

  • PCD is a scoring reformulation, not a faster generator. For bounded-candidate fields, it replaces "generate tokens, then validate" with "score every candidate directly from cached logits, then assemble" — eliminating the generation step for those fields entirely.
  • The complexity win is structural: \(K\) sequential passes (autoregressive) collapse to 1 prefill pass plus \(M\) independent, parallelizable field evaluations, which is why the speedup ratio improves as schema size grows in the reference benchmarks (5.6× at 4 fields, 7.0–7.1× at 28).
  • Syntax validity is a hard guarantee, accuracy is not. Every output is schema-valid by construction; nothing in the technique guarantees the selected candidate is semantically correct — that's a function of the base model's logit quality, unmeasured in the public benchmark data.
  • It is not grammar-constrained decoding. Grammar-constrained samplers still decode autoregressively, one forward pass per output token, with constraints applied at each step. PCD removes the autoregressive loop for field values altogether.
  • The constraint set is real: flat schemas only, no cross-field conditioning in one call, no open-ended text fields, 255-choice ceiling per field, and the published benchmarks are specific to Apple Silicon/MLX and one 1.5B base model.
